## 2. 점검 항목별 검토

### 2.1 확정 정책 누락 여부
- 통합 정책의 글머리표 32개를 하나씩 PRD 요구사항·AC와 대조했다. 누락은 없었다.
- 통합 정책 §8의 대조표 11행(OQ 반영, 운영 한도, 방 이름, 거래 금액, 거래 수정, 중복 요청, 정렬, 필터, 실시간, 정산, 지원 환경)도 모두 대응 FR/NFR이 있다.
- 기존 정책에만 있고 통합 정책에 없는 항목 7건은 충돌하지 않아 유지했다(`policy-verification.md` C-05). 통합 정책에 되돌려 적을지는 사용자 확인 사항이다.

### 2.2 정책과 PRD 간 모순
- 정책 두 문서 사이의 **직접 모순은 발견하지 못했다.** 긴장 지점은 모두 모호함으로 분류해 OQ로 보냈다(C-03 예상 정산 복사, C-04 복사 단위, C-17 참여자 추가 권한).
- PRD 내부 모순을 점검했다. `AC-TXN-007-2`(같은 키 재요청은 최초 결과 반환)와 `AC-TXN-005-8`(새 삭제 요청은 거부)는 키가 같은지 다른지로 갈리므로 충돌하지 않는다. `AC-SET-001-6`·`-8`도 같은 방식으로 정리된다.

### 2.4 요구사항의 모호성
- 해소: 통합 정책의 결정으로 v0.1.0의 모호함 대부분(OQ-006, 007, 010~018, 020~025)이 해소됐다.
- 남은 모호함은 전부 `[결정 대기: OQ-xxx]`로 표시되거나 "OQ-xxx 해결 전까지 정의하지 않는다"로 AC에 명시했다. 표시 없이 숨은 모호함을 찾기 위해 "적절/등의/기타/필요 시/충분히/빠르게/즉시/신속" 표현을 검색했고, `AC-TXN-005-5`의 "즉시" 1건이 측정 불가능한 표현이어서 수정했다(SR-08). 이 검색은 일부 단어만 보므로 모든 모호함을 찾는다고 보장하지 않는다.

### 2.5 예외 상황 및 동시성 처리 누락
리뷰 중 발견해 수정한 항목은 3절 SR-01~SR-04다. 확인한 동시성 시나리오는 다음과 같다.

| 시나리오 | 대응 AC |
| --- | --- |
| 같은 거래 동시 수정 | AC-TXN-006-1 |
| 수정과 삭제 동시 | AC-TXN-006-4 |
| 동일 요청 중복 도착 | AC-TXN-007-2, -4, -5 |
| 거래 저장과 게임 종료 동시 | AC-TXN-009-5 (세부 규칙은 OQ-030) |

| 같은 닉네임 동시 등록 | AC-ROOM-006-11 |
| 비활성화와 신규 거래 동시 | AC-PART-002-8 |
| 참여자 등록 순서 경합 | AC-PART-001-5 |

점검했으나 PRD가 다루지 않는 항목: 참여자 활성 상태 변경과 **기존 거래 수정**이 동시에 일어나는 경우는 수정이 허용 필드 변경뿐이라 정합성에 영향이 없다고 판단했다. 같은 거래를 여러 사용자가 보는 동안의 낙관적 충돌 알림은 정책이 LWW만 정해 요구하지 않았다.

### 2.6 수용 기준의 테스트 가능성
- 대부분의 AC는 입력과 기대 결과가 구체적이다(경계값 1/12/13, 0/1/999,999,999/1,000,000,000, 정산 사례 2건).
- 테스트 가능하지 않은 AC는 없다. 수치 기준이 정책에 없는 항목(실시간 지연, 멱등 키 보관 기간, 최소 브라우저 버전)은 AC 대신 "정의하지 않는다"로 명시하고 OQ로 연결했다.
- 한계: 정산 AC의 기대값을 문서에서 손으로 계산했다. `AC-SET-003-1`, `-2`는 정책의 "매번 재정렬" 규칙으로 단계별로 계산해 검증했으나, 구현 전 속성 기반 테스트로 다시 확인해야 한다.

## 4. Spec 작성 가능 여부와 남은 선행 조건

**결론: 지금은 Spec을 시작할 수 없다.** 이유는 세 가지다.

1. **사용자 승인이 없다.** `.agents/governance.md` §3은 G1에서 PRD 확정에 사용자 승인을 요구하고, G2는 승인된 PRD를 입력으로 한다. 현재는 v0.2.0 초안이다.
2. **독립 검수가 없다.** v0.2.0은 Claude 자체 리뷰만 거쳤다. 정책이 크게 바뀌었으므로(예상 정산, 한도, 멱등 확대 등) 새 독립 검수가 필요하다.
3. **필수 결정이 남아 있다.** 아래 10개는 Spec의 동작 정의에 직접 영향을 준다.

   OQ-004(삭제 거래 한도 포함), OQ-008(정규화·반복 공백), OQ-009(사유·라운드 형식), OQ-026(멱등 키 정책), OQ-027(생성자 닉네임), OQ-028(한도 산정 대상), OQ-029(예상 정산 복사·단위), OQ-035(정산 동률 기준), OQ-036(정산 단위 입력 방식), OQ-037(참여자 추가 권한)

선행 조건이 충족된 뒤에도 기능 단위로 Spec을 나눌 수 있다. 영향이 적은 기능은 위 결정 일부만 기다리면 시작할 수 있다.

## 5. 이 리뷰가 확인하지 못한 것

- 독립적 시각이 아니다. 작성자가 같은 맥락으로 검토했으므로 같은 오해를 반복했을 수 있다.
- 통합 정책 파일이 확정 문서인지(버전, 승인)는 확인하지 못했다. 문서에 "GitHub 반영 전 초안"이라고 적혀 있다.
- Notion 원문과 직접 대조하지 못했다. 이 PRD는 통합 정책 파일의 내용만 근거로 한다.
- 구현·런타임·보안 관련 검증은 해당 단계가 아니다.

## 6. 다음 단계 제안

1. 열린 질문 중 필수 10개를 결정한다.
2. 통합 정책을 저장소에 정식 반영한다(버전, 승인). 그 뒤 PRD의 근거 표기를 정리한다.
3. 새 Codex 독립 검수를 실행한다. 이때 `.agents/governance.md`의 "게이트당 최대 3회"를 v0.2.0에 새로 적용할지, v0.1.0의 3회 소진 기록을 이어받을지는 **사용자가 정해야 한다.** Claude가 임의로 횟수를 초기화하지 않았다.
4. 검수 통과 후 사용자가 PRD v0.2.0(또는 수정본)을 승인한다.
