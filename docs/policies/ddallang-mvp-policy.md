# 딸랑 MVP Policy

- 버전: 1.0.0
- 기준일: 2026-11-06
- 상태: MVP 범위 확정 / 정책 추출본
- 원본: https://app.notion.com/p/410436ae094481b1bd2be2349a575570
- 용도: Claude가 PRD를 구체화할 때 사용하는 상위 정책 문서
- 주의: 원본 PRD에 기록된 후속 개발 정책은 폐기된 것이 아니다.

## 1. 제품 목적 및 경계

딸랑은 오프라인 게임 참여자 간 지급 의무를 기록하고 실시간 순손익과 최종 정산을 계산하는 웹 서비스다. 게임 점수를 자동 산출하지 않으며 실제 송금·결제·송금 완료 여부를 관리하지 않는다.

## 2. MVP 포함 범위

- 방 생성 및 초대 링크 입장
- 참여자 등록 및 기본 관리
- 단건 거래 등록·수정·삭제
- 실시간 누적 손익 및 거래 목록
- 방장에 의한 게임 종료, 정산 계산·조회·텍스트 복사
- 기본 서버 권한 검사, 데이터 정합성, 중복 요청 방지, 연결 오류 처리

## 3. 방과 익명 신원

- [POL-ROOM-001] 회원가입 없이 닉네임으로 초대 링크를 통해 입장한다. 방 코드와 최근 방 목록은 없다.
- [POL-ROOM-002] 방 생성 시 정산 단위(원·점수·칩 등)를 정하며 이후 변경할 수 없다. 단위 간 환산은 없다.
- [POL-ROOM-003] RoomMember(접속자)와 Participant(게임 참여자)는 서로 다른 개념이다. 접속자가 참여자가 아니어도 거래를 기록할 수 있고, 참여자는 접속하지 않아도 존재한다.
- [POL-ROOM-004] 익명 신원은 동일 브라우저 재접속 시 복원한다. 브라우저 식별자를 잃으면 새 RoomMember로 입장하며 기존 작성자 신원이나 방장 권한을 복구하지 않는다.
- [POL-ROOM-005] RoomMember 및 Participant 닉네임은 각각 같은 방 내에서 대소문자 구분 없이 고유하다. 1~12자, 한글·영문·숫자·중간 공백만 허용한다. 앞뒤 공백·특수문자·이모지는 거부하며 등록 후 변경할 수 없다.
- [POL-ROOM-006] 현재 방장은 게임을 종료할 수 있다. 방장 권한은 초대 링크 자체로 부여되지 않는다.

## 4. 참여자

- [POL-PART-001] 방장은 참여자를 미리 등록할 수 있고, 게임 진행 중 참여자를 추가할 수 있다.
- [POL-PART-002] 방장은 진행 중 참여자를 비활성화·재활성화할 수 있다. 비활성 참여자의 과거 거래·손익은 보존하되 신규 일반 거래의 당사자로 선택할 수 없다.
- [POL-PART-003] 참여자 이름을 잘못 입력했더라도 이름을 직접 변경하거나 기록을 다른 참여자에게 이전하지 않는다. 기존 참여자를 비활성화하고 새 참여자를 등록한다.
- [POL-PART-004] 게임 종료 후에는 참여자 추가, 활성 상태 변경을 허용하지 않는다.

## 5. 단건 거래

- [POL-TXN-001] 거래 필드는 지급자, 수취자, 금액, 선택적 사유와 라운드다.
- [POL-TXN-002] 금액은 0보다 큰 정수만 허용한다. 동일한 Participant ID 간 거래는 금지한다.
- [POL-TXN-003] 방에 입장한 RoomMember는 게임 진행 중 단건 거래를 등록할 수 있다.
- [POL-TXN-004] 거래 수정·삭제는 거래 작성자 또는 현재 방장만 할 수 있다. 서버에서 권한을 검증한다.
- [POL-TXN-005] 수정은 별도 확인 없이 저장한다. 삭제는 확인 절차를 거치며 손익 집계에서 제외하되 최소한의 원본·작성자 기록은 보존한다.
- [POL-TXN-006] 동일 거래에 대한 동시 수정은 서버에서 마지막으로 성공한 저장을 최종값으로 삼는다. 삭제된 거래에 대한 수정은 거부한다.
- [POL-TXN-007] 저장 중 중복 제출을 방지하고, 서버는 동일 요청 ID의 중복 생성을 막는다. 내용이 같은 서로 다른 거래는 허용한다.
- [POL-TXN-008] 저장 실패 시 성공한 것처럼 표시하지 않는다. 입력값은 현재 화면에서 유지하며 사용자가 수동 재시도한다.
- [POL-TXN-009] 게임 종료 후에는 일반 거래 추가·수정·삭제가 불가능하다. 서버에서 처리 시점의 게임 상태를 검사한다.

## 6. 거래 목록 및 실시간 손익

- [POL-VIEW-001] '누적 손익'과 '거래 내역'을 구분한다.
- [POL-VIEW-002] 순손익은 내림차순으로 표시하고 동률이면 참여자 등록 순서를 따른다.
- [POL-VIEW-003] 거래 목록은 원본 생성 시각 내림차순이다. 수정으로 목록 위치를 변경하지 않는다.
- [POL-VIEW-004] 거래 목록은 20건 단위로 불러오며, 참여자 1명 기준 필터를 제공한다. 해당 참여자가 지급자 또는 수취자인 거래를 포함한다.
- [POL-VIEW-005] 거래 변경은 다른 접속자의 손익과 목록에 실시간 반영한다. 변경 토스트는 필수가 아니다.

## 7. 게임 종료 및 정산

- [POL-SET-001] 방장만 수동 종료할 수 있으며 종료 전 확인한다. 종료 후 일반 거래를 잠근다.
- [POL-SET-002] 거래별 지급자 순손익을 차감하고 수취자 순손익을 가산한다. 모든 참여자의 순손익 합계는 0이어야 한다.
- [POL-SET-003] 정산은 순채무자와 순채권자를 잔액 큰 순서대로 탐욕 매칭한다. 동률은 참여자 등록 순서를 따른다. 전역 최소 송금 횟수는 보장하지 않는다.
- [POL-SET-004] 정산 항목은 금액 내림차순, 동률은 참여자 등록 순서로 표시한다.
- [POL-SET-005] 정산 결과는 조회하고 일반 텍스트로 복사할 수 있다. 방 이름·정산 상태·지급자·수취자·금액·단위를 포함하며 거래 전체 내역은 복사하지 않는다.
- [POL-SET-006] 정산할 송금 항목이 없으면 '정산할 내역이 없습니다.'를 표시하고 복사 버튼을 비활성화한다.
- [POL-SET-007] MVP에는 정산 확정·버전 관리 기능이 없으므로 종료 후 정산은 별도 확정 단계 없이 계산 결과로 제공한다. 후속 개발의 확정/미확정 상태 정책을 MVP에 억지로 적용하지 않는다.

## 8. 연결 및 오류 처리

- [POL-SYS-001] 온라인 상태에서만 데이터를 조회·변경한다. 연결이 끊기면 최신 데이터로 오인할 수 있는 오래된 조회 결과를 표시하지 않는다.
- [POL-SYS-002] 연결 복구 시 최신 서버 상태를 다시 조회한다. 미완료 거래를 자동 제출하지 않는다.
- [POL-SYS-003] 서버는 사용자 권한, 방 상태, 참여자 상태, 거래 유효성을 최종 검증한다.

## 9. 후속 개발로 연기 (기존 정책 보존)

- 여러 거래 일괄 입력
- 정산 확정·버전 관리, 과거 확정 버전 조회
- 종료 후 정정 거래
- 방장 권한 이전·강제 퇴장·초대 링크 재발급
- 상세 감사 이력 및 전체 변경 이력 조회
- 자동 종료·재개·접근 만료·데이터 자동 삭제
- 입력 초안 자동 복원

위 기능의 세부 정책은 원본 Notion PRD를 기준으로 보존하며, MVP PRD와 Spec에는 구현 대상으로 포함하지 않는다.

## 10. OPEN QUESTIONS — Claude가 임의 결정하지 말 것

- [OQ-001] RoomMember와 Participant의 연결·해제 기능이 MVP에 반드시 필요한가? 익명 접속자와 플레이어의 분리만으로 기본 사용 흐름이 가능한지 검토.
- [OQ-002] 후속 기능인 정산 확정이 없는 MVP에서 정산 상태 문구와 복사 텍스트를 어떻게 단순화할 것인가?
- [OQ-003] 자동 만료가 없는 MVP의 방 데이터 보관·수동 삭제 운영 정책은 어떻게 할 것인가?
- [OQ-004] 방당 참여자·접속자·거래 건수의 기술적 한도는 무엇인가?
- [OQ-005] 참여자 관리의 최소 화면 흐름과 게임 종료 후 조회 권한의 구체적 경계는 무엇인가?

## 11. Claude 작업 계약

1. 이 문서를 제품 정책의 기준으로 삼고, 기능 추가나 정책 변경을 임의로 하지 않는다.
2. PRD에는 기능 요구사항 ID(FR-xxx)와 수용 기준을 작성하고 관련 POL ID를 연결한다.
3. 정책상 빈틈이 있으면 OPEN QUESTIONS에 기록하고 제품 결정을 임의로 확정하지 않는다.
4. Spec은 승인된 PRD를 바탕으로 기능별로 분리하고, 요구사항과 테스트를 추적 가능하게 한다.
5. 후속 개발 항목은 현재 구현 범위에서 제외한다. 다만 향후 확장을 막는 데이터 모델상의 위험은 별도 제안할 수 있다.
6. 구현 시작 전 사용자 승인이 필요한 OPEN QUESTIONS를 명확히 제시한다.
