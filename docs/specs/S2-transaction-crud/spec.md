## 1. 범위

### 1.1 담당 FR (AC 53개 + 다른 Spec의 거래 쪽 계약)
FR-TXN-001~009(AC 53개). 그리고 S1이 "S2 소관"으로 넘긴 거래 쪽 계약: AC-ROOM-008-3, -9, -10과 -5·-4의 거래 부분, AC-PART-002-3, -7과 -8의 거래 쪽, AC-SYS-003-3, -4와 거래 관련 -1, -2, -5~-8. AC별 담당과 검증은 §11 추적표.

### 1.2 포함
거래 생성·수정·삭제 API, 거래 값 검증, 작성자·방장 권한, 멱등 키(전송 방식, 유효 기간, 재전송 결과, 충돌, 만료), 삭제된 거래와 감사 데이터 보존, 거래 한도(삭제 포함 1,000건), 종료 후 잠금, 저장 실패·결과 불명 처리의 프론트엔드 책임, 동시성 규칙.

### 1.3 제외와 다른 Spec과의 경계

| 대상 | 담당 | S2의 관계 |
| --- | --- | --- |

## 2. 도메인 모델과 불변식

### 2.1 개체
| 개체 | 필드 | 설명 |
| --- | --- | --- |
| Transaction | `id`, `payerId`, `payeeId`, `amount`, `reason`, `round`, `authorId`, `createdAt`, `updatedAt` | 클라이언트에 노출되는 거래. `payerId`·`payeeId`는 Participant ID, `authorId`는 RoomMember ID. `reason`·`round`는 문자열 또는 `null`. `createdAt`은 서버가 부여한 원본 생성 시각, `updatedAt`은 마지막으로 값이 바뀐 시각(생성 시 `createdAt`과 같다) |
| 거래 내부 기록 | 위 필드 + `originalAmount`, `originalReason`, `originalRound`, `deletedAt`, `deletedById` | 서버만 가진다. 삭제는 행을 지우지 않고 `deletedAt`을 채운다(§6.4). 클라이언트에는 노출하지 않는다 |
| 멱등 기록 | `roomId`, `memberId`, `key`, `fingerprint`, `firstAttemptAt`, `expiresAt`, `operation`, `response`(상태 코드와 본문) | (방, RoomMember, 키)가 유일하다. 서버만 가진다(§5) |

ID(`id`)는 서버가 만드는 불투명 문자열이며 추측하기 어려워야 한다. 금액은 서버와 DB에서 64비트 정수로 다룬다(NFR-009: 상한 999,999,999 × 1,000건 = 약 10¹²는 53비트 안에 들어가지만 합산 안전을 위해 64비트 정수형을 쓴다).

### 2.2 불변식
- T-I1. 거래의 `payerId ≠ payeeId`이고 둘 다 같은 방의 Participant다. 한 번 정해지면 바뀌지 않는다.
- T-I2. `amount`는 1 이상 999,999,999 이하의 정수다.
- T-I3. `id`, `payerId`, `payeeId`, `authorId`, `createdAt`은 생성 뒤 변하지 않는다. 바뀔 수 있는 것은 `amount`, `reason`, `round`(와 그에 따른 `updatedAt`)뿐이다.
- T-I4. 방마다 거래 행의 수(삭제된 행 포함)는 1,000 이하다. 행은 지워지지 않으므로 이 수는 줄지 않는다.
- T-I5. 삭제된 거래(`deletedAt`이 있는 행)는 되살아나지 않고 수정되지 않는다. 일반 목록, 순손익, 정산 계산에서 제외된다.
- T-I6. 한 방의 모든 변경은 방 단위로 직렬화된다(§7).
- T-I7. 모든 변경은 한 요청 단위로 원자적이다. 거부된 요청은 거래 데이터를 저장하지 않는다. 멱등 기록은 거래 데이터가 아니며 §5.3이 정한 경우에만 쓴다.

## 3. 공통 규약

### 3.1 인증과 권한
- 모든 거래 API는 `Authorization: Bearer <신원 키>`가 필요하다(S1 §3.1). 키가 이 방의 RoomMember에 해당하지 않으면 존재하지 않는 방과 같이 `404 ROOM_NOT_FOUND`다(S1 §3.3 3번, N-10). 작성자는 서버가 이 인증으로 정한 RoomMember이고 **요청 본문의 작성자 값은 신뢰하지 않는다**(§3.5).
- 거래 생성: 방에 입장한 모든 RoomMember(방장 포함).
- 거래 수정·삭제: 그 거래의 작성자(`authorId` = 요청자) 또는 현재 방장. 작성자도 방장도 아니면 `403 NOT_AUTHOR_OR_HOST`. 서버는 요청 시점에 판정하며 화면의 버튼 노출과 무관하다.

### 3.2 문자열 검증 (`reason`, `round`) — T-5 (사용자 승인 2026-11-08)
`reason`(사유)과 `round`(라운드)는 선택 입력이다. 검증은 다음 순서이며 자동 공백 제거는 하지 않는다.
0. **없음 처리**: 필드가 없거나 `null`이거나 빈 문자열 `""`이면 "입력 없음"이고 `null`로 저장한다. 문자열이 아니면 `INVALID_TYPE`이다. 원본 문자열이 코드 포인트 200(`reason`) 또는 48(`round`)을 넘으면 정규화하지 않고 `LENGTH_OUT_OF_RANGE`로 거부한다.
1. 입력을 Unicode **NFC**로 정규화한다. 이후 검사·저장·응답은 정규화한 값이다.
2. **길이**: 코드 포인트 수가 `reason` 50 이하, `round` 12 이하여야 한다. 초과하면 `LENGTH_OUT_OF_RANGE`다(AC-TXN-001-6: 50자·12자 허용, 51자·13자 거부).
3. **허용 문자**: 다음을 거부하고 `INVALID_CHARACTER`로 반환한다. 제어 문자(줄바꿈·탭 포함, 범주 Cc), 서식 문자(범주 Cf: 제로폭 문자, 방향 제어 문자, ZWJ 포함), 한글 채움 문자(U+115F, U+1160, U+3164, U+FFA0), 서로게이트·사용자 정의·미할당 코드 포인트(Cs, Co, Cn), 줄·문단 구분자(Zl, Zp), U+0020을 제외한 모든 공백 구분자(Zs). 그 밖의 글자·숫자·구두점·기호·결합 문자·이모지(ZWJ 연결 없이 단일 코드 포인트로 된 것)는 허용한다.
4. **공백 규칙**: 첫 문자나 마지막 문자가 U+0020이면 `LEADING_OR_TRAILING_SPACE`로 거부한다. 공백만으로 된 값도 같다. 값 안의 일반 공백(U+0020)은 허용하며 연속 공백도 허용한다(자유 서술이므로 닉네임과 달리 막지 않는다). 서버는 공백을 자동으로 제거(trim)하지 않는다.
5. 2~4의 위반은 독립이므로 모아서 한 번에 반환한다(§3.4).

이 규칙은 PRD OQ-039를 해소하는 사용자 승인 결정(T-5)이다. 줄바꿈·탭·제어 문자·보이지 않는 서식 문자는 거부하고, 한글·영문·숫자·기호·이모지는 허용한다. 수정(§4.2)에도 같은 규칙을 적용한다. 화면은 사유와 라운드를 항상 일반 텍스트로 이스케이프해 표시한다(§9).

### 3.3 금액 검증
`amount`는 JSON 숫자여야 하며 파싱한 값이 정수이고 1 이상 999,999,999 이하여야 한다. 누락·`null`은 `REQUIRED`, 숫자가 아닌 값(문자열 `"100"` 포함)은 `INVALID_TYPE`, 소수는 `INVALID_VALUE`, 0·음수·1,000,000,000 이상은 `OUT_OF_RANGE`다(AC-TXN-002-1, -2). 정산 단위와 무관하게 같은 상한이다(AC-TXN-002-5).

### 3.4 검사 순서
요청은 다음 순서로 검사하고 **처음 걸린 오류 하나**를 반환한다. 단 입력 검증 오류(8번)는 위반 항목 전체를 담는다. S1 §3.3의 순서를 따르되 멱등 처리 단계를 추가했다.
0. **라우트**: 없는 경로 `404 ROUTE_NOT_FOUND`, 없는 메서드 `405 NOT_SUPPORTED`(`Allow` 포함). 인증 전이며 정보를 드러내지 않는다.
1. 신원 키 누락·형식 오류: `401 UNAUTHENTICATED`
2. 방 존재, 방 멤버 여부(비멤버는 방이 없는 것과 같은 응답): `404 ROOM_NOT_FOUND`
3. **멱등 헤더 검증**(§5.1): 헤더 누락·형식 오류 → `422 VALIDATION_FAILED`(필드 `idempotencyKey`, `firstAttemptAt`). 미래 시각은 오류가 아니라 수신 시각으로 낮춘다(§5.4).
4. **만료**: 최초 시도 시각 + 24시간이 지났으면 `409 IDEMPOTENCY_KEY_EXPIRED`(§5.4). 기록 유무와 무관하다. `details`에 서버 시각을 담는다.
5. **재전송 판정**(§5.3): (방, 요청자, 키) 기록이 있으면 같은 내용(지문 일치)이면 저장된 결과를 반환하고 끝낸다. 다른 내용이면 `409 IDEMPOTENCY_CONFLICT`.
6. (수정·삭제만) 대상 거래: 이 방에 없거나 다른 방의 거래이면 `404 TRANSACTION_NOT_FOUND`. 삭제된 거래도 존재한다.
7. (수정·삭제만) 작성자·방장 여부: `403 NOT_AUTHOR_OR_HOST`
8. 방 상태: `ENDED`면 `409 GAME_ENDED`
9. (수정·삭제만) 이미 삭제된 거래: `409 TRANSACTION_DELETED`("이미 삭제된 거래입니다")
10. 입력 검증과 참조 확인: `422 VALIDATION_FAILED`. 본문 형식, 금액, 사유·라운드, 허용되지 않은 필드, 지급자·수취자 ID가 이 방의 Participant인지, 지급자와 수취자가 같은지(생성만)를 모아 반환한다.
11. (생성만) 비활성 참여자 지정: `409 PARTICIPANT_INACTIVE`
12. (생성만) 거래 한도: `409 TRANSACTION_LIMIT_EXCEEDED`

- 5번(재전송)이 6~12번보다 앞이므로 최초 결과가 성공이거나 영구적 거부였던 요청의 재전송은 상태가 달라졌어도 상태 검사를 다시 받지 않는다(AC-TXN-007-8, -9, -10).
- 3·4번과 10·11번의 거부는 멱등 기록을 만들지 않는다. 6·7번(404, 403)도 기록하지 않는다. 기록하는 것은 §5.2의 성공과 영구적 거부뿐이다.
- 비작성자·비방장은 방이 종료됐어도 `NOT_AUTHOR_OR_HOST`를 받는다(7번이 8번보다 앞, S1의 `HOST_ONLY`와 같은 원칙).
- 생성에는 6·7·9번이 없다. 방 상태(8번)가 10번보다 앞이므로 종료된 방에서는 본문이 틀려도 `GAME_ENDED`다.

### 3.5 허용 필드
생성은 `payerId`, `payeeId`, `amount`, `reason`, `round`만, 수정은 `amount`, `reason`, `round`만 받는다. **이 밖의 필드는 모두 `NOT_ALLOWED_FIELD`로 거부한다**(예: 생성의 `authorId`·`createdAt`, 수정의 `payerId`·`payeeId`·`id`·`authorId`·`createdAt`). 무시하고 통과시키지 않으며 아무것도 바꾸지 않는다(AC-TXN-003-3, AC-TXN-005-6).

### 3.6 오류 코드
S1 §3.4의 형식과 코드를 쓰고 다음을 더한다. `message`는 한국어 사용자 안내 문구이며 클라이언트가 그대로 보여 줄 수 있다.

| HTTP | `code` | 의미 | 멱등 기록 |
| --- | --- | --- | --- |
| 403 | `NOT_AUTHOR_OR_HOST` | 작성자도 방장도 아닌 방 멤버의 수정·삭제 | 안 함 |
| 404 | `TRANSACTION_NOT_FOUND` | 거래 없음. 다른 방의 거래 ID 포함(AC-SYS-003-8) | 안 함 |
| 409 | `GAME_ENDED` | 종료된 방(S1과 같은 코드) | **함** |
| 409 | `TRANSACTION_DELETED` | "이미 삭제된 거래입니다". 수정·삭제 공통 | **함** |
| 409 | `PARTICIPANT_INACTIVE` | 비활성 참여자를 지급자·수취자로 지정한 생성. `details`는 `[{ "field": "payerId" 또는 "payeeId" }]` | 안 함 |
| 409 | `TRANSACTION_LIMIT_EXCEEDED` | 거래 1,000건(삭제 포함) 초과. `details`는 `[{ "limit": 1000 }]` | **함** |
| 409 | `IDEMPOTENCY_CONFLICT` | 같은 키로 다른 내용 | — |
| 409 | `IDEMPOTENCY_KEY_EXPIRED` | 키 유효 기간 경과. `details`는 `[{ "serverTime": RFC 3339 }]` | 안 함 |
| 422 | `VALIDATION_FAILED` | 입력 위반 | 안 함 |

추가 검증 사유 코드(`details[].code`): `OUT_OF_RANGE`, `SAME_AS_PAYER`(`payeeId`가 `payerId`와 같음), `PARTICIPANT_NOT_FOUND`(`payerId`·`payeeId`가 이 방에 없거나 다른 방의 Participant). 그 밖은 S1과 같다(`REQUIRED`, `INVALID_TYPE`, `INVALID_VALUE`, `LENGTH_OUT_OF_RANGE`, `LEADING_OR_TRAILING_SPACE`, `INVALID_CHARACTER`, `NOT_ALLOWED_FIELD`).

## 4. API 계약

경로의 `{roomId}`는 방 ID, `{transactionId}`는 거래 ID다. 요청·응답 본문은 JSON(UTF-8)이다. 아래 세 요청은 모두 §5의 헤더 `Idempotency-Key`, `Idempotency-First-Attempt-At`가 필수다.

### 4.1 `POST /rooms/{roomId}/transactions` — 거래 생성 (FR-TXN-001~003, 007, 009, FR-ROOM-008)
- 인증: 필수, 이 방의 RoomMember.
- 요청: `{ "payerId": string, "payeeId": string, "amount": number, "reason"?: string|null, "round"?: string|null }`. `payerId`, `payeeId`, `amount`는 필수다.
- 처리: §3.4 순서. 통과하면 `authorId`를 요청자로, `createdAt`·`updatedAt`을 서버 시각으로 하여 만들고 `originalAmount`, `originalReason`, `originalRound`를 같은 값으로 보존한다. 방 단위 직렬화 안에서 한도와 참여자 상태를 확인하고 삽입한다(§7).
- 응답 `201`: `{ "transaction": Transaction }`
- 오류: 401, 404 `ROOM_NOT_FOUND`(비멤버 포함), 409 `IDEMPOTENCY_KEY_EXPIRED`/`IDEMPOTENCY_CONFLICT`/`GAME_ENDED`/`PARTICIPANT_INACTIVE`/`TRANSACTION_LIMIT_EXCEEDED`, 422.
- 지급자·수취자, 금액, 사유, 라운드가 모두 같아도 키가 다르면 별개의 거래다(AC-TXN-007-3).

### 4.2 `PUT /rooms/{roomId}/transactions/{transactionId}` — 거래 수정 (FR-TXN-004~006)
- 인증: 필수. 작성자 또는 방장.
- 요청: `{ "amount": number, "reason"?: string|null, "round"?: string|null }`. 수정은 이 세 값을 **통째로 교체**한다(T-4). `amount`는 필수이고, `reason`·`round`를 생략하거나 `null`·`""`로 보내면 `null`로 지운다. 이 밖의 필드는 `NOT_ALLOWED_FIELD`다.
- 처리: §3.4 순서. 새 값이 현재 값과 모두 같으면 변경 없이 `200`으로 현재 거래를 반환하고 `updatedAt`과 이벤트도 바꾸지 않는다(T-4). 다르면 값을 바꾸고 `updatedAt`을 갱신한다. 별도 확인 절차는 없다(AC-TXN-005-1). 동시 수정은 방 단위 직렬화 안에서 나중에 성공한 저장이 최종값이다(AC-TXN-006-1).
- 응답 `200`: `{ "transaction": Transaction }`
- 오류: 401, 404 `ROOM_NOT_FOUND`/`TRANSACTION_NOT_FOUND`, 403 `NOT_AUTHOR_OR_HOST`, 409 `IDEMPOTENCY_*`/`GAME_ENDED`/`TRANSACTION_DELETED`, 422.

### 4.3 `DELETE /rooms/{roomId}/transactions/{transactionId}` — 거래 삭제 (FR-TXN-004, 005)
- 인증: 필수. 작성자 또는 방장. 본문은 없다. 삭제 확인은 클라이언트 책임이다(§9).
- 처리: §3.4 순서. `deletedAt`과 `deletedById`를 채운다. 행과 원본·작성자 정보는 지우지 않는다(§6.4).
- 응답 `200`: `{ "transactionId": string, "deletedAt": string }`
- 오류: 401, 404 `ROOM_NOT_FOUND`/`TRANSACTION_NOT_FOUND`, 403 `NOT_AUTHOR_OR_HOST`, 409 `IDEMPOTENCY_*`/`GAME_ENDED`/`TRANSACTION_DELETED`, 422(헤더 형식).
- 최초 삭제만 성공한다. 새 키의 반복 삭제는 `409 TRANSACTION_DELETED`다(AC-TXN-005-8).

### 4.4 존재하지 않는 동작 (S1 §4.8과 같은 원칙)
| 동작 | 응답 |
| --- | --- |
| `PATCH /rooms/{roomId}/transactions/{transactionId}`, `POST`, `GET`(단건) | 405 `NOT_SUPPORTED`, `Allow: PUT, DELETE` |
| `PUT`/`PATCH`/`DELETE /rooms/{roomId}/transactions` | 405 `NOT_SUPPORTED`, `Allow`는 이 경로가 지원하는 메서드(`POST`, S3가 목록을 추가하면 `GET, POST`) |
| 일괄 등록(`POST /rooms/{roomId}/transactions/batch` 등), 당사자 변경, 거래 이전, 종료 후 정정 거래, 변경 이력·감사 조회 | 경로를 정의하지 않으므로 404 `ROUTE_NOT_FOUND` |

## 5. 멱등 키 (FR-TXN-007, NFR-003, 부록 A)

### 5.1 전송과 형식 (T-1)
- 헤더 `Idempotency-Key`: 클라이언트가 만든 값. 정규식 `^[A-Za-z0-9_-]{16,64}$`(UUID v4 또는 22자 이상 base64url 난수를 권장). 요청마다 하나이고 거래 생성·수정·삭제 세 요청에 필수다.
- 헤더 `Idempotency-First-Attempt-At`: 클라이언트가 **이 요청 내용을 처음 시도한 시각**. RFC 3339 UTC 밀리초 형식(예: `2026-11-08T03:21:45.123Z`). 같은 내용의 재시도는 첫 시도에서 보낸 값을 그대로 다시 보낸다.
- 키의 효력 범위는 (방, 요청자 RoomMember)다. 다른 방이나 다른 RoomMember의 같은 키 값은 별개의 요청이며 서로의 결과를 재사용하지 않는다(AC-TXN-007-7).
- 헤더 누락·형식 위반은 `422 VALIDATION_FAILED`(`field`: `idempotencyKey` 또는 `firstAttemptAt`, `code`: `REQUIRED` 또는 `INVALID_VALUE`)이며 기록하지 않는다. 서버 시각 이후의 값은 형식 위반이 아니다(§5.4).

### 5.2 "같은 내용"과 기록 대상 (T-3)
- **지문(fingerprint)**: 연산 종류(생성/수정/삭제), 대상 거래 ID(수정·삭제), 정규화한 요청 값(`payerId`, `payeeId`, `amount`, NFC 정규화한 `reason`·`round`와 `null` 구분 없는 "입력 없음")의 SHA-256. 같은 키로 연산 종류나 값이 다르면 다른 내용이다.
- **기록하는 결과**: (a) 성공, (b) 상태에 따른 영구적 거부 — `GAME_ENDED`, `TRANSACTION_DELETED`, `TRANSACTION_LIMIT_EXCEEDED`(AC-TXN-007-10, 한도는 슬롯 회수가 없어 영구). 응답의 상태 코드와 본문을 그대로 저장한다.
- **기록하지 않는 결과**: 3·4번(헤더·만료), 401, 404, 403, `PARTICIPANT_INACTIVE`, 422(AC-TXN-007-13). 부작용이 없는 거부이므로 같은 키·같은 내용의 재전송은 새 요청으로 상태를 다시 검사한다. 같은 키로 내용을 바꿔 보내도 기록이 없으므로 충돌이 아니라 새 요청이다.
- 기록은 거래 변경과 **같은 트랜잭션**에서 쓴다. 거래는 저장됐는데 기록이 없거나 그 반대인 상태는 없다.

### 5.3 재전송 판정
키 유효 기간 이내(5.4)에 (방, 요청자, 키) 기록이 있으면 다음과 같다. 상태 검사(§3.4의 6~12)는 하지 않는다.
- 지문이 같으면 **저장된 응답을 같은 상태 코드와 본문으로 반환**한다. 거래를 다시 만들거나 바꾸지 않는다. 응답 헤더 `Idempotent-Replayed: true`를 더한다. 반환되는 본문은 처리 당시의 결과이며 현재 거래 상태가 아니다.
- 지문이 다르면 `409 IDEMPOTENCY_CONFLICT`이고 기존 데이터는 변하지 않는다(AC-TXN-007-4).
- 같은 키·같은 내용의 요청이 동시에 둘 이상 도착하면 방 단위 직렬화(§7)로 하나만 처리되고 나머지는 위 재전송으로 같은 결과를 받는다(AC-TXN-007-2, ROOM-008-5의 마지막 문장).
- 기록이 없는 키(요청이 도달하지 못했던 경우)는 새 요청이다. 그 시점의 방 상태·권한·한도·거래 상태 검사를 모두 받는다. 종료 뒤에 처음 도착하면 같은 키여도 거부된다(AC-TXN-007-11, AC-TXN-009-1).

### 5.4 유효 기간과 만료 (T-2, 사용자 결정 OQ-040)
- **유효 기간은 클라이언트가 요청을 처음 시도한 시각(`Idempotency-First-Attempt-At`)부터 24시간**이다. 서버가 이 시각을 아는 방법이 이 헤더다.
- **만료**: 서버 수신 시각이 `firstAttemptAt + 24시간`을 지났으면 `409 IDEMPOTENCY_KEY_EXPIRED`로 거부한다. 서버 기록이 남아 있든 없든, 내용이 같든 다르든 같다. 거래·게임 상태는 변하지 않고 멱등 기록도 만들지 않는다. 메시지는 요청이 만료되었음과 거래 목록에서 저장 여부를 확인하라는 안내를 담는다(AC-TXN-007-12). 만료 판정은 충돌 판정(5번)보다 앞이다(4번 < 5번).
- 기록이 있는 키로 재전송할 때 `firstAttemptAt`이 기록과 다르면 **더 이른 값**으로 만료를 판정한다. 재시도로 유효 기간을 늘릴 수 없다. 기록이 없으면(요청이 도달하지 못했던 경우) 요청에 실린 값(미래면 수신 시각으로 낮춘 값)으로 판정한다.
- **미래 시각**: 서버 수신 시각보다 뒤의 `firstAttemptAt`은 거부하지 않고 **서버 수신 시각으로 낮춰** 쓴다(`min(보낸 값, 수신 시각)`). 시계가 빠른 기기가 정상 요청을 거부당하지 않게 하고, 유효 기간이 실제 최초 수신보다 늘어나지 않게 한다. 기록에 저장하는 `firstAttemptAt`도 이 낮춘 값이다.
- **시계 오차와 만료** (분석은 아래 표): 기기 시계가 느린 만큼 유효 기간(재시도 가능 시간)이 줄고, 24시간 넘게 느리면 첫 요청부터 만료로 거부된다. 이를 줄이기 위해 클라이언트는 §9의 보정 규칙을 따르고, 서버는 만료 오류에 서버 시각을 담는다(`details: [{ "serverTime": "<RFC 3339>" }]`). 서버는 PRD의 기준점(클라이언트가 처음 시도한 시각)을 바꾸지 않는다.

| 클라이언트 시계 (실제 대비) | 보정 없이 보낸 `firstAttemptAt` | 서버 처리 | 결과 |
| --- | --- | --- | --- |
| 정확 | 실제 시각 | 그대로 | 최초 시도 후 24시간 이내 재시도 가능 |
| 느림, 24시간 미만 (예: 1시간) | 실제보다 1시간 이전 | 그대로 | 재시도 가능 시간이 23시간으로 줄어듦. 정상 요청은 거부되지 않음 |
| 느림, 24시간 이상 | 실제보다 24시간 이상 이전 | 첫 요청부터 만료 | 모든 거래 요청이 `IDEMPOTENCY_KEY_EXPIRED`. 보정(§9)으로 회피 |
| 빠름 (예: 10분) | 실제보다 10분 이후 | 수신 시각으로 낮춤 | 정상 처리. 유효 기간은 서버 수신 시각부터 24시간 |
| 임의 조작 | 임의 | 위 규칙을 그대로 적용 | 자기 키의 만료에만 영향 |
- **보관**: 서버는 최소 `firstAttemptAt + 24시간`까지 기록을 보관한다. 그 뒤 삭제해도 되며(삭제 시점에는 어차피 만료 거부), 삭제 방법과 주기는 Plan이 정한다.
- **새 키의 새 요청은 이 규칙의 대상이 아니다**(AC-TXN-007-12). 새 요청은 처음 시도하는 것이므로 클라이언트가 현재 시각을 `firstAttemptAt`으로 보내 24시간 이내이고, 서버는 상태 검사(AC-TXN-009-1 등)만 한다. 서버는 새 키와 기록이 지워진 옛 키를 구분할 수 없으므로, `firstAttemptAt`이 24시간을 지났다는 사실 자체를 "오래전에 처음 시도한 요청의 재시도"로 보고 만료로 거부한다. 이는 PRD가 만료 판정을 서버 기록의 유무와 무관하게 하라고 한 규칙(AC-TXN-007-12)을 구현 가능하게 한 것이다.

## 6. 동작 규칙

### 6.1 생성
- 지급자와 수취자는 이 방의 Participant여야 하고(`PARTICIPANT_NOT_FOUND`), 같을 수 없고(`SAME_AS_PAYER`), 둘 다 `ACTIVE`여야 한다(`PARTICIPANT_INACTIVE`). 참여자 상태는 방 단위 직렬화 안의 같은 트랜잭션에서 읽는다(S1 §7 6번, AC-PART-002-8).
- 접속자가 없는 Participant도 당사자가 될 수 있고, 거래를 쓰는 RoomMember가 당사자일 필요는 없다(AC-ROOM-004-1, -2).
- 작성자는 항상 요청자다. 작성자가 방장이라는 사실은 기록하지 않는다(방장은 방 단위 현재 상태다).
- 일괄 등록 경로는 없다(AC-TXN-001-5).

### 6.2 수정
- 바꿀 수 있는 것은 `amount`, `reason`, `round`뿐이다(AC-TXN-005-6). 비활성 참여자가 당사자인 거래도 수정할 수 있다(AC-PART-002-7). 방장은 타인의 거래도 수정할 수 있다(AC-TXN-004-2).
- 수정은 한도에 영향을 주지 않는다.
- 당사자를 잘못 적었으면 삭제 후 새 거래를 만든다. 새 거래는 새 `id`와 새 `createdAt`을 가지며 거래 한도 슬롯을 하나 더 쓴다(AC-TXN-005-7, 삭제된 행도 센다).

### 6.3 삭제
- 삭제된 거래는 일반 거래 목록, 모든 참여자의 순손익, 예상·최종 정산에서 제외된다(S3·S4가 이 정의를 따른다). 삭제된 거래는 수정할 수 없다. 반복 삭제는 `409 TRANSACTION_DELETED`다.
- 삭제는 거래 한도 슬롯을 돌려주지 않는다(AC-ROOM-008-9, 사용자 결정 OQ-004).

### 6.4 감사 데이터 보존 (T-8)
삭제 후에도 서버는 거래 행을 지우지 않고 다음을 보존한다: 거래 `id`, 당사자 ID, 작성자 `authorId`, `createdAt`, 생성 당시 원본 값(`originalAmount`, `originalReason`, `originalRound`), 삭제 시각과 삭제한 RoomMember(`deletedAt`, `deletedById`). 이 기록을 조회하는 API와 화면, 변경 이력은 MVP에 없다(AC-TXN-005-4, FR 제외 범위). 중간 수정 값의 이력은 남기지 않는다.

### 6.5 종료 후 잠금
방이 `ENDED`이면 생성·수정·삭제 새 요청은 방장도 `409 GAME_ENDED`다(AC-TXN-009-1). 종료 전에 성공 처리된 요청의 같은 키 재전송은 거부되지 않고 최초 성공 결과를 받는다(5.3, AC-TXN-007-8, -9). 종료 후 정정 거래 기능은 없다(AC-TXN-009-4).

## 7. 동시성과 정합성 (T-6, 사용자 결정 대기)

서버는 다음을 보장해야 한다. 구현 방법은 Plan이 정한다.

1. **방 단위 직렬화**: 한 방에서 거래 생성·수정·삭제, 참여자 상태 변경·등록, 게임 종료(S4)는 하나의 직렬 순서로 처리한다. **"처리 시점"은 이 직렬화에서 요청이 차례를 얻은 순간**이며, 요청이 클라이언트를 떠나거나 서버에 도착한 순서가 아니다. 검사와 변경은 같은 트랜잭션 안에서 하고 잠금은 커밋까지 유지하므로 직렬 순서가 곧 확정(커밋) 순서다. **직렬화는 서버 인스턴스가 여러 개여도 성립해야 한다.** 프로세스 안의 메모리 잠금(mutex, 인메모리 큐)만으로 구현하지 않고, 인스턴스가 공유하는 저장소의 트랜잭션 수준 잠금(예: PostgreSQL의 방 행 잠금 또는 advisory lock)을 쓴다. 세부 수단은 Plan이 정한다.
2. **종료와 저장의 경쟁**(AC-TXN-009-5, OQ-030): 거래 요청과 종료 요청이 동시에 도착하면 직렬 순서가 먼저인 쪽이 먼저 반영된다. 종료가 앞서면 뒤의 새 거래 요청은 `GAME_ENDED`이고, 거래가 앞서면 그 거래는 최종 정산에 포함된다. 클라이언트에게 순서를 보장하지는 않는다.
3. **동시 수정**(AC-TXN-006-1): 나중에 직렬 순서를 얻은 저장이 최종값이다. 통째 교체(T-4)이므로 한 필드의 값이 다른 요청의 필드 값과 섞이지 않는다.
4. **수정·삭제의 경쟁**(AC-TXN-006-4): 삭제가 앞서면 뒤의 수정은 `TRANSACTION_DELETED`다. 수정이 앞서면 삭제가 이어진다. 결과는 하나로 일관된다.
5. **비활성화와 생성의 경쟁**(AC-PART-002-8, S1 §7 6번): 비활성화가 앞서면 뒤의 생성은 `PARTICIPANT_INACTIVE`다.
6. **한도의 마지막 슬롯**(AC-ROOM-008-5): 한도 확인과 삽입은 직렬화 안에서 하므로 서로 다른 키의 생성 요청 N개가 마지막 슬롯에 동시에 도착하면 정확히 하나만 성공하고 나머지는 `TRANSACTION_LIMIT_EXCEEDED`다. 거래 행 수는 1,000을 넘지 않는다.
7. **같은 키 동시 요청**: 5.3처럼 하나만 처리하고 나머지는 재전송 결과를 받는다. 멱등 기록은 (방, 요청자, 키) 유일 제약과 거래 변경을 한 트랜잭션에 둔다.
8. **순손익 합 0**(NFR-001): 모든 거래가 (지급자 −금액, 수취자 +금액)이고 삭제 거래를 제외하므로 어떤 시점에도 합이 0이다. 이는 서버 계산(S3)의 속성 기반 테스트로 검증한다(AC-TXN-006-3).

## 8. 실시간 이벤트 발생 지점 (스키마는 S5)

FR-VIEW-005에 따라 다른 접속자에게 새로고침 없이 반영해야 하는 변경은 다음이다. 이름·페이로드·전달은 S5가 정한다.
- 거래 생성 성공, 거래 수정 성공(값이 실제로 바뀐 경우), 거래 삭제 성공.
- 멱등 재전송(5.3)과 값이 같은 수정(no-op)은 새 변경이 아니므로 이벤트를 만들지 않는다.
- 거부된 요청은 이벤트를 만들지 않는다.

## 9. 프론트엔드 책임

- **입력**: 지급자, 수취자(활성 참여자만 선택지에 보이며 비활성은 제외, AC-PART-002-3), 금액, 사유(최대 50자), 라운드(최대 12자). 클라이언트 검증(§3.2, §3.3, 같은 당사자 금지)은 즉시 오류를 보이는 편의이며 서버가 최종이다. 오류가 있으면 저장하지 않고 입력을 유지한다(AC-TXN-001-3, 008-2). 일괄 입력 UI는 없다.
- **저장 중 보호**: 요청이 진행 중이면 저장 컨트롤을 비활성화한다(AC-TXN-007-1).
- **시각 보정**: 클라이언트는 서버 응답의 `Date` 헤더로 기기 시계와 서버 시계의 차이를 추정해 보관하고(가장 최근 응답 기준), `Idempotency-First-Attempt-At`에 **보정한 현재 시각**(기기 시각 + 추정 차이)을 쓴다. 차이를 아직 모르면 거래 요청 전에 방 조회 같은 응답으로 먼저 알아낸다. 차이가 5분을 넘으면 기기 시간 설정을 확인하라고 안내할 수 있다. 이 보정은 PRD가 정한 "클라이언트가 처음 시도한 시각"을 서버 시계 기준으로 표현하는 것이며 기준점을 바꾸지 않는다.
- **멱등 키 수명**: 사용자가 처음 저장을 누르면 새 `Idempotency-Key`와 보정한 현재 시각의 `Idempotency-First-Attempt-At`을 만들어 **메모리에** 보관한다. 같은 입력 내용의 수동 재시도에는 같은 키와 같은 `firstAttemptAt`을 다시 보낸다(AC-TXN-007-5). 입력 내용을 바꿨다면 새 키와 새 `firstAttemptAt`을 쓴다(AC-TXN-007-6). 성공하면 키를 버린다. `firstAttemptAt`에서 24시간이 지났으면 새 키를 쓴다. 키는 저장소에 보관하지 않으므로 새로고침하면 사라진다(입력 초안 복원 없음, AC-SYS-002-4).
- **실패 표시**(FR-TXN-008): 서버가 확정 거부하면 사유를 보이고 성공을 표시하지 않으며 입력을 유지한다. 자동 재전송은 하지 않는다(AC-TXN-008-3). 응답이 없어 결과를 모르면 "결과를 확인하지 못했습니다"라고 알리고 성공으로 표시하지 않는다. 연결이 복구되면 거래 목록(S3)을 다시 조회해 해당 거래가 있으면 보여 주고, 없으면 저장되지 않았다고 단정하지 않고 확정할 수 없음을 유지한다(AC-TXN-008-5, AC-SYS-002-5). 사용자가 원하면 같은 키로 수동 재시도한다.
- **만료 안내**: `IDEMPOTENCY_KEY_EXPIRED`이면 서버 `message`를 그대로 보여 주고 목록에서 저장 여부를 확인하도록 안내한다. 응답의 `serverTime`과 기기 시각의 차이가 크거나 사용자가 방금 시작한 요청인데 만료이면 기기 시간 설정을 확인하라고 덧붙이고 새 키로 다시 저장하도록 한다.
- **삭제**: 확인 절차를 거친 뒤에만 요청하고 취소하면 아무것도 보내지 않는다(AC-TXN-005-2). 수정은 확인 없이 저장한다(AC-TXN-005-1). 수정 UI에는 당사자 입력이 없다(AC-TXN-005-6).
- **종료 후**: 거래 입력·수정·삭제 컨트롤을 숨기거나 비활성화한다(AC-TXN-009-3). 오프라인에서는 변경을 보내지 않으며 큐에 쌓지 않는다(AC-SYS-001-3).
- **한도**: `TRANSACTION_LIMIT_EXCEEDED`이면 거래 한도 초과를 안내하고 입력값을 유지한다(AC-ROOM-008-3).
- **텍스트 표시**: 사유·라운드는 항상 일반 텍스트로 이스케이프해 표시한다(HTML로 해석하지 않는다).
- 오류 `code`로 분기하고 `message`는 그대로 쓴다.

## 10. 백엔드 책임

- S1 §3.1 신원 인증과 §3.4 검사 순서(이 Spec의 §3.4), §4 엔드포인트, §5 멱등 처리, §7 직렬화·원자성을 정확히 구현한다.
- 작성자, 방, 참여자 상태, 한도, 권한, 금액 규칙을 모두 서버가 판정한다. 클라이언트 값(작성자, 시각 등)을 신뢰하지 않는다(NFR-002).
- 삭제는 행을 지우지 않는다. 금액은 64비트 정수로 저장·합산한다.
- §7의 직렬화는 다중 인스턴스에서도 성립하도록 공유 저장소의 트랜잭션 잠금으로 구현하고, 인스턴스 둘 이상을 같은 DB에 붙인 동시성 테스트로 검증한다.
- 이 Spec의 계약을 다른 저장소 문서에 복제하지 않고 Spec 버전 또는 `ddallang` 커밋으로 참조한다.

## 13. 위험
- **클라이언트 시계 의존(T-1, T-2)**: 최초 시도 시각을 클라이언트가 보내므로 시계가 느리면 재시도 가능 시간이 그만큼 줄고, 24시간 넘게 느리면 첫 요청부터 만료된다. 시계가 빠른 경우는 서버가 수신 시각으로 낮추므로 거부되지 않는다. 서버가 시각을 대신 정하는 방식은 PRD(AC-TXN-007-12, OQ-040)가 클라이언트 최초 시도 기준으로 확정했기 때문에 택하지 않았다. 완화: 클라이언트의 `Date` 보정(§9), 만료 응답의 `serverTime`, 안내 문구. 서버 `Date`를 아직 한 번도 받지 못한 첫 요청은 기기 시계를 그대로 쓰므로 위험이 남는다.
- **신뢰하지 않는 시각**: 악의적 클라이언트가 `firstAttemptAt`을 조작해도 만료는 자신의 키에만 영향을 주고 다른 사용자나 데이터에 영향을 주지 않는다. 멱등 기록 보관량은 키 수에 비례하므로 속도 제한은 Plan이 검토한다(MVP 방 규모가 작아 영향은 제한적).
- **한도 슬롯 회수 불가(R-01)**: 삭제 후에도 거래 행이 남아 1,000건이 차면 그 방은 더 거래를 만들 수 없다. 정책 결정이며 수용된다.
- **영구 거부 기록의 부작용**: 종료 뒤 처음 도착한 요청이 `GAME_ENDED`로 기록되므로 같은 키의 재전송은 같은 거부다. 이는 부록 A와 일치한다.
- **직렬화 비용(T-6)**: 방 단위 직렬화는 한 방의 모든 쓰기를 순서화한다. 방당 RoomMember 10명, 거래 1,000건 규모에서는 문제가 작지만 Plan에서 잠금 방식과 지연을 확인한다. 다중 인스턴스 요구로 DB 트랜잭션 잠금이 필요하므로 잠금 대기와 데드락(참여자·거래·종료의 잠금 순서)을 Plan에서 확인한다.
- **멱등 기록과 "거부는 데이터를 바꾸지 않는다"(AC-SYS-003-5)**: 영구적 거부를 멱등 기록으로 저장하는 것은 거래·참여자·방 데이터를 바꾸지 않으며 PRD 부록 A의 재전송 규칙을 구현하는 데 필요하다. 이 기록을 "데이터 변경"으로 엄격히 읽는 해석이 나오면 T-3을 재검토해야 한다.
- **통째 교체의 생략 해석(T-4)**: 수정에서 `reason`·`round`를 생략하면 지워진다. 수정 화면은 세 값을 항상 보내야 한다.
- **재전송 본문의 시점**: 재전송은 처리 당시 결과를 반환하므로 그 사이 다른 사용자가 수정·삭제한 최신 상태와 다를 수 있다. 클라이언트는 응답을 최종 상태로 가정하지 않고 목록 재조회(S3)로 현재 상태를 갱신한다.
- **통째 교체 수정(T-4)**: 두 사용자가 서로 다른 필드를 동시에 고치면 나중 저장이 다른 필드까지 덮어쓴다. "마지막 성공 저장이 최종값"이라는 정책에 부합하는 수용된 귀결이다.
- **사유·라운드의 자유 서술(T-5)**: 이모지와 기호를 허용하므로 눈으로 구별되지 않는 문자가 일부 남을 수 있고 표시 길이가 코드 포인트 수와 다를 수 있다. 텍스트는 항상 이스케이프해 표시한다.
