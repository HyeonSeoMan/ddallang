## 1. 범위

### 1.1 담당 FR (AC 82개)
FR-ROOM-001~008(61), FR-PART-001~004(21). AC별 담당과 검증은 §11 추적표.

### 1.2 포함
방 생성, 초대 링크 조회·입장, 익명 RoomMember 신원 발급·복원, 닉네임·방 이름·정산 단위 검증, 방장 지정과 방장 전용 동작의 권한 경계, 참여자 등록·비활성화·재활성화·목록 조회, RoomMember·Participant 한도, 종료 후 참여자 변경 금지.

### 1.3 제외와 다른 Spec과의 경계

| 대상 | 담당 | S1의 관계 |
| --- | --- | --- |
| 거래 생성·수정·삭제, 멱등 키, 거래 한도 1,000건 | S2 | 거래 한도 AC(ROOM-008-3, -9, -10, -5의 거래 부분)는 S2가 계약을 정의한다. S1은 §6.4에서 "슬롯 규칙"만 인용한다. 거래가 참조하는 `memberId`·`participantId`·참여자 `status`의 의미는 S1이 정한다 |

| 게임 종료, 최종·예상 정산, 복사 | S4 | S1은 방 `status` 값을 읽어 참여자 변경과 입장을 판정한다. `IN_PROGRESS → ENDED` 전이는 S4가 정의한다 |

## 2. 도메인 모델과 불변식

### 2.1 개체
| 개체 | 필드 | 설명 |
| --- | --- | --- |
| Room | `id`, `name`, `unit`, `status`, `inviteCode`, `createdAt` | `status`는 `IN_PROGRESS` 또는 `ENDED`. `name`, `unit`, `inviteCode`는 생성 뒤 변하지 않는다 |
| RoomMember | `id`, `roomId`, `nickname`, `isHost`, `createdAt` | 익명 접속 주체. 신원 키 해시를 서버가 보관한다(§3.1) |
| Participant | `id`, `roomId`, `nickname`, `status`, `order`, `createdAt` | `status`는 `ACTIVE` 또는 `INACTIVE`. `order`는 방 안에서 유일한 양의 정수이며 한 번 부여되면 바뀌지 않는다 |

ID(`id`)는 서버가 만드는 불투명 문자열이며 추측하기 어려워야 한다. 클라이언트는 형식을 가정하지 않는다.

### 2.2 불변식
- I1. 방마다 방장은 정확히 한 명이다. 생성 시 지정되고 바뀌지 않는다. 방장이 없어지는 경로도, 다른 사람이 방장이 되는 경로도 없다.
- I2. RoomMember와 Participant는 서로 다른 ID 공간이며 둘을 잇는 필드·관계·API가 없다.
- I3. 닉네임 고유성은 (방, 유형, 정규화한 비교 키) 단위다. 유형은 RoomMember와 Participant로 나뉜다. Participant는 `status`와 무관하게 센다.
- I4. 방마다 RoomMember는 10명 이하, Participant는 10명 이하다. 상태·접속 여부와 무관하게 존재하는 모든 개체를 센다.
- I5. 참여자 `order`는 방 안에서 서로 다르고 증가하며(서버 처리 순서), 비활성화·재활성화로 바뀌지 않는다. 결번이 생겨도 된다.
- I6. 방 이름, 정산 단위, 초대 코드, 닉네임은 생성 뒤 변경 경로가 없다.
- I7. 모든 변경은 한 요청 단위로 원자적이다. 거부된 요청은 아무것도 저장하지 않는다.

## 3. 공통 규약

### 3.1 신원 키와 인증
- **신원 키(identity key)**: 클라이언트가 방 입장 시도 또는 방 생성 시도마다 새로 만드는 암호학적 난수 32바이트를 base64url(패딩 없음)로 인코딩한 43자 문자열이다. 방 생성 또는 첫 입장 요청에서 서버에 처음 제시되며, 키는 **그것이 등록된 방 안에서만** RoomMember를 식별한다(서버는 키 해시를 (방, 해시)로만 구분하므로 같은 키를 다른 방에 제시하면 그 방과 무관한 별개의 신원이 된다).  서버는 SHA-256 해시만 (방, 해시) 유일 제약으로 저장한다.
- 클라이언트는 이 키를 브라우저 저장소에 **초대 코드별**로 보관한다. 브라우저 저장소를 지우면 키를 잃고, 잃은 키는 서버도 복구할 수 없다. 이것이 "브라우저 기반 신원"의 정의다(FR-ROOM-005).
- 변경·방 한정 조회 요청은 `Authorization: Bearer <신원 키>`로 보낸다. 서버는 요청 경로의 방에서 이 키에 해당하는 RoomMember를 찾아 요청자로 삼는다. 다른 방의 RoomMember로 등록된 키라도 이 방에서 등록되지 않았다면 이 방의 멤버가 아니다(방 단위 권한, AC-SYS-003-6, -7).
- **키 생성·저장 계약**: 클라이언트는 키를 저장소에 저장하고 읽어서 확인한 뒤에만 서버에 보낸다. 같은 브라우저의 여러 탭이 같은 초대 링크로 동시에 첫 입장을 해도 키가 하나만 만들어지도록 다음을 **하나의 배타 구간**에서 수행한다. 잠금 이름은 초대 코드별로 하나다(예: `ddallang-identity:{inviteCode}`).
  1. 잠금을 얻는다(Web Locks API의 `exclusive`).
  2. **잠금 안에서** 저장소를 다시 읽는다. 키가 이미 있으면 그것을 쓴다(다른 탭이 먼저 만든 경우).
  3. 없을 때만 CSPRNG로 새로 만들고 저장한 뒤 **다시 읽어** 저장됐음을 확인한다. 저장·재확인이 실패하면 키를 쓰지 않고 입장을 막고 사유를 안내한다.
  4. 잠금을 놓은 뒤에 요청을 보낸다. 요청에 쓰는 키는 항상 2~3에서 확인한 값이다.
  Web Locks를 쓸 수 없는 환경은 입장을 막고 안내한다(최소 브라우저 버전은 OQ-032). 서버는 서로 다른 키로 온 요청을 같은 브라우저인지 알 수 없으므로 서로 다른 신원으로 처리한다(같은 닉네임이면 하나만 성공하고 나머지는 `NICKNAME_TAKEN`이다). 이 한계는 §13에 기록한다.
- **방 생성 시도와 키 연결**: 방 생성 전에는 초대 코드를 모르므로, 클라이언트는 방 생성 시도마다 "생성 대기" 항목(시도 ID, 신원 키)을 저장·재확인한 뒤 요청하고, `201` 응답의 `inviteCode`를 받으면 그 키를 코드에 연결하고 대기 항목을 지운다. 응답을 받지 못한(결과 불명) 재시도는 **같은 시도의 기존 신원 키를 재사용**한다(§6.5). 같은 시도의 수동 재시도는 서버 거부(4xx)로 방이 만들어지지 않은 경우의 재제출도 포함한다. 사용자가 시도를 취소하면 대기 항목을 지운다. 새 방을 만들려는 별개의 시도는 새 키를 만든다.
- 신원 키 인증 방식(헤더)은 이 Spec에서 확정한다. **SSE 연결의 인증 방식은 S5에서 결정**하며 S1은 정하지 않는다.

### 3.2 문자열 검증 (방 이름, 정산 단위, RoomMember 닉네임, Participant 닉네임에 공통)
검증은 다음 순서로 한다. 자동 공백 제거는 하지 않는다.
0. 값이 없으면(`null` 포함) `REQUIRED`, 문자열이 아니면 `INVALID_TYPE`으로 거부한다. 원본 문자열이 64 코드 포인트를 넘으면 정규화하지 않고 `LENGTH_OUT_OF_RANGE`로 거부한다(분해형 한글 12자는 최대 36 코드 포인트이므로 정상 입력을 막지 않는다).
1. 입력 문자열을 Unicode **NFC**로 정규화한다. 이후 검사·저장·응답은 모두 정규화한 값이다.
2. **길이**: 정규화한 문자열의 코드 포인트 수가 1 이상 12 이하인지 본다. 빈 문자열은 `LENGTH_OUT_OF_RANGE`다.
3. **허용 문자**: 정규화한 문자열의 모든 코드 포인트가 다음 중 하나여야 한다. 아니면 `INVALID_CHARACTER`다.
   - 한글 완성형 음절 U+AC00~U+D7A3
   - 한글 호환 자모 U+3131~U+3163 (키보드로 입력하는 단독 자음·모음 ㄱ~ㅎ, ㅏ~ㅣ; NFC로 바뀌지 않는다)
   - 영문 `A-Z` `a-z`
   - 숫자 `0-9`
   - 공백 U+0020
   허용 범위 밖의 한글 코드 포인트는 거부한다: 조합용 자모 U+1100~U+11FF가 NFC 이후에도 음절로 합쳐지지 않고 남은 경우, 한글 채움 문자 U+3164(보이지 않음), 고어·확장 자모(U+3165~U+318E, U+A960~U+A97F, U+D7B0~U+D7FF). 제어 문자, 영문 외 라틴 문자, 전각 문자, 이모지, 특수문자도 거부한다.
4. **공백 규칙**: 첫 문자나 마지막 문자가 공백이면 `LEADING_OR_TRAILING_SPACE`, 공백이 둘 이상 이어지면 `CONSECUTIVE_SPACES`로 거부한다. 중간의 공백 한 칸은 허용한다.
5. 2~4의 위반은 서로 독립이므로 모아서 한 번에 반환한다(§3.4). 하나라도 있으면 거부한다.

닉네임 비교 키는 정규화한 문자열의 `A-Z`를 소문자로 바꾼 값이다. 이 키로 §2.2 I3의 중복을 판정한다. 한글·호환 자모·숫자·공백은 그대로 쓴다. 조합용 자모와 호환 자모는 눈으로 구별하기 어렵지만 서로 다른 코드 포인트라 중복으로 취급되지 않는다(§13). AC-ROOM-006-13(분해형·조합형 한글이 같은 길이, 서로 중복)은 NFC로 음절이 합쳐지므로 그대로 충족된다.

### 3.3 검사 순서와 정보 노출
요청은 다음 순서로 검사하고 **처음 걸린 오류 하나**를 반환한다. 단 입력 검증 오류(7번)는 §3.4처럼 위반 항목 전체를 담는다.
0. **라우트 단계(인증 전)**: 정의되지 않은 경로는 `404 ROUTE_NOT_FOUND`, 경로는 있으나 메서드가 정의되지 않았으면 `405 NOT_SUPPORTED`(`Allow` 헤더 포함). 이 판정은 방·참여자 존재 여부를 조회하지 않으므로 어떤 정보도 드러내지 않는다.
1. 신원 키 누락·형식 오류(키가 필수인 경로): `401 UNAUTHENTICATED`
2. 방 또는 초대 코드 존재: `404 ROOM_NOT_FOUND`, `404 INVITE_NOT_FOUND`
3. 방 멤버 여부: 이 방의 RoomMember가 아니면 **`404 ROOM_NOT_FOUND`**로 응답한다. 방이 없는 경우와 구별할 수 없게 해 임의의 키 보유자가 방 존재 여부를 확인하지 못하게 한다.
4. 방장 여부(방장 전용 동작): `403 HOST_ONLY`. 방 멤버에게만 도달하므로 비멤버에게 방 정보를 드러내지 않는다.
5. 방 상태(`ENDED`에서 불가한 동작): `409 GAME_ENDED`
6. 대상 존재(예: 참여자 ID): `404 PARTICIPANT_NOT_FOUND`. 다른 방의 참여자 ID도 같다(AC-SYS-003-8).
7. 입력 검증: `422 VALIDATION_FAILED`
8. 닉네임 중복: `409 NICKNAME_TAKEN`
9. 한도: `409 MEMBER_LIMIT_EXCEEDED`, `409 PARTICIPANT_LIMIT_EXCEEDED`

- 6번이 7번보다 앞이다. 존재하지 않는 대상에는 본문 검증 결과를 알려 주지 않는다.
- 비방장은 방이 종료됐든 본문이 틀렸든 `HOST_ONLY`를 받는다(4번이 5~7번보다 앞).
- 7~9번은 요청 처리 중 하나의 트랜잭션 안에서 판정한다(§7). 8번과 9번이 동시에 해당하면 8번을 반환한다.
- 입장(§4.3)은 3~4번이 없다. 신원 키가 이 방에서 등록되어 있으면 복원하고 이후 검사를 건너뛴다.

### 3.4 오류 응답
```json
{ "error": { "code": "VALIDATION_FAILED", "message": "…", "details": [ { "field": "nickname", "code": "CONSECUTIVE_SPACES" } ] } }
```
- `message`는 한국어 사용자 안내 문구이며 클라이언트가 그대로 보여 줄 수 있다. 분기는 `code`로 한다.
- `details`는 검증 오류와 한도 오류에서 쓴다. 한도 오류는 `[{ "limit": 10 }]`다.
- 검증 사유 코드(`details[].code`): `REQUIRED`, `LENGTH_OUT_OF_RANGE`, `LEADING_OR_TRAILING_SPACE`, `CONSECUTIVE_SPACES`, `INVALID_CHARACTER`, `INVALID_TYPE`(문자열이 아님), `NOT_ALLOWED_FIELD`(변경 불가 필드를 보낸 경우).
- 모든 거부는 AC-SYS-003-5에 따라 데이터를 바꾸지 않고, 위 `code`로 서로 구분된다.

| HTTP | `code` | 의미 |
| --- | --- | --- |
| 401 | `UNAUTHENTICATED` | 신원 키 누락·형식 오류 |
| 403 | `HOST_ONLY` | 방 멤버인 비방장이 방장 전용 동작을 요청 |
| 404 | `ROOM_NOT_FOUND`, `INVITE_NOT_FOUND`, `PARTICIPANT_NOT_FOUND` | 대상 없음. 방 비멤버도 `ROOM_NOT_FOUND`다(§3.3 3). 다른 방에 속한 참여자 ID는 `PARTICIPANT_NOT_FOUND`(AC-SYS-003-8) |
| 404 | `ROUTE_NOT_FOUND` | 정의되지 않은 경로(MVP에 없는 기능의 경로 포함) |
| 405 | `NOT_SUPPORTED` | 경로는 있으나 지원하지 않는 메서드(`Allow` 헤더) |
| 409 | `GAME_ENDED`, `NICKNAME_TAKEN`, `MEMBER_LIMIT_EXCEEDED`, `PARTICIPANT_LIMIT_EXCEEDED` | 상태·충돌·한도 |
| 422 | `VALIDATION_FAILED` | 입력 형식 위반 |

## 4. API 계약

경로의 `{inviteCode}`는 초대 코드, `{roomId}`는 방 ID다. 모든 본문은 JSON(UTF-8)이다. 목록은 정렬 순서가 명시된 대로 반환한다.

### 4.1 `POST /rooms` — 방 생성 (FR-ROOM-001, 003, 007)
- 인증: `Authorization: Bearer <이 생성 시도의 신원 키>` 필수. 방과 최초 RoomMember가 이 키에 묶인다.
- 요청: `{ "name": string, "unit": string, "nickname": string }` 세 필드 모두 필수. `name`, `unit`, `nickname`은 §3.2를 따른다. `unit`의 목록 선택(`원`, `점수`, `칩`)과 직접 입력은 서버에서 구분하지 않는다. 같은 문자열 규칙을 쓴다.
- 처리: 방, 최초 RoomMember(`isHost = true`), `status = IN_PROGRESS`, 초대 코드를 한 트랜잭션에서 만든다. 초대 코드는 추측하기 어려운 URL-safe 난수(128비트 이상)다.
- 응답 `201`: `{ "room": Room 전체(inviteCode 포함), "me": RoomMember }`
- 오류: 401, 422. 이름 중복은 허용한다(AC-ROOM-001-5). 하나라도 위반하면 방이 만들어지지 않는다.
- 멱등 키는 없다. 같은 요청을 다시 보내면 별도의 방이 생긴다.

### 4.2 `GET /invites/{inviteCode}` — 초대 링크 조회 (FR-ROOM-002, 005)
- 인증: `Authorization` 선택. 형식이 틀린 값은 오류 없이 "키 없음"으로 취급한다.
- 응답 `200`: `{ "room": { "name", "unit", "status" }, "isMember": boolean }`. **입장 전에 공개하는 것은 방 이름, 정산 단위, 진행 상태뿐이다.** 방 ID, 초대 코드, 참여자 목록, 거래 내역, 멤버 ID·닉네임, 인원 수는 담지 않는다. `isMember`는 요청에 실린 키가 이 방의 RoomMember로 등록되어 있는지만 알려 준다(자기 자신에 대한 정보다).
- 오류: `404 INVITE_NOT_FOUND`(존재하지 않거나 형식이 틀린 초대 코드, AC-ROOM-002-4).
- 방이 `ENDED`여도 `200`이다(AC-ROOM-002-5).

### 4.3 `POST /invites/{inviteCode}/members` — 입장 (FR-ROOM-002, 005, 006, 008)
- 인증: `Authorization: Bearer <신원 키>` 필수. 이전에 입장한 브라우저는 저장해 둔 키를, 처음이면 새로 만든 키를 보낸다.
- 요청: `{ "nickname"?: string }`
- 처리:
  1. 이 방에서 키에 해당하는 RoomMember가 있으면 **복원**한다. 닉네임은 무시하고 한도·닉네임 검사를 하지 않는다. 응답 `200`, `{ "room": {id,name,unit,status}, "me": RoomMember }`. 입장 응답이 이 방의 `id`를 처음 알려 준다.
  2. 없으면 `nickname`이 필수다. §3.3 순서로 검증·중복·한도를 판정하고 통과하면 RoomMember(`isHost = false`)를 만든다. 응답 `201`, 같은 형태.
- 같은 키로 동시에 두 요청이 도착하면 (방, 키 해시) 유일 제약에 따라 하나만 만들어지고 나머지는 같은 RoomMember를 `200`으로 복원한다(AC-ROOM-006-11 마지막 문장).
- 방이 `ENDED`여도 입장·복원은 허용한다.
- 오류: 401, 404 `INVITE_NOT_FOUND`, 422, 409 `NICKNAME_TAKEN`, 409 `MEMBER_LIMIT_EXCEEDED`. 검사 순서는 §3.3의 1, 2, 7, 8, 9번이다.

### 4.4 `GET /rooms/{roomId}` — 방 조회 (FR-ROOM-003)
- 인증: 필수, 이 방의 RoomMember.
- 응답 `200`: `{ "room": Room 전체, "me": RoomMember }`
- 오류: 401, 404 `ROOM_NOT_FOUND`(비멤버 포함).

### 4.5 `GET /rooms/{roomId}/participants` — 참여자 목록 (FR-PART-001, 002)
- 인증: 필수, 이 방의 RoomMember. 방 상태와 무관하게 조회할 수 있다.
- 응답 `200`: `{ "participants": Participant[] }` — `order` 오름차순, 비활성 참여자 포함.
- 오류: 401, 404 `ROOM_NOT_FOUND`(비멤버 포함).

### 4.6 `POST /rooms/{roomId}/participants` — 참여자 등록 (FR-PART-001, FR-ROOM-006, 008, FR-PART-004)
- 인증: 필수. 방장 전용.
- 요청: `{ "nickname": string }`
- 처리: §3.3 순서. `ENDED`면 `409 GAME_ENDED`. 통과하면 `status = ACTIVE`, 서버가 처리한 순서대로 `order`를 부여해 만든다.
- 응답 `201`: `{ "participant": Participant }`
- 오류: 401, 403 `HOST_ONLY`, 404 `ROOM_NOT_FOUND`(비멤버 포함), 409 `GAME_ENDED`/`NICKNAME_TAKEN`/`PARTICIPANT_LIMIT_EXCEEDED`, 422.

### 4.7 `PATCH /rooms/{roomId}/participants/{participantId}` — 참여자 활성 상태 변경 (FR-PART-002, 003, 004)
- 인증: 필수. 방장 전용.
- 요청: `{ "status": "ACTIVE" | "INACTIVE" }` 이 한 필드만 허용한다. 다른 필드(`nickname` 등)가 있으면 `422 VALIDATION_FAILED`(`NOT_ALLOWED_FIELD`)로 거부하고 아무것도 바꾸지 않는다(AC-ROOM-006-8, AC-PART-003-1).
- 처리: `ENDED`면 `409 GAME_ENDED`. 현재 상태와 같은 값을 보내면 실제 변경을 만들지 않고 `200`으로 현재 참여자를 반환한다(결정 N-4). 이 경우 이벤트도 발생시키지 않는다. 다르면 상태를 바꾸되 `order`, 닉네임, 과거 거래·손익은 바뀌지 않는다.
- 응답 `200`: `{ "participant": Participant }`
- 오류: 401, 403 `HOST_ONLY`, 404 `ROOM_NOT_FOUND`/`PARTICIPANT_NOT_FOUND`(다른 방의 참여자 ID 포함), 409 `GAME_ENDED`, 422. 검사 순서는 §3.3(5 → 6 → 7).

### 4.8 존재하지 않는 동작 (AC-ROOM-003-2, 004-5, 007-3, PART-003-1, 003-2)
HTTP 의미를 구분한다: **경로가 없으면 404 `ROUTE_NOT_FOUND`, 경로는 있으나 그 메서드를 지원하지 않으면 405 `NOT_SUPPORTED`** (`Allow` 헤더로 지원 메서드를 알린다). 둘 다 라우트 단계에서 판정하며(§3.3 0) 방·참여자 존재와 인증 여부에 따라 달라지지 않는다.

| 동작 | 응답 |
| --- | --- |
| 방 수정(이름·정산 단위 포함): `PATCH`/`PUT`/`DELETE /rooms/{roomId}` | 405, `Allow: GET` — 방장·게임 상태와 무관 |
| 참여자 수정(`status` 외)·삭제: `PUT`/`DELETE`/`POST /rooms/{roomId}/participants/{participantId}` | 405, `Allow: PATCH`. `PATCH`로 `status` 외 필드를 보내면 422 `NOT_ALLOWED_FIELD` |
| 참여자 목록·등록 경로의 다른 메서드 | 405, `Allow: GET, POST` |
| RoomMember 수정·삭제·강제 퇴장, 방장 이전, 초대 링크 재발급, RoomMember–Participant 연결·해제, 참여자 간 거래 이전 | 해당 경로를 정의하지 않으므로 404 `ROUTE_NOT_FOUND` |

## 5. 상태와 권한 표

### 5.1 방장 전용 동작 (FR-ROOM-007)
참여자 추가(§4.6), 참여자 비활성화·재활성화(§4.7), 타인 거래 수정·삭제(S2), 게임 종료(S4). 비방장이 요청하면 `403 HOST_ONLY`이다. 이 Spec의 방장 전용 API는 §4.6, §4.7이다.

### 5.2 방 상태별 허용
| 동작 | `IN_PROGRESS` | `ENDED` |
| --- | --- | --- |
| 방 생성 | — | — |
| 초대 조회, 입장, 복원 | 허용 | 허용 |
| 방·참여자 조회 | 허용 | 허용 |
| 참여자 등록 | 방장 | `409 GAME_ENDED` |
| 참여자 활성 상태 변경 | 방장 | `409 GAME_ENDED` |

### 5.3 참여자 상태 전이
`ACTIVE ⇄ INACTIVE`(방장, 진행 중에만). 초기 상태는 `ACTIVE`. 삭제 상태는 없다. 비활성 참여자는 새 거래의 당사자가 될 수 없고(S2가 처리 시점 상태로 거부), 기존 거래·손익·정산에서는 그대로 남으며 기존 거래의 금액·사유·라운드 수정은 가능하다(S2). 닉네임은 계속 점유한다.

## 6. 동작 규칙

### 6.1 신원
- 같은 신원 키로 같은 방에 다시 들어오면 같은 RoomMember가 복원된다. 이전 거래의 작성자이고 방장이면 방장 권한도 그대로다(AC-ROOM-005-1, -2, -6).
- 키를 잃은 상태에서의 입장은 항상 새 RoomMember다. 이전 작성자·방장으로 인식되지 않는다(AC-ROOM-005-3, -4). 다른 브라우저·기기도 같다(005-5).
- 방장 신원 키가 사라져도 아무도 방장이 되지 않는다. 그 방은 종료할 수 없는 상태로 남을 수 있고 수용된 귀결이다(AC-ROOM-005-7, 운영은 OQ-034).
- 입장은 Participant를 만들지 않고 Participant 등록은 RoomMember를 만들지 않는다(AC-ROOM-004-3, -4).

### 6.2 닉네임
- §3.2 규칙을 RoomMember와 Participant에 각각 적용한다. 서로 다른 유형의 같은 닉네임은 공존한다(AC-ROOM-006-6). 방이 다르면 같은 닉네임을 쓸 수 있다(006-7).
- 같은 유형 안에서 정규화 후 소문자 키가 같으면 중복이다. 조합형·분해형 한글은 정규화 뒤 같아지므로 중복이다(AC-ROOM-006-13).
- 비활성 참여자의 닉네임도 중복 판정에 포함한다(AC-ROOM-006-10).

### 6.3 방 이름, 정산 단위
- 방 이름은 §3.2를 따르고 중복을 허용한다. 정산 단위는 §3.2를 따르며, 방에 저장된 같은 값이 금액 표시·정산 결과·복사 텍스트에 쓰인다(AC-ROOM-001-14, AC-ROOM-003-3). 변경과 환산은 없다.

### 6.4 한도 (FR-ROOM-008)
- RoomMember 한도: 새 RoomMember를 만드는 입장 요청만 한도를 검사한다. 기존 신원 복원은 한도와 무관하게 성공한다(AC-ROOM-008-11). 10명이 접속해 있지 않아도, 신원을 잃어 남은 RoomMember가 있어도 센다(008-6, -8).
- Participant 한도: 비활성도 센다. 10명 중 1명을 비활성화해도 11번째 등록은 거부된다(008-6, -7).
- 한도 초과 요청은 부분 저장 없이 거부된다(008-4). 오류 응답은 어떤 항목이 넘었는지 `code`와 `details.limit`로 알린다.
- 동시 요청: 닉네임 중복을 포함해 다른 검증을 모두 통과하는 서로 다른 신원의 새 입장이 마지막 슬롯에 동시에 도착하면 정확히 하나만 슬롯을 얻고 나머지는 `MEMBER_LIMIT_EXCEEDED`다. 참여자 등록도 같다(008-5). 같은 닉네임이 겹치는 경쟁에서는 §3.3에 따라 중복 판정이 우선하므로 진 요청은 `NICKNAME_TAKEN`이다(006-11). 같은 키의 입장은 슬롯을 한 번만 소비하고 나머지는 `200` 복원이다(§4.3).
- 거래 한도(1,000건, 삭제된 거래 포함)는 S2 계약이 정한다(AC-ROOM-008-3, -9, -10과 008-5의 거래 부분).

### 6.5 응답 유실과 재시도
- 방 생성: PRD는 방 생성에 멱등 키를 두지 않고(C§3.4는 거래 생성·수정·삭제, C§5.1은 종료에만 적용) 방 이름 중복을 허용한다(AC-ROOM-001-5). 따라서 서버는 같은 요청의 재시도를 중복으로 판별하지 않으며, 재시도하면 별도의 방이 생긴다. 이 규칙을 바꾸려면(예: 키 기준 중복 방지) 정책 변경이므로 이 Spec에서 만들지 않았다. 응답을 못 받은 경우 클라이언트는 자동 재전송하지 않는다. 결과를 알 수 없어 사용자가 같은 시도를 재시도할 때는 **그 시도의 기존 신원 키를 재사용**한다(N-11). 이는 멱등성을 보장하지 않는다. 첫 요청이 실제로 성공했다면 재시도는 별도의 두 번째 방을 만들고, 두 방의 최초 방장 해시가 같아진다. 서버는 키를 방 안에서만 식별하므로(§3.1, (방, 해시) 유일) 이 상태는 계약 위반이 아니다. 클라이언트는 두 번째 방의 `201` 응답에 연결하며, 응답을 잃은 첫 방은 초대 코드를 아는 사람이 없는 고아 방이 된다. 최근 방 목록이 없고(AC-ROOM-002-3) 방 보관 정책은 OQ-034이므로 복구 경로를 만들지 않는다.
- 입장: 같은 신원 키로 재시도하면 `200`으로 같은 RoomMember가 복원되므로 안전하다.
- 참여자 등록(방장): 멱등 키가 없다. 응답이 유실된 뒤 같은 닉네임으로 다시 등록하면 `409 NICKNAME_TAKEN`일 수 있다. 클라이언트는 이 오류를 받으면 참여자 목록(§4.5)을 다시 조회하고, 같은 닉네임(비교 키 기준)의 참여자가 이미 있으면 "이미 등록되어 있습니다"로 안내한다. 이 처리는 OQ-038의 권장안 (a)이며 사용자가 채택했다(N-3). 상위 문서 기록은 §12.3 U-1.
- 입장(§4.3)의 `NICKNAME_TAKEN`: 아직 이 방의 멤버가 아니므로 목록을 조회하지 않는다. 다른 닉네임을 입력하도록 안내한다. 같은 신원 키의 재시도는 복원이라 이 오류가 나지 않는다.
- 참여자 상태 변경: 방이 진행 중이고 그 사이 다른 변경이 없었다면 같은 값 재요청은 `200`이라 재시도해도 안전하다. 그러나 응답 유실 사이에 다른 방장 탭이 상태를 바꿨다면 재시도는 그 변경을 덮어쓰고, 종료됐다면 `409 GAME_ENDED`다. 클라이언트는 재시도 전에 참여자 목록을 다시 조회해 현재 상태를 확인한다. 이 한계도 OQ-038의 가안(N-3, N-4)에 포함된다.

## 7. 동시성과 정합성

서버는 다음을 요청 처리 중 한 트랜잭션(또는 동등한 원자성)에서 보장해야 한다. 구현 방법은 Plan에서 정하며 DB 유일 제약, 방 단위 직렬화 같은 수단을 쓸 수 있다.
1. **닉네임 유일성**: (방, 유형, 비교 키) 유일. 동시에 같은 닉네임이 오면 정확히 하나가 성공하고 나머지는 `NICKNAME_TAKEN`이다(AC-ROOM-006-11). 단 같은 신원 키의 입장 요청은 중복으로 거부하지 않고 `200`으로 같은 RoomMember를 복원한다(§4.3).
2. **한도**: 방마다 개체 수 확인과 삽입이 분리되지 않는다. 마지막 슬롯 경쟁에서 한도를 넘지 않는다(AC-ROOM-008-5).
3. **참여자 `order`**: 서버 처리 순서대로 서로 다른 값. 동시 등록에서도 유일하다(AC-PART-001-5).
4. **신원 키 유일**: (방, 키 해시) 유일. 같은 키의 동시 입장은 한 명만 만든다(AC-ROOM-006-11).
5. **참여자 변경과 게임 종료**: 상태 검사와 변경은 같은 직렬화 안에 있어야 한다. 종료가 먼저 처리되면 이후 도착한 참여자 변경은 `GAME_ENDED`다. 종료 이후에 참여자 변경이 반영되는 일은 없다(AC-PART-004-1, -2).
6. **참여자 비활성화와 거래 생성**: 처리 시점의 참여자 상태로 판정한다. 비활성화가 먼저 처리되면 이후의 거래 생성은 거부된다(AC-PART-002-8, 거래 쪽 거부는 S2). 이를 위해 S2의 거래 생성은 참여자 `status`를 같은 트랜잭션에서 읽어야 한다.
7. **방장 일의성**: 방 생성 트랜잭션 안에서만 `isHost`가 정해지며 이후 쓰기 경로가 없다.

## 8. 실시간 이벤트 발생 지점 (스키마는 S5)

S1이 만드는 변경 중 다른 접속자에게 새로고침 없이 반영되어야 하는 것(FR-VIEW-005)은 다음이다. 이벤트 이름·페이로드·전달 방식은 S5가 정한다.
- 참여자 등록(§4.6)
- 참여자 활성 상태 변경(§4.7)
**RoomMember 입장·복원은 MVP의 실시간 이벤트 반영 대상이 아니다**(N-5). PRD FR-VIEW-005의 대상은 거래·참여자·게임 종료·정산이며 RoomMember와 Participant는 별개의 개체다(PRD §2). 같은 값으로의 참여자 상태 변경 재요청(§4.7)은 이벤트를 만들지 않는다.

## 9. 프론트엔드 책임

- 방 생성 화면: 방 이름, 정산 단위(목록 `원`·`점수`·`칩` 선택 또는 직접 입력), 생성자 닉네임. §3.2 규칙으로 즉시 검증하되 서버 검증이 최종이다(AC-ROOM-001-12, -13). 오류 시 입력을 유지하고 사유를 안내한다.
- 신원 키: §3.1의 배타 구간(잠금 → 저장소 재확인 → 없으면 생성·저장·재확인 → 잠금 해제)을 지킨다. 저장 실패, 저장소 차단, Web Locks 미지원은 입장 전에 사용자에게 알린다. 키를 서버가 복구할 수 없음을 사용자에게 숨기지 않는다. 방 생성 응답을 받지 못했을 때 자동 재전송하지 않으며, 사용자가 같은 시도를 재시도할 때는 그 시도의 기존 신원 키를 재사용한다(§3.1, §6.5). 별개의 새 방 생성은 새 키를 쓴다.
- 초대 링크 화면(`/invite/{inviteCode}`): `GET /invites/{inviteCode}`로 시작한다. `isMember`가 참이면 닉네임 입력 없이 입장 요청(§4.3)으로 복원하고, 거짓이면 닉네임을 받는다. 입장 전 화면에는 방 이름·정산 단위·진행 상태만 보인다. 404면 오류를 보인다. 입장 요청이 `NICKNAME_TAKEN`이면 목록을 조회하지 않고 다른 닉네임을 입력하도록 안내한다. 방 코드 입력 화면과 최근 방 목록은 만들지 않는다(AC-ROOM-002-2, -3).
- 정산 단위·방 이름·닉네임의 변경 UI를 만들지 않는다(AC-ROOM-003-1, 006-8, PART-003-1). 방장 이전, 강제 퇴장, 링크 재발급, 연결 UI도 만들지 않는다.
- 한도 초과(`*_LIMIT_EXCEEDED`)는 초과 항목을 안내하고 입력한 닉네임을 화면에 유지한다(AC-ROOM-008-1, -2).
- 참여자 화면: 목록은 `order` 순. 비활성 참여자 표시, 방장에게만 추가·비활성화·재활성화 컨트롤. 종료 후에는 컨트롤을 숨기거나 비활성화한다(AC-PART-004-3). 비활성 참여자는 거래 입력의 당사자 선택지에서 제외한다(AC-PART-002-3의 UI 쪽).
- 참여자 등록의 `NICKNAME_TAKEN` 수신 시 §6.5의 재조회·안내를 한다.
- 오류 `code`로 분기하고 `message`는 그대로 쓴다. 클라이언트 검증은 서버를 대체하지 않는다.

### 12.4 N-10 검증: AC-SYS-003-5와의 충돌 여부
- AC-SYS-003-5: "거부된 요청은 데이터를 변경하지 않으며 클라이언트에 구분 가능한 오류가 반환된다."
- 비멤버 요청은 404 `ROOM_NOT_FOUND`로 거부되고 데이터는 변하지 않는다. 오류는 `code`가 있어 401, 403 `HOST_ONLY`, 409, 422 등 다른 거부와 구분된다.
- 구분되지 않는 것은 "방이 없음"과 "방 비멤버"뿐이다. AC는 이 둘의 구분을 요구하지 않으며, PRD의 다른 AC도 비멤버 전용 오류 문구를 정하지 않는다. AC-SYS-003-1, -6, -7(권한 없는 요청 거부, 다른 방 변경 거부, 방장 권한은 방 단위)도 거부와 데이터 불변만 요구한다. 방장이 아닌 방 멤버의 거부는 `HOST_ONLY`로 계속 구분된다(AC-ROOM-007-2).
- **결론: 충돌하지 않는다.** 단 AC를 "거부 사유마다 서로 다른 오류"로 엄격히 읽으면 "비멤버"를 별도 사유로 볼 여지가 있다. 이 읽기를 택하면 PRD 변경이 아니라 이 Spec의 N-10을 되돌려야 한다(`NOT_A_MEMBER` 403 복원). 검증 방법: 비멤버와 존재하지 않는 방의 응답(상태, `code`, `message`)이 같은지, 비멤버 변경 요청 뒤 데이터가 그대로인지 API 테스트로 확인한다.

### 12.5 U-1: OQ-038 확정과 상위 문서 변경 통제
OQ-038은 권장안 (a)(재조회 후 안내, 규칙 추가 없음)로 확정되었다. 이 Spec은 이를 §6.5와 §9에 반영했다. 영향받는 상위 문서와 절차는 별도 보고(사용자 승인 대기)로 정리했으며, `open-questions.md`와 PRD는 수정하지 않았다.

## 13. 위험
- 신원 키는 브라우저 저장소에 있으므로 같은 브라우저에서 스크립트가 읽을 수 있다(XSS 방지는 프론트 Plan 책임). 유출되면 해당 신원을 도용할 수 있다.
- 조합용 자모(U+1100 계열)와 호환 자모(U+3131 계열)는 모양이 같아도 서로 다른 닉네임이라 눈으로 구별되지 않는 닉네임이 공존할 수 있다. 조합용 자모 단독은 거부하므로 실제 입력 경로로는 드물다.
- 서버는 서로 다른 신원 키를 같은 브라우저로 묶지 못한다. 탭 사이 배타 수행(§3.1)을 지키지 못하는 클라이언트는 같은 사람이 둘로 보일 수 있다.
- 방 생성은 멱등하지 않다. 응답 유실 후 같은 시도를 재시도하면 별도의 방이 중복 생성될 수 있고(이름 중복 허용 정책의 귀결), 이때 같은 신원 키가 두 방의 최초 방장 해시가 된다. 서버는 이 두 방을 서로 연결하는 정보(같은 해시)를 보관하게 되지만 다른 사용자에게는 노출하지 않는다. 키가 유출되면 두 방이 모두 영향을 받는다. 응답을 잃은 방은 아무도 초대 코드를 모르는 고아 방으로 남을 수 있다(OQ-034).
- R-01(`open-questions.md`): 한도 슬롯을 회수할 수단이 없다. 신원을 잃은 RoomMember와 비활성 참여자가 슬롯을 계속 점유한다.
- 남용 방지(요청 속도 제한 등)는 PRD 범위가 아니며 이 Spec에서 정하지 않았다.
