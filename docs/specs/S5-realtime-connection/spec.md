## 1. 범위

### 1.1 담당 FR (AC 27개 + 다른 Spec이 넘긴 계약)
FR-VIEW-005(9), FR-SYS-001(5), FR-SYS-002(5), FR-SYS-003(8). 비기능 요구 NFR-004(최신성 표시), NFR-006(실시간성), NFR-008(지원 환경, OQ-032 결정). 그리고 S1이 S5로 넘긴 **SSE 인증 방식**(S1 §3.1), S1·S2·S3·S4의 "이벤트 발생 지점" 선언(S1 §8, S2 §8, S3 §8)에 대한 이벤트 계약, S1이 넘긴 이어받기 결과의 전달(방 밖의 요청자 포함, S1 §1.3·§4.10)과 접근을 잃은 신원의 안내(AC-VIEW-005-9), S3가 S5로 넘긴 목록 갱신 조건(S3 §6.4). FR-SYS-003의 8개 AC는 S1(§11.12)·S2(§11.9)·S3(§11.6)이 변경·조회 엔드포인트에서 충족하며, S5는 새 엔드포인트(SSE)에 같은 원칙을 적용한다(§11.4). AC별 담당과 검증은 §11 추적표.

### 1.2 포함
SSE 연결 엔드포인트와 인증, 이벤트 형식·종류·순서·중복·누락 처리, 방 변경 번호(revision), 하트비트와 연결 상태 판정, 재연결과 재동기화(refresh), 오래된 데이터 표시 금지와 입력 유지, 실시간 지연 기준과 측정 방법(OQ-019), 지원 환경과 필수 기능 검사(OQ-032 결정의 계약화), S4 종료 이벤트 인터페이스.

## 2. 도메인 모델과 불변식

### 2.1 개체
| 개체 | 필드 | 설명 |
| --- | --- | --- |
| 방 변경 번호 | `revision` | 서버 내부의 방별 정수 카운터. 방의 상태를 바꾸는 변경이 확정될 때마다 1씩 증가한다. 클라이언트는 SSE 이벤트의 `revision`으로만 본다 |
| 이벤트 | `id`, `event`, `data` | 서버가 SSE로 보내는 알림(§4.2). 변경된 데이터 자체가 아니라 **변경이 일어났다는 사실과 식별자**만 담는다 |
| 연결 상태 | `connected` / `disconnected` | 클라이언트가 SSE 스트림의 건강 여부로 판단하는 상태(§6.5) |

### 2.2 불변식
- R-I1. `revision`은 방 안에서 1부터 시작해 **빠짐없이 1씩** 증가한다. 변경 하나(= 방 단위 직렬화 안의 한 트랜잭션)가 정확히 하나의 `revision`과 하나의 이벤트를 만든다.
- R-I2. 이벤트는 해당 변경이 **커밋된 뒤에만** 전달된다. 커밋되지 않았거나 롤백된 변경, 거부된 요청, 멱등 재전송, 값이 같은 수정·상태 변경(no-op)은 `revision`을 소비하지 않고 이벤트를 만들지 않는다(S1 N-4, S2 §8).
- R-I3. 이벤트는 **알림**이다. 클라이언트가 보여 주는 값의 근거는 항상 REST 조회 응답(S1·S3·S4)이다. 이벤트 본문의 내용으로 화면 값을 직접 갱신하지 않는다.
- R-I4. 이벤트 전달은 **최소 한 번(at-least-once)을 가정하지 않는다**. 중복·순서 뒤바뀜·누락이 있어도 클라이언트가 §6.3에 따라 재동기화하면 정확한 상태에 수렴한다.

## 3. 공통 규약

### 3.1 지원 환경과 필수 기능 검사 (OQ-032 결정, `open-questions.md` 2.6절)
- **지원 목표**: Chrome, Edge, Firefox, Safari(모바일 브라우저 포함)의 **최신 안정 버전과 직전 주요 버전**. 이 Spec은 구체 버전 숫자를 정하지 않는다. 실제 호환성 범위는 구현·검증 단계에서 확인해 정한다. PRD NFR-008의 기존 목록(iOS Safari, Android Chrome, 데스크톱 Chrome·Safari·Edge)은 이 목표에 포함된다. Firefox와 그 밖의 모바일 브라우저는 NFR-008을 넓히는 부분이며 §12.2 E-4에 따른다.
- **실행 시 기능 검사**: 앱은 진입 시 다음이 모두 있는지 검사한다. 하나라도 없으면 **진입을 차단하고** 어떤 기능이 없는지 안내한다. 부분 동작이나 우회는 만들지 않는다.
  1. Web Locks API(`navigator.locks`) — 신원 키 생성·저장의 탭 간 배타(S1 §3.1)
  2. 암호학적 난수(`crypto.getRandomValues`) — 신원 키·Idempotency Key 생성
  3. 브라우저 저장소 읽기·쓰기(`localStorage`) — 신원 키 보관(S1 §3.1)
  4. `fetch`와 스트리밍 응답 본문(`Response.body.getReader()`), `TextDecoder`, `AbortController` — SSE 수신(§3.2)
  5. `navigator.onLine`, `visibilitychange` 이벤트, 타이머 — 연결 상태 판단(§6.5)
- 구형 브라우저용 폴백(폴리필, 폴링 등)은 MVP 범위가 아니다. 검사는 모바일 브라우저에도 같다.
- 검사 결과의 안내 문구는 UX 기준(OQ-033)에서 정하며 이 Spec은 "차단과 안내"만 요구한다.

### 3.2 SSE 인증 (E-1, 사용자 결정 2026-11-08)
브라우저의 기본 `EventSource`는 요청 헤더를 설정할 수 없어 S1의 `Authorization: Bearer <신원 키>`(S1 §3.1)를 보낼 수 없다. 사용자가 확정한 방식은 다음과 같다.
- 클라이언트는 `EventSource`를 쓰지 않고 **`fetch`로 SSE 스트림을 연다.** 요청에 `Authorization: Bearer <신원 키>`와 `Accept: text/event-stream`을 실어 S1과 **같은 인증**을 쓰고, 응답 본문 스트림을 읽어 SSE 형식을 직접 해석한다(§9).
- 신원 키는 URL, 쿼리 문자열, 쿠키에 싣지 않는다. 서버 로그와 프록시에 키가 남을 위험을 만들지 않는다.
- 별도의 인증 엔드포인트나 단기 토큰은 만들지 않는다. 요청자(이 방에 연결된 참여자) 확인은 S1 §3.3과 같은 순서(§3.3)로 한다.
- 대안((b) 일회용 티켓, (c) 쿼리의 키)은 채택하지 않았다(§12.2 E-1).

### 3.3 검사 순서와 오류
SSE 엔드포인트의 연결 요청은 스트림을 열기 전에 다음 순서로 검사하고, 오류는 스트림이 아니라 **일반 JSON 오류 응답**(S1 §3.4 형식)으로 돌려준다.
0. 라우트: 없는 경로 `404 ROUTE_NOT_FOUND`, `GET`이 아닌 메서드 `405 NOT_SUPPORTED`(`Allow: GET`)
1. 신원 키 누락·형식 오류: `401 UNAUTHENTICATED`
2. 방 존재와 요청자: 방이 없거나 키에 연결된 참여자가 없으면(신원 없음, 이어받기 대기) `404 ROOM_NOT_FOUND`, 키가 이 방에서 접근 상실이면 `401 IDENTITY_REVOKED`(S1 §3.3). 활성·비활성 참여자 모두 연결할 수 있다(AC-PART-002-11)
3. 입력 검증: 쿼리 매개변수가 있으면 최상위 `422 VALIDATION_FAILED`, `details`에 `{ "field": "<이름>", "code": "NOT_ALLOWED_FIELD" }`(S3 §3.3 표와 같은 형식). 이 엔드포인트는 쿼리 매개변수를 받지 않는다.

4. 연결 한도(§4.1): 한 참여자의 동시 스트림이 5개이거나 방의 동시 스트림이 50개이면 새 연결을 `429 CONNECTION_LIMIT_EXCEEDED`로 거부한다(`Retry-After: 30`).

권한(403)·방 상태(409)는 없다. 방이 `ENDED`여도 연결할 수 있다(종료 뒤 복원하거나 이어받기로 연결된 참여자도 최종 정산을 보려면 연결이 필요하다, AC-ROOM-009-10). 다른 방의 참여자 키는 이 방에 연결할 수 없다(AC-SYS-003-6, -7과 같은 원칙).

## 4. API 계약

### 4.1 `GET /rooms/{roomId}/events` — 실시간 스트림 (FR-VIEW-005, FR-SYS-001, 002)
- 인증: 필수, 이 방의 참여자(활성·비활성, §3.2).
- 요청 헤더: `Authorization: Bearer <신원 키>`, `Accept: text/event-stream`. `Last-Event-ID` 헤더는 보내도 **무시한다**(이벤트 재전송 없음, §6.2).
- 성공 응답 `200`: `Content-Type: text/event-stream; charset=utf-8`, `Cache-Control: no-store`, `X-Accel-Buffering: no`. 서버는 헤더를 보낸 즉시 `ready` 이벤트를 보낸다. 연결은 클라이언트가 끊거나 서버가 닫을 때까지 유지된다.
- 오류: 401 `UNAUTHENTICATED`/`IDENTITY_REVOKED`, 404 `ROOM_NOT_FOUND`(비참여자 포함), 422(쿼리 매개변수), 429 `CONNECTION_LIMIT_EXCEEDED`. 오류 응답은 스트림이 열리기 전의 JSON이다.
- CORS(프론트엔드가 다른 출처에서 호출할 때): `Authorization` 헤더를 허용하는 사전 요청(preflight) 응답, 응답 헤더 `Date`를 `Access-Control-Expose-Headers`로 노출한다.
- **서버의 연결 한도**(E-9): 한 참여자당 동시 스트림 5개, 방당 50개. 한도에 이미 도달했을 때 온 **새 연결은 거부**한다(`429 CONNECTION_LIMIT_EXCEEDED`, `Retry-After: 30`). 기존 스트림을 대신 닫지 않는다. 그래서 한 참여자가 탭 6개를 열어도 기존 5개는 유지되고 6번째만 거부되며 서로를 쫓아내는 재연결 순환이 생기지 않는다. 서버는 끊어진 연결(쓰기 실패, 하트비트 전송 실패)을 15초 안에 정리해 슬롯을 돌려준다. 클라이언트의 처리는 §6.6.
- **느린 클라이언트**: 전송 대기 이벤트가 100개를 넘으면 서버는 그 스트림을 닫는다. 메모리를 무한히 쓰지 않는다. 클라이언트는 재연결 후 재동기화한다.

### 4.2 이벤트 형식과 종류
스트림은 SSE 형식(`text/event-stream`)이다. 이벤트 하나는 다음 줄들과 빈 줄로 끝난다. `data`는 한 줄 JSON이다.
```
id: 12
event: transaction.created
data: {"roomId":"…","revision":12,"serverTime":"2026-11-08T03:21:45.123Z","transactionId":"…"}

```
- `id`는 `revision` 값과 같다(`ready`, `heartbeat`에는 `id`를 붙이지 않는다).
- 모든 `data`는 `roomId`와 `serverTime`(RFC 3339 UTC 밀리초)을 포함한다. 변경 이벤트는 `revision`을 더 포함한다.
- `data`에는 거래의 금액·사유·라운드·작성자·닉네임 같은 **내용을 싣지 않는다.** 식별자와 변경 종류만 싣는다(R-I3).

| `event` | 발생 지점 | `data`의 추가 필드 |
| --- | --- | --- |
| `ready` | 연결 직후 한 번(변경 아님) | `revision`: 연결 시점의 현재 방 변경 번호 |
| `heartbeat` | 15초마다(변경 아님) | `revision`: 그 시점의 현재 방 변경 번호 |
| `transaction.created` | S2 거래 생성 성공(§4.1) | `revision`, `transactionId` |
| `transaction.updated` | S2 거래 수정 성공(값이 실제로 바뀐 경우, §4.2) | `revision`, `transactionId` |
| `transaction.deleted` | S2 거래 삭제 성공(§4.3) | `revision`, `transactionId` |
| `participant.created` | S1 참여자 생성 성공: 입장의 `201`(§4.3)과 직접 추가(§4.6) | `revision`, `participantId` |
| `participant.status_changed` | S1 참여자 활성 상태 실제 변경(§4.7) | `revision`, `participantId` |
| `claim.created` | S1 이어받기 요청 생성(§4.9) | `revision`, `claimId` |
| `claim.canceled` | S1 이어받기 요청 취소(§4.11) | `revision`, `claimId` |
| `claim.resolved` | S1 이어받기 승인·거절(§4.13, §4.14). 승인에 딸린 `TARGET_CLAIMED` 거절과 `REQUESTER_LINKED` 거절도 이 이벤트 하나에 포함된다(한 트랜잭션 = 한 이벤트, R-I1) | `revision`, `claimId`(승인·거절을 요청받은 요청의 ID) |
| `access.revoked` | S1 이어받기 승인으로 접근을 잃은 신원(§4.13 4)의 **그 신원으로 연 스트림에만** 보낸다(변경 이벤트가 아님, `revision` 없음). 보낸 뒤 서버가 그 스트림을 닫는다 | 없음 |
| `room.ended` | S4 게임 종료 전이 성공(§8) | `revision` |

- 알 수 없는 `event` 이름은 클라이언트가 **무시하지 않고 변경 이벤트로 취급**해 재동기화한다(미래의 이벤트 추가에 대비, E-11). 알 수 없는 `data` 필드는 무시한다.
- 입장의 복원(`200`)은 이벤트 대상이 아니다(참여자가 바뀌지 않는다). 새 참여자를 만든 입장은 `participant.created`다(S1 §8, N-5 대체).
- 이어받기 이벤트는 방의 모든 스트림에 보낸다(방장이 아닌 참여자에게는 내용 없는 알림이며, 받은 클라이언트는 §6.4 갱신만 한다, S5-C1). 이어받기 승인은 참여자의 표시 필드를 바꾸지 않으므로 `participant.*` 이벤트를 따로 만들지 않는다.

## 6. 동작 규칙

### 6.1 변경 번호(revision)와 이벤트 생성 (E-3, 사용자 결정 2026-11-08)
- 방의 상태를 바꾸는 변경(S1 참여자 생성(입장·직접 추가)·상태 변경·이어받기 요청 생성·취소·승인·거절, S2 거래 생성·수정·삭제, S4 게임 종료)은 **방 단위 직렬화 안의 같은 트랜잭션에서** `revision`을 1 증가시키고 그 값으로 이벤트를 만든다(S2 §7 1과 같은 잠금). 다중 서버 인스턴스에서도 성립해야 하며 프로세스 메모리 카운터만으로 구현하지 않는다.
- 이벤트는 그 트랜잭션이 커밋된 뒤에 전달한다(R-I2). 커밋과 이벤트 발행 사이의 실패로 이벤트가 사라질 수 있으며, 이는 하트비트(§6.4)가 보완한다. 이벤트가 커밋 전에 나가는 일은 없어야 한다.
- 이 요구는 S1·S2·S4가 "서버만 가지는 내부 기록"(S1 §2.1, S2 §2.1)에 둘 저장 모델 의존성이며 그 Spec들의 API·오류·AC 계약을 바꾸지 않는다. S1·S2·S3 문서는 수정하지 않는다(S3 C-1과 같은 방식, §12.2 E-3). 이 항목은 Plan/Tasks의 S1·S2·S4 구현 Task에 포함하고 검증한다.
- 거부된 요청, 멱등 재전송, 값이 같은 수정·상태 변경은 `revision`을 소비하지 않는다(R-I1, R-I2).

### 6.2 전달 (서버)
- 서버는 한 방의 이벤트를 그 방에 연결된 **모든 스트림**(모든 서버 인스턴스에 걸쳐)에 전달해야 한다. 변경을 처리한 인스턴스와 스트림을 가진 인스턴스가 다를 수 있다. 전달 수단(예: PostgreSQL LISTEN/NOTIFY, 방 단위 구독)은 Plan이 정한다. 확정된 기술 스택에 없는 Redis·메시지 큐는 구체적 필요가 확인될 때만 쓴다(`.agents/governance.md` §12).
- 한 스트림에는 `revision` 오름차순으로 보낸다. 서버가 이 순서를 지키지 못해도 클라이언트의 검사(§6.3)가 복구하므로 순서는 최선 노력이다.
- **접근 상실**: 이어받기 승인이 커밋되면 서버는 이전 신원 키로 연 이 방의 스트림에 `access.revoked`를 보내고 그 스트림을 닫는다. 이후 그 스트림에는 어떤 이벤트도 보내지 않는다. 다른 인스턴스의 스트림에도 같은 전달 수단으로 알린다. `access.revoked`를 놓쳐도 다음 재연결이나 REST 요청이 `401 IDENTITY_REVOKED`를 받으므로 안내가 늦어질 뿐 접근은 막힌다(AC-VIEW-005-9, AC-ROOM-009-5).
- **이벤트를 저장하거나 재전송하지 않는다.** `Last-Event-ID`는 무시한다. 재연결한 클라이언트는 새 `ready`를 받고 전체를 재동기화한다(§6.4, E-6).
- 하트비트(`heartbeat`)는 15초마다 보내고, 그 시점에 **DB에서 읽은 현재 `revision`**을 싣는다. 알림이 유실되었어도 하트비트가 클라이언트가 뒤처졌음을 알린다.

### 6.3 순서·중복·누락 처리 (클라이언트)
클라이언트는 연결마다 `seen`(지금까지 알게 된 가장 큰 `revision`)과 `dirty`(아직 성공한 갱신으로 반영되지 않은 변경이 있음)를 유지한다. `dirty`는 §6.4의 갱신 주기가 **성공적으로 끝난 뒤에만** 거짓으로 돌아간다(`seen`만으로 반영 여부를 판단하지 않는다).
1. `ready{revision: R}`을 받으면 `seen = R`, `dirty = 참`으로 두고 §6.4의 갱신을 시작한다(재동기화).
2. 변경 이벤트 `e`를 받으면:
   - `e.revision ≤ seen`: 중복 또는 이미 알고 있는 과거 이벤트이므로 **무시**한다.
   - `e.revision ≥ seen + 1`: `seen = e.revision`, `dirty = 참`으로 두고 갱신을 예약한다. `e.revision > seen + 1`(누락)이어도 같다. 갱신은 항상 전체를 조회하므로(§6.4) 누락된 변경도 함께 반영된다.
3. `heartbeat{revision: H}`를 받으면 `H > seen`이면 누락이므로 `seen = H`, `dirty = 참`으로 두고 갱신한다. `H ≤ seen`이어도 `dirty`가 참이면 아무것도 새로 하지 않는다(진행 중이거나 재시도 중인 갱신이 처리한다).
4. 알 수 없는 `event` 이름은 `revision` 필드가 있으면 2번을, 없으면 `dirty = 참`으로 두고 갱신한다. `data`의 파싱 실패나 잘린 이벤트도 `dirty = 참`으로 갱신한다.
5. `access.revoked`는 변경 이벤트가 아니므로 `seen`·`dirty`를 바꾸지 않는다. 받으면 즉시 스트림을 중단하고 갱신 주기를 버린 뒤 재연결하지 않고 §9의 접근 상실 처리를 한다.

갱신이 실패하면 `dirty`는 참으로 남고 §6.4의 실패 처리(끊김 전환과 재연결)가 복구한다. 따라서 순서 뒤바뀜·중복·누락·갱신 실패 모두 정확한 상태로 수렴한다.

### 6.4 갱신과 재동기화 (refresh)
**갱신(refresh)**은 서버 상태를 다시 조회해 화면의 서버 유래 데이터를 교체하는 동작이며 **이벤트 종류와 무관하게 항상 다음 표의 갱신 대상 전체를 조회한다**(일반 참여자 5개, 방장은 대기 요청 목록을 더해 6개, S5-C2)(`ready` 직후의 재동기화, 모든 변경 이벤트, 누락 감지, 재연결 모두 같다). 이벤트 종류별로 조회를 줄이는 최적화는 하지 않는다. S3 §3.2·§8이 "변경 알림 뒤 두 S3 API를 다시 조회"를 확정했고, 전체 조회가 순서·누락 처리를 가장 단순하게 만들기 때문이다. 방당 참여자 10명·거래 1,000건 규모에서 조회 비용은 작다(§13).

| 대상 | API |
| --- | --- |
| 방(상태 포함) | `GET /rooms/{roomId}` (S1 §4.4) |
| 참여자 목록 | `GET /rooms/{roomId}/participants` (S1 §4.5) |
| 누적 손익 | `GET /rooms/{roomId}/balances` (S3 §4.2) |
| 거래 목록(첫 페이지, 새 순회) | `GET /rooms/{roomId}/transactions` (S3 §4.1) |
| 정산(예상·최종) | S4가 정한 정산 조회 API |
| (방장만) 대기 중인 이어받기 요청 | `GET /rooms/{roomId}/claims` (S1 §4.12). 방장 여부는 직전 방 조회의 `me.isHost`로 정한다 |

- **한 주기의 완료**: 갱신 대상 조회를 같은 주기로 시작하고 **모든 응답이 성공(2xx)한 뒤에만 함께 화면에 반영**한다(S3 §3.2). 그 시점에 이 주기가 시작될 때 이미 알려진 변경에 대해 `dirty`를 거짓으로 되돌린다. 주기 도중 새 변경이 알려지면(`dirty`가 다시 참) 한 주기를 더 한다.
- **갱신 실패 처리**: 갱신 대상 중 하나라도 네트워크 오류, 시간 초과(요청당 10초), 5xx이면 그 주기는 실패다. 실패한 주기의 결과는 일부도 반영하지 않으며, 클라이언트는 **연결 끊김(`disconnected`, §6.5)으로 전환**하고 현재 스트림을 중단한 뒤 §6.6의 재연결을 한다. 새 `ready` 뒤의 재동기화가 다시 갱신을 시도한다. 이로써 갱신 실패 뒤의 복구 경로가 하나(재연결)로 정해진다. `401`이거나 `404 ROOM_NOT_FOUND`이면 재시도하지 않고 오류를 안내한다(§6.6). `401 IDENTITY_REVOKED`는 S1 §9의 접근 상실 처리를 한다.
- **거래 목록은 S3 §6.4의 새 순회로 교체한다.** 현재 선택된 참여자 필터를 유지한 채 첫 페이지부터 다시 불러오고 기존 페이지는 폐기한다. 이로써 필터 선택과 정렬 규칙이 유지된다(AC-VIEW-005-7). 이전에 더 불러 두었던 페이지 수만큼 이어서 불러와 보이는 범위를 복원하는 것은 허용하되, 완료 전에는 기존 목록을 유지하다가 한 번에 교체한다.
- **병합 금지 유지**: S3 §6.4의 "병합하지 않는다"를 바꾸지 않는다. 부분 갱신은 이 Spec에서 정의하지 않는다.
- **합치기(coalescing)**: 갱신 주기는 한 번에 하나만 진행한다. 진행 중에 변경이 알려지면(`dirty`) 끝난 뒤 한 주기를 더 한다. 주기의 응답은 **가장 최근에 시작한 주기의 것만** 반영하고 늦게 도착한 이전 주기의 응답은 버린다.
- **초기 로드도 같은 절차**다: 스트림을 먼저 연결하고 `ready`를 받은 뒤 재동기화로 처음 데이터를 채운다. 스트림이 연결되지 않으면 데이터 영역은 표시되지 않는다(§6.5).
- 변경 알림 토스트는 필수가 아니다(AC-VIEW-005-6).

### 6.5 연결 상태와 오래된 데이터 표시 금지 (FR-SYS-001, NFR-004)
- **연결됨(`connected`)**: 스트림이 열려 있고, 마지막 수신(이벤트·하트비트 포함)이 **40초 이내**이며, `navigator.onLine`이 거짓이 아니다.
- **끊김(`disconnected`)**: 다음 중 하나라도 해당한다. 스트림이 닫히거나 오류로 끝남, 40초 동안 아무것도 수신하지 않음(하트비트 두 번 이상 연속 누락), `navigator.onLine`이 거짓, 갱신 주기의 실패(§6.4: 네트워크 오류, 시간 초과, 5xx), 스트림이 아직 연결되지 않은 최초 상태.
- 끊김 상태에서 클라이언트는 다음을 한다.
  1. 연결 끊김 상태와 오류 안내를 표시한다(AC-SYS-001-1).
  2. **서버에서 받은 모든 데이터 영역을 표시하지 않는다**: 누적 손익, 거래 목록, 정산 결과, 참여자 목록, 게임 상태. 이전에 불러온 값을 "최신이 아님" 표시와 함께 보여 주는 것도 하지 않는다(AC-SYS-001-2, -4). 캐시로 대체 표시하는 기능을 만들지 않는다.
  3. 변경 조작(거래 등록·수정·삭제, 참여자 변경, 종료)을 수행하지 못하게 한다. 오프라인 큐잉은 없다(AC-SYS-001-3).
  4. 현재 화면에서 작성 중이던 입력값(거래 입력 폼, 닉네임 입력 등)은 유지한다(AC-SYS-001-5).
- 끊김에서 연결됨으로 돌아오면 `ready` 뒤의 재동기화가 끝난 시점에 데이터 영역을 다시 표시한다. 재동기화가 끝나기 전에는 표시하지 않는다.
- **적용 범위**: 이 규칙은 **참여자로 들어간 뒤(입장·복원·이어받기 승인 뒤)의 방 화면**에 적용한다. 방 생성 화면과 초대 링크 화면(입장 전과 이어받기 대기, S1 §4.1~4.3, §4.9~§4.11)은 스트림이 없는 REST 전용 화면이며 연결 끊김 상태 모델의 대상이 아니다. 그 화면의 요청 실패는 S1·S2의 오류 처리를 따르고 입력은 유지한다. 입장(또는 복원)에 성공한 뒤 방 화면에 들어가면서 스트림을 연결한다.
- **복귀 처리(기준 위치)**: 페이지가 백그라운드에서 돌아올 때(`visibilitychange`로 보임)와 `online` 이벤트에서 즉시 연결 상태를 점검한다. (1) 페이지가 숨겨져 있던 시간이 15초(하트비트 간격)를 넘었거나 마지막 수신이 40초를 넘었으면, 백그라운드 중 하트비트와 이벤트를 처리하지 못했을 수 있으므로 **즉시 `disconnected`로 전환해 데이터 영역을 숨기고** 현재 스트림을 중단한 뒤 §6.6으로 재연결한다. 새 `ready` 뒤의 재동기화가 성공하면 데이터 영역을 다시 표시한다. (2) 그렇지 않으면 연결 상태를 유지한다.

### 6.6 재연결 (FR-SYS-002)
- 스트림이 끊기거나 40초 무수신이면 클라이언트는 현재 스트림을 중단(abort)하고 재연결한다. 간격은 1초에서 시작해 연속 실패마다 2배(최대 30초)로 늘리고 ±20% 무작위를 더한다. 간격은 **재연결 뒤 첫 갱신 주기(재동기화, §6.4)가 성공한 뒤에만** 1초로 되돌린다. 스트림 연결만 성공하고 갱신이 실패하면 간격은 초기화되지 않고 계속 늘어난다(서버의 5xx가 이어질 때 1초 간격의 재시도 폭주를 막는다). `online`·`visibilitychange`(보임) 이벤트에서는 대기 중이어도 즉시 시도한다.
- 재연결 응답이 `401` 또는 `404 ROOM_NOT_FOUND`이면 **재시도하지 않고** 오류를 안내한다(신원 키가 이 방에서 유효하지 않거나 방이 없음). `401 IDENTITY_REVOKED`면 S1 §9에 따라 접근을 잃었다고 안내하고 키를 조건부로 지운 뒤 초대 링크 화면으로 보낸다. `5xx`·네트워크 오류는 위 간격으로 계속 재시도한다. `429 CONNECTION_LIMIT_EXCEEDED`는 서버의 `Retry-After`(30초) 이상 간격으로만 재시도하고 "다른 탭을 닫으세요"처럼 연결 수 한도를 안내한다(연결이 없으므로 §6.5에 따라 데이터는 표시하지 않는다). 오류 `code`로 분기한다.
- 재연결 후 새 `ready`를 받으면 `seen`을 재설정하고 **전체 재동기화**를 한다(AC-SYS-002-1). 끊긴 동안 게임이 종료되었다면 재동기화한 방 상태에 종료가 반영된다(AC-SYS-002-3).
- **자동 제출 금지**: 재연결·재동기화는 끊김 중에 작성하다 제출하지 못한 거래를 자동으로 제출하지 않는다(AC-SYS-002-2). 응답을 받지 못해 결과를 알 수 없는 저장은 S2 §9에 따라 수동 재시도할 때만 같은 키로 다시 보낸다.
- **저장 응답 유실 뒤 복구**(AC-SYS-002-5, AC-TXN-008-5): 재동기화로 받은 현재 거래 목록에서 사용자가 해당 거래를 볼 수 있다. 시스템은 거래를 자동으로 성공으로 판정하지 않고, 목록에서 해당 거래를 확인할 수 없으면 "저장 여부를 확정할 수 없음" 상태를 유지한다. 재조회한 현재 상태가 최초 요청의 결과를 증명하지 못할 수 있다(그 뒤 다른 사용자가 수정·삭제했거나 Idempotency Key 유효 기간이 지난 경우).
- **새로고침·재방문**: 저장되지 않은 입력 초안은 복원하지 않는다(AC-SYS-002-4). 새로 연결하고 `ready` 뒤 재동기화로 데이터를 채운다.

### 6.7 실시간 지연 기준과 측정 (OQ-019, E-2, 사용자 결정 2026-11-08)
PRD는 지연 목표의 수치와 측정 조건을 Spec으로 넘겼다(AC-VIEW-005-8, NFR-006). 사용자가 다음을 확정했다.

| 지표 | 정의 | 목표 |
| --- | --- | --- |
| 이벤트 전달 지연 | 기준 시각 T0부터 연결된 클라이언트가 이벤트를 받은 시각까지 | 95번째 백분위 1초 이하, 최댓값 3초 이하 |
| 화면 반영 지연 | T0부터 다른 참여자의 화면이 §6.4 갱신(모든 갱신 대상 조회 성공)을 끝내 새 값을 표시하기까지. 방 밖의 이어받기 요청자는 §6.8의 주기 조회로 결과를 표시하기까지 | 95번째 백분위 3초 이하, 최댓값 5초 이하 |
| 유실 시 수렴 지연 | 알림이 유실된 경우 T0부터 하트비트로 뒤처짐을 감지해 화면이 수렴하기까지 | 20초 이하(하트비트 15초 + 갱신) |

- **기준 시각 T0**: 변경 트랜잭션이 **커밋된 시각**이다. 시험 환경에서는 서버가 커밋 직후 계측으로 남긴 시각(또는 DB 커밋 시각)을 쓴다. 이를 얻을 수 없으면 시험 드라이버가 변경 요청을 **보낸 시각**을 쓴다(요청 송신은 커밋보다 앞서므로 지연을 과소 평가하지 않는 보수 기준이며 요청 처리 시간이 포함된다). 변경 요청의 **응답 수신 시각은 T0로 쓰지 않는다**(응답이 늦으면 지연이 합격으로 잘못 판정될 수 있다). 이벤트의 `serverTime`은 **발행 시각**이며 합격 판정의 기준이 아니다. 커밋부터 발행까지의 지연도 T0 기준 측정에 포함된다.
- **측정 조건**: 방마다 신원이 연결된 참여자 10명(방 한도)이 SSE로 연결된 상태(아래 표에서 참여자 수가 다른 행은 그 행의 참여자 수만큼 연결). 서버는 정상 부하, 클라이언트와 서버 사이 왕복 지연 150ms 이하의 일반 모바일·유선망. 변경은 한 번에 하나씩 일어난다(동시 다발 변경 중에는 합치기로 지연이 늘 수 있다). 방 한도(AC-ROOM-008-1~3, -7, -9)를 지키기 위해 **변경 종류별로 아래 초기 상태에서 측정한다.**

| 변경 | 초기 상태 | 횟수 |
| --- | --- | --- |
| 거래 생성 | 활성 참여자 10명, 거래 900건(생성이 끝나면 1,000건) | 100건 |
| 거래 수정 | 활성 참여자 10명, 거래 1,000건(삭제 없음) | 100건 |
| 거래 삭제 | 활성 참여자 10명, 거래 1,000건 | 100건(서로 다른 거래) |
| 참여자 생성(입장·직접 추가) | 참여자 9명(SSE 9개), 거래 1,000건인 방 | 방마다 1건, 방 10개 이상(입장과 직접 추가를 각각) |
| 참여자 상태 변경 | 참여자 10명, 거래 1,000건 | 100건(활성·비활성 번갈아) |
| 게임 종료 | 진행 중, 참여자 10명, 거래 1,000건인 방 | 방마다 1건, 방 10개 이상 |
| 이어받기 요청 생성·취소(방장 화면) | 참여자 10명(신원 있는 9명 SSE 연결, 직접 추가한 1명), 거래 1,000건. 방 밖의 브라우저가 직접 추가한 참여자를 요청 | 생성·취소 번갈아 100건 |
| 이어받기 승인·거절(요청자 화면, §6.8) | 위와 같은 방, 대기 요청 1건 | 승인·거절 각각 방마다 1건, 방 10개 이상. 거절은 같은 방에서 반복 가능 |
| 접근 상실 안내(이전 브라우저) | 참여자 10명 모두 SSE 연결, 대상 참여자의 이전 브라우저 포함 | 방마다 1건, 방 10개 이상. 이전 브라우저의 `access.revoked` 수신까지를 이벤트 전달 지연으로 잰다 |

- **측정 방법**: 자동화된 통합 시험에서 위 각 상태의 방마다 SSE 클라이언트 10개를 연결하고, 변경을 한 건씩 보내며 변경마다 T0와 각 클라이언트의 이벤트 수신 시각, 화면 반영 시각을 기록한다. 서버와 시험 클라이언트가 같은 기기 또는 시계 동기된 환경에서 측정하고 변경 종류별과 전체의 95번째 백분위·최댓값을 보고한다. 유실 시나리오는 알림 전달을 의도적으로 버려 하트비트 경로를 시험한다.
- **합격 판정**: 위 조건에서 측정한 값이 목표를 **초과하면 불합격**이다(통합 시험 실패). 목표는 정상 조건의 합격 기준이며 운영 중 보장(SLA)은 아니다. 조건을 벗어난 상황(연결이 끊긴 상태, 동시 다발 변경, 느린 망)은 합격 기준이 아니며 연결이 끊긴 상태는 §6.5가 정한다.

### 6.8 이어받기 요청자의 결과 수신 (AC-VIEW-005-9, S5-C4)
- 이어받기를 요청한 브라우저는 방의 참여자가 아니므로 §4.1의 스트림을 열 수 없다(§3.3).
- 요청이 `PENDING`인 동안 초대 링크 화면은 내 요청 조회(S1 §4.10)를 **2초 간격**으로 한다. 화면이 보일 때만 조회하고(`visibilitychange`), 다시 보이거나 `online` 이벤트가 오면 즉시 조회한다. 요청당 시간 제한은 10초이며 실패하면 다음 간격에 다시 한다(입력이 없으므로 끊김 상태 모델은 적용하지 않는다, §6.5 적용 범위).
- 결과가 `APPROVED`면 조회를 멈추고 입장 요청(S1 §4.3)으로 복원해 방 화면에 들어가며 그때 스트림을 연다. `REJECTED`·`CANCELED`면 조회를 멈추고 결과를 안내한다(S1 §9).
- 지연: 정상 조건에서 승인·거절 커밋부터 요청자 화면 표시까지 최대 약 2초 + 요청 왕복이며, AC-VIEW-005-8의 화면 반영 기준(95번째 백분위 3초, 최댓값 5초)을 목표로 §6.7에서 측정한다.

## 7. 동시성과 정합성
- **직렬화와 revision**: `revision`은 S2 §7의 방 단위 잠금 안에서 증가하므로 동시 변경에서도 서로 다른 연속 번호를 갖는다(R-I1).
- **커밋 순서**: 같은 잠금 안에서 번호가 매겨지고 커밋되므로 더 큰 `revision`의 변경이 작은 것보다 먼저 커밋되지 않는다. 읽기 스냅샷이 큰 번호만 보고 작은 번호를 놓치는 일이 없다.
- **재동기화와 새 변경의 경쟁**: `ready{R}` 뒤의 조회는 번호 R 이상의 커밋을 반영한다. R보다 큰 이벤트는 별도로 도착해 추가 갱신을 만든다. 갱신은 멱등이므로 조회가 이벤트보다 더 최신 상태를 가져와도 틀리지 않는다.
- **같은 변경의 이중 처리**: 알림 전달 경로가 둘 이상이거나 재시도되어도 클라이언트의 `seen` 검사(§6.3)가 중복을 걸러 낸다.
- **스트림 수 한도**(E-9)와 느린 클라이언트 차단은 다른 방과 변경 처리에 영향을 주지 않아야 한다(스트림 쓰기는 변경 트랜잭션을 지연시키지 않는다).

### 8.1 S1·S2·S3에 대한 요구 (계약 변경 없음)
| 대상 | 요구 |
| --- | --- |
| S1 참여자 생성: 입장(§4.3의 `201`)과 직접 추가(§4.6) | 성공 시 `participant.created` 이벤트, `revision` 증가. 복원(`200`)과 거부는 없음 |
| S1 이어받기 요청·취소·승인·거절(§4.9, §4.11, §4.13, §4.14) | 성공 시 `claim.created`/`claim.canceled`/`claim.resolved`, `revision` 증가. `CLAIM_REQUESTER_LINKED`로 거부된 승인도 요청 상태가 바뀌므로(S1 §2.3 I9) `claim.resolved`를 만든다. 그 밖의 거부는 없음. 승인은 이전 신원의 스트림에 `access.revoked`(§6.2) |
| S1 참여자 상태 변경(§4.7) | **실제 변경이 있을 때만** `participant.status_changed`. 같은 값 요청(N-4)은 없음 |
| S2 거래 생성·수정·삭제(§4) | 성공 시 `transaction.created/updated/deleted`. 멱등 재전송(§5.3), 값이 같은 수정(§4.2), 거부는 없음 |
| S3 조회 API | 변경 없음. 이벤트 후 재조회 대상(§6.4). 추가 필드를 요구하지 않는다 |

이 요구는 S1·S2의 구현이 해당 트랜잭션 안에서 §6.1을 수행하는 저장 모델 의존성이다. S1·S2·S3 문서는 수정하지 않는다.

### 8.2 S4가 이 Spec에서 가져가는 계약
S4 Spec(미작성)은 다음을 따라야 한다. S5가 S4에 요구하는 것이며 S4 작성 시 반영하고 검수한다.
1. **종료 전이와 이벤트**: 게임 종료(`IN_PROGRESS → ENDED`)는 S2 §7 1의 방 단위 직렬화 안에서 일어나고, **전이를 일으킨 트랜잭션에서 정확히 한 번** `revision`을 증가시키며 `room.ended` 이벤트를 만든다(AC-SET-001-9, AC-VIEW-005-4). 같은 Idempotency Key의 재전송, 이미 종료된 게임에 대한 새 종료 요청(거부), 24시간 만료 거부는 이벤트를 만들지 않는다.
2. **정산 조회 API**: S4가 예상·최종 정산을 돌려주는 조회 API를 정한다. 방 상태에 따라 예상 또는 최종을 돌려주고 필터와 무관하게 전체 유효 거래 기준이다(AC-SET-008-6). 스냅샷 일관성은 S3 §3.2와 같은 원칙을 쓴다. S5는 이 API의 경로·형식에 의존하지 않고 "정산 조회 API"로만 참조한다.
3. **정산 변경 이벤트**: 정산은 S3 순손익에서 계산되는 파생 값이므로 **별도의 정산 이벤트를 만들지 않는다.** 예상 정산이 바뀌는 시점은 `transaction.*`, `participant.*`, `room.ended` 이벤트와 같다(AC-VIEW-005-5). 최종 정산은 종료 후 거래가 잠기므로 변하지 않는다(AC-SET-007-3).
4. **순손익의 단일 정의**: S4는 S3 §6.1의 순손익 정의를 쓴다(S3 §1.3).
5. **이벤트 페이로드**: `room.ended`의 `data`는 §4.2의 형식(`roomId`, `revision`, `serverTime`)이며 정산 내용을 싣지 않는다. 정산은 REST 조회로 받는다.

## 9. 프론트엔드 책임
- **진입 검사**: §3.1의 필수 기능을 검사하고 하나라도 없으면 진입을 차단하고 안내한다.
- **스트림 클라이언트**: `fetch`로 §4.1에 연결하고 `ReadableStream`을 `TextDecoder`(스트리밍 모드)로 읽어 SSE 형식을 해석한다. 줄 경계에서 잘린 이벤트를 이어 붙이고(버퍼링), `\n\n`로 끝나는 이벤트만 처리한다. 알 수 없는 줄(주석 `:` 등)은 수신 시각 갱신에만 쓴다. `AbortController`로 중단·재연결한다. 네이티브 `EventSource`는 쓰지 않는다(E-1).
- **연결 상태 모델**: §6.5의 `connected`/`disconnected`를 앱 전역 상태로 두고 모든 서버 유래 영역이 이 상태를 따른다. 끊김 중 표시 금지, 입력 유지, 변경 컨트롤 비활성(AC-SYS-001-1~5).
- **순서·중복·누락**: §6.3의 `seen`·`dirty`를 그대로 구현한다. 갱신은 항상 갱신 대상 전체(방장은 대기 요청 목록 포함)를 조회한다(§6.4).
- **갱신**: 갱신 대상 조회가 모두 성공한 뒤 함께 반영하고, 실패하면 끊김으로 전환해 재연결한다. 합치기와 최신 주기 응답만 반영(§6.4). 거래 목록은 S3 §6.4의 새 순회이며 현재 필터를 유지한다.
- **재연결**: §6.6의 간격과 즉시 재시도 조건, 401/404 중단, 429는 30초 이상 간격과 연결 수 한도 안내.
- **시각 보정 연계**: `ready`의 `serverTime`(그리고 REST 응답 `Date`)으로 S2 §9의 시계 차이 추정을 갱신해도 된다.
- **저장 결과 불명**: S2 §9와 §6.6의 규칙을 따른다. 재동기화는 자동 재전송을 하지 않는다.
- **종료 반영**: `room.ended` 또는 재동기화로 방이 `ENDED`가 되면 거래 입력·수정·삭제 UI를 잠그고 최종 정산을 표시한다(AC-VIEW-005-4, AC-TXN-009-3). 정산 화면은 S4가 정한다.
- **접근 상실**: `access.revoked`를 받거나 어떤 요청이 `401 IDENTITY_REVOKED`면 스트림을 중단하고 재연결하지 않으며 S1 §9의 처리(안내, 키 조건부 삭제, 초대 링크 화면)를 한다(AC-VIEW-005-9).
- **권한 변화 반영**: 갱신으로 받은 `me.status`가 바뀌면 거래 컨트롤을 바로 잠그거나 되돌린다(AC-VIEW-005-3의 자기 권한, S2 §9).
- **이어받기 대기 화면**: §6.8의 주기 조회를 한다.
- 변경 알림 토스트는 만들지 않아도 된다.

## 10. 백엔드 책임
- §3.3 검사 순서, §4.1 SSE 엔드포인트와 헤더, §4.2 이벤트 형식과 종류, §6.1 `revision`·이벤트 생성(커밋 뒤 전달), §6.2 전달(다중 인스턴스, 하트비트가 DB의 현재 `revision`을 싣기), §4.1의 연결 한도(초과 시 새 연결 거부 `429`, 끊어진 연결의 15초 내 정리)와 대기 한도를 구현한다.
- 이벤트에 거래·참여자의 내용, 신원 키, 키 해시를 싣지 않는다.
- 스트림 쓰기는 변경 트랜잭션의 지연이나 실패 원인이 되지 않는다(전달은 비동기).
- 프록시 버퍼링을 막는 응답 헤더(`X-Accel-Buffering: no`, `Cache-Control: no-store`)와 하트비트로 유휴 연결 종료를 완화한다.
- 이 Spec의 계약을 다른 저장소 문서에 복제하지 않고 Spec 버전 또는 `ddallang` 커밋으로 참조한다.

### 12.3 자체 점검 (상위 문서와의 충돌)
- FR-VIEW-005(8), FR-SYS-001(5), FR-SYS-002(5)의 AC 18개와 FR-SYS-003(8)의 적용을 추적표에 연결했다. AC를 약화하거나 바꾸지 않았다.
- AC-VIEW-005-8(지연 수치는 OQ-019 해결 전까지 정의하지 않는다)은 PRD가 비워 둔 부분이며 E-2가 채운다. E-2는 사용자가 확정했다(2026-11-08).
- S1 §3.1이 SSE 인증을 S5로 넘겼고 E-1이 채운다. S1의 인증 방식(Bearer)은 바뀌지 않는다.
- S3 §6.4의 "병합하지 않는다, 교체한다"를 유지한다. S3 C-9의 "응답에 변경 번호를 두지 않는다. S5가 필요하면 기존 필드를 바꾸지 않는 추가"에 대해 이 Spec은 REST 응답에 변경 번호를 **추가하지 않고** SSE 이벤트 안에서만 `revision`을 쓴다. S1·S2·S3 API 응답은 바뀌지 않는다.
- 변경 번호의 저장 모델 의존성(E-3)은 S1 §2.1·S2 §2.1이 "서버만 가진다"고 한 내부 기록 영역에 속한다. S3 C-1 (a)와 같은 해석 위험이 있다(§13).
- NFR-008과 OQ-032 결정의 플랫폼 목록 차이(E-4)는 충돌 가능성으로 보고한다.
- PRD의 OQ-030·031·039 오래된 문구는 S5 계약 해석에 영향이 없다.
- 제품 정책 변경, MVP 제외 기능(오프라인 큐잉, 입력 초안 복원, 폴백) 추가는 없다.

## 13. 위험
- **SSE 의존(E-5)**: 스트림이 막힌 네트워크(일부 기업 프록시)에서는 앱이 데이터를 표시하지 못한다. 폴링 폴백은 범위 밖이다.
- **직접 재연결 구현(E-1)**: `fetch` 스트리밍은 브라우저가 재연결·파싱을 해 주지 않는다. 파서·재연결 코드의 결함이 연결 신뢰성을 좌우하므로 단위·통합 시험이 필요하다.
- **모바일 백그라운드**: iOS Safari 등은 백그라운드 탭의 연결을 중단한다. 복귀 시의 처리는 §6.5의 "복귀 처리"가 기준이다(15초를 넘게 숨겨졌으면 즉시 숨기고 재연결·재동기화). 숨겨져 있던 시간이 15초 이하인데 연결이 이미 죽어 있었다면 마지막 수신 후 40초가 지나 끊김으로 판정될 때까지 오래된 화면이 남을 수 있다(마지막 수신 직후 숨겨지고 연결이 끊긴 뒤 곧바로 복귀하면 상한은 약 40초에 가깝다). 이는 40초 무수신 판정(§6.5)의 귀결이다.
- **다중 인스턴스 전달**: 알림 전달 수단(예: LISTEN/NOTIFY)이 일시적으로 끊기면 이벤트가 유실될 수 있다. 하트비트의 DB `revision`이 보완하며 수렴 상한은 약 20초다.
- **전체 재동기화 비용**: 재연결·누락 때마다 갱신 대상 전체(방장은 6개)를 조회한다. 이어받기 이벤트도 모든 참여자의 갱신을 일으킨다(S5-C1). 방당 참여자 10명·거래 1,000건 규모에서는 작지만 Plan에서 측정한다.
- **요청자 주기 조회(S5-C4)**: 대기 요청은 만료가 없으므로(P-9) 화면을 열어 둔 요청자는 계속 조회한다. 보이는 화면에서만 2초 간격이며, 요청자 수가 방마다 적어 부하는 작다. 화면을 숨기면 결과 표시는 다시 보일 때까지 늦어진다(지연 기준은 보이는 화면 기준).
- **`access.revoked` 유실**: 알림이 사라지면 이전 브라우저는 다음 하트비트가 아니라 다음 요청·재연결에서야 안내받는다. 스트림이 열려 있는 동안에는 서버가 그 스트림에 이벤트를 더 보내지 않으므로 40초 무수신 뒤 재연결에서 401을 받는다(최대 약 40초 지연, §6.7 측정은 정상 조건 기준).
- **재연결 폭주**: 서버 재시작 시 모든 클라이언트가 동시에 재연결·재동기화한다. 지터와 백오프로 완화하며 규모는 방당 10명 한도로 제한된다.
- **변경 번호 저장 모델(E-3)**: S1·S2 문서의 내부 기록 목록을 엄격히 완전 목록으로 읽으면 S1·S2 개정으로 볼 여지가 있다. 이 경우 S1·S2 재검수가 필요하다.
- **시계 오차와 지연 측정**: 지연 측정은 서버 시각과 클라이언트 시각을 비교하므로 시계 동기된 시험 환경이 필요하다(§6.7).
- **이벤트 폭주 시 합치기**: 짧은 시간에 변경이 몰리면 화면이 한 주기 늦을 수 있다. 합치기로 조회 수를 제한하며 지연 목표는 한 번에 하나씩 일어나는 변경 기준이다(§6.7).
- **브라우저 지원 범위(OQ-032)**: 구체 버전 숫자가 없다. 구현·검증 단계에서 실제 호환성을 확인해 정해야 한다.
