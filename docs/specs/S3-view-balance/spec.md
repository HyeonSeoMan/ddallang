## 1. 범위

### 1.1 담당 FR (AC 25개 + 다른 Spec이 넘긴 조회 쪽 계약)
FR-VIEW-001~004(AC 20개: 2+3+6+9), FR-SET-002(AC 5개). 그리고 S1·S2가 "S3 소관"으로 넘긴 것: 삭제된 거래의 집계 제외(AC-TXN-005-3), 수정 반영(AC-TXN-005-5), 동시 수정 뒤 합 0(AC-TXN-006-3), 비활성 참여자의 손익 보존(AC-PART-002-2, -6), 정산 단위 표시(AC-ROOM-003-3, AC-ROOM-001-14), 최대 금액 경계(NFR-009). AC별 담당과 검증은 §11 추적표.

### 1.2 포함
거래 목록 조회 API(정렬, 20건 단위 커서 페이지네이션, 참여자 1명 필터), 누적 손익(참여자별 순손익) 조회 API와 계산 규칙, 순손익 정렬, 거래 생성 순번 규칙, 조회 권한, 화면 구성 책임(누적 손익과 거래 내역의 구분).

## 2. 도메인 모델과 불변식

### 2.1 읽는 개체
S1의 Room(`unit`, `status`), Participant(`id`, `nickname`, `status`, `order`), S2의 Transaction(`id`, `payerId`, `payeeId`, `amount`, `reason`, `round`, `authorId`, `createdAt`, `updatedAt`)과 서버 내부 기록(삭제 여부, 생성 순번). S3가 새로 저장하는 개체는 없다. 순손익과 목록은 모두 저장된 유효 거래에서 계산·조회한다.

### 2.2 불변식
- V-I1. **유효 거래**는 삭제되지 않은 거래(`deletedAt` 없음)다. 목록, 순손익은 유효 거래만 쓴다.
- V-I2. 한 방에서 어떤 커밋 시점에도 모든 참여자의 순손익 합은 0이다(NFR-001, AC-SET-002-2).
- V-I3. 순손익은 필터와 무관하게 항상 방의 전체 유효 거래 기준이다(AC-VIEW-004-7).
- V-I4. 거래의 목록 위치(원본 생성 시각, 생성 순번)는 생성 때 정해지고 수정으로 바뀌지 않는다(AC-VIEW-003-3).

### 2.3 거래 생성 순번과 생성 시각 (C-1, 사용자 결정 2026-11-08)
PRD는 목록을 "원본 서버 생성 시각 내림차순, 같으면 서버 생성 순번 내림차순"으로 정하고(FR-VIEW-003) 순번의 고유성·증가 보장은 열어 뒀다(OQ-031, AC-VIEW-003-6). 이 Spec은 다음을 요구한다.
- **생성 순번(`seq`)**: 거래마다 서버가 부여하는 양의 정수. 한 방 안에서 (a) 서로 다르고(고유), (b) 방 단위 직렬화(S2 §7 1)에서 거래가 삽입된 순서대로 **증가**하며, (c) 삭제·수정·한도 계산과 무관하게 한 번 부여되면 바뀌지 않고 재사용되지 않는다. 결번은 허용한다(거부된 요청이 번호를 소비해도 된다). 클라이언트에는 노출하지 않고 커서 안에서만 쓴다.
- **생성 시각(`createdAt`)**: 같은 방 안에서 감소하지 않는다. 서버(DB) 시각이 같은 방의 마지막 거래의 `createdAt`보다 앞서 있으면(시계 보정 등) 마지막 `createdAt`을 쓴다. 이로써 (`createdAt`, `seq`) 순서는 삽입 순서와 같다.
- 두 값은 S2의 거래 생성과 같은 트랜잭션에서 방 잠금을 쥔 채 부여한다. 다중 서버 인스턴스에서도 성립해야 하며 프로세스 메모리 카운터만으로 구현하지 않는다(S2 §7 1과 같은 요구).
- 이 요구는 S2가 "서버만 가지는 내부 기록"(S2 §2.1)으로 둔 영역이며 S2의 API·오류·AC 계약을 바꾸지 않는다. **S2 문서는 수정하지 않는다**(사용자 결정 C-1 (a)).
- **커밋 순서 = `seq` 순서**: `seq` 부여부터 커밋까지 방 잠금을 쥐므로(S2 §7 1) 거래의 커밋 순서는 `seq` 순서와 같다. 따라서 어느 읽기 스냅샷도 `seq`가 큰 거래를 보면서 작은 거래를 놓치지 않는다. 키셋 페이지네이션의 무누락 보장(§4.1.2)이 이 성질에 기댄다.

#### 2.3.1 S2 구현에 대한 필수 저장 모델 의존성
S2를 구현하는 저장 모델은 다음을 반드시 만족해야 한다. 어느 하나라도 빠지면 S3의 정렬·페이지네이션 계약(AC-VIEW-003-2, -003-4, -003-6)을 지킬 수 없다. 이 항목은 Plan/Tasks에서 S2 구현 Task에 포함하고 검증한다.
1. 거래 행에 내부 필드 `seq`(64비트 정수)와 `createdAt`을 둔다. `seq`는 `(방, seq)` 유일 제약을 갖는다.
2. 거래 생성(S2 §4.1)과 같은 트랜잭션에서, 방 잠금을 쥔 채 `seq`는 그 방의 마지막 `seq`보다 큰 값으로, `createdAt`은 `max(DB 현재 시각, 그 방의 마지막 거래의 createdAt)`으로 부여한다. 마지막 값의 조회와 삽입 사이에 다른 삽입이 끼어들 수 없어야 한다.
3. `seq`는 한 번 쓰이면 재사용되지 않는다. 삭제(S2 §6.3)·수정(S2 §4.2)·멱등 재전송(S2 §5.3)은 `seq`와 `createdAt`을 바꾸거나 새로 만들지 않는다. 거부된 요청이 번호를 소비해 결번이 생겨도 된다.
4. `seq`와 정렬 키는 클라이언트 응답(S2 `Transaction`, 재전송 본문 포함)에 노출하지 않는다.
5. 목록 질의를 위한 (방, `createdAt` 내림차순, `seq` 내림차순) 인덱스를 둔다. 삭제 행은 질의에서 제외한다.

## 3. 공통 규약

### 3.1 인증과 권한
모든 조회 API는 `Authorization: Bearer <신원 키>`가 필요하고 이 방의 RoomMember여야 한다(S1 §3.1). 비멤버는 존재하지 않는 방과 같은 `404 ROOM_NOT_FOUND`다(S1 N-10). 방장과 일반 접속자의 조회 권한은 같다. 방이 `ENDED`여도 조회할 수 있다(종료 후 입장자 포함, AC-SET-005-1·AC-ROOM-002-5와 같은 원칙). 조회는 멱등 키가 필요 없고 상태를 바꾸지 않는다.

### 3.2 읽기 일관성 (C-6)
- 각 응답은 **하나의 일관된 DB 스냅샷**에서 만든다. 순손익은 한 질의(또는 한 스냅샷 트랜잭션)로 모든 참여자를 계산하므로 부분 반영된 거래가 섞이지 않는다(합 0 유지).
- 조회는 S2 §7의 방 잠금을 쓰지 않는다(쓰기를 막지 않는다). 따라서 서로 다른 두 요청(목록과 순손익)은 서로 다른 시점일 수 있다. 클라이언트는 변경 알림(S5)을 받으면 두 API를 다시 조회한다. 한 응답 안에서만 일관성을 보장한다.
- 오류 시 이전에 받은 값을 새 값처럼 보이게 하는 처리는 S5가 정한다.

### 3.3 검사 순서
S1 §3.3·S2 §3.4와 같은 원칙으로 **처음 걸린 오류 하나**를 반환하되 입력 검증 오류는 모아서 반환한다.
0. 라우트: 없는 경로 `404 ROUTE_NOT_FOUND`, 없는 메서드 `405 NOT_SUPPORTED`(`Allow` 포함)
1. 신원 키 누락·형식 오류: `401 UNAUTHENTICATED`
2. 방 존재, 방 멤버 여부(비멤버는 방이 없는 것과 같은 응답): `404 ROOM_NOT_FOUND`
3. 입력 검증: `422 VALIDATION_FAILED`. 허용되지 않은 쿼리 매개변수는 `NOT_ALLOWED_FIELD`, `participantId`·`cursor` 값의 위반은 §4.1이 정한 사유 코드. 위반 항목을 모아 반환한다.

조회에는 권한(403), 방 상태(409), 한도 오류가 없다.

### 3.4 오류 응답
S1 §3.4의 형식을 쓴다. `details[].field`는 쿼리 매개변수 이름(`participantId`, `cursor` 등)이다. 거부된 요청은 데이터를 바꾸지 않는다(조회이므로 항상 성립한다).

## 4. API 계약

경로의 `{roomId}`는 방 ID다. 응답 본문은 JSON(UTF-8)이다. 금액과 순손익은 JSON 숫자(정수)이며 절댓값이 2^53 미만이다(최대 약 10¹², §6.1).

### 4.1 `GET /rooms/{roomId}/transactions` — 거래 목록 (FR-VIEW-003, 004)
- 인증: 필수, 이 방의 RoomMember.
- 쿼리: `participantId`(선택, 참여자 1명 필터), `cursor`(선택, 이전 응답의 `nextCursor`). **그 밖의 쿼리 매개변수는 `422 NOT_ALLOWED_FIELD`다**(페이지 크기 매개변수 없음).
  - `participantId`는 한 번만, 비어 있지 않은 문자열로 줄 수 있다. 같은 매개변수를 두 번 이상 보내거나(`?participantId=a&participantId=b`, AC-VIEW-004-3) 빈 값이면 `INVALID_VALUE`다. 이 방의 Participant가 아니면(없거나 다른 방, AC-SYS-003-8과 같은 원칙) `PARTICIPANT_NOT_FOUND`다. 비활성 참여자도 허용한다(AC-VIEW-004-6).
  - `cursor`가 §4.1.2의 형식이 아니거나, 이 요청의 `participantId` 필터와 커서가 발급될 때의 필터가 다르면 `INVALID_VALUE`다. 필터를 바꾸면 커서를 버리고 처음부터 시작해야 한다(AC-VIEW-004-8).
- 응답 `200`: `{ "transactions": Transaction[], "nextCursor": string | null }`
  - `transactions`는 **유효 거래만**, 정렬은 §4.1.1, **최대 20건**이다. `Transaction`은 S2 §2.1의 클라이언트 노출 필드 그대로다(`id`, `payerId`, `payeeId`, `amount`, `reason`, `round`, `authorId`, `createdAt`, `updatedAt`). `authorId`는 S1 §2.1의 RoomMember `id`와 같은 값이다(서버가 만든 불투명 ID이며 신원 키나 그 해시에서 파생하지 않는다). 응답 어디에도 신원 키, 키 해시, 인증 값을 담지 않는다(사용자 결정 C-2). 작성자 닉네임은 담지 않는다.
  - `nextCursor`는 이 응답의 마지막 항목 뒤에 항목이 더 있으면 불투명 문자열, 없으면 `null`이다(마지막 페이지 판정을 위해 서버는 21번째 항목 유무를 확인한다). 정확히 20건이 남았을 때 `null`이다.
  - 필터가 있으면 해당 참여자가 `payerId` 또는 `payeeId`인 거래만 포함한다(AC-VIEW-004-2).
  - 거래가 없으면 `{ "transactions": [], "nextCursor": null }`이다.
- 오류: 401, 404 `ROOM_NOT_FOUND`(비멤버 포함), 422.

#### 4.1.1 정렬 (FR-VIEW-003)
(`createdAt` 내림차순, `seq` 내림차순)이다. §2.3에 따라 이는 삽입의 역순과 같다. 수정은 두 값을 바꾸지 않으므로 목록 위치가 바뀌지 않는다(AC-VIEW-003-3). 삭제된 거래는 질의 단계에서 제외하므로 페이지를 비우거나 채움을 줄이지 않는다(AC-VIEW-004-9).

#### 4.1.2 커서 (C-4)
커서는 키셋 방식이다. 서버가 만든 불투명 문자열(예: 마지막 항목의 `createdAt`, `seq`, 필터 `participantId`를 base64url로 인코딩)이며 클라이언트는 해석하지 않는다. 다음 페이지는 "커서보다 정렬상 뒤"인 유효 거래 20건(+1)이다.
- 페이지 사이에 새 거래가 만들어지면 정렬상 맨 앞에 놓이므로 이미 받은 페이지의 경계를 밀지 않는다. 항목이 중복되거나 누락되지 않는다(AC-VIEW-003-4).
- 이미 받은 항목이 그 사이 삭제되거나 수정되어도 커서는 위치(값)로 해석하므로 영향이 없다. 커서가 가리킨 거래가 삭제되었어도 유효하다.
- 커서는 방 ID의 해시도 담고, 서버는 요청 경로의 방과 일치하는지 확인해 맞지 않으면(다른 방의 커서) `INVALID_VALUE`로 거부한다.
- 커서 위조는 같은 방의 같은 질의 안에서 위치를 바꿀 뿐 권한이나 다른 방의 데이터에 영향을 주지 않는다.

### 4.2 `GET /rooms/{roomId}/balances` — 누적 손익 (FR-VIEW-001, 002, FR-SET-002)
- 인증: 필수, 이 방의 RoomMember.
- 쿼리: 없다. 어떤 쿼리 매개변수든 `422 NOT_ALLOWED_FIELD`다(필터는 순손익에 적용되지 않는다, AC-VIEW-004-7).
- 응답 `200`: `{ "balances": Balance[] }`
  - `Balance`: `{ "participantId": string, "nickname": string, "status": "ACTIVE" | "INACTIVE", "order": number, "balance": number }`
  - **방의 모든 참여자**를 포함한다(비활성, 거래가 없는 참여자 포함, AC-VIEW-002-3, AC-PART-002-6).
  - 정렬은 `balance` 내림차순, 같으면 `order` 오름차순(등록이 먼저인 참여자가 앞, AC-VIEW-002-2).
  - `balance`는 §6.1로 계산한 정수다. 음수일 수 있다.
- 오류: 401, 404 `ROOM_NOT_FOUND`(비멤버 포함), 422.

### 4.3 존재하지 않는 동작 (S1 §4.8과 같은 원칙)

| --- | --- |
| `POST`/`PUT`/`PATCH`/`DELETE /rooms/{roomId}/balances` | 405 `NOT_SUPPORTED`, `Allow: GET` |
| `PUT`/`PATCH`/`DELETE /rooms/{roomId}/transactions` | 405 `NOT_SUPPORTED`, `Allow: GET, POST` (`POST`는 S2) |

## 6. 동작 규칙

### 6.1 순손익 계산 (FR-SET-002)
참여자 `p`의 순손익은 다음과 같다. 합은 **유효 거래**에 대해서만 낸다.

```
balance(p) = Σ amount (payeeId = p인 유효 거래) − Σ amount (payerId = p인 유효 거래)
```

- A→B 100 한 건이면 A는 −100, B는 +100이다(AC-SET-002-1).
- 삭제된 거래는 제외한다(AC-SET-002-3). 수정은 저장된 현재 `amount`로 계산하므로 수정 후 값만 쓴다(AC-SET-002-4).
- 비활성 참여자도 계산에 포함되고 합 0에 기여한다(AC-SET-002-5). 비활성화·재활성화는 값을 바꾸지 않는다(AC-PART-002-2).
- 지급자와 수취자는 서로 다르므로(S2 T-I1) 각 거래는 합에 +amount와 −amount를 한 번씩 기여하고, 따라서 모든 참여자의 합은 0이다(AC-SET-002-2).
- 정수 연산만 쓴다. 금액 상한 999,999,999 × 거래 1,000건이라도 한 참여자의 절댓값이 약 10¹²를 넘지 않으며 64비트 정수로 안전하다(NFR-009). 서버는 합산을 64비트 정수로 하고 부동소수점을 쓰지 않는다.

### 6.2 정렬
- 누적 손익: `balance` 내림차순, 동률은 `order` 오름차순(FR-VIEW-002). 거래가 없는 참여자는 `balance` 0이며 같은 규칙으로 놓인다(+300, +100, 0, −400처럼 0이 가운데에 올 수 있다).
- 거래 목록: §4.1.1.

### 6.3 필터
- 한 번에 참여자 1명만 선택한다. 필터는 목록에만 적용되고 순손익과 예상 정산에는 적용되지 않는다(AC-VIEW-004-7).
- 필터를 바꾸거나 해제하면 이전 커서와 받은 페이지를 버리고 새 조건의 첫 페이지부터 다시 시작한다(AC-VIEW-004-5, -8).
- 필터 대상은 현재 방의 모든 참여자(비활성 포함)다.

## 7. 동시성과 정합성
- 읽기는 S2 §7의 직렬화에 참여하지 않는다. 대신 §3.2의 스냅샷 일관성을 쓴다.
- **쓰기와의 경쟁**: 목록 조회 중에 거래가 생성·수정·삭제되어도 한 응답 안의 항목은 한 스냅샷이다. 연속 조회에서 다음 페이지가 조회 사이에 모두 삭제되면 `transactions`가 짧거나 비고 `nextCursor`가 `null`일 수 있다. 이는 조회 중 변경이 없다는 AC-VIEW-004-1·-004-9의 전제를 벗어난 경쟁이며 중복·누락이 아니다. 연속 조회 사이의 변경은 §4.1.2의 키셋 규칙으로 중복·누락 없이 이어진다. 한 응답 안에서 같은 거래가 두 번 나오지 않는다.
- **순손익 합 0**: 모든 커밋 시점에서 성립한다(V-I2). 한 스냅샷에서 계산하므로 읽기도 항상 합이 0이다. 속성 기반 테스트로 무작위 생성·수정·삭제·동시 요청 뒤 합 0과, 거래 재계산 값과의 일치를 검증한다.
- **생성 순번**: §2.3의 고유·증가는 S2의 방 단위 직렬화와 같은 트랜잭션에서 부여하므로 동시 생성에서도 (`createdAt`, `seq`)가 모두 다르거나 `seq`로 구분된다. 커밋 순서가 `seq` 순서와 같으므로(§2.3) 동시 생성 중에도 어떤 읽기 스냅샷에서 뒤늦게 커밋된 낮은 `seq`가 이미 지난 페이지 경계 위에 나타나는 일이 없다.

## 8. 실시간 이벤트 발생 지점 (스키마는 S5)
S3는 읽기 전용이라 이벤트를 만들지 않는다. S5는 S1·S2·S4가 정한 변경 이벤트를 받은 클라이언트가 §4.1과 §4.2를 다시 조회하도록 설계하며, 필터 선택과 정렬이 갱신 뒤에도 유지되어야 한다(AC-VIEW-005-7)는 요구는 S5가 담당한다. 응답에 필요한 추가 필드(예: 방의 변경 번호)는 기존 필드를 바꾸지 않는 추가만 가능하다.

## 9. 프론트엔드 책임
- **화면 구성**: 한 화면에서 누적 손익 영역과 거래 내역 영역을 구분해 표시한다(AC-VIEW-001-1). 누적 손익 영역에는 거래 항목이 아닌 참여자별 순손익만 보인다(AC-VIEW-001-2). 금액과 손익은 방의 `unit`으로 표시하며 환산하지 않는다(AC-ROOM-003-3, AC-ROOM-001-14).
- **누적 손익**: `GET /rooms/{roomId}/balances`의 순서를 그대로 쓴다(클라이언트가 다시 정렬하지 않는다). 비활성 참여자와 거래가 없는 참여자도 표시한다. 부호와 숫자 서식(천 단위 구분 등)은 OQ-033에서 정한다.
- **거래 내역**: 서버가 준 순서대로 이어 붙인다. 첫 로드에 첫 페이지, 추가 로드에 `nextCursor`로 다음 페이지를 불러온다. `nextCursor`가 `null`이면 더 불러오지 않는다. 추가 로드를 버튼으로 할지 스크롤로 할지는 UI 선택이다(PRD는 방식을 요구하지 않는다). 항목의 `id`로 중복을 방어한다.
- **필터**: 참여자 1명만 선택할 수 있다(비활성 포함). 선택·변경·해제하면 받은 목록과 커서를 버리고 새 조건의 첫 페이지를 요청한다. 필터 선택은 누적 손익 요청에 영향을 주지 않는다.
- **작성자·권한 표시**: 목록의 `authorId`와 방 조회(S1)의 `me.id`, `isHost`로 본인 작성 거래의 수정·삭제 버튼 노출을 정한다. 노출 여부와 무관하게 서버가 권한을 검증한다(S2 §3.1). 작성자 이름을 보이는지는 §12.2 C-2의 결정에 따른다.
- **삭제된 거래**: 목록에 보이지 않는다. 수정은 위치를 바꾸지 않는다.
- 커서 오류(`INVALID_VALUE`)를 받으면 커서를 버리고 첫 페이지부터 다시 불러온다. `message`는 그대로 쓰고 분기는 `code`로 한다.
- 오래된 데이터의 표시 금지, 연결 끊김 처리, 재조회 시점은 S5가 정한다.

## 10. 백엔드 책임
- S1 §3.1 인증, §3 검사 순서(이 Spec의 §3.3), §4의 두 엔드포인트와 비제공 동작을 구현한다.
- §2.3의 생성 순번·생성 시각 부여를 S2의 거래 생성 트랜잭션에 포함한다. 목록 질의는 (방, 생성 시각, 생성 순번) 순서의 인덱스를 쓰도록 한다(Plan).
- 순손익은 64비트 정수로 집계하고 응답은 정수를 그대로 낸다. 클라이언트 값은 신뢰하지 않는다(쿼리의 `participantId`는 이 방의 참여자인지 확인한다).
- 이 Spec의 계약을 다른 저장소 문서에 복제하지 않고 Spec 버전 또는 `ddallang` 커밋으로 참조한다.

### 12.3 자체 점검 (상위 문서와의 충돌)
사용자 요청 5개 점검 결과:
1. **키셋 페이지네이션**: 새 거래는 정렬상 맨 앞이라 이미 받은 페이지 경계를 밀지 않고, 삭제·수정은 위치(값)로 해석하는 커서에 영향이 없다. 커밋 순서 = `seq` 순서이므로 낮은 `seq`가 뒤늦게 경계 위에 나타나지 않는다(§2.3, §7). 중복·누락 없음. 남는 것은 조회 사이에 다음 페이지가 모두 삭제되는 경쟁의 짧은/빈 마지막 페이지(§7)뿐이다.
2. **S2 수정 계약과의 정합**: S2 `PUT`은 `amount`·`reason`·`round`와 `updatedAt`만 바꾸고 `createdAt`·`id`·`authorId`는 불변(S2 T-I3, §4.2)이다. `seq`는 수정·삭제·재전송에서 불변(§2.3.1 3). 정렬·커서 키가 수정으로 변하지 않아 충돌이 없다. 잔여 판단: S2 §2.1 "거래 내부 기록" 표를 완전 목록으로 읽으면 `seq`는 그 표에 없는 필드다. S2는 내부 필드의 추가를 금지하지 않고 노출 필드·API·AC를 바꾸지 않으므로 충돌로 보지 않았다(§13에 위험으로 기록). 또 `createdAt`을 마지막 값 이상으로 올리는 규칙은 서버 시계가 정상이면 S2 §2.1의 "서버 부여 원본 생성 시각"과 같은 값이다.
3. **합 0과 비활성 포함**: §6.1 수식이 모든 유효 거래에 +amount와 −amount를 한 번씩 더하므로 합이 0이며, 비활성 참여자도 모든 참여자 집합에 포함해 계산한다(§4.2). 삭제 제외와 수정 반영은 저장된 현재 값 기준이다. 스냅샷 일관성(§3.2)으로 읽기도 합 0이다.
4. **S3·S4 책임 분리**: S3는 순손익과 목록만, S4는 정산 항목을 맡는다. 순손익 정의는 서버에 하나만 두고 S4는 같은 정의를 쓴다(§1.3).
5. **OQ-033**: 확정하지 않았다(§12.1).

기타 점검:
- FR-VIEW-001~004, FR-SET-002의 AC 25개를 모두 추적표에 연결했다. 약화하거나 바꾼 AC는 없다.
- AC-VIEW-003-6(순번 고유성)은 "OQ-031 해결 전까지 정의하지 않는다"로 PRD가 비워 둔 부분이며 C-1이 채운다. 사용자 승인이 필요하다.
- S2 §1.3과 T-10은 "S3 작성 시 거래 개체 필드 추가가 필요하면 S2 재검토"라고 했다. C-1은 노출 필드를 추가하지 않고 내부 부여 요구만 건다. C-2는 노출 필드 추가 여부를 사용자 결정으로 분리했다.
- S2 §4.4가 `GET`(목록)을 막아 둔 405 표는 S3 확정으로 `GET, POST`가 된다. 이는 S2가 이미 "S3가 목록을 추가하면 `GET, POST`"라고 적어 둔 것이다.
- 정산 항목(FR-SET-003~008)은 S4 담당이며 S3는 순손익만 정의한다.
- 제품 정책 변경, MVP 제외 기능 추가는 없다.

### 12.4 후속 후보 (범위 밖, 기록만)
- 거래 항목의 작성자 닉네임 표시(접속자 이름을 보이는 방법)는 후속 UX 개선 후보다. PRD 범위를 확대하지 않으며 이 Spec은 만들지 않는다. 도입하려면 PRD 개정과 S1·S3 재검토가 필요하다.

## 13. 위험
- **생성 시각의 시계 역행(C-1)**: DB 시각이 되돌아가면 `createdAt`을 마지막 값으로 고정하므로 같은 값이 연속될 수 있고 `seq`가 순서를 가른다. 이 보정이 없으면 (`createdAt`, `seq`) 순서가 삽입 순서와 어긋난다.
- **읽기 시점 차이(C-6)**: 목록과 순손익을 따로 요청하므로 순간적으로 서로 다른 시점의 값을 보일 수 있다. 변경 알림 뒤 두 API를 함께 재조회하면 수렴한다.
- **커서 위조**: 커서는 같은 방·같은 질의 안에서 위치만 바꾼다. 권한 우회나 다른 방 데이터 노출은 없다(§4.1.2).
- **목록 성능**: 방당 거래 1,000건 규모이므로 단순 질의와 인덱스로 충분하다. Plan에서 확인한다.
- **정렬 기준의 복합성**: 클라이언트가 같은 정렬을 재현해 중복을 걸러내지 않도록 서버 순서를 그대로 쓴다(§9).
- **작성자 표시 부재(C-2)**: 이름을 보이지 않으면 사용자가 거래 작성자를 알아보기 어려울 수 있다. 사용자가 PRD 범위 유지를 결정했고 후속 UX 개선 후보로 남겼다.
- **S2 내부 기록 목록 해석(C-1)**: S2 §2.1의 내부 기록 표를 엄격히 완전 목록으로 읽으면 `seq` 추가를 S2 개정으로 볼 여지가 있다. 이 경우 S2 재검수가 필요하다. 이 Spec은 사용자 결정 (a)에 따라 S2 구현의 필수 저장 모델 의존성으로 처리한다(§2.3.1).
