## 4. 실행 순서와 백엔드 의존

### 4.1 실행 순서

```
FE-F1 → F2 → F7 → F5 → F3 → F4 → F6 → F8
   → S1-1 → S1-2                       (REST 전용 화면: 스트림 없음)
   → S5-1 → S5-2 → S5-3                (S5 코어: 방 화면의 선행 조건)
   → S1-3 → S1-4 → S1-5 → S1-6
   → S2-1 → S2-2
   → S3-1 → S3-2
   → S2-3 → S2-4 → S3-3                (S2-3은 거래 행이 있는 S3-2 뒤)
   → S5-4
   → S4-1 → S4-2 → S4-3
   → S5-5 → S4-4                       (S5-5는 정산 영역이 있는 S4-2 뒤)
   → S5-6 (실서버 필요) → FE-I1 (실서버 필요) → FE-Z1
```

- S1(생성·입장) → S2 → S3 → S5 → S4의 의존 순서를 따르되, 방 화면의 데이터 영역은 연결 게이트(S5 §6.5)를 통해서만 보이므로 S5 코어가 S1-3보다 앞선다.
- S2-3(수정·삭제)은 거래 행이 필요해 S3-2 뒤로, S5-5(통합 시험)는 정산 영역이 필요해 S4-2 뒤로 둔다. 이는 각 Task의 "선행" 열(실행 가능 조건)을 따른 결과이며 작성 순서와 다른 지점이다. 위 목록과 `tasks.md`의 수행 순서는 모든 선행을 만족한다.
- 각 묶음은 **그 묶음이 소유한 시험**이 통과하면 끝난다. 다른 Spec의 기능이 있어야 하는 횡단 시험은 `tasks.md`의 "횡단 시험 이관표"가 소유 Task를 정하고, 이관된 시험이 통과하기 전에는 해당 AC를 완료로 세지 않는다.

## 5. 변경 통제와 상위 문서와의 관계

- 이 Plan 자체의 의미 있는 변경(결정 FD-n, Task 소유·선행, 완료 기준)은 재검토를 거친다.

## 8. 검증 전략 (OQ-033 G 적용)

- **AC 매핑**: FE 대상 AC 79행은 `ac-matrix.md`에 있다(Spec §11이 기준). 시험 제목에 `[AC-…]` 태그를 붙이고 `FE-F7`의 검사 스크립트가 "프론트엔드 담당 AC마다 태그 달린 시험이 있는가"를 실패 조건으로 검사한다. 서버 전용 AC는 백엔드 매핑표가 맡는다.
- **시험 종류**:
  - 단위: 포맷 모듈, 클라이언트 검증, SSE 파서(`fast-check`로 조각 나누기 불변·UTF-8 경계), 멱등 키 매니저(가짜 시계), 복사 텍스트, 신원 키 모듈(가짜 Web Locks·저장소 실패).
  - 컴포넌트·훅(Testing Library + MSW): 각 화면의 입력 유지, 오류 코드별 표시, 컨트롤 노출 조건, 포커스 처리.
  - 갱신 코디네이터·연결 제어: 가짜 스트림과 가짜 시계로 §6.3~§6.6 규칙(중복·누락·순서·합치기·실패 복구·재연결 간격·복귀 처리) 전수.
  - 접근성: 화면마다 `vitest-axe` 자동 검사 + 키보드·포커스 시험(OQ-033 D). 색 대비는 토큰 쌍 단위 시험.
  - 정적: `EventSource`·`dangerouslySetInnerHTML`·저장소 직접 접근·콘솔 키 출력 없음(ESLint 제한 규칙과 시험).
- **실서버 연동**(`FE-I1`): 위 R 항목을 실제 백엔드로 확인한다. 백엔드 Task와 `ddallang-server`가 준비된 뒤에만 가능하다. 준비되지 않으면 실행하지 못했다고 보고하며 해당 AC를 완료로 세지 않는다.
- **화면 반영 지연**(`FE-S5-6`): 자동 하네스(Vitest 별도 프로젝트, jsdom에 렌더링한 FE 클라이언트 10개를 실서버에 연결, 릴리스 전 실행, 매 커밋 게이트 아님)다. 브라우저 페인트 시간은 포함되지 않는 한계를 보고한다. 접속자 10명 방을 두고 S5 §6.7의 변경 종류·횟수·초기 상태로 T0부터 화면 표시까지 잰다. AC-VIEW-005-8은 백엔드 측정(BE-S5-4, BE-S4-7)과 이 측정이 **모두** 통과해야 완료다.
- **호환성**: OQ-033 G에 따라 실브라우저 호환성은 수동 점검 표다. 대상은 Chrome·Edge·Firefox·Safari(모바일 포함)의 최신과 직전 주요 버전이고 `FE-Z1`이 결과를 채운다. 점검하지 못한 칸은 숨기지 않고 보고한다.
- **실행하지 못한 검증은 숨기지 않는다**(예: 실서버·측정 도구·특정 브라우저가 없었던 경우).
- **G4 증거**: 타입 검사·린트·빌드·전체 시험 결과, AC 태그 검사 결과, 접근성 자동 검사 결과, 연동 점검 결과, 지연 측정 결과, 수동 점검 표, 남은 위험을 `FE-Z1`이 묶는다.

## 9. G3 검수에서 확인받고 싶은 점

1. 모든 화면 데이터가 연결 게이트와 한 번에 반영하는 스냅샷(FD-3)을 거쳐, S5 §6.3~6.6·S4 §6.4의 규칙(5개 조회 모두 성공 뒤 반영, 최신 주기만, 방 상태·`kind` 일치)을 어기지 않는가.
2. 멱등 키 수명·시각 보정·24시간 자동 재전송 금지·결과 불명 처리(FE-F8)가 S2 §9·S4 §9와 어긋나지 않는가.
3. 신원 키 저장·Web Locks 배타 구간·생성 대기 항목(FE-F3)이 S1 §3.1과 어긋나지 않는가.
4. Task 사이 의존·공통 기반 소유가 중복·누락 없이 정의되었는가. S5 코어를 S1 방 화면 앞에 둔 순서가 타당한가.
5. `ac-matrix.md`가 FE 담당 AC(FE 34 + BE+FE 45)를 빠뜨리지 않았는가. 모의로 끝내는 AC와 실서버가 필요한 AC의 구분이 맞는가.
6. §7의 문구와 구역 구성이 OQ-033 B·C·E와 Spec이 고정한 문자열에 맞는가.
7. 백엔드 Plan이 제공한다고 한 계약(§4.3)을 프론트엔드가 그대로 기대하는가.

## 10. 알려진 한계

- 정적 문서 검토 대상이다. 구현·시험은 아직 없다.
- 시각 디자인 원본이 없다(U-1). 화면 구성과 문구는 제안이다.
- 배포·호스팅은 정해지지 않았다(FD-17).
- 실서버 연동은 `ddallang-server` 생성과 백엔드 구현이 끝나야 가능하다.
