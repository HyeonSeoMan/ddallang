## 1. 제품 목적과 MVP 범위

### 1.1 목적
딸랑은 오프라인 게임 참여자 사이의 지급 의무를 기록하고, 실시간 순손익과 게임 종료 후 최종 정산을 계산하는 웹 서비스다. (POL §1)

### 1.2 하지 않는 일
게임 점수를 자동 산출하지 않는다. 실제 송금·결제를 처리하지 않고 송금 완료 여부도 관리하지 않는다. (POL §1)

### 1.3 MVP 포함 범위 (POL §2)
1. 방 생성 및 초대 링크 입장
2. 참여자 등록 및 기본 관리
3. 단건 거래 등록·수정·삭제
4. 실시간 누적 손익 및 거래 목록
5. 방장에 의한 게임 종료, 정산 계산·조회·텍스트 복사
6. 기본 서버 권한 검사, 데이터 정합성, 중복 요청 방지, 연결 오류 처리

## 2. 용어

| 용어 | 정의 |
| --- | --- |
| 방 (Room) | 하나의 게임 정산 단위. 정산 단위(원·점수·칩 등)를 가진다. |
| RoomMember (접속자) | 초대 링크로 방에 입장한 익명 접속 주체. 거래 작성자·방장이 될 수 있다. |
| Participant (참여자) | 손익이 집계되는 게임 참여자. 접속하지 않아도 존재한다. |
| 방장 | 현재 방장 권한을 가진 RoomMember. 정책상 "현재 방장"이 항상 특정된다. |
| 거래 | 지급자(Participant)가 수취자(Participant)에게 금액을 지급할 의무를 기록한 단건 기록. |
| 게임 상태 | `진행 중` 또는 `종료됨`. 이 두 상태 외의 상태는 MVP에 없다. |
| 순손익 | 참여자별로 (수취한 유효 거래 금액 합) − (지급한 유효 거래 금액 합). 삭제된 거래는 제외한다. |

## 3. 사용자 역할

| 역할 | 설명 | 주요 권한 |
| --- | --- | --- |
| 방장 | 현재 방장인 RoomMember | 참여자 추가·비활성화·재활성화, 모든 거래 수정·삭제, 게임 종료 |
| 일반 접속자 | 방장이 아닌 RoomMember | 거래 등록, 본인이 작성한 거래의 수정·삭제, 조회 |
| 참여자 | 게임 참여자(Participant). 접속 여부와 무관 | 거래의 지급자/수취자가 됨. 별도 로그인 권한 없음 |

방장 권한은 초대 링크 자체로 부여되지 않는다. (POL-ROOM-006)

## 4. 핵심 사용자 시나리오

- **S1 방 시작**: 방장 후보가 방 이름과 정산 단위를 정해 방을 만들고 초대 링크를 공유한다. 다른 사람은 링크와 닉네임만으로 입장한다. (FR-ROOM-001~003, 006)
- **S2 참여자 구성**: 방장이 게임 전에 참여자를 등록하고, 진행 중 추가하거나 이탈한 참여자를 비활성화한다. (FR-PART-001~003)
- **S3 거래 기록**: 접속자가 "A가 B에게 N"을 기록한다. 잘못 기록하면 작성자 또는 방장이 수정·삭제한다. (FR-TXN-001~008)
- **S4 실시간 확인**: 모든 접속자가 순손익 순위와 거래 목록을 보고, 참여자별 필터로 거래를 좁혀 본다. (FR-VIEW-001~005)
- **S5 종료와 정산**: 방장이 게임을 종료하고, 정산 결과를 조회해 텍스트로 복사해 공유한다. (FR-SET-001~006)
- **S6 연결 끊김**: 네트워크가 끊기면 오래된 데이터를 최신처럼 보이지 않게 하고, 복구 시 서버 상태를 다시 조회한다. (FR-SYS-001~002)
- **S7 브라우저 재접속**: 같은 브라우저로 다시 열면 이전 신원을 복원한다. 브라우저 식별자를 잃으면 새 접속자로 입장한다. (FR-ROOM-005)

## 5. 기능 요구사항

표기: 각 FR은 근거 `POL` ID와 수용 기준(AC)을 가진다. AC는 Given/When/Then의 간략형이다. "서버가 거부한다"는 클라이언트 검증과 무관하게 서버 API가 거부함을 뜻한다.

### 5.1 방과 익명 신원

#### FR-ROOM-001 방 생성
- POL: POL-ROOM-002, (범위 §2 "방 생성")
- 요구사항: 사용자는 방 이름과 정산 단위를 입력해 방을 생성한다. 생성된 방은 `진행 중` 상태이며 초대 링크를 가진다. 생성 직후 방장은 정확히 1명이다. 방 이름의 허용 규칙(OQ-006)과 최초 방장이 지정되는 방식(OQ-007)은 미결정이다.
- AC:
  - AC-ROOM-001-1: 정산 단위와 방 이름을 입력해 생성하면 `진행 중` 상태의 방과 초대 링크가 만들어진다.
  - AC-ROOM-001-2: 정산 단위가 비어 있으면 방이 생성되지 않고 오류가 표시된다.
  - AC-ROOM-001-3: 생성 직후 해당 방의 방장 수는 1이다.

#### FR-ROOM-002 초대 링크 입장
- POL: POL-ROOM-001
- 요구사항: 회원가입 없이 닉네임과 초대 링크만으로 방에 입장한다. 방 코드 입력 방식과 최근 방 목록은 제공하지 않는다. 종료된 방에 대한 입장 허용 여부는 OQ-005에서 정한다.
- AC:
  - AC-ROOM-002-1: 유효한 초대 링크와 유효한 닉네임으로 계정 생성 없이 입장하면 RoomMember가 생성된다.
  - AC-ROOM-002-2: 방 코드를 입력해 입장하는 화면·API가 존재하지 않는다.
  - AC-ROOM-002-3: 최근 방 목록 화면이 존재하지 않는다.
  - AC-ROOM-002-4: 존재하지 않거나 잘못된 초대 링크로는 입장되지 않고 오류가 표시된다.

#### FR-ROOM-003 정산 단위 불변
- POL: POL-ROOM-002
- 요구사항: 정산 단위는 방 생성 시 정해지며 이후 변경할 수 없다. 단위 간 환산 기능은 없다.
- AC:
  - AC-ROOM-003-1: 방 생성 후 정산 단위를 변경하는 UI가 없다.
  - AC-ROOM-003-2: 정산 단위 변경을 요구하는 서버 요청은 방장 여부와 게임 상태와 무관하게 거부된다.
  - AC-ROOM-003-3: 금액·정산 결과의 단위는 방의 정산 단위로만 표시되며 환산 값은 표시되지 않는다.

#### FR-ROOM-004 RoomMember와 Participant 분리
- POL: POL-ROOM-003
- 요구사항: RoomMember와 Participant는 별개 개념이다. 참여자가 아닌 접속자도 거래를 기록할 수 있고, 접속하지 않은 참여자도 존재할 수 있다. 둘의 연결·해제 기능이 MVP에 필요한지는 OQ-001에서 정한다.
- AC:
  - AC-ROOM-004-1: 어떤 Participant와도 연결되지 않은 RoomMember가 거래를 등록할 수 있다.
  - AC-ROOM-004-2: 접속한 RoomMember가 없는 Participant가 거래의 지급자·수취자가 될 수 있다.
  - AC-ROOM-004-3: 입장(RoomMember 생성)만으로 Participant가 자동 생성되지 않는다.
  - AC-ROOM-004-4: Participant 등록만으로 RoomMember가 자동 생성되지 않는다.

#### FR-ROOM-005 브라우저 기반 신원 복원
- POL: POL-ROOM-004
- 요구사항: 동일 브라우저에서 같은 방에 재접속하면 기존 RoomMember 신원을 복원한다. 브라우저 식별자를 잃으면 새 RoomMember로 입장하며 기존 작성자 신원과 방장 권한을 복구하지 않는다.
- AC:
  - AC-ROOM-005-1: 입장한 브라우저에서 같은 초대 링크를 다시 열면 닉네임 재입력 없이 같은 RoomMember로 복원된다.
  - AC-ROOM-005-2: 복원된 RoomMember는 이전에 작성한 거래를 수정·삭제할 수 있다.
  - AC-ROOM-005-3: 브라우저 식별자가 삭제된 상태에서 입장하면 새 RoomMember가 되고, 이전 거래의 작성자로 인식되지 않는다.
  - AC-ROOM-005-4: 브라우저 식별자를 잃은 이전 방장은 새 RoomMember로 입장해도 방장 권한이 없다.
  - AC-ROOM-005-5: 다른 브라우저·기기에서 같은 링크로 입장하면 새 RoomMember가 된다.
  - AC-ROOM-005-6: 브라우저 식별자를 유지한 방장이 같은 브라우저로 재접속하면 같은 RoomMember로 복원되고 방장 권한을 그대로 가진다.

#### FR-ROOM-006 닉네임 규칙
- POL: POL-ROOM-005
- 요구사항: RoomMember 닉네임과 Participant 닉네임은 각각 같은 방 안에서 대소문자 구분 없이 고유해야 한다. 정책에 비활성 참여자 예외가 없으므로 Participant 고유성은 활성·비활성 참여자를 모두 포함한다. 길이는 1~12자이며 한글·영문·숫자·중간 공백만 허용한다. 앞뒤 공백, 특수문자, 이모지는 거부한다. 등록 후 변경할 수 없다. 연속 공백 허용 여부와 글자 수 계산 방식은 미결정이다(OQ-008). 비활성 참여자 닉네임의 재사용 허용은 정책 변경이 필요한 사항이며 OQ-010에서 확인한다.
- AC:
  - AC-ROOM-006-1: 길이 1과 12의 닉네임은 허용되고, 길이 0과 13은 거부된다.
  - AC-ROOM-006-2: 한글·영문·숫자로 구성된 닉네임은 허용된다. 단어 사이에 공백 하나를 둔 닉네임("Kim Min")은 허용된다.
  - AC-ROOM-006-3: 앞 또는 뒤에 공백이 있는 닉네임은 거부된다.
  - AC-ROOM-006-4: 특수문자(예: `!`, `_`, `-`)와 이모지가 포함된 닉네임은 거부된다.
  - AC-ROOM-006-5: 같은 방에서 "Kim"이 사용 중이면 "kim"과 "KIM"은 RoomMember 닉네임으로 거부된다. Participant 닉네임도 동일하다.
  - AC-ROOM-006-6: RoomMember 닉네임 "Kim"과 Participant 닉네임 "Kim"은 같은 방에서 공존할 수 있다.
  - AC-ROOM-006-10: 비활성 참여자의 닉네임과 대소문자 구분 없이 같은 닉네임으로 새 참여자를 등록하면 거부된다.
  - AC-ROOM-006-7: 서로 다른 방에서는 같은 닉네임을 사용할 수 있다.
  - AC-ROOM-006-8: 등록된 RoomMember·Participant 닉네임을 변경하는 UI가 없고, 변경 요청은 서버가 거부한다.
  - AC-ROOM-006-9: 위 규칙 위반은 클라이언트 검증을 우회한 요청에서도 서버가 거부한다.

#### FR-ROOM-007 방장 권한 경계
- POL: POL-ROOM-006, POL-PART-001, POL-PART-002, POL-TXN-004, POL-SET-001, (§9 연기 항목 4)
- 요구사항: 현재 방장은 게임을 종료할 수 있다. 방장 전용 동작의 목록은 참여자 추가·비활성화·재활성화(POL-PART-001·002), 타인 거래 수정·삭제(POL-TXN-004), 게임 종료(POL-ROOM-006, POL-SET-001)다. 방장 권한은 초대 링크 자체로 부여되지 않는다. 방장 권한 이전·강제 퇴장·초대 링크 재발급은 MVP 범위가 아니다.
- AC:
  - AC-ROOM-007-1: 초대 링크로 새로 입장해 생성된 RoomMember는 방장이 아니다(최초 방장은 OQ-007에 따른 방식으로만 지정된다). 방장이 복원 가능한 재접속을 한 경우는 AC-ROOM-005-6을 따른다.
  - AC-ROOM-007-2: 방장 전용 동작(참여자 추가·비활성화·재활성화, 타인 거래 수정·삭제, 게임 종료)을 비방장 RoomMember가 요청하면 서버가 거부한다.
  - AC-ROOM-007-3: 방장 이전, 강제 퇴장, 초대 링크 재발급 기능과 API가 존재하지 않는다.

### 5.2 참여자

#### FR-PART-001 참여자 등록
- POL: POL-PART-001
- 요구사항: 방장은 참여자를 게임 시작 전에 미리 등록하고, 게임 진행 중에도 추가할 수 있다. 닉네임은 FR-ROOM-006을 따른다.
- AC:
  - AC-PART-001-1: 방장이 유효한 닉네임으로 참여자를 등록하면 참여자가 `활성` 상태로 생성된다.
  - AC-PART-001-2: 게임 `진행 중`에도 방장이 참여자를 추가할 수 있다.
  - AC-PART-001-3: 비방장 RoomMember의 참여자 추가 요청은 서버가 거부한다.
  - AC-PART-001-4: 참여자에게 등록 순서가 부여되고 이후 변하지 않는다(정렬 기준: FR-VIEW-002, FR-SET-003, FR-SET-004).

#### FR-PART-002 참여자 비활성화·재활성화
- POL: POL-PART-002
- 요구사항: 방장은 진행 중 참여자를 비활성화·재활성화할 수 있다. 비활성 참여자의 과거 거래와 손익은 보존되고, 신규 일반 거래의 당사자로는 선택할 수 없다. 기존 거래 수정 시 비활성 참여자가 포함된 경우의 동작은 OQ-011에서 정한다.
- AC:
  - AC-PART-002-1: 방장이 활성 참여자를 비활성화하면 상태가 `비활성`이 되고, 재활성화하면 `활성`으로 돌아간다.
  - AC-PART-002-2: 비활성화 전후로 해당 참여자의 과거 거래와 누적 손익 값이 변하지 않는다.
  - AC-PART-002-3: 신규 거래 등록 시 비활성 참여자는 지급자·수취자로 선택할 수 없고, 서버도 이를 지정한 신규 거래 요청을 거부한다.
  - AC-PART-002-4: 재활성화된 참여자는 다시 신규 거래의 당사자로 선택할 수 있다.
  - AC-PART-002-5: 비방장의 비활성화·재활성화 요청은 서버가 거부한다.
  - AC-PART-002-6: 비활성 참여자의 손익은 순손익 목록과 정산 계산에서 제외되지 않는다.

#### FR-PART-003 참여자 이름 변경·기록 이전 금지
- POL: POL-PART-003
- 요구사항: 참여자 이름 직접 변경과 기록의 다른 참여자 이전은 제공하지 않는다. 오입력은 기존 참여자를 비활성화하고 새 참여자를 등록하는 방식으로 처리한다.
- AC:
  - AC-PART-003-1: 참여자 이름 변경 UI와 API가 없다.
  - AC-PART-003-2: 거래의 지급자·수취자를 다른 참여자로 일괄 이전하는 기능이 없다.
  - AC-PART-003-3: 오입력 참여자를 비활성화한 뒤 새 참여자를 등록하는 흐름이 가능하다.

#### FR-PART-004 종료 후 참여자 변경 금지
- POL: POL-PART-004
- 요구사항: 게임 종료 후에는 참여자 추가와 활성 상태 변경이 불가능하다.
- AC:
  - AC-PART-004-1: 종료된 게임에서 방장이 참여자 추가를 요청하면 서버가 거부한다.
  - AC-PART-004-2: 종료된 게임에서 방장이 참여자 비활성화·재활성화를 요청하면 서버가 거부한다.
  - AC-PART-004-3: 종료된 게임에서는 관련 UI 컨트롤이 비활성화되거나 숨겨진다.

### 5.3 단건 거래

#### FR-TXN-001 거래 데이터
- POL: POL-TXN-001
- 요구사항: 거래는 지급자, 수취자, 금액, 선택적 사유와 라운드를 가진다. 사유와 라운드의 형식·길이·필수 여부는 OQ-009에서 정한다. 수정 가능한 필드 범위는 OQ-012에서 정한다.
- AC:
  - AC-TXN-001-1: 유효한 지급자, 수취자, 금액을 지정하면 거래가 등록된다. [결정 대기: 이 세 값 외에 라운드가 필수 입력인지는 OQ-009 해결 전까지 확정되지 않는다. 라운드가 필수로 결정되면 이 AC에 라운드를 추가한다.]
  - AC-TXN-001-2: 사유 없이도 거래가 등록된다(정책: 선택적 사유). [결정 대기: 라운드의 필수 여부는 OQ-009 해결 전까지 확정되지 않으며, 이 AC는 라운드에 대해 아무것도 단정하지 않는다.]
  - AC-TXN-001-5: 한 번의 요청·입력으로 여러 거래를 일괄 등록하는 기능이 없다(연기 항목 1).
  - AC-TXN-001-3: 지급자, 수취자, 금액 중 하나라도 없으면 거래가 등록되지 않는다.
  - AC-TXN-001-4: 거래는 작성자(RoomMember)와 원본 생성 시각을 기록한다.

#### FR-TXN-002 거래 값 검증
- POL: POL-TXN-002
- 요구사항: 금액은 0보다 큰 정수만 허용한다. 지급자와 수취자가 같은 Participant ID인 거래는 금지한다.
- AC:
  - AC-TXN-002-1: 금액 1은 허용된다.
  - AC-TXN-002-2: 금액 0, 음수, 소수(예: 1.5), 숫자가 아닌 값은 거부된다.
  - AC-TXN-002-3: 지급자와 수취자가 동일 Participant ID이면 거부된다. 이는 서로 다른 참여자가 같은 이름을 쓸 수 없다는 FR-ROOM-006과 별개로 ID 기준이다.
  - AC-TXN-002-4: 위 위반은 등록·수정 모두에서 서버가 거부한다.
  - AC-TXN-002-5: 금액 상한은 정해지지 않았다(OQ-004, OQ-009). 서버는 처리 불가능한 크기의 값을 오류로 거부하고 데이터를 손상시키지 않는다.

#### FR-TXN-003 거래 등록 권한
- POL: POL-TXN-003
- 요구사항: 방에 입장한 RoomMember는 게임 진행 중 단건 거래를 등록할 수 있다.
- AC:
  - AC-TXN-003-1: 방장이 아닌 RoomMember도 진행 중 게임에서 거래를 등록할 수 있다.
  - AC-TXN-003-2: 방에 입장하지 않은 주체의 거래 등록 요청은 서버가 거부한다.
  - AC-TXN-003-3: 등록된 거래의 작성자는 요청한 RoomMember로 서버가 기록한다. 요청 본문의 작성자 값은 신뢰하지 않는다.

#### FR-TXN-004 거래 수정·삭제 권한
- POL: POL-TXN-004
- 요구사항: 거래의 수정·삭제는 해당 거래의 작성자 또는 현재 방장만 할 수 있으며, 서버가 권한을 검증한다.
- AC:
  - AC-TXN-004-1: 작성자는 자신의 거래를 수정·삭제할 수 있다.
  - AC-TXN-004-2: 현재 방장은 타인이 작성한 거래를 수정·삭제할 수 있다.
  - AC-TXN-004-3: 작성자도 방장도 아닌 RoomMember의 수정·삭제 요청은 서버가 거부한다.
  - AC-TXN-004-4: 화면의 버튼 노출 여부와 무관하게 서버가 요청 시점에 권한을 검증한다.

#### FR-TXN-005 수정·삭제 동작
- POL: POL-TXN-005
- 요구사항: 수정은 별도 확인 없이 저장한다. 삭제는 확인 절차를 거치며, 삭제된 거래는 손익 집계에서 제외하되 최소한의 원본·작성자 기록은 보존한다. 삭제된 거래를 목록에 표시할지는 OQ-013에서 정한다.
- AC:
  - AC-TXN-005-1: 수정 시 확인 대화상자 없이 저장 동작으로 곧바로 반영된다.
  - AC-TXN-005-2: 삭제 시 확인 절차가 있고, 확인 전에는 거래가 삭제되지 않는다. 확인을 취소하면 거래는 그대로다.
  - AC-TXN-005-3: 삭제 확정 후 모든 참여자의 순손익에서 해당 거래 금액이 제외된다.
  - AC-TXN-005-4: 삭제 후에도 서버에 원본 내용과 작성자 식별 정보가 보존된다. 이 기록의 조회 화면과 변경 이력 조회 기능은 MVP에 없다(연기 항목 5).
  - AC-TXN-005-5: 수정으로 변경된 값은 순손익에 즉시 정확히 반영된다. [결정 대기: 당사자(지급자·수취자) 변경이 가능한지는 OQ-012 해결 전까지 확정되지 않는다. 가능한 경우에 한해 당사자 변경도 동일하게 반영된다.]

#### FR-TXN-006 동시 수정과 삭제된 거래
- POL: POL-TXN-006
- 요구사항: 같은 거래에 대한 동시 수정은 서버에서 마지막으로 성공한 저장을 최종값으로 한다. 삭제된 거래에 대한 수정은 거부한다.
- AC:
  - AC-TXN-006-1: 두 사용자가 같은 거래를 거의 동시에 수정하면, 서버에서 나중에 성공한 저장 값이 최종값이 된다.
  - AC-TXN-006-2: 삭제된 거래에 대한 수정 요청은 서버가 거부하고 오류를 사용자에게 알린다.
  - AC-TXN-006-3: 동시 수정 후에도 순손익 합계는 0이다.
  - AC-TXN-006-4: 이미 삭제된 거래의 재삭제 요청의 처리는 정책에 정의되어 있지 않다(OQ-014). 서버는 오류 또는 무변경으로 응답하며 순손익은 변하지 않는다.

#### FR-TXN-007 중복 제출 방지
- POL: POL-TXN-007
- 요구사항: 저장 중에는 중복 제출을 방지하고, 서버는 동일 요청 ID로 거래가 중복 생성되지 않게 한다. 내용이 같은 서로 다른 거래는 허용한다.
- AC:
  - AC-TXN-007-1: 저장 요청이 진행 중인 동안 저장 컨트롤이 비활성화되어 두 번째 제출이 발생하지 않는다.
  - AC-TXN-007-2: 동일 요청 ID로 생성 요청이 두 번 이상 도달해도 거래는 정확히 1건만 생성된다.
  - AC-TXN-007-3: 지급자·수취자·금액·사유·라운드가 모두 같아도 요청 ID가 다른 두 거래는 별개의 거래로 모두 저장된다.
  - AC-TXN-007-4: 동일 요청 ID의 재요청에는 최초 처리 결과가 반환되거나 중복이 무시되고, 오류로 인해 사용자가 성공 거래를 실패로 오인하지 않는다.
  - AC-TXN-007-5: 수정·삭제 요청의 요청 ID 정책은 정의되어 있지 않다(OQ-015).
  - AC-TXN-007-6: 서버가 거래를 저장했으나 응답이 클라이언트에 도달하지 못한 경우, 사용자가 화면에 유지된 같은 입력을 수동 재시도해도 거래는 1건만 존재한다(재시도는 최초 제출과 같은 요청 ID를 사용한다는 해석은 OQ-026에서 확인).
  - AC-TXN-007-7: 사용자가 새로 작성해 제출한 내용이 같은 거래는 새 요청 ID를 사용하므로 별개의 거래로 저장된다(AC-TXN-007-3).

#### FR-TXN-008 저장 실패 처리
- POL: POL-TXN-008
- 요구사항: 저장 실패 시 성공한 것처럼 표시하지 않는다. 입력값은 현재 화면에 유지되며 사용자가 수동으로 재시도한다.
- AC:
  - AC-TXN-008-1: 서버 오류·네트워크 오류로 저장이 실패하면 실패 메시지가 표시되고 성공 표시는 나타나지 않는다.
  - AC-TXN-008-2: 실패 후 입력 필드 값이 유지된다.
  - AC-TXN-008-3: 시스템은 실패한 저장을 자동으로 재전송하지 않는다. 사용자가 다시 제출해야 한다.
  - AC-TXN-008-4: 서버가 확정적으로 거부한 저장은 순손익과 거래 목록에 반영되지 않는다.
  - AC-TXN-008-5: 응답을 받지 못해 저장 여부를 알 수 없는 경우, 시스템은 성공으로 표시하지 않고 결과가 확인되지 않았음을 알린다. 재조회 후 해당 거래가 실제로 저장되어 있으면 목록에 나타난다. 시스템은 자동 재제출하지 않는다.

#### FR-TXN-009 종료 후 일반 거래 잠금
- POL: POL-TXN-009
- 요구사항: 게임 종료 후에는 일반 거래의 추가·수정·삭제가 불가능하며, 서버가 요청 처리 시점의 게임 상태를 검사한다.
- AC:
  - AC-TXN-009-1: 종료된 게임에서 거래 추가·수정·삭제 요청은 서버가 거부한다. 방장도 예외가 아니다.
  - AC-TXN-009-2: 종료 직전에 시작된 요청이 종료 이후에 처리되면 처리 시점의 상태 기준으로 거부된다.
  - AC-TXN-009-4: 종료 후 정정 거래를 등록하는 별도 기능이 없다(연기 항목 3).
  - AC-TXN-009-3: 종료된 게임에서는 거래 입력·수정·삭제 UI가 비활성화되거나 숨겨진다.

### 5.4 거래 목록과 실시간 손익

#### FR-VIEW-001 누적 손익과 거래 내역 구분
- POL: POL-VIEW-001
- 요구사항: '누적 손익'과 '거래 내역'을 구분해 제공한다.
- AC:
  - AC-VIEW-001-1: 한 화면 안에서 누적 손익 영역과 거래 내역 영역이 구분되어 표시된다.
  - AC-VIEW-001-2: 누적 손익 영역에는 거래 항목 목록이 아닌 참여자별 순손익이 표시된다.

#### FR-VIEW-002 순손익 정렬
- POL: POL-VIEW-002
- 요구사항: 참여자별 순손익은 내림차순으로 표시하고, 동률이면 참여자 등록 순서를 따른다.
- AC:
  - AC-VIEW-002-1: 순손익이 +300, +100, -400인 세 참여자는 +300, +100, -400 순으로 표시된다.
  - AC-VIEW-002-2: 순손익이 같은 참여자들은 등록이 먼저인 참여자가 앞에 표시된다.
  - AC-VIEW-002-3: 거래가 없는 참여자(순손익 0)도 목록에 표시되고, 0 위치에 정렬 규칙대로 놓인다.

#### FR-VIEW-003 거래 목록 정렬
- POL: POL-VIEW-003
- 요구사항: 거래 목록은 원본 생성 시각의 내림차순이다. 수정은 목록 위치를 바꾸지 않는다.
- AC:
  - AC-VIEW-003-1: 나중에 등록한 거래가 먼저 등록한 거래보다 위에 표시된다.
  - AC-VIEW-003-2: 거래를 수정해도 목록 순서가 바뀌지 않는다.
  - AC-VIEW-003-3: 원본 생성 시각이 같은 거래의 순서는 정책에 정의되어 있지 않다(OQ-016). 구현은 안정적인 정렬을 보장해야 하며 페이지 사이에 중복·누락이 생기지 않아야 한다.

#### FR-VIEW-004 목록 페이지 단위와 참여자 필터
- POL: POL-VIEW-004
- 요구사항: 거래 목록은 20건 단위로 불러오고, 참여자 1명을 기준으로 한 필터를 제공한다. 필터는 해당 참여자가 지급자 또는 수취자인 거래를 포함한다.
- AC:
  - AC-VIEW-004-1: 거래가 45건이면 첫 로드에 20건, 이후 추가 로드에 20건, 다시 5건이 불러와진다.
  - AC-VIEW-004-2: 참여자 A를 필터로 선택하면 A가 지급자인 거래와 A가 수취자인 거래가 모두 표시되고, A가 관여하지 않은 거래는 표시되지 않는다.
  - AC-VIEW-004-3: 필터는 한 번에 참여자 1명만 선택할 수 있다.
  - AC-VIEW-004-4: 필터 적용 상태에서도 20건 단위 로드가 동작한다.
  - AC-VIEW-004-5: 필터를 해제하면 전체 거래 목록으로 돌아간다.
  - AC-VIEW-004-6: 비활성 참여자도 필터 대상으로 선택할 수 있다(과거 거래 보존, FR-PART-002). 이는 정책에서 명시적으로 금지되지 않은 해석이며 검수 대상이다.
  - AC-VIEW-004-7: 필터 중에도 누적 손익 영역의 값은 필터와 무관하게 전체 기준이다(FR-VIEW-001의 구분). 이 해석은 OQ-017에서 확인한다.

#### FR-VIEW-005 실시간 반영
- POL: POL-VIEW-005
- 요구사항: 거래 변경(등록·수정·삭제)은 다른 접속자의 손익과 목록에 실시간으로 반영된다. 변경 토스트는 필수가 아니다. 참여자 변경과 게임 종료의 실시간 전파는 OQ-018에서 정한다. 실시간 반영 지연 목표는 OQ-019에서 정한다.
- AC:
  - AC-VIEW-005-1: 접속자 A가 거래를 등록하면 접속 중인 B의 순손익과 거래 목록이 새로 고침 없이 갱신된다.
  - AC-VIEW-005-2: 수정과 삭제도 동일하게 다른 접속자에게 반영된다.
  - AC-VIEW-005-3: 변경 알림 토스트가 없어도 요구사항을 충족한다.
  - AC-VIEW-005-4: 실시간 갱신이 현재 필터와 페이지 상태를 깨뜨리지 않고 정렬 규칙(FR-VIEW-002, FR-VIEW-003)을 유지한다.

### 5.5 게임 종료와 정산

#### FR-SET-001 게임 종료
- POL: POL-SET-001
- 요구사항: 방장만 게임을 수동으로 종료할 수 있다. 종료 전 확인 절차를 거치며, 종료 후 일반 거래를 잠근다. 자동 종료와 재개는 MVP 범위가 아니다.
- AC:
  - AC-SET-001-1: 방장이 종료를 요청하면 확인 절차가 표시되고, 확인 후에만 게임이 `종료됨`이 된다. 확인 취소 시 상태가 바뀌지 않는다.
  - AC-SET-001-2: 비방장의 종료 요청은 서버가 거부한다.
  - AC-SET-001-3: 종료 후 일반 거래의 추가·수정·삭제는 FR-TXN-009에 따라 거부된다.
  - AC-SET-001-4: 시간 경과나 비활동으로 게임이 자동 종료되지 않는다.
  - AC-SET-001-5: `종료됨` 게임을 `진행 중`으로 되돌리는 기능이 없다.
  - AC-SET-001-7: 시간 경과에 따른 방 접근 만료와 데이터 자동 삭제 기능이 없다(연기 항목 6). 방 데이터 보관·삭제 운영은 OQ-003에서 정한다.
  - AC-SET-001-6: 이미 종료된 게임에 대한 종료 재요청의 처리는 정의되어 있지 않다(OQ-020). 게임 상태와 정산 결과는 변하지 않는다.

#### FR-SET-002 순손익 계산
- POL: POL-SET-002
- 요구사항: 유효한 각 거래에 대해 지급자의 순손익을 차감하고 수취자의 순손익을 가산한다. 모든 참여자의 순손익 합계는 0이어야 한다.
- AC:
  - AC-SET-002-1: A→B 100 거래 한 건이면 A는 −100, B는 +100이다.
  - AC-SET-002-2: 여러 거래 후 참여자 순손익의 합이 항상 0이다.
  - AC-SET-002-3: 삭제된 거래는 계산에서 제외된다.
  - AC-SET-002-4: 수정된 거래는 수정 후 값으로만 계산된다.

#### FR-SET-003 정산 매칭
- POL: POL-SET-003
- 요구사항: 순채무자(순손익 < 0)와 순채권자(순손익 > 0)를 각각 잔액이 큰 순서(절댓값 기준)로 탐욕 매칭한다. 동률이면 참여자 등록 순서를 따른다. 전역 최소 송금 횟수는 보장하지 않는다. 매 단계 남은 잔액으로 순위를 다시 정하는지, 처음 정렬한 순서를 유지하는지는 정책이 명시하지 않아 OQ-025로 남긴다.
- AC:
  - AC-SET-003-1: 채무자 A(−300), B(−100), 채권자 C(+250), D(+150)이면 정산 항목은 A→C 250, A→D 50, B→D 100이다. 이 예시는 "처음 정렬한 순서로 진행"과 "매 단계 남은 잔액으로 다시 순위 결정" 두 해석에서 결과가 같도록 고른 예시다. 두 해석에서 결과가 달라지는 입력의 기대값은 OQ-025 해결 전까지 정의하지 않는다.
  - AC-SET-003-2: 채무자 또는 채권자의 잔액이 같으면 등록 순서가 빠른 참여자가 먼저 매칭된다.
  - AC-SET-003-3: 정산 항목의 합계로 모든 순손익이 0이 된다.
  - AC-SET-003-4: 순손익이 0인 참여자는 정산 항목에 나타나지 않는다.
  - AC-SET-003-5: 위 알고리즘 결과가 송금 횟수 최소가 아니어도 결함으로 보지 않는다.
  - AC-SET-003-6: 동일한 거래 집합은 항상 동일한 정산 결과를 만든다(결정적).

#### FR-SET-004 정산 항목 정렬
- POL: POL-SET-004
- 요구사항: 정산 항목은 금액 내림차순으로 표시하고, 동률은 참여자 등록 순서를 따른다. 동률 비교 대상이 되는 참여자(지급자·수취자)의 우선순위는 OQ-021에서 정한다.
- AC:
  - AC-SET-004-1: 정산 항목이 250, 100, 50이면 그 순서로 표시된다.
  - AC-SET-004-2: 금액이 같은 항목은 등록 순서 규칙으로 일관되게 정렬된다(구체 기준은 OQ-021).

#### FR-SET-005 정산 조회와 텍스트 복사
- POL: POL-SET-005
- 요구사항: 정산 결과를 조회하고 일반 텍스트로 복사할 수 있다. 복사 텍스트에는 방 이름, 정산 상태, 지급자, 수취자, 금액, 단위가 포함되며 거래 전체 내역은 포함하지 않는다. "정산 상태" 문구와 구체 형식은 OQ-002에서 정한다.
- AC:
  - AC-SET-005-1: 종료된 게임에서 접속자가 정산 결과를 조회할 수 있다(종료 후 조회 권한의 경계: OQ-005). 종료 전 정산 조회·미리보기의 허용 여부는 OQ-024에서 정하며, 그 전까지 종료 전 정산 결과는 제공하지 않는다고 가정하지 않고 미정으로 둔다.
  - AC-SET-005-2: 복사 버튼을 누르면 일반 텍스트가 클립보드에 복사된다.
  - AC-SET-005-3: 복사된 텍스트에 방 이름, 정산 상태, 각 항목의 지급자·수취자·금액·정산 단위가 포함된다.
  - AC-SET-005-4: 복사된 텍스트에 개별 거래 목록(사유·라운드·작성자 등)이 포함되지 않는다.
  - AC-SET-005-5: 클립보드 접근이 실패하면 사용자에게 복사 실패가 알려진다. 성공으로 표시되지 않는다.

#### FR-SET-006 정산 항목 없음
- POL: POL-SET-006
- 요구사항: 정산할 송금 항목이 없으면 '정산할 내역이 없습니다.'를 표시하고 복사 버튼을 비활성화한다.
- AC:
  - AC-SET-006-1: 거래가 없거나 모든 순손익이 0이면 정확히 '정산할 내역이 없습니다.' 문구가 표시된다.
  - AC-SET-006-2: 이 경우 복사 버튼이 비활성화되어 클릭해도 복사되지 않는다.
  - AC-SET-006-3: 정산 항목이 1건 이상이면 이 문구가 표시되지 않고 복사 버튼이 활성화된다.

#### FR-SET-007 정산 확정·버전 없음
- POL: POL-SET-007
- 요구사항: MVP에는 정산 확정과 버전 관리가 없다. 종료 후 정산은 별도 확정 단계 없이 계산 결과로 제공한다. 후속 개발의 확정/미확정 상태 정책을 MVP에 적용하지 않는다.
- AC:
  - AC-SET-007-1: 게임 종료 후 정산 결과가 별도 확정 조작 없이 조회된다.
  - AC-SET-007-2: 정산 확정·확정 취소·과거 버전 조회 UI와 API가 없다.
  - AC-SET-007-3: 정산 결과는 종료 시점의 유효 거래로 계산되며(종료 후 거래 변경이 잠겨 있으므로) 조회 시마다 동일하다.

### 5.6 연결과 오류 처리

#### FR-SYS-001 온라인 전용과 오래된 데이터 표시 금지
- POL: POL-SYS-001
- 요구사항: 데이터는 온라인 상태에서만 조회·변경한다. 연결이 끊기면 최신으로 오인할 수 있는 오래된 조회 결과를 표시하지 않는다.
- AC:
  - AC-SYS-001-1: 연결이 끊기면 사용자에게 연결 끊김 상태가 표시된다.
  - AC-SYS-001-2: 연결이 끊긴 동안 손익·거래 목록·정산 결과를 현재 값처럼 표시하지 않는다(숨기거나 최신이 아님을 명확히 표시). 구체 표현 방식은 Spec에서 정하되 최신으로 오인될 수 있어서는 안 된다.
  - AC-SYS-001-3: 오프라인에서 거래 등록·수정·삭제·종료 같은 변경은 수행되지 않는다. 오프라인 큐잉은 없다.
  - AC-SYS-001-4: 오프라인 상태의 화면에서 이전 조회 결과를 캐시로 대체 표시하는 기능이 없다.

#### FR-SYS-002 연결 복구
- POL: POL-SYS-002
- 요구사항: 연결이 복구되면 최신 서버 상태를 다시 조회한다. 미완료 거래를 자동으로 제출하지 않는다.
- AC:
  - AC-SYS-002-1: 연결 복구 후 서버의 최신 순손익·거래 목록·게임 상태가 다시 조회되어 표시된다.
  - AC-SYS-002-2: 끊김 중에 입력하다 제출되지 않은 거래는 복구 시 자동 제출되지 않는다.
  - AC-SYS-002-5: 저장 응답 유실 후 연결이 복구되면 서버 상태를 재조회해 해당 거래의 저장 여부를 확인할 수 있고, 사용자가 수동 재시도하기 전에 자동으로 재전송되지 않는다.
  - AC-SYS-002-3: 끊김 중에 게임이 종료된 경우 복구 후 종료 상태가 반영된다.
  - AC-SYS-002-4: 끊김 중 작성하던 입력 초안의 자동 복원은 MVP 범위가 아니다(§7).

#### FR-SYS-003 서버 최종 검증
- POL: POL-SYS-003
- 요구사항: 서버는 사용자 권한, 방 상태, 참여자 상태, 거래 유효성을 최종 검증한다.
- AC:
  - AC-SYS-003-1: 클라이언트 검증을 우회한 요청도 권한이 없으면 서버가 거부한다.
  - AC-SYS-003-2: 방 상태(종료됨)에 어긋나는 변경 요청은 서버가 거부한다.
  - AC-SYS-003-3: 참여자 상태(비활성)에 어긋나는 신규 거래 요청은 서버가 거부한다.
  - AC-SYS-003-4: 거래 유효성(금액·당사자·존재하는 거래)에 어긋나는 요청은 서버가 거부한다.
  - AC-SYS-003-6: 다른 방의 RoomMember가 이 방의 거래·참여자·게임 상태에 대한 변경 요청을 보내면 서버가 거부하고 이 방의 데이터는 변하지 않는다.
  - AC-SYS-003-7: 다른 방의 방장은 이 방에서 방장 권한을 갖지 않는다(방장 권한은 방 단위다).
  - AC-SYS-003-8: 다른 방에 속한 거래 ID에 대한 수정·삭제 요청과, 다른 방에 속하거나 존재하지 않는 Participant ID를 지급자·수취자로 지정한 거래 요청은 서버가 거부한다.
  - AC-SYS-003-5: 거부된 요청은 데이터를 변경하지 않으며 클라이언트에 구분 가능한 오류가 반환된다.

## 7. MVP 제외 범위

다음은 폐기가 아니라 후속 개발로 연기된 항목이다. MVP의 PRD·Spec·구현 대상이 아니다. (POL §9)

1. 여러 거래 일괄 입력
2. 정산 확정·버전 관리, 과거 확정 버전 조회

6. 자동 종료·재개·접근 만료·데이터 자동 삭제
7. 입력 초안 자동 복원

## 8. 정책 간 해석 메모

- 거래의 "원본·작성자 기록 보존"(POL-TXN-005)은 화면 제공 의무가 아니다. 상세 감사 이력 조회는 연기 항목이다(POL §9).
- 방장 이전이 없고 브라우저 식별자를 잃으면 방장 권한이 복구되지 않으므로(POL-ROOM-004, POL-ROOM-006), 방장 신원을 잃은 방은 종료할 수 없는 상태가 될 수 있다. 이 결과는 정책의 귀결이며 MVP가 해결하지 않는다. 운영 정책은 OQ-003, OQ-023에서 다룬다.
- 종료 후 정산은 거래가 잠긴 상태이므로 계산 결과가 고정된다. 확정 기능이 없는 것과 별개다.
