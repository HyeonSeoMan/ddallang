## 1. 범위

### 1.1 담당 FR (AC 26개 + 다른 Spec이 넘긴 계약)
FR-VIEW-005(8), FR-SYS-001(5), FR-SYS-002(5), FR-SYS-003(8). 비기능 요구 NFR-004(최신성 표시), NFR-006(실시간성), NFR-008(지원 환경, OQ-032 결정). 그리고 S1이 S5로 넘긴 **SSE 인증 방식**(S1 §3.1), S1·S2·S3·S4의 "이벤트 발생 지점" 선언(S1 §8, S2 §8, S3 §8)에 대한 이벤트 계약, S3가 S5로 넘긴 목록 갱신 조건(S3 §6.4). FR-SYS-003의 8개 AC는 S1(§11.12)·S2(§11.9)·S3(§11.6)이 변경·조회 엔드포인트에서 충족하며, S5는 새 엔드포인트(SSE)에 같은 원칙을 적용한다(§11.4). AC별 담당과 검증은 §11 추적표.

### 1.2 포함
SSE 연결 엔드포인트와 인증, 이벤트 형식·종류·순서·중복·누락 처리, 방 변경 번호(revision), 하트비트와 연결 상태 판정, 재연결과 재동기화(refresh), 오래된 데이터 표시 금지와 입력 유지, 실시간 지연 기준과 측정 방법(OQ-019), 지원 환경과 필수 기능 검사(OQ-032 결정의 계약화), S4 종료 이벤트 인터페이스.

## 2. 도메인 모델과 불변식

### 2.1 개체
| 개체 | 필드 | 설명 |
| --- | --- | --- |
| 방 변경 번호 | `revision` | 서버 내부의 방별 정수 카운터. 방의 상태를 바꾸는 변경이 확정될 때마다 1씩 증가한다. 클라이언트는 SSE 이벤트의 `revision`으로만 본다 |
| 이벤트 | `id`, `event`, `data` | 서버가 SSE로 보내는 알림(§4.2). 변경된 데이터 자체가 아니라 **변경이 일어났다는 사실과 식별자**만 담는다 |
| 연결 상태 | `connected` / `disconnected` | 클라이언트가 SSE 스트림의 건강 여부로 판단하는 상태(§6.5) |

### 2.2 불변식
- R-I1. `revision`은 방 안에서 1부터 시작해 **빠짐없이 1씩** 증가한다. 변경 하나(= 방 단위 직렬화 안의 한 트랜잭션)가 정확히 하나의 `revision`과 하나의 이벤트를 만든다.
- R-I2. 이벤트는 해당 변경이 **커밋된 뒤에만** 전달된다. 커밋되지 않았거나 롤백된 변경, 거부된 요청, 멱등 재전송, 값이 같은 수정·상태 변경(no-op)은 `revision`을 소비하지 않고 이벤트를 만들지 않는다(S1 N-4, S2 §8).
- R-I3. 이벤트는 **알림**이다. 클라이언트가 보여 주는 값의 근거는 항상 REST 조회 응답(S1·S3·S4)이다. 이벤트 본문의 내용으로 화면 값을 직접 갱신하지 않는다.
- R-I4. 이벤트 전달은 **최소 한 번(at-least-once)을 가정하지 않는다**. 중복·순서 뒤바뀜·누락이 있어도 클라이언트가 §6.3에 따라 재동기화하면 정확한 상태에 수렴한다.

## 3. 공통 규약

### 3.1 지원 환경과 필수 기능 검사 (OQ-032 결정, `open-questions.md` 2.6절)
- **지원 목표**: Chrome, Edge, Firefox, Safari(모바일 브라우저 포함)의 **최신 안정 버전과 직전 주요 버전**. 이 Spec은 구체 버전 숫자를 정하지 않는다. 실제 호환성 범위는 구현·검증 단계에서 확인해 정한다. PRD NFR-008의 기존 목록(iOS Safari, Android Chrome, 데스크톱 Chrome·Safari·Edge)은 이 목표에 포함된다. Firefox와 그 밖의 모바일 브라우저는 NFR-008을 넓히는 부분이며 §12.2 E-4에 따른다.
- **실행 시 기능 검사**: 앱은 진입 시 다음이 모두 있는지 검사한다. 하나라도 없으면 **진입을 차단하고** 어떤 기능이 없는지 안내한다. 부분 동작이나 우회는 만들지 않는다.
  1. Web Locks API(`navigator.locks`) — 신원 키 생성·저장의 탭 간 배타(S1 §3.1)
  2. 암호학적 난수(`crypto.getRandomValues`) — 신원 키·멱등 키 생성
  3. 브라우저 저장소 읽기·쓰기(`localStorage`) — 신원 키 보관(S1 §3.1)
  4. `fetch`와 스트리밍 응답 본문(`Response.body.getReader()`), `TextDecoder`, `AbortController` — SSE 수신(§3.2)
  5. `navigator.onLine`, `visibilitychange` 이벤트, 타이머 — 연결 상태 판단(§6.5)
- 구형 브라우저용 폴백(폴리필, 폴링 등)은 MVP 범위가 아니다. 검사는 모바일 브라우저에도 같다.
- 검사 결과의 안내 문구는 UX 기준(OQ-033)에서 정하며 이 Spec은 "차단과 안내"만 요구한다.

### 3.2 SSE 인증 (E-1, 사용자 결정 2026-11-08)
브라우저의 기본 `EventSource`는 요청 헤더를 설정할 수 없어 S1의 `Authorization: Bearer <신원 키>`(S1 §3.1)를 보낼 수 없다. 사용자가 확정한 방식은 다음과 같다.
- 클라이언트는 `EventSource`를 쓰지 않고 **`fetch`로 SSE 스트림을 연다.** 요청에 `Authorization: Bearer <신원 키>`와 `Accept: text/event-stream`을 실어 S1과 **같은 인증**을 쓰고, 응답 본문 스트림을 읽어 SSE 형식을 직접 해석한다(§9).
- 신원 키는 URL, 쿼리 문자열, 쿠키에 싣지 않는다. 서버 로그와 프록시에 키가 남을 위험을 만들지 않는다.
- 별도의 인증 엔드포인트나 단기 토큰은 만들지 않는다. 방 멤버 확인은 S1 §3.3과 같은 순서(§3.3)로 한다.
- 대안((b) 일회용 티켓, (c) 쿼리의 키)은 채택하지 않았다(§12.2 E-1).

### 3.3 검사 순서와 오류
SSE 엔드포인트의 연결 요청은 스트림을 열기 전에 다음 순서로 검사하고, 오류는 스트림이 아니라 **일반 JSON 오류 응답**(S1 §3.4 형식)으로 돌려준다.
0. 라우트: 없는 경로 `404 ROUTE_NOT_FOUND`, `GET`이 아닌 메서드 `405 NOT_SUPPORTED`(`Allow: GET`)
1. 신원 키 누락·형식 오류: `401 UNAUTHENTICATED`
2. 방 존재, 방 멤버 여부(비멤버는 방이 없는 것과 같은 응답): `404 ROOM_NOT_FOUND`
3. 입력 검증: 쿼리 매개변수가 있으면 최상위 `422 VALIDATION_FAILED`, `details`에 `{ "field": "<이름>", "code": "NOT_ALLOWED_FIELD" }`(S3 §3.3 표와 같은 형식). 이 엔드포인트는 쿼리 매개변수를 받지 않는다.

권한(403)·방 상태(409)·한도 오류는 없다. 방이 `ENDED`여도 연결할 수 있다(종료 후 입장자도 최종 정산을 보려면 연결이 필요하다). 다른 방의 RoomMember는 이 방에 연결할 수 없다(AC-SYS-003-6, -7과 같은 원칙).

## 4. API 계약

### 4.1 `GET /rooms/{roomId}/events` — 실시간 스트림 (FR-VIEW-005, FR-SYS-001, 002)
- 인증: 필수, 이 방의 RoomMember(§3.2).
- 요청 헤더: `Authorization: Bearer <신원 키>`, `Accept: text/event-stream`. `Last-Event-ID` 헤더는 보내도 **무시한다**(이벤트 재전송 없음, §6.2).
- 성공 응답 `200`: `Content-Type: text/event-stream; charset=utf-8`, `Cache-Control: no-store`, `X-Accel-Buffering: no`. 서버는 헤더를 보낸 즉시 `ready` 이벤트를 보낸다. 연결은 클라이언트가 끊거나 서버가 닫을 때까지 유지된다.
- 오류: 401, 404 `ROOM_NOT_FOUND`(비멤버 포함), 422(쿼리 매개변수). 오류 응답은 스트림이 열리기 전의 JSON이다.
- CORS(프론트엔드가 다른 출처에서 호출할 때): `Authorization` 헤더를 허용하는 사전 요청(preflight) 응답, 응답 헤더 `Date`를 `Access-Control-Expose-Headers`로 노출한다.
- **서버의 연결 한도**(E-9): 한 RoomMember당 동시 스트림 5개, 방당 50개. 한도를 넘어 새 연결이 오면 같은 RoomMember의 가장 오래된 스트림을 서버가 닫고 새 연결을 받는다. 닫힌 클라이언트는 §6.6에 따라 재연결·재동기화한다.
- **느린 클라이언트**: 전송 대기 이벤트가 100개를 넘으면 서버는 그 스트림을 닫는다. 메모리를 무한히 쓰지 않는다. 클라이언트는 재연결 후 재동기화한다.

### 4.2 이벤트 형식과 종류
스트림은 SSE 형식(`text/event-stream`)이다. 이벤트 하나는 다음 줄들과 빈 줄로 끝난다. `data`는 한 줄 JSON이다.
```
id: 12
event: transaction.created
data: {"roomId":"…","revision":12,"serverTime":"2026-11-08T03:21:45.123Z","transactionId":"…"}

```
- `id`는 `revision` 값과 같다(`ready`, `heartbeat`에는 `id`를 붙이지 않는다).
- 모든 `data`는 `roomId`와 `serverTime`(RFC 3339 UTC 밀리초)을 포함한다. 변경 이벤트는 `revision`을 더 포함한다.
- `data`에는 거래의 금액·사유·라운드·작성자·닉네임 같은 **내용을 싣지 않는다.** 식별자와 변경 종류만 싣는다(R-I3).

| `event` | 발생 지점 | `data`의 추가 필드 |
| --- | --- | --- |
| `ready` | 연결 직후 한 번(변경 아님) | `revision`: 연결 시점의 현재 방 변경 번호 |
| `heartbeat` | 15초마다(변경 아님) | `revision`: 그 시점의 현재 방 변경 번호 |
| `transaction.created` | S2 거래 생성 성공(§4.1) | `revision`, `transactionId` |
| `transaction.updated` | S2 거래 수정 성공(값이 실제로 바뀐 경우, §4.2) | `revision`, `transactionId` |
| `transaction.deleted` | S2 거래 삭제 성공(§4.3) | `revision`, `transactionId` |
| `participant.created` | S1 참여자 등록 성공(§4.6) | `revision`, `participantId` |
| `participant.status_changed` | S1 참여자 활성 상태 실제 변경(§4.7) | `revision`, `participantId` |
| `room.ended` | S4 게임 종료 전이 성공(§8) | `revision` |

- 알 수 없는 `event` 이름은 클라이언트가 **무시하지 않고 변경 이벤트로 취급**해 재동기화한다(미래의 이벤트 추가에 대비, E-11). 알 수 없는 `data` 필드는 무시한다.
- RoomMember 입장·복원은 이벤트 대상이 아니다(S1 N-5).

### 4.3 존재하지 않는 동작
| 동작 | 응답 |
| --- | --- |
| `POST`/`PUT`/`PATCH`/`DELETE /rooms/{roomId}/events` | 405 `NOT_SUPPORTED`, `Allow: GET` |
| 이벤트 재전송·과거 이벤트 조회(`Last-Event-ID`로의 재생, 별도 이력 조회 경로) | 정의하지 않는다. 경로는 404 `ROUTE_NOT_FOUND`, 헤더는 무시 |
| 클라이언트가 보내는 이벤트·구독 채널 선택·방 목록 스트림 | 만들지 않는다 |

## 5. 상태와 권한 표
| 동작 | `IN_PROGRESS` | `ENDED` |

## 6. 동작 규칙

### 6.1 변경 번호(revision)와 이벤트 생성 (E-3, 사용자 결정 2026-11-08)
- 방의 상태를 바꾸는 변경(S1 참여자 등록·상태 변경, S2 거래 생성·수정·삭제, S4 게임 종료)은 **방 단위 직렬화 안의 같은 트랜잭션에서** `revision`을 1 증가시키고 그 값으로 이벤트를 만든다(S2 §7 1과 같은 잠금). 다중 서버 인스턴스에서도 성립해야 하며 프로세스 메모리 카운터만으로 구현하지 않는다.
- 이벤트는 그 트랜잭션이 커밋된 뒤에 전달한다(R-I2). 커밋과 이벤트 발행 사이의 실패로 이벤트가 사라질 수 있으며, 이는 하트비트(§6.4)가 보완한다. 이벤트가 커밋 전에 나가는 일은 없어야 한다.
- 이 요구는 S1·S2·S4가 "서버만 가지는 내부 기록"(S1 §2.1, S2 §2.1)에 둘 저장 모델 의존성이며 그 Spec들의 API·오류·AC 계약을 바꾸지 않는다. S1·S2·S3 문서는 수정하지 않는다(S3 C-1과 같은 방식, §12.2 E-3). 이 항목은 Plan/Tasks의 S1·S2·S4 구현 Task에 포함하고 검증한다.
- 거부된 요청, 멱등 재전송, 값이 같은 수정·상태 변경은 `revision`을 소비하지 않는다(R-I1, R-I2).

### 6.2 전달 (서버)
- 서버는 한 방의 이벤트를 그 방에 연결된 **모든 스트림**(모든 서버 인스턴스에 걸쳐)에 전달해야 한다. 변경을 처리한 인스턴스와 스트림을 가진 인스턴스가 다를 수 있다. 전달 수단(예: PostgreSQL LISTEN/NOTIFY, 방 단위 구독)은 Plan이 정한다. 확정된 기술 스택에 없는 Redis·메시지 큐는 구체적 필요가 확인될 때만 쓴다(`.agents/governance.md` §12).
- 한 스트림에는 `revision` 오름차순으로 보낸다. 서버가 이 순서를 지키지 못해도 클라이언트의 검사(§6.3)가 복구하므로 순서는 최선 노력이다.
- **이벤트를 저장하거나 재전송하지 않는다.** `Last-Event-ID`는 무시한다. 재연결한 클라이언트는 새 `ready`를 받고 전체를 재동기화한다(§6.4, E-6).
- 하트비트(`heartbeat`)는 15초마다 보내고, 그 시점에 **DB에서 읽은 현재 `revision`**을 싣는다. 알림이 유실되었어도 하트비트가 클라이언트가 뒤처졌음을 알린다.

### 6.3 순서·중복·누락 처리 (클라이언트)
클라이언트는 연결마다 `seen`(마지막으로 반영한 `revision`)을 유지한다.
1. `ready{revision: R}`을 받으면 `seen = R`로 두고 §6.4의 **재동기화**를 시작한다.
2. 변경 이벤트 `e`를 받으면:
   - `e.revision ≤ seen`: 중복 또는 이미 반영된 과거 이벤트이므로 **무시**한다.
   - `e.revision = seen + 1`: `seen = e.revision`으로 하고 **갱신**(§6.4)을 예약한다.
   - `e.revision > seen + 1`: **누락 발생.** `seen = e.revision`으로 하고 전체 재동기화(§6.4)를 한다.
3. `heartbeat{revision: H}`를 받으면 `H > seen`이면 누락이므로 `seen = H`로 하고 전체 재동기화한다. `H ≤ seen`이면 아무것도 하지 않는다.
4. 알 수 없는 `event` 이름은 `revision` 필드가 있으면 2번을 따르고 없으면 전체 재동기화한다.

이 규칙으로 순서 뒤바뀜·중복·누락 모두 정확한 상태로 수렴한다. `data`의 파싱 실패나 잘린 이벤트는 누락과 같이 전체 재동기화한다.

### 6.4 갱신과 재동기화 (refresh)
**갱신(refresh)**은 서버 상태를 다시 조회해 화면의 서버 유래 데이터를 교체하는 동작이다. 조회 대상은 다음과 같다. 이벤트 종류별 필요 최소 집합은 아래 표이며 **더 넓게(전체) 조회해도 된다.** 전체 재동기화는 모든 대상을 조회한다.

| 대상 | API | 이벤트 |
| --- | --- | --- |
| 방(상태 포함) | `GET /rooms/{roomId}` (S1 §4.4) | `room.ended`, 재동기화 |
| 참여자 목록 | `GET /rooms/{roomId}/participants` (S1 §4.5) | `participant.*`, 재동기화 |
| 누적 손익 | `GET /rooms/{roomId}/balances` (S3 §4.2) | `transaction.*`, `participant.*`, `room.ended`, 재동기화 |
| 거래 목록 | `GET /rooms/{roomId}/transactions` (S3 §4.1) | `transaction.*`, `room.ended`, 재동기화 |
| 정산(예상·최종) | S4가 정한 정산 조회 API | `transaction.*`, `participant.*`, `room.ended`, 재동기화 |

- **거래 목록은 S3 §6.4의 새 순회로 교체한다.** 현재 선택된 참여자 필터를 유지한 채 첫 페이지부터 다시 불러오고 기존 페이지는 폐기한다. 이로써 필터 선택과 정렬 규칙이 유지된다(AC-VIEW-005-7). 이전에 더 불러 두었던 페이지 수만큼 이어서 불러와 보이는 범위를 복원하는 것은 허용하되, 완료 전에는 기존 목록을 유지하다가 한 번에 교체한다.
- **병합 금지 유지**: S3 §6.4의 "병합하지 않는다"를 바꾸지 않는다. 부분 갱신은 이 Spec에서 정의하지 않는다.
- **합치기(coalescing)**: 리소스마다 조회를 한 번에 하나만 진행한다. 진행 중에 이벤트가 오면 "다시 필요함"으로 표시하고 끝난 뒤 한 번 더 조회한다. 조회 응답은 **가장 최근에 시작한 조회의 것만** 반영하고 늦게 도착한 이전 조회의 응답은 버린다.
- **한 주기의 일관성**: 누적 손익과 거래 목록은 별도 요청이므로 같은 주기의 응답이 모두 도착한 뒤 함께 반영한다(S3 §3.2). 주기 도중 이벤트가 오면 한 주기를 더 한다.
- **초기 로드도 같은 절차**다: 스트림을 먼저 연결하고 `ready`를 받은 뒤 재동기화로 처음 데이터를 채운다. 스트림이 연결되지 않으면 데이터 영역은 표시되지 않는다(§6.5).
- 변경 알림 토스트는 필수가 아니다(AC-VIEW-005-6).

### 6.5 연결 상태와 오래된 데이터 표시 금지 (FR-SYS-001, NFR-004)
- **연결됨(`connected`)**: 스트림이 열려 있고, 마지막 수신(이벤트·하트비트 포함)이 **40초 이내**이며, `navigator.onLine`이 거짓이 아니다.
- **끊김(`disconnected`)**: 다음 중 하나라도 해당한다. 스트림이 닫히거나 오류로 끝남, 40초 동안 아무것도 수신하지 않음(하트비트 두 번 이상 연속 누락), `navigator.onLine`이 거짓, 재동기화 조회가 네트워크 오류로 실패, 스트림이 아직 연결되지 않은 최초 상태.
- 끊김 상태에서 클라이언트는 다음을 한다.
  1. 연결 끊김 상태와 오류 안내를 표시한다(AC-SYS-001-1).
  2. **서버에서 받은 모든 데이터 영역을 표시하지 않는다**: 누적 손익, 거래 목록, 정산 결과, 참여자 목록, 게임 상태. 이전에 불러온 값을 "최신이 아님" 표시와 함께 보여 주는 것도 하지 않는다(AC-SYS-001-2, -4). 캐시로 대체 표시하는 기능을 만들지 않는다.
  3. 변경 조작(거래 등록·수정·삭제, 참여자 변경, 종료)을 수행하지 못하게 한다. 오프라인 큐잉은 없다(AC-SYS-001-3).
  4. 현재 화면에서 작성 중이던 입력값(거래 입력 폼, 닉네임 입력 등)은 유지한다(AC-SYS-001-5).
- 끊김에서 연결됨으로 돌아오면 `ready` 뒤의 재동기화가 끝난 시점에 데이터 영역을 다시 표시한다. 재동기화가 끝나기 전에는 표시하지 않는다.
- 페이지가 백그라운드에서 돌아올 때(`visibilitychange`)와 `online` 이벤트에서는 즉시 연결 상태를 점검하고, 마지막 수신이 40초를 넘었으면 §6.6으로 재연결한다.

### 6.6 재연결 (FR-SYS-002)
- 스트림이 끊기거나 40초 무수신이면 클라이언트는 현재 스트림을 중단(abort)하고 재연결한다. 간격은 1초에서 시작해 연속 실패마다 2배(최대 30초)로 늘리고 ±20% 무작위를 더한다. 연결에 성공하면 간격을 1초로 되돌린다. `online`·`visibilitychange`(보임) 이벤트에서는 대기 중이어도 즉시 시도한다.
- 재연결 응답이 `401` 또는 `404 ROOM_NOT_FOUND`이면 **재시도하지 않고** 오류를 안내한다(신원 키가 이 방에서 유효하지 않거나 방이 없음). `5xx`·네트워크 오류·`429`는 계속 재시도한다. 오류 `code`로 분기한다.
- 재연결 후 새 `ready`를 받으면 `seen`을 재설정하고 **전체 재동기화**를 한다(AC-SYS-002-1). 끊긴 동안 게임이 종료되었다면 재동기화한 방 상태에 종료가 반영된다(AC-SYS-002-3).
- **자동 제출 금지**: 재연결·재동기화는 끊김 중에 작성하다 제출하지 못한 거래를 자동으로 제출하지 않는다(AC-SYS-002-2). 응답을 받지 못해 결과를 알 수 없는 저장은 S2 §9에 따라 수동 재시도할 때만 같은 키로 다시 보낸다.
- **저장 응답 유실 뒤 복구**(AC-SYS-002-5, AC-TXN-008-5): 재동기화로 받은 현재 거래 목록에서 사용자가 해당 거래를 볼 수 있다. 시스템은 거래를 자동으로 성공으로 판정하지 않고, 목록에서 해당 거래를 확인할 수 없으면 "저장 여부를 확정할 수 없음" 상태를 유지한다. 재조회한 현재 상태가 최초 요청의 결과를 증명하지 못할 수 있다(그 뒤 다른 사용자가 수정·삭제했거나 멱등 키 유효 기간이 지난 경우).
- **새로고침·재방문**: 저장되지 않은 입력 초안은 복원하지 않는다(AC-SYS-002-4). 새로 연결하고 `ready` 뒤 재동기화로 데이터를 채운다.

### 6.7 실시간 지연 기준과 측정 (OQ-019, E-2, 사용자 결정 2026-11-08)
PRD는 지연 목표의 수치와 측정 조건을 Spec으로 넘겼다(AC-VIEW-005-8, NFR-006). 사용자가 다음을 확정했다.

| 지표 | 정의 | 목표 |
| --- | --- | --- |
| 이벤트 전달 지연 | 변경이 커밋된 시각(서버)부터 연결된 클라이언트가 이벤트를 받은 시각까지 | 95번째 백분위 1초 이하, 최댓값 3초 이하 |
| 화면 반영 지연 | 변경 커밋 시각부터 다른 접속자의 화면이 §6.4 갱신을 끝내 새 값을 표시하기까지 | 95번째 백분위 3초 이하, 최댓값 5초 이하 |
| 유실 시 수렴 지연 | 알림이 유실된 경우 하트비트로 뒤처짐을 감지해 화면이 수렴하기까지 | 20초 이하(하트비트 15초 + 갱신) |

- **측정 조건**: 방 하나에 접속자 10명(방 한도), 거래 1,000건, 참여자 10명이 있는 상태. 서버는 정상 부하, 클라이언트와 서버 사이 왕복 지연 150ms 이하의 일반 모바일·유선망. 변경은 한 번에 하나씩 일어난다(동시 다발 변경 중에는 합치기, §6.4로 지연이 늘 수 있다).
- **측정 방법**: 자동화된 통합 시험에서 SSE에 연결한 클라이언트 10개를 두고 서로 다른 변경 100건(거래 생성·수정·삭제, 참여자 등록·상태 변경, 종료 포함)을 한 건씩 보내며 각 변경의 `serverTime`(이벤트의 `serverTime`)과 각 클라이언트의 수신·화면 반영 시각의 차이를 기록한다. 서버와 시험 클라이언트가 같은 기기 또는 시계 동기된 환경에서 측정하며 백분위와 최댓값을 보고한다. 유실 시나리오는 알림을 의도적으로 버려 하트비트 경로를 시험한다.
- 이 목표는 **정상 조건의 합격 기준**이며 운영 중 보장(SLA)이 아니다. 목표를 넘는 사례는 결함이 아니라 측정 보고 대상이 되며, 연결이 끊긴 상태는 §6.5가 정한다.

## 7. 동시성과 정합성
- **직렬화와 revision**: `revision`은 S2 §7의 방 단위 잠금 안에서 증가하므로 동시 변경에서도 서로 다른 연속 번호를 갖는다(R-I1).
- **커밋 순서**: 같은 잠금 안에서 번호가 매겨지고 커밋되므로 더 큰 `revision`의 변경이 작은 것보다 먼저 커밋되지 않는다. 읽기 스냅샷이 큰 번호만 보고 작은 번호를 놓치는 일이 없다.
- **재동기화와 새 변경의 경쟁**: `ready{R}` 뒤의 조회는 번호 R 이상의 커밋을 반영한다. R보다 큰 이벤트는 별도로 도착해 추가 갱신을 만든다. 갱신은 멱등이므로 조회가 이벤트보다 더 최신 상태를 가져와도 틀리지 않는다.
- **같은 변경의 이중 처리**: 알림 전달 경로가 둘 이상이거나 재시도되어도 클라이언트의 `seen` 검사(§6.3)가 중복을 걸러 낸다.
- **스트림 수 한도**(E-9)와 느린 클라이언트 차단은 다른 방과 변경 처리에 영향을 주지 않아야 한다(스트림 쓰기는 변경 트랜잭션을 지연시키지 않는다).

## 8. 다른 Spec과의 인터페이스

### 8.1 S1·S2·S3에 대한 요구 (계약 변경 없음)
| 대상 | 요구 |
| --- | --- |
| S1 참여자 등록(§4.6) | 성공 시 `participant.created` 이벤트, `revision` 증가. 거부는 없음 |
| S1 참여자 상태 변경(§4.7) | **실제 변경이 있을 때만** `participant.status_changed`. 같은 값 요청(N-4)은 없음 |
| S2 거래 생성·수정·삭제(§4) | 성공 시 `transaction.created/updated/deleted`. 멱등 재전송(§5.3), 값이 같은 수정(§4.2), 거부는 없음 |
| S3 조회 API | 변경 없음. 이벤트 후 재조회 대상(§6.4). 추가 필드를 요구하지 않는다 |

이 요구는 S1·S2의 구현이 해당 트랜잭션 안에서 §6.1을 수행하는 저장 모델 의존성이다. S1·S2·S3 문서는 수정하지 않는다.

### 8.2 S4가 이 Spec에서 가져가는 계약
S4 Spec(미작성)은 다음을 따라야 한다. S5가 S4에 요구하는 것이며 S4 작성 시 반영하고 검수한다.
1. **종료 전이와 이벤트**: 게임 종료(`IN_PROGRESS → ENDED`)는 S2 §7 1의 방 단위 직렬화 안에서 일어나고, **전이를 일으킨 트랜잭션에서 정확히 한 번** `revision`을 증가시키며 `room.ended` 이벤트를 만든다(AC-SET-001-9, AC-VIEW-005-4). 같은 멱등 키의 재전송, 이미 종료된 게임에 대한 새 종료 요청(거부), 24시간 만료 거부는 이벤트를 만들지 않는다.
2. **정산 조회 API**: S4가 예상·최종 정산을 돌려주는 조회 API를 정한다. 방 상태에 따라 예상 또는 최종을 돌려주고 필터와 무관하게 전체 유효 거래 기준이다(AC-SET-008-6). 스냅샷 일관성은 S3 §3.2와 같은 원칙을 쓴다. S5는 이 API의 경로·형식에 의존하지 않고 "정산 조회 API"로만 참조한다.
3. **정산 변경 이벤트**: 정산은 S3 순손익에서 계산되는 파생 값이므로 **별도의 정산 이벤트를 만들지 않는다.** 예상 정산이 바뀌는 시점은 `transaction.*`, `participant.*`, `room.ended` 이벤트와 같다(AC-VIEW-005-5). 최종 정산은 종료 후 거래가 잠기므로 변하지 않는다(AC-SET-007-3).
4. **순손익의 단일 정의**: S4는 S3 §6.1의 순손익 정의를 쓴다(S3 §1.3).
5. **이벤트 페이로드**: `room.ended`의 `data`는 §4.2의 형식(`roomId`, `revision`, `serverTime`)이며 정산 내용을 싣지 않는다. 정산은 REST 조회로 받는다.

## 9. 프론트엔드 책임
- **진입 검사**: §3.1의 필수 기능을 검사하고 하나라도 없으면 진입을 차단하고 안내한다.
- **스트림 클라이언트**: `fetch`로 §4.1에 연결하고 `ReadableStream`을 `TextDecoder`(스트리밍 모드)로 읽어 SSE 형식을 해석한다. 줄 경계에서 잘린 이벤트를 이어 붙이고(버퍼링), `\n\n`로 끝나는 이벤트만 처리한다. 알 수 없는 줄(주석 `:` 등)은 수신 시각 갱신에만 쓴다. `AbortController`로 중단·재연결한다. 네이티브 `EventSource`는 쓰지 않는다(E-1).
- **연결 상태 모델**: §6.5의 `connected`/`disconnected`를 앱 전역 상태로 두고 모든 서버 유래 영역이 이 상태를 따른다. 끊김 중 표시 금지, 입력 유지, 변경 컨트롤 비활성(AC-SYS-001-1~5).
- **순서·중복·누락**: §6.3을 그대로 구현한다. 이벤트 종류별 조회 최소 집합을 쓰거나 전체를 조회한다(§6.4).
- **갱신**: 합치기와 최신 요청 응답만 반영, 두 조회의 한 주기 일관성(§6.4). 거래 목록은 S3 §6.4의 새 순회이며 현재 필터를 유지한다.
- **재연결**: §6.6의 간격과 즉시 재시도 조건, 401/404 중단.
- **시각 보정 연계**: `ready`의 `serverTime`(그리고 REST 응답 `Date`)으로 S2 §9의 시계 차이 추정을 갱신해도 된다.
- **저장 결과 불명**: S2 §9와 §6.6의 규칙을 따른다. 재동기화는 자동 재전송을 하지 않는다.
- **종료 반영**: `room.ended` 또는 재동기화로 방이 `ENDED`가 되면 거래 입력·수정·삭제 UI를 잠그고 최종 정산을 표시한다(AC-VIEW-005-4, AC-TXN-009-3). 정산 화면은 S4가 정한다.
- 변경 알림 토스트는 만들지 않아도 된다.

## 10. 백엔드 책임
- §3.3 검사 순서, §4.1 SSE 엔드포인트와 헤더, §4.2 이벤트 형식과 종류, §6.1 `revision`·이벤트 생성(커밋 뒤 전달), §6.2 전달(다중 인스턴스, 하트비트가 DB의 현재 `revision`을 싣기), §4.1의 연결·대기 한도를 구현한다.
- 이벤트에 거래·참여자의 내용, 신원 키, 키 해시를 싣지 않는다.
- 스트림 쓰기는 변경 트랜잭션의 지연이나 실패 원인이 되지 않는다(전달은 비동기).
- 프록시 버퍼링을 막는 응답 헤더(`X-Accel-Buffering: no`, `Cache-Control: no-store`)와 하트비트로 유휴 연결 종료를 완화한다.
- 이 Spec의 계약을 다른 저장소 문서에 복제하지 않고 Spec 버전 또는 `ddallang` 커밋으로 참조한다.

### 12.3 자체 점검 (상위 문서와의 충돌)
- FR-VIEW-005(8), FR-SYS-001(5), FR-SYS-002(5)의 AC 18개와 FR-SYS-003(8)의 적용을 추적표에 연결했다. AC를 약화하거나 바꾸지 않았다.
- AC-VIEW-005-8(지연 수치는 OQ-019 해결 전까지 정의하지 않는다)은 PRD가 비워 둔 부분이며 E-2가 채운다. E-2는 사용자가 확정했다(2026-11-08).
- S1 §3.1이 SSE 인증을 S5로 넘겼고 E-1이 채운다. S1의 인증 방식(Bearer)은 바뀌지 않는다.
- S3 §6.4의 "병합하지 않는다, 교체한다"를 유지한다. S3 C-9의 "응답에 변경 번호를 두지 않는다. S5가 필요하면 기존 필드를 바꾸지 않는 추가"에 대해 이 Spec은 REST 응답에 변경 번호를 **추가하지 않고** SSE 이벤트 안에서만 `revision`을 쓴다. S1·S2·S3 API 응답은 바뀌지 않는다.
- 변경 번호의 저장 모델 의존성(E-3)은 S1 §2.1·S2 §2.1이 "서버만 가진다"고 한 내부 기록 영역에 속한다. S3 C-1 (a)와 같은 해석 위험이 있다(§13).
- NFR-008과 OQ-032 결정의 플랫폼 목록 차이(E-4)는 충돌 가능성으로 보고한다.
- PRD의 OQ-030·031·039 오래된 문구는 S5 계약 해석에 영향이 없다.
- 제품 정책 변경, MVP 제외 기능(오프라인 큐잉, 입력 초안 복원, 폴백) 추가는 없다.

## 13. 위험
- **SSE 의존(E-5)**: 스트림이 막힌 네트워크(일부 기업 프록시)에서는 앱이 데이터를 표시하지 못한다. 폴링 폴백은 범위 밖이다.
- **직접 재연결 구현(E-1)**: `fetch` 스트리밍은 브라우저가 재연결·파싱을 해 주지 않는다. 파서·재연결 코드의 결함이 연결 신뢰성을 좌우하므로 단위·통합 시험이 필요하다.
- **모바일 백그라운드**: iOS Safari 등은 백그라운드 탭의 연결을 중단한다. `visibilitychange`로 복귀 시 재연결·재동기화한다(§6.5). 복귀 직전에는 오래된 화면이 잠깐 보일 수 있으므로 복귀 즉시 데이터 영역을 숨기고 재동기화를 기다리는 구현이 필요하다.
- **다중 인스턴스 전달**: 알림 전달 수단(예: LISTEN/NOTIFY)이 일시적으로 끊기면 이벤트가 유실될 수 있다. 하트비트의 DB `revision`이 보완하며 수렴 상한은 약 20초다.
- **전체 재동기화 비용**: 재연결·누락 때마다 5개 대상을 조회한다. 방당 접속자 10명·거래 1,000건 규모에서는 작지만 Plan에서 측정한다.
- **재연결 폭주**: 서버 재시작 시 모든 클라이언트가 동시에 재연결·재동기화한다. 지터와 백오프로 완화하며 규모는 방당 10명 한도로 제한된다.
- **변경 번호 저장 모델(E-3)**: S1·S2 문서의 내부 기록 목록을 엄격히 완전 목록으로 읽으면 S1·S2 개정으로 볼 여지가 있다. 이 경우 S1·S2 재검수가 필요하다.
- **시계 오차와 지연 측정**: 지연 측정은 서버 시각과 클라이언트 시각을 비교하므로 시계 동기된 시험 환경이 필요하다(§6.7).
- **이벤트 폭주 시 합치기**: 짧은 시간에 변경이 몰리면 화면이 한 주기 늦을 수 있다. 합치기로 조회 수를 제한하며 지연 목표는 한 번에 하나씩 일어나는 변경 기준이다(§6.7).
- **브라우저 지원 범위(OQ-032)**: 구체 버전 숫자가 없다. 구현·검증 단계에서 실제 호환성을 확인해 정해야 한다.
