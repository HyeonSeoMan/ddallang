## 1. 범위

### 1.1 담당 FR (AC 104개)
FR-ROOM-001~009(79), FR-PART-001~004(25). AC별 담당과 검증은 §11 추적표.

### 1.2 포함
방 생성(생성자 = 첫 참여자·방장), 초대 링크 조회·입장(입장 = 참여자 생성), 브라우저 신원 키의 발급·복원·접근 상실, 이어받기 요청·조회·취소·승인·거절, 닉네임·방 이름·정산 단위 검증, 방장 지정과 방장 전용 동작의 권한 경계, 참여자 직접 추가·비활성화·재활성화·목록 조회, 참여자 한도, 종료 후 참여자 생성·상태 변경 금지.

## 2. 도메인 모델과 불변식

### 2.1 개체
| 개체 | 필드 | 설명 |
| --- | --- | --- |
| Room | `id`, `name`, `unit`, `status`, `inviteCode`, `createdAt` | `status`는 `IN_PROGRESS` 또는 `ENDED`. `name`, `unit`, `inviteCode`는 생성 뒤 변하지 않는다 |
| Participant | `id`, `roomId`, `nickname`, `status`, `order`, `isHost`, `createdAt` | 방의 유일한 사람 단위(OQ-041). `status`는 `ACTIVE` 또는 `INACTIVE`. `order`는 방 안에서 유일한 양의 정수이며 한 번 부여되면 바뀌지 않는다. `isHost`는 방을 만든 참여자만 `true`다. 서버는 이 참여자에 연결된 신원 키 해시를 최대 하나 보관하며(없을 수 있다), 이 해시와 연결 여부는 응답에 담지 않는다(S1-C6) |
| ClaimRequest (이어받기 요청) | `id`, `participantId`, `nickname`, `status`, `rejectReason`, `createdAt`, `resolvedAt`, `resolvedById` | `status`는 `PENDING`, `APPROVED`, `REJECTED`, `CANCELED`. `nickname`은 대상 참여자의 닉네임이다. `rejectReason`은 `REJECTED`일 때만 값이 있다: `HOST_REJECTED`(방장 거절), `TARGET_CLAIMED`(같은 참여자의 다른 요청이 승인됨, P-7), `REQUESTER_LINKED`(승인 시점에 요청 브라우저가 이미 다른 참여자에 연결됨, AC-ROOM-009-14). `resolvedById`는 요청을 처리한 방장의 **Participant ID**다(승인, 방장 거절, 그 승인에 딸린 `TARGET_CLAIMED`, `REQUESTER_LINKED`를 만든 승인 시도. 취소는 `null`, AC-ROOM-004-5). 서버는 요청한 브라우저의 신원 키 해시를 함께 보관하며 응답에 담지 않는다 |
| RevokedIdentity (접근을 잃은 신원) | (방, 신원 키 해시), `participantId`, `revokedAt` | 이어받기 승인으로 참여자에서 끊긴 이전 신원 키 해시. 응답 개체가 아니라 서버 내부 기록이다(§3.1, S1-C4) |

ID(`id`)는 서버가 만드는 불투명 문자열이며 추측하기 어려워야 한다. 클라이언트는 형식을 가정하지 않는다.

### 2.2 신원 키 해시의 상태
한 방에서 신원 키 해시 하나는 다음 중 정확히 하나의 상태에 있다.

| 상태 | 뜻 | 서버의 판정 |
| --- | --- | --- |
| 연결됨(LINKED) | 어떤 참여자에 연결되어 있다 | 그 참여자가 요청자다(`me`) |
| 대기(PENDING) | 연결된 참여자는 없고 `PENDING` 이어받기 요청이 하나 있다 | 방 비멤버. 자기 요청의 조회·취소만 할 수 있다 |
| 접근 상실(REVOKED) | 이어받기 승인으로 참여자에서 끊겼다 | 그 키로 오는 이 방의 모든 요청을 `401 IDENTITY_REVOKED`로 거부한다(§3.3) |
| 없음(NONE) | 위 어느 것도 아니다(처음 보는 키, 또는 요청이 모두 거절·취소된 키) | 방 비멤버. 입장이나 이어받기 요청을 할 수 있다 |

### 2.3 불변식
- I1. 방마다 방장은 정확히 한 명이다. 방을 만든 참여자이며(`isHost = true`), 생성 시 정해지고 바뀌지 않는다. 방장 참여자는 이어받을 수 없고(AC-ROOM-009-3) 비활성화할 수 없으므로(P-4) 항상 `ACTIVE`다. 다른 참여자가 방장이 되는 경로는 없다.
- I2. 방에 접근하는 주체는 언제나 한 참여자다(AC-ROOM-004-1). 참여자가 아닌 접속 주체 개체는 없다.
- I3. 한 참여자에 연결된 신원 키 해시는 최대 하나이고, 한 방에서 한 해시는 최대 한 참여자에 연결된다(AC-ROOM-004-3). 해시가 바뀌는 경로는 이어받기 승인(§4.13)뿐이다.
- I4. 한 방에서 한 해시는 §2.2의 상태 중 하나에만 있다. 특히 한 해시의 `PENDING` 요청은 최대 하나이고(P-8), 연결된 해시는 `PENDING` 요청을 갖지 않는다.
- I5. 닉네임 고유성은 (방, 정규화한 비교 키) 단위다. 입장으로 생긴 참여자, 직접 추가한 참여자, 비활성 참여자가 모두 하나의 범위다(FR-ROOM-006).
- I6. 방마다 참여자는 10명 이하다. 상태와 신원 연결 여부와 무관하게 존재하는 모든 참여자를 센다. 이어받기 요청은 세지 않는다(P-3).
- I7. 참여자 `order`는 방 안에서 서로 다르고 증가하며(서버 처리 순서), 방 생성·입장·직접 추가 모두에 같은 순서로 부여된다. 비활성화·재활성화·이어받기로 바뀌지 않는다. 결번이 생겨도 된다. 방 생성자는 `1`이다.
- I8. 방 이름, 정산 단위, 초대 코드, 닉네임은 생성 뒤 변경 경로가 없다. 이어받기도 닉네임·상태·`order`·`isHost`를 바꾸지 않는다(AC-ROOM-009-6).
- I9. 모든 변경은 한 요청 단위로 원자적이다. 거부된 요청은 아무것도 저장하지 않는다. **예외 하나**: 승인 시점에 요청 브라우저가 이미 연결된 경우의 승인 거부는 그 이어받기 요청을 `REJECTED`(`REQUESTER_LINKED`)로 바꾼다(AC-ROOM-009-14, AC-SYS-003-5).

## 3. 공통 규약

### 3.1 신원 키와 인증
- **신원 키(identity key)**: 클라이언트가 방 입장·이어받기 시도 또는 방 생성 시도마다 새로 만드는 암호학적 난수 32바이트를 base64url(패딩 없음)로 인코딩한 43자 문자열이다. 방 생성, 첫 입장, 첫 이어받기 요청에서 서버에 처음 제시되며, 키는 **그것이 제시된 방 안에서만** 의미를 가진다(서버는 키 해시를 (방, 해시)로만 구분하므로 같은 키를 다른 방에 제시하면 그 방과 무관한 별개의 신원이 된다). 서버는 SHA-256 해시만 보관한다.
- 클라이언트는 이 키를 브라우저 저장소에 **초대 코드별**로 보관한다. 브라우저 저장소를 지우면 키를 잃고, 잃은 키는 서버도 복구할 수 없다. 이것이 "브라우저 기반 신원"의 정의다(FR-ROOM-005). 키를 잃은 사람이 기존 참여자를 되찾는 길은 이어받기(FR-ROOM-009)뿐이다.
- 변경·방 한정 조회 요청은 `Authorization: Bearer <신원 키>`로 보낸다. 서버는 요청 경로의 방에서 이 키 해시의 상태(§2.2)를 찾는다. **연결됨**이면 그 참여자가 요청자다. 다른 방에서 연결된 키라도 이 방에서 연결되지 않았다면 이 방의 참여자가 아니다(방 단위 권한, AC-SYS-003-6, -7).
- **접근 상실과 키 폐기**: 이어받기 승인으로 끊긴 키(REVOKED)는 그 방에서 다시 쓸 수 없다. 클라이언트는 `401 IDENTITY_REVOKED`를 받거나 초대 조회(§4.2)의 `identity`가 `REVOKED`이면 접근을 잃었다는 사실을 안내하고(AC-VIEW-005-9) 그 초대 코드의 키를 저장소에서 지운다(아래 배타 구간의 조건부 삭제). 이후 그 브라우저는 신원이 없는 브라우저로서(D-2) 새 키를 만들어 입장하거나 이어받기를 다시 요청한다(S1-C4).
- **키 생성·저장 계약**: 클라이언트는 키를 저장소에 저장하고 읽어서 확인한 뒤에만 서버에 보낸다. 같은 브라우저의 여러 탭이 같은 초대 링크로 동시에 첫 입장·이어받기를 해도 키가 하나만 만들어지도록 다음을 **하나의 배타 구간**에서 수행한다. 잠금 이름은 초대 코드별로 하나다(예: `ddallang-identity:{inviteCode}`).
  1. 잠금을 얻는다(Web Locks API의 `exclusive`).
  2. **잠금 안에서** 저장소를 다시 읽는다. 키가 이미 있으면 그것을 쓴다(다른 탭이 먼저 만든 경우).
  3. 없을 때만 CSPRNG로 새로 만들고 저장한 뒤 **다시 읽어** 저장됐음을 확인한다. 저장·재확인이 실패하면 키를 쓰지 않고 입장을 막고 사유를 안내한다.
  4. 잠금을 놓은 뒤에 요청을 보낸다. 요청에 쓰는 키는 항상 2~3에서 확인한 값이다.
  키를 지울 때(접근 상실)도 같은 잠금 안에서, **저장소의 현재 키가 `IDENTITY_REVOKED`를 받은 요청에 쓴 키와 같을 때만** 지운다. 다르면(다른 탭이 이미 지우고 새 키를 만든 경우) 지우지 않는다. 늦게 도착한 이전 키의 응답이 새 키를 지우지 않게 하기 위해서다(S1-C4). Web Locks를 쓸 수 없는 환경은 입장을 막고 안내한다(NFR-008, 사용자 결정 OQ-032). 서버는 서로 다른 키로 온 요청을 같은 브라우저인지 알 수 없으므로 서로 다른 신원으로 처리한다(같은 닉네임이면 하나만 성공하고 나머지는 `NICKNAME_TAKEN`이다). 이 한계는 §13에 기록한다.
- **방 생성 시도와 키 연결**: 방 생성 전에는 초대 코드를 모르므로, 클라이언트는 방 생성 시도마다 "생성 대기" 항목(시도 ID, 신원 키)을 저장·재확인한 뒤 요청하고, `201` 응답의 `inviteCode`를 받으면 그 키를 코드에 연결하고 대기 항목을 지운다. 응답을 받지 못한(결과 불명) 재시도는 **같은 시도의 기존 신원 키를 재사용**한다(§6.5). 기존 키 재사용은 **응답 유실·결과 불명으로 인한 재시도에 한정**한다. 서버가 거부(4xx)해 방이 만들어지지 않았거나 사용자가 시도를 취소하면 시도가 끝나고 대기 항목을 지운다. 서로 다른 정상적인 방 생성 시도는 각각 새 키를 만든다.
- 신원 키 인증 방식(헤더)은 이 Spec에서 확정한다. **SSE 연결의 인증 방식은 S5에서 결정**하며 S1은 정하지 않는다.

### 3.2 문자열 검증 (방 이름, 정산 단위, 참여자 닉네임에 공통)
검증은 다음 순서로 한다. 자동 공백 제거는 하지 않는다.
0. 값이 없거나(`null` 포함) 빈 문자열이면 `REQUIRED`, 문자열이 아니면 `INVALID_TYPE`으로 거부한다. 원본 문자열이 64 코드 포인트를 넘으면 정규화하지 않고 `LENGTH_OUT_OF_RANGE`로 거부한다(분해형 한글 12자는 최대 36 코드 포인트이므로 정상 입력을 막지 않는다).
1. 입력 문자열을 Unicode **NFC**로 정규화한다. 이후 검사·저장·응답은 모두 정규화한 값이다.
2. **길이**: 정규화한 문자열의 코드 포인트 수가 12 이하인지 본다. 13 이상이면 `LENGTH_OUT_OF_RANGE`다. 길이 0(빈 문자열·누락)은 0번에서 `REQUIRED`로 이미 거부되었다.
3. **허용 문자**: 정규화한 문자열의 모든 코드 포인트가 다음 중 하나여야 한다. 아니면 `INVALID_CHARACTER`다.
   - 한글 완성형 음절 U+AC00~U+D7A3
   - 한글 호환 자모 U+3131~U+3163 (키보드로 입력하는 단독 자음·모음 ㄱ~ㅎ, ㅏ~ㅣ; NFC로 바뀌지 않는다)
   - 영문 `A-Z` `a-z`
   - 숫자 `0-9`
   - 공백 U+0020
   허용 범위 밖의 한글 코드 포인트는 거부한다: 조합용 자모 U+1100~U+11FF가 NFC 이후에도 음절로 합쳐지지 않고 남은 경우, 한글 채움 문자 U+3164(보이지 않음), 고어·확장 자모(U+3165~U+318E, U+A960~U+A97F, U+D7B0~U+D7FF). 제어 문자, 영문 외 라틴 문자, 전각 문자, 이모지, 특수문자도 거부한다.
4. **공백 규칙**: 첫 문자나 마지막 문자가 공백이면 `LEADING_OR_TRAILING_SPACE`, 공백이 둘 이상 이어지면 `CONSECUTIVE_SPACES`로 거부한다. 중간의 공백 한 칸은 허용한다.
5. 2~4의 위반은 서로 독립이므로 모아서 한 번에 반환한다(§3.4). 하나라도 있으면 거부한다.

닉네임 비교 키는 정규화한 문자열의 `A-Z`를 소문자로 바꾼 값이다. 이 키로 §2.3 I5의 중복을 판정하고, 이어받기 요청의 대상 참여자를 찾는다(§4.9). 한글·호환 자모·숫자·공백은 그대로 쓴다. 호환 자모 낱자 나열("ㅎㅏㄴ")과 완성형 음절("한")은 서로 다른 닉네임이며 NFC로 합쳐지지 않는다. 낱자 나열은 허용된 입력이다. AC-ROOM-006-13(분해형·조합형 한글이 같은 길이, 서로 중복)은 NFC로 음절이 합쳐지므로 그대로 충족된다.

### 3.3 검사 순서와 정보 노출
요청은 다음 순서로 검사하고 **처음 걸린 오류 하나**를 반환한다. 단 입력 검증 오류(7번)는 §3.4처럼 위반 항목 전체를 담는다.
0. **라우트 단계(인증 전)**: 정의되지 않은 경로는 `404 ROUTE_NOT_FOUND`, 경로는 있으나 메서드가 정의되지 않았으면 `405 NOT_SUPPORTED`(`Allow` 헤더 포함). 이 판정은 방·참여자 존재 여부를 조회하지 않으므로 어떤 정보도 드러내지 않는다.
1. 신원 키 누락·형식 오류(키가 필수인 경로): `401 UNAUTHENTICATED`
2. 방 또는 초대 코드 존재: `404 ROOM_NOT_FOUND`, `404 INVITE_NOT_FOUND`
3. **신원 상태**:
   - 키가 이 방에서 접근 상실(REVOKED)이면 `401 IDENTITY_REVOKED`. 이 키는 이 방을 이미 알던 브라우저만 가질 수 있으므로 방 존재를 새로 드러내지 않는다. 이 거부는 거래 요청의 같은 키 재전송(S2 부록 A)보다 먼저 판정한다(AC-ROOM-009-5).
   - `/rooms/{roomId}/…` 경로에서 키가 연결됨이 아니면(NONE, PENDING) **`404 ROOM_NOT_FOUND`**. 방이 없는 경우와 구별할 수 없게 해 임의의 키 보유자가 방 존재 여부를 확인하지 못하게 한다.
   - `/invites/{inviteCode}/…` 경로의 상태별 처리는 각 엔드포인트(§4.2, §4.3, §4.9~§4.11)가 정한다.
4. 방장 여부(방장 전용 동작): `403 HOST_ONLY`. 이 방의 참여자에게만 도달하므로 비참여자에게 방 정보를 드러내지 않는다.
5. 방 상태(`ENDED`에서 불가한 동작): `409 GAME_ENDED`
6. 대상 존재(예: 참여자 ID, 이어받기 요청 ID): `404 PARTICIPANT_NOT_FOUND`, `404 CLAIM_NOT_FOUND`. 다른 방의 대상 ID도 같다(AC-SYS-003-8).
7. 입력 검증: `422 VALIDATION_FAILED`
8. 상태 충돌: `409 NICKNAME_TAKEN`, `409 HOST_CANNOT_BE_DEACTIVATED`, `409 CLAIM_ALREADY_RESOLVED`, `409 CLAIM_REQUESTER_LINKED`
9. 한도: `409 PARTICIPANT_LIMIT_EXCEEDED`

- 6번이 7번보다 앞이다. 존재하지 않는 대상에는 본문 검증 결과를 알려 주지 않는다. 단 이어받기 요청 생성(§4.9)은 대상을 본문의 닉네임으로 찾으므로 7번(본문 형식) 뒤에 대상 존재를 본다.
- 비방장은 방이 종료됐든 본문이 틀렸든 `HOST_ONLY`를 받는다(4번이 5~7번보다 앞).
- 7~9번은 요청 처리 중 하나의 트랜잭션 안에서 판정한다(§7). 닉네임 중복과 한도가 동시에 해당하면 `NICKNAME_TAKEN`을 반환한다.

### 3.4 오류 응답
```json
{ "error": { "code": "VALIDATION_FAILED", "message": "…", "details": [ { "field": "nickname", "code": "CONSECUTIVE_SPACES" } ] } }
```
- `message`는 한국어 사용자 안내 문구이며 클라이언트가 그대로 보여 줄 수 있다. 분기는 `code`로 한다.
- `details`는 검증 오류와 한도 오류에서 쓴다. 한도 오류는 `[{ "limit": 10 }]`다.
- 검증 사유 코드(`details[].code`): `REQUIRED`, `LENGTH_OUT_OF_RANGE`, `LEADING_OR_TRAILING_SPACE`, `CONSECUTIVE_SPACES`, `INVALID_CHARACTER`, `INVALID_TYPE`(문자열이 아님), `INVALID_VALUE`(허용 목록 밖의 값, 예: `status`), `NOT_ALLOWED_FIELD`(변경 불가 필드를 보낸 경우).
- 모든 거부는 AC-SYS-003-5에 따라 데이터를 바꾸지 않고, 위 `code`로 서로 구분된다. 예외는 §2.3 I9 하나다.

| HTTP | `code` | 의미 |
| --- | --- | --- |
| 401 | `UNAUTHENTICATED` | 신원 키 누락·형식 오류 |
| 401 | `IDENTITY_REVOKED` | 이 방에서 이어받기 승인으로 접근을 잃은 신원 키(§3.1). 클라이언트는 키를 지우고 안내한다 |
| 403 | `HOST_ONLY` | 이 방의 비방장 참여자가 방장 전용 동작을 요청 |
| 404 | `ROOM_NOT_FOUND`, `INVITE_NOT_FOUND`, `PARTICIPANT_NOT_FOUND`, `CLAIM_NOT_FOUND` | 대상 없음. 방 비참여자도 `ROOM_NOT_FOUND`다(§3.3 3). 다른 방에 속한 참여자·요청 ID도 각각 `PARTICIPANT_NOT_FOUND`, `CLAIM_NOT_FOUND`(AC-SYS-003-8). 이어받을 수 없는 대상(방장 참여자)도 `PARTICIPANT_NOT_FOUND`다(§4.9, S1-C7) |
| 404 | `ROUTE_NOT_FOUND` | 정의되지 않은 경로(MVP에 없는 기능의 경로 포함) |
| 405 | `NOT_SUPPORTED` | 경로는 있으나 지원하지 않는 메서드(`Allow` 헤더) |
| 409 | `GAME_ENDED` | 종료된 방에서 불가한 동작(새 입장, 직접 추가, 상태 변경) |
| 409 | `NICKNAME_TAKEN` | 같은 방에 비교 키가 같은 참여자가 있음 |
| 409 | `PARTICIPANT_LIMIT_EXCEEDED` | 참여자 10명 한도 |
| 409 | `HOST_CANNOT_BE_DEACTIVATED` | 방장 참여자의 비활성화 요청(P-4) |
| 409 | `ALREADY_PARTICIPANT` | 이미 이 방의 참여자에 연결된 키의 이어받기 요청(AC-ROOM-009-2) |
| 409 | `CLAIM_PENDING` | 대기 중인 이어받기 요청이 있는 키의 새 입장 또는 두 번째 이어받기 요청(P-8) |
| 409 | `CLAIM_ALREADY_RESOLVED` | 이미 승인·거절·취소된 요청의 승인·거절·취소(AC-ROOM-009-8) |
| 409 | `CLAIM_REQUESTER_LINKED` | 승인 시점에 요청 브라우저가 이미 다른 참여자에 연결됨. 요청은 `REJECTED`로 바뀐다(AC-ROOM-009-14) |
| 422 | `VALIDATION_FAILED` | 입력 형식 위반 |

v0.2.3의 `MEMBER_LIMIT_EXCEEDED`는 없어졌다(한도가 참여자 하나로 합쳐짐, P-3).

## 4. API 계약

경로의 `{inviteCode}`는 초대 코드, `{roomId}`는 방 ID다. 모든 본문은 JSON(UTF-8)이다. 목록은 정렬 순서가 명시된 대로 반환한다. `Participant`는 §2.1의 응답 필드 전체(`id`, `roomId`, `nickname`, `status`, `order`, `isHost`, `createdAt`)다. 이어받기 요청은 받는 사람에 따라 두 형태로 응답한다(S1-C13).
- `Claim`(방장용, §4.12~§4.15): `id`, `participantId`, `nickname`, `status`, `rejectReason`, `createdAt`, `resolvedAt`, `resolvedById`.
- `MyClaim`(요청자용, §4.2, §4.9~§4.11): `id`, `nickname`, `status`, `rejectReason`, `createdAt`, `resolvedAt`. **참여자 ID와 처리한 방장의 ID는 담지 않는다.** 요청자는 아직 방 비참여자이므로 입장 전 공개 범위(AC-ROOM-004-1)를 지킨다. 승인된 요청자는 입장 요청(§4.3)으로 자기 참여자를 받는다.
`rejectReason`, `resolvedAt`, `resolvedById`는 해당 없으면 `null`이다.

### 4.1 `POST /rooms` — 방 생성 (FR-ROOM-001, 003, 007)
- 인증: `Authorization: Bearer <이 생성 시도의 신원 키>` 필수. 첫 참여자가 이 키에 연결된다.
- 요청: `{ "name": string, "unit": string, "nickname": string }` 세 필드 모두 필수. `name`, `unit`, `nickname`은 §3.2를 따른다. `unit`의 목록 선택(`원`, `점수`, `칩`)과 직접 입력은 서버에서 구분하지 않는다. 같은 문자열 규칙을 쓴다.
- 처리: 방(`status = IN_PROGRESS`, 초대 코드)과 첫 참여자(`nickname`, `status = ACTIVE`, `order = 1`, `isHost = true`, 이 키에 연결)를 한 트랜잭션에서 만든다. 초대 코드는 추측하기 어려운 URL-safe 난수(128비트 이상)다.
- 응답 `201`: `{ "room": Room 전체(inviteCode 포함), "me": Participant }`
- 오류: 401, 422. 이름 중복은 허용한다(AC-ROOM-001-5). 하나라도 위반하면 방도 참여자도 만들어지지 않는다.
- Idempotency Key는 없다. 같은 요청을 다시 보내면 별도의 방이 생긴다.

### 4.2 `GET /invites/{inviteCode}` — 초대 링크 조회 (FR-ROOM-002, 005, 009)
- 인증: `Authorization` 선택. 형식이 틀린 값은 오류 없이 "키 없음"으로 취급한다.
- 응답 `200`:
  ```json
  {
    "room": { "name": "…", "unit": "…", "status": "IN_PROGRESS" },
    "identity": "NONE" | "PARTICIPANT" | "PENDING" | "REVOKED",
    "claim": MyClaim | null,
    "claimableNicknames": ["…"]
  }
  ```
  - `identity`는 요청에 실린 키의 이 방 상태(§2.2)다. 키가 없으면 `NONE`이다. 자기 자신에 대한 정보이므로 노출해도 된다.
  - `claim`은 이 키로 만든 이어받기 요청 중 **가장 최근 것**이다(없으면 `null`). `PENDING`이면 대기 안내, `REJECTED`·`CANCELED`면 결과 안내에 쓴다(S1-C9).
  - `claimableNicknames`는 이어받기 후보다. **방장 참여자를 뺀 모든 참여자의 닉네임**을 `order` 오름차순으로 담는다(활성·비활성, 신원 연결 여부 무관, P-1). `identity`가 `NONE` 또는 `REVOKED`일 때만 채우고, `PARTICIPANT`·`PENDING`이면 빈 배열이다.
- **입장 전에 공개하는 것은 방 이름, 정산 단위, 진행 상태, 이어받기 후보 닉네임뿐이다**(AC-ROOM-004-1, AC-ROOM-009-1). 방 ID, 초대 코드, 참여자 ID·상태·`order` 값·방장 닉네임, 거래 내역, 인원 수는 담지 않는다. 후보 닉네임의 공개 범위가 종료된 방과 가득 찬 방에서 넓어지는 것은 PRD §8의 수용된 귀결이다.
- 오류: `404 INVITE_NOT_FOUND`(존재하지 않거나 형식이 틀린 초대 코드, AC-ROOM-002-4). 이 경로는 `IDENTITY_REVOKED`로 거부하지 않고 `identity = REVOKED`로 알린다.
- 방이 `ENDED`여도 `200`이다.

### 4.3 `POST /invites/{inviteCode}/members` — 입장 (FR-ROOM-002, 005, 006, 008, FR-PART-004)
경로 이름은 v0.2.3과 같다(S1-C3). 이 경로가 만드는 것은 참여자다.
- 인증: `Authorization: Bearer <신원 키>` 필수. 이전에 입장한 브라우저는 저장해 둔 키를, 처음이면 새로 만든 키를 보낸다.
- 요청: `{ "nickname"?: string }`
- 처리 (키의 이 방 상태로 분기):
  1. **연결됨**: **복원**한다. 닉네임은 무시하고 게임 상태·한도·닉네임 검사를 하지 않는다. 응답 `200`, `{ "room": {id,name,unit,status}, "me": Participant }`. 입장 응답이 이 방의 `id`를 처음 알려 준다. 방이 `ENDED`여도 복원한다(AC-ROOM-005-1).
  2. **접근 상실**: `401 IDENTITY_REVOKED`.
  3. **대기**: `409 CLAIM_PENDING`(P-8, AC-ROOM-009-9). 먼저 요청을 취소해야 한다.
  4. **없음**: 새 참여자를 만든다. 방이 `ENDED`면 `409 GAME_ENDED`(AC-ROOM-002-5, OQ-043). `nickname`은 필수이며 §3.3의 7(검증), 8(중복), 9(한도) 순서로 판정한다. 통과하면 참여자(`status = ACTIVE`, 다음 `order`, `isHost = false`, 이 키에 연결)를 만든다. 응답 `201`, 같은 형태.
- 같은 키로 동시에 두 요청이 도착하면 (방, 키 해시) 유일 제약에 따라 하나만 만들어지고 나머지는 같은 참여자를 `200`으로 복원한다(AC-ROOM-006-11 마지막 문장, AC-ROOM-002-8).
- 오류: 401 `UNAUTHENTICATED`/`IDENTITY_REVOKED`, 404 `INVITE_NOT_FOUND`, 409 `CLAIM_PENDING`/`GAME_ENDED`/`NICKNAME_TAKEN`/`PARTICIPANT_LIMIT_EXCEEDED`, 422.
- `NICKNAME_TAKEN`과 `PARTICIPANT_LIMIT_EXCEEDED`의 `message`는 기존 참여자라면 이어받기를 요청할 수 있음을 안내한다(AC-ROOM-002-6, AC-ROOM-008-8).

### 4.4 `GET /rooms/{roomId}` — 방 조회 (FR-ROOM-003)
- 인증: 필수, 이 방의 참여자(연결됨). 활성·비활성 모두.
- 응답 `200`: `{ "room": Room 전체, "me": Participant }`
- 오류: 401 `UNAUTHENTICATED`/`IDENTITY_REVOKED`, 404 `ROOM_NOT_FOUND`(비참여자 포함).

### 4.5 `GET /rooms/{roomId}/participants` — 참여자 목록 (FR-PART-001, 002)
- 인증: 필수, 이 방의 참여자. 활성·비활성 모두(OQ-044의 조회). 방 상태와 무관하게 조회할 수 있다.
- 응답 `200`: `{ "participants": Participant[] }` — `order` 오름차순, 비활성 참여자와 직접 추가한 참여자 포함.
- 오류: 401 `UNAUTHENTICATED`/`IDENTITY_REVOKED`, 404 `ROOM_NOT_FOUND`(비참여자 포함).

### 4.6 `POST /rooms/{roomId}/participants` — 참여자 직접 추가 (FR-PART-001, FR-ROOM-006, 008, FR-PART-004)
- 인증: 필수. 방장 전용.
- 요청: `{ "nickname": string }`
- 처리: §3.3 순서. `ENDED`면 `409 GAME_ENDED`. 통과하면 신원 키가 연결되지 않은 참여자(`status = ACTIVE`, 다음 `order`, `isHost = false`)를 만든다(OQ-042).
- 응답 `201`: `{ "participant": Participant }`
- 오류: 401, 403 `HOST_ONLY`, 404 `ROOM_NOT_FOUND`(비참여자 포함), 409 `GAME_ENDED`/`NICKNAME_TAKEN`/`PARTICIPANT_LIMIT_EXCEEDED`, 422.

### 4.7 `PATCH /rooms/{roomId}/participants/{participantId}` — 참여자 활성 상태 변경 (FR-PART-002, 003, 004)
- 인증: 필수. 방장 전용.
- 요청: `{ "status": "ACTIVE" | "INACTIVE" }` 이 한 필드만 허용한다. `status`가 없으면 `REQUIRED`, 문자열이 아니면 `INVALID_TYPE`, `ACTIVE`/`INACTIVE`가 아닌 값(예: `"PAUSED"`)이면 `INVALID_VALUE`로 `422 VALIDATION_FAILED`다. 다른 필드(`nickname` 등)가 있으면 `422 VALIDATION_FAILED`(`NOT_ALLOWED_FIELD`)로 거부하고 아무것도 바꾸지 않는다(AC-ROOM-006-8, AC-PART-003-1).
- 처리: `ENDED`면 `409 GAME_ENDED`. 대상이 방장 참여자이고 `status`가 `INACTIVE`면 `409 HOST_CANNOT_BE_DEACTIVATED`(P-4, AC-PART-002-10). 현재 상태와 같은 값을 보내면 실제 변경을 만들지 않고 `200`으로 현재 참여자를 반환한다(결정 N-4). 이 경우 이벤트도 발생시키지 않는다. 다르면 상태를 바꾸되 `order`, 닉네임, 신원 연결, 과거 거래·손익은 바뀌지 않는다. 비활성 참여자의 신원은 연결된 채로 남고 조회만 할 수 있다(OQ-044, 거래 변경 거부는 S2).
- 응답 `200`: `{ "participant": Participant }`
- 오류: 401, 403 `HOST_ONLY`, 404 `ROOM_NOT_FOUND`/`PARTICIPANT_NOT_FOUND`(다른 방의 참여자 ID 포함), 409 `GAME_ENDED`/`HOST_CANNOT_BE_DEACTIVATED`, 422. 검사 순서는 §3.3(5 → 6 → 7 → 8).

### 4.8 존재하지 않는 동작 (AC-ROOM-003-2, 004-4, 007-3, PART-003-1, 003-2)
HTTP 의미를 구분한다: **경로가 없으면 404 `ROUTE_NOT_FOUND`, 경로는 있으나 그 메서드를 지원하지 않으면 405 `NOT_SUPPORTED`** (`Allow` 헤더로 지원 메서드를 알린다). 둘 다 라우트 단계에서 판정하며(§3.3 0) 방·참여자 존재와 인증 여부에 따라 달라지지 않는다.

| 동작 | 응답 |
| --- | --- |
| 방 수정(이름·정산 단위 포함): `PATCH`/`PUT`/`DELETE /rooms/{roomId}` | 405, `Allow: GET` — 방장·게임 상태와 무관 |
| 참여자 수정(`status` 외)·삭제: `PUT`/`DELETE`/`POST /rooms/{roomId}/participants/{participantId}` | 405, `Allow: PATCH`. `PATCH`로 `status` 외 필드를 보내면 422 `NOT_ALLOWED_FIELD` |
| 참여자 목록·추가 경로의 다른 메서드 | 405, `Allow: GET, POST` |
| 이어받기 경로(§4.9~§4.15)의 정의되지 않은 메서드 | 405, 각 경로의 `Allow` |
| 방장 이전, 강제 퇴장, 초대 링크 재발급, 이어받기 밖의 신원 연결·해제·이동, 참여자 간 거래 이전, 이어받기 요청 수정 | 해당 경로를 정의하지 않으므로 404 `ROUTE_NOT_FOUND` |

### 4.9 `POST /invites/{inviteCode}/claims` — 이어받기 요청 (FR-ROOM-009)
- 인증: `Authorization: Bearer <신원 키>` 필수. 키 생성은 §3.1의 배타 구간을 따른다.
- 요청: `{ "nickname": string }` — 이어받을 참여자의 닉네임(초대 조회의 `claimableNicknames` 중 하나, S1-C7).
- 처리 (§3.3 순서. 3번은 아래 상태 분기):
  1. 키가 **연결됨**이면 `409 ALREADY_PARTICIPANT`(AC-ROOM-009-2). **접근 상실**이면 `401 IDENTITY_REVOKED`. **대기**면 `409 CLAIM_PENDING`(P-8).
  2. `nickname`이 없거나 문자열이 아니면 `422 VALIDATION_FAILED`(`REQUIRED`/`INVALID_TYPE`). 그 밖의 문자 규칙 검사는 하지 않는다(어차피 일치하는 참여자가 없으면 404다).
  3. NFC 정규화 후 비교 키(§3.2)가 같은 참여자를 찾는다. 없거나 **방장 참여자**면 `404 PARTICIPANT_NOT_FOUND`(AC-ROOM-009-3).
  4. 통과하면 `PENDING` 요청을 만든다. 게임 상태(`ENDED` 포함)와 한도는 보지 않는다(P-6, AC-ROOM-008-11). 대상의 상태(활성·비활성)와 신원 연결 여부도 보지 않는다(P-1).
- 응답 `201`: `{ "claim": MyClaim }`
- 같은 키로 동시에 두 요청이 도착하면 하나만 `PENDING`이 되고 나머지는 `409 CLAIM_PENDING`이다(§7).
- 이 요청은 참여자도 신원 연결도 만들지 않는다. 대기 중인 키는 방 비참여자다(AC-ROOM-004-1, AC-ROOM-009-1).
- 오류: 401 `UNAUTHENTICATED`/`IDENTITY_REVOKED`, 404 `INVITE_NOT_FOUND`/`PARTICIPANT_NOT_FOUND`, 409 `ALREADY_PARTICIPANT`/`CLAIM_PENDING`, 422.

### 4.10 `GET /invites/{inviteCode}/claims/{claimId}` — 내 이어받기 요청 조회 (FR-ROOM-009)
- 인증: 필수. 그 요청을 만든 키만 조회한다. 승인되어 키가 연결된 뒤에도 조회할 수 있다.
- 응답 `200`: `{ "claim": MyClaim }`
- 오류: 401 `UNAUTHENTICATED`/`IDENTITY_REVOKED`, 404 `INVITE_NOT_FOUND`/`CLAIM_NOT_FOUND`(다른 키의 요청, 다른 방의 요청 ID 포함).
- 결과를 새로고침 없이 전달하는 방법(실시간 또는 이 경로의 주기 조회)은 S5가 정한다(AC-VIEW-005-9).

### 4.11 `POST /invites/{inviteCode}/claims/{claimId}/cancel` — 이어받기 요청 취소 (FR-ROOM-009)
- 인증: 필수. 그 요청을 만든 키만 취소한다(AC-ROOM-009-9).
- 처리: 요청이 `PENDING`이면 `CANCELED`로 바꾼다(`resolvedAt` 기록). 아니면 `409 CLAIM_ALREADY_RESOLVED`. 게임 상태와 무관하다(AC-ROOM-009-10).
- 응답 `200`: `{ "claim": MyClaim }`
- 오류: 401 `UNAUTHENTICATED`/`IDENTITY_REVOKED`, 404 `INVITE_NOT_FOUND`/`CLAIM_NOT_FOUND`, 409 `CLAIM_ALREADY_RESOLVED`.

### 4.12 `GET /rooms/{roomId}/claims` — 대기 중인 이어받기 요청 목록 (FR-ROOM-009)
- 인증: 필수. 방장 전용(S1-C10).
- 응답 `200`: `{ "claims": Claim[] }` — `PENDING`만, `createdAt` 오름차순(같으면 `id` 오름차순). 요청 브라우저를 식별하는 정보는 담지 않는다. 방장은 대상 참여자(`participantId`, `nickname`)로 확인한다(AC-ROOM-009-4).
- 오류: 401 `UNAUTHENTICATED`/`IDENTITY_REVOKED`, 403 `HOST_ONLY`, 404 `ROOM_NOT_FOUND`(비참여자 포함).

### 4.13 `POST /rooms/{roomId}/claims/{claimId}/approve` — 이어받기 승인 (FR-ROOM-009)
- 인증: 필수. 방장 전용(AC-ROOM-009-11).
- 처리 (§3.3 순서, 한 트랜잭션):
  1. 요청이 없거나 다른 방의 요청이면 `404 CLAIM_NOT_FOUND`.
  2. 요청이 `PENDING`이 아니면 `409 CLAIM_ALREADY_RESOLVED`(AC-ROOM-009-8).
  3. 요청 키가 이 방에서 이미 다른 참여자에 연결되어 있으면 `409 CLAIM_REQUESTER_LINKED`로 거부하고, **같은 트랜잭션에서 그 요청만** `REJECTED`(`REQUESTER_LINKED`, `resolvedById` = 요청한 방장)로 바꾼다. 참여자 연결은 바뀌지 않는다(AC-ROOM-009-14, §2.3 I9). (정상 흐름에서는 대기 키의 입장이 `CLAIM_PENDING`으로 막히므로 일어나지 않지만, 경합과 우회 요청에 대비한 규칙이다.)
  4. 대상 참여자에 연결된 키가 있으면 그 키를 접근 상실(REVOKED)로 기록한다(P-2).
  5. 요청 키를 대상 참여자에 연결한다.
  6. 요청을 `APPROVED`로 바꾼다(`resolvedAt`, `resolvedById` = 요청한 방장 참여자 기록).
  7. 같은 대상 참여자의 다른 `PENDING` 요청을 모두 `REJECTED`(`TARGET_CLAIMED`, 같은 `resolvedById`)로 바꾼다(P-7).
- 게임 상태, 한도, 대상의 활성 상태와 무관하다(P-6, AC-ROOM-008-11). 대상의 닉네임·상태·`order`·`isHost`·거래·손익은 바뀌지 않는다(AC-ROOM-009-6).
- 응답 `200`: `{ "claim": Claim, "participant": Participant }`
- 오류: 401 `UNAUTHENTICATED`/`IDENTITY_REVOKED`, 403 `HOST_ONLY`, 404 `ROOM_NOT_FOUND`/`CLAIM_NOT_FOUND`, 409 `CLAIM_ALREADY_RESOLVED`/`CLAIM_REQUESTER_LINKED`.
- 요청 본문은 받지 않는다. 본문이 있으면 무시한다.

### 4.14 `POST /rooms/{roomId}/claims/{claimId}/reject` — 이어받기 거절 (FR-ROOM-009)
- 인증: 필수. 방장 전용(AC-ROOM-009-11).
- 처리: 요청이 없으면 `404 CLAIM_NOT_FOUND`, `PENDING`이 아니면 `409 CLAIM_ALREADY_RESOLVED`. 통과하면 `REJECTED`(`HOST_REJECTED`, `resolvedById` = 요청한 방장)로 바꾼다. 신원 연결은 바뀌지 않는다(AC-ROOM-009-7). 게임 상태와 무관하다.
- 응답 `200`: `{ "claim": Claim }`
- 오류: 401 `UNAUTHENTICATED`/`IDENTITY_REVOKED`, 403 `HOST_ONLY`, 404 `ROOM_NOT_FOUND`/`CLAIM_NOT_FOUND`, 409 `CLAIM_ALREADY_RESOLVED`.

### 4.15 `GET /rooms/{roomId}/claims/{claimId}` — 이어받기 요청 단건 조회 (방장, FR-ROOM-009)
- 인증: 필수. 방장 전용.
- 응답 `200`: `{ "claim": Claim }` — 상태와 무관하게(끝난 요청 포함) 돌려준다. 승인·거절의 응답이 유실됐을 때 방장이 현재 상태를 확인하는 데 쓴다(P-10, §6.5).
- 오류: 401 `UNAUTHENTICATED`/`IDENTITY_REVOKED`, 403 `HOST_ONLY`, 404 `ROOM_NOT_FOUND`/`CLAIM_NOT_FOUND`(다른 방의 요청 ID 포함).

## 5. 상태와 권한 표

### 5.1 방장 전용 동작 (FR-ROOM-007)
참여자 직접 추가(§4.6), 참여자 비활성화·재활성화(§4.7, 자기 자신의 비활성화 제외), 이어받기 요청 목록·단건 조회·승인·거절(§4.12~§4.15), 타인 거래 수정·삭제(S2), 게임 종료(S4). 이 방의 비방장 참여자가 요청하면 `403 HOST_ONLY`이다.

| 입장 | 없음: 새 입장(진행 중), 대기: `CLAIM_PENDING`, 접근 상실: `IDENTITY_REVOKED` | 복원 | 복원 | 복원 |

### 5.4 참여자 상태 전이
`ACTIVE ⇄ INACTIVE`(방장, 진행 중에만, 방장 참여자 제외). 초기 상태는 `ACTIVE`. 삭제 상태는 없다. 비활성 참여자는 새 거래의 당사자가 될 수 없고, 그 신원은 조회만 할 수 있다(거래 변경 거부는 S2, OQ-044). 기존 거래·손익·정산에서는 그대로 남으며 비활성 참여자가 포함된 기존 거래의 금액·사유·라운드는 권한 있는 사용자가 수정할 수 있다(S2). 닉네임은 계속 점유한다.

### 5.5 이어받기 요청 상태 전이
`PENDING → APPROVED`(방장 승인), `PENDING → REJECTED`(방장 거절 `HOST_REJECTED`, 같은 대상의 다른 요청 승인 `TARGET_CLAIMED`, 승인 시 요청 키가 이미 연결됨 `REQUESTER_LINKED`), `PENDING → CANCELED`(요청자 취소). 끝난 상태(`APPROVED`, `REJECTED`, `CANCELED`)에서 나가는 전이는 없다. 자동 만료는 없다(P-9).

## 6. 동작 규칙

### 6.1 신원
- 같은 신원 키로 같은 방에 다시 들어오면 같은 참여자로 복원된다. 이전 거래의 작성자이고 방장이면 방장 권한도 그대로다. 게임이 종료되어도 복원된다(AC-ROOM-005-1, -2, -6).
- 키를 잃은 브라우저는 이전 참여자로 인식되지 않는다. 새 닉네임으로 입장하거나(진행 중이고 한도가 남았을 때) 이어받기를 요청할 수 있다(AC-ROOM-005-3). 다른 브라우저·기기도 같다(005-5).
- 키를 잃은 이전 방장은 방장 참여자를 이어받을 수 없고(후보에 없고 요청은 `PARTICIPANT_NOT_FOUND`), 새로 입장하거나 다른 참여자를 이어받아도 방장이 아니다(AC-ROOM-005-4, 009-3).
- 방장 신원 키가 사라져도 아무도 방장이 되지 않는다. 그 방은 종료할 수 없고 이어받기 요청을 승인할 사람이 없는 상태로 남을 수 있으며 수용된 귀결이다(AC-ROOM-005-7, 운영은 OQ-034). 이런 방의 대기 요청은 요청자가 취소할 때까지 남는다(P-9).
- 이어받기 승인으로 끊긴 이전 키는 그 방의 모든 요청에서 `401 IDENTITY_REVOKED`를 받는다(AC-ROOM-005-8, 009-5). 클라이언트는 키를 지우고 신원 없는 브라우저로 돌아간다(D-2, §3.1).
- 새 참여자로 접근하는 경로는 방 생성과 입장뿐이고, 기존 참여자로 접근하는 경로는 복원과 이어받기 승인뿐이다(AC-ROOM-004-1).

### 6.2 닉네임
- §3.2 규칙을 모든 참여자에 하나의 범위로 적용한다. 입장으로 생긴 참여자와 직접 추가한 참여자, 비활성 참여자 사이에서도 비교 키가 같으면 중복이다(AC-ROOM-006-5, -6, -10). 방이 다르면 같은 닉네임을 쓸 수 있다(006-7).
- 조합형·분해형 한글은 정규화 뒤 같아지므로 중복이다(AC-ROOM-006-13).
- 이어받기는 닉네임을 새로 정하지 않는다(AC-ROOM-006-8).

### 6.3 방 이름, 정산 단위
- 방 이름은 §3.2를 따르고 중복을 허용한다. 정산 단위는 §3.2를 따르며, 방에 저장된 같은 값이 금액 표시·정산 결과·복사 텍스트에 쓰인다(AC-ROOM-001-14, AC-ROOM-003-3). 변경과 환산은 없다.

### 6.4 한도 (FR-ROOM-008)
- 참여자 한도 10명은 새 참여자를 만드는 요청(새 입장 §4.3 4, 직접 추가 §4.6)만 검사한다. 방 생성은 첫 참여자를 만들지만 빈 방이므로 한도에 걸리지 않는다. 복원과 이어받기 요청·승인은 한도와 무관하게 성공한다(AC-ROOM-008-11).
- 비활성 참여자, 직접 추가한 참여자, 신원을 잃어 더는 접속하지 않는 참여자도 센다(008-6, -7, -8). 대기 중인 이어받기 요청은 세지 않는다.
- 한도 초과 요청은 부분 저장 없이 거부된다(008-4). 오류 응답은 `code`와 `details.limit`로 알린다.
- 동시 요청: 닉네임 중복을 포함해 다른 검증을 모두 통과하는 서로 다른 새 입장·직접 추가가 마지막 슬롯에 동시에 도착하면 정확히 하나만 슬롯을 얻고 나머지는 `PARTICIPANT_LIMIT_EXCEEDED`다(008-5). 같은 닉네임이 겹치는 경쟁에서는 중복 판정이 우선하므로 진 요청은 `NICKNAME_TAKEN`이다(006-11). 같은 키의 입장은 슬롯을 한 번만 소비하고 나머지는 `200` 복원이다(§4.3).
- 거래 한도(1,000건, 삭제된 거래 포함)는 S2 계약이 정한다(AC-ROOM-008-3, -9, -10과 008-5의 거래 부분).

### 6.5 응답 유실과 재시도
- 방 생성: PRD는 방 생성에 Idempotency Key를 두지 않고(C§3.4는 거래 생성·수정·삭제, C§5.1은 종료에만 적용) 방 이름 중복을 허용한다(AC-ROOM-001-5). 따라서 서버는 같은 요청의 재시도를 중복으로 판별하지 않으며, 재시도하면 별도의 방이 생긴다. 이 규칙을 바꾸려면(예: 키 기준 중복 방지) 정책 변경이므로 이 Spec에서 만들지 않았다. 응답을 못 받은 경우 클라이언트는 자동 재전송하지 않는다. 결과를 알 수 없어 사용자가 같은 시도를 재시도할 때는 **그 시도의 기존 신원 키를 재사용**한다(N-11). 이는 멱등성을 보장하지 않는다. 첫 요청이 실제로 성공했다면 재시도는 별도의 두 번째 방을 만들고, 두 방의 방장 참여자에 같은 키 해시가 연결된다. 서버는 키를 방 안에서만 식별하므로(§3.1) 이 상태는 계약 위반이 아니다. 클라이언트는 두 번째 방의 `201` 응답에 연결하며, 응답을 잃은 첫 방은 초대 코드를 아는 사람이 없는 고아 방이 된다. 최근 방 목록이 없고(AC-ROOM-002-3) 방 보관 정책은 OQ-034이므로 복구 경로를 만들지 않는다.
- 입장: 같은 신원 키로 재시도하면 서버가 이미 참여자를 만들었다면 `200`으로 같은 참여자가 복원되고, 만들지 않았다면 새 입장으로 처리된다(AC-ROOM-002-8).
- 입장의 `NICKNAME_TAKEN`·`PARTICIPANT_LIMIT_EXCEEDED`: 아직 참여자가 아니므로 참여자 목록을 조회하지 않는다. 다른 닉네임을 입력하거나, 기존 참여자라면 이어받기를 요청하도록 안내한다(AC-ROOM-002-6, 008-8). 같은 신원 키의 재시도는 복원이라 이 오류가 나지 않는다.
- 참여자 직접 추가(방장): Idempotency Key가 없다. 응답이 유실된 뒤 같은 닉네임으로 다시 추가하면 `409 NICKNAME_TAKEN`일 수 있다. 클라이언트는 이 오류를 받으면 참여자 목록(§4.5)을 다시 조회하고, 같은 닉네임(비교 키 기준)의 참여자가 이미 있으면 "이미 등록되어 있습니다"로 안내한다. 이 안내는 기존 등록 사실만 알리며, 그 등록이 응답이 유실된 요청의 결과라고 단정하지 않는다(다른 방장 탭, 이전 시도, 같은 닉네임의 입장이 만들었을 수 있다). 이 처리는 AC-PART-001-6(사용자 결정 OQ-038)이다.
- 참여자 상태 변경: 방이 진행 중이고 그 사이 다른 변경이 없었다면 같은 값 재요청은 `200`이라 재시도해도 안전하다. 그러나 응답 유실 사이에 다른 방장 탭이 상태를 바꿨다면 재시도는 그 변경을 덮어쓰고, 종료됐다면 `409 GAME_ENDED`다. 클라이언트는 재시도 전에 참여자 목록을 다시 조회해 현재 상태를 확인한다(N-3, N-4).
- 이어받기(P-10, Idempotency Key 없음):
  - 요청 생성의 응답 유실: 같은 키로 다시 보내면 첫 요청이 저장됐다면 `409 CLAIM_PENDING`이다. 클라이언트는 이 오류를 받거나 결과를 모르면 초대 조회(§4.2)를 다시 해 `claim`으로 현재 요청을 안내한다.
  - 취소·승인·거절의 응답 유실: 다시 보내면 첫 요청이 처리됐다면 `409 CLAIM_ALREADY_RESOLVED`다. 요청자(취소)는 내 요청 조회(§4.10)로, 방장(승인·거절)은 요청 단건 조회(§4.15)로 현재 상태를 다시 확인해 안내하며, 그 상태가 자기 요청의 결과라고 단정하지 않는다(다른 방장 탭이나 같은 대상의 다른 승인이 만들었을 수 있다).

## 7. 동시성과 정합성

서버는 다음을 요청 처리 중 한 트랜잭션(또는 동등한 원자성)에서 보장해야 한다. 구현 방법은 Plan에서 정하며 DB 유일 제약, 방 단위 직렬화 같은 수단을 쓸 수 있다.
1. **닉네임 유일성**: (방, 비교 키) 유일. 동시에 같은 닉네임으로 참여자를 만드는 요청(입장·직접 추가·둘의 조합)이 오면 정확히 하나가 성공하고 나머지는 `NICKNAME_TAKEN`이다(AC-ROOM-006-11). 단 같은 신원 키의 입장 요청은 중복으로 거부하지 않고 `200`으로 같은 참여자를 복원한다(§4.3).
2. **한도**: 방마다 참여자 수 확인과 삽입이 분리되지 않는다. 마지막 슬롯 경쟁에서 한도를 넘지 않는다(AC-ROOM-008-5).
3. **참여자 `order`**: 서버 처리 순서대로 서로 다른 값. 입장과 직접 추가가 동시에 와도 유일하다(AC-PART-001-4, -5).
4. **신원 키 상태의 유일성**: (방, 키 해시)는 §2.2 상태 중 하나에만 있다. 같은 키의 동시 입장은 한 참여자만 만들고, 같은 키의 동시 이어받기 요청은 `PENDING` 하나만 만들며, 같은 키의 입장과 이어받기 요청이 동시에 오면 먼저 처리된 쪽만 성공하고 다른 쪽은 각각 `CLAIM_PENDING` 또는 `ALREADY_PARTICIPANT`다(AC-ROOM-004-3, 006-11, 009-9).
5. **이어받기 처리의 단일성**: 같은 요청에 승인·거절·취소가 동시에 오면 정확히 하나만 성공하고 나머지는 `CLAIM_ALREADY_RESOLVED`다. 같은 대상에 대한 서로 다른 요청의 승인이 동시에 오면 하나만 승인되고 나머지 요청은 `TARGET_CLAIMED`로 거절되어, 늦게 처리된 승인 요청은 `CLAIM_ALREADY_RESOLVED`를 받는다(AC-ROOM-009-8). 승인의 2~7단계(§4.13)는 한 트랜잭션이다.
6. **이어받기 승인과 입장의 경합**: 승인은 처리 시점에 요청 키가 연결됐는지 다시 확인한다(§4.13 3, AC-ROOM-009-14). 어떤 경합에서도 한 키는 한 방에서 최대 한 참여자에 연결된다.
7. **참여자 변경·새 입장과 게임 종료**: 상태 검사와 변경은 같은 직렬화 안에 있어야 한다. 종료가 먼저 처리되면 이후 도착한 직접 추가·상태 변경·새 입장은 `GAME_ENDED`다(AC-PART-004-1, -2, AC-ROOM-002-7). 이어받기는 종료와 무관하다.
8. **참여자 비활성화와 거래 생성·변경**: 처리 시점의 참여자 상태로 판정한다. 비활성화가 먼저 처리되면 이후의 거래 생성(그 참여자를 당사자로 하는 것)과 그 참여자 신원의 거래 변경은 거부된다(AC-PART-002-8, -13, 거래 쪽 거부는 S2). 이를 위해 S2의 거래 처리는 참여자 `status`를 같은 트랜잭션에서 읽어야 한다.
9. **이어받기 승인과 이전 키의 요청**: 승인이 먼저 처리되면 이후 도착한 이전 키의 요청은 `IDENTITY_REVOKED`다. 승인 전에 처리된 요청의 결과는 유효하다.
10. **방장 일의성**: 방 생성 트랜잭션 안에서만 `isHost`가 정해지며 이후 쓰기 경로가 없다.

## 8. 실시간 이벤트 발생 지점 (스키마는 S5)

S1이 만드는 변경 중 새로고침 없이 반영되어야 하는 것(FR-VIEW-005)은 다음이다. 이벤트 이름·페이로드·전달 대상·방식은 S5가 정한다.
- 참여자 생성: 입장(§4.3의 `201`)과 직접 추가(§4.6) — 방의 참여자에게(AC-VIEW-005-3)
- 참여자 활성 상태 변경(§4.7) — 방의 참여자에게, 상태가 바뀐 참여자 자신의 권한 표시 포함(AC-VIEW-005-3)
- 이어받기 요청 생성·취소(§4.9, §4.11) — 방장의 대기 요청 표시(AC-VIEW-005-9)
- 이어받기 승인·거절(§4.13, §4.14, 승인에 딸린 `TARGET_CLAIMED` 거절 포함) — 요청한 브라우저에 결과, 방장의 대기 요청 표시(AC-VIEW-005-9)
- 이어받기 승인에 따른 이전 신원의 접근 상실(§4.13 4) — 이전 브라우저가 다음 요청(`IDENTITY_REVOKED`)이나 실시간 연결에서 안내받음(AC-VIEW-005-9)

입장의 복원(`200`)은 이벤트 대상이 아니다(참여자가 바뀌지 않는다). 같은 값으로의 참여자 상태 변경 재요청(§4.7)은 이벤트를 만들지 않는다. 승인은 참여자의 표시 필드를 바꾸지 않으므로 다른 참여자에게 참여자 변경 이벤트를 보낼 필요가 없다.

## 9. 프론트엔드 책임

- 방 생성 화면: 방 이름, 정산 단위(목록 `원`·`점수`·`칩` 선택 또는 직접 입력), 생성자 닉네임. §3.2 규칙으로 즉시 검증하되 서버 검증이 최종이다(AC-ROOM-001-12, -13). 오류 시 입력을 유지하고 사유를 안내한다. 생성 뒤 생성자는 첫 참여자(방장)로 방 화면에 들어간다.
- 신원 키: §3.1의 배타 구간(잠금 → 저장소 재확인 → 없으면 생성·저장·재확인 → 잠금 해제)을 지킨다. 저장 실패, 저장소 차단, Web Locks 미지원은 입장 전에 사용자에게 알린다. 키를 서버가 복구할 수 없고 잃으면 방장 승인으로만 되찾을 수 있음을 사용자에게 숨기지 않는다. 방 생성 응답을 받지 못했을 때 자동 재전송하지 않으며, 사용자가 같은 시도를 재시도할 때는 그 시도의 기존 신원 키를 재사용한다(§3.1, §6.5). 별개의 새 방 생성은 새 키를 쓴다.
- 초대 링크 화면(`/invite/{inviteCode}`): `GET /invites/{inviteCode}`로 시작한다.
  - `identity = PARTICIPANT`: 닉네임 입력 없이 입장 요청(§4.3)으로 복원한다.
  - `identity = NONE`: 진행 중이면 닉네임 입장과 이어받기(후보 닉네임 목록에서 선택)를 함께 보인다. 종료된 방이면 새 입장 대신 "게임이 종료되어 새로 입장할 수 없습니다"를 보이고 이어받기만 보인다(AC-ROOM-002-5). 후보가 없으면 이어받기를 보이지 않는다. 최근 요청(`claim`)이 `REJECTED`나 `CANCELED`면 그 결과를 한 번 안내한다(AC-ROOM-009-7).
  - `identity = PENDING`: 대상 닉네임과 "방장의 승인을 기다리는 중"을 보이고 취소 버튼을 둔다(AC-ROOM-009-1, -9). 방 정보는 보이지 않는다. 결과가 오면(S5) 승인이면 입장 요청(§4.3)으로 방에 들어가고, 거절이면 안내 뒤 `NONE` 화면으로 돌아간다.
  - `identity = REVOKED`: 접근을 잃었다는 사실을 안내하고 키를 지운 뒤 `NONE` 화면을 보인다(AC-ROOM-005-8, D-2).
  - 입장 전 화면에는 방 이름·정산 단위·진행 상태와 이어받기 후보 닉네임만 보인다. 404면 오류를 보인다. 방 코드 입력 화면과 최근 방 목록은 만들지 않는다(AC-ROOM-002-2, -3).
- 입장 요청의 `NICKNAME_TAKEN`·`PARTICIPANT_LIMIT_EXCEEDED`: 입력한 닉네임을 유지하고, 기존 참여자라면 이어받기를 할 수 있다고 안내하며 이어받기 선택으로 이동할 수 있게 한다(AC-ROOM-002-6, 008-1, 008-8). `CLAIM_PENDING`이면 대기 화면으로, `GAME_ENDED`면 종료 안내로 바꾼다.
- 어떤 방 요청에서든 `401 IDENTITY_REVOKED`를 받으면 방 화면을 닫고 접근을 잃었다는 안내와 함께 초대 링크 화면의 `NONE` 상태로 보낸다(AC-VIEW-005-9). 이때 저장된 키를 §3.1의 조건부 삭제로 지운다(저장 키가 그 요청에 쓴 키와 같을 때만).
- 방장 화면: 대기 중인 이어받기 요청을 대상 닉네임과 함께 보이고 요청마다 승인·거절 컨트롤을 둔다(AC-ROOM-009-4). 같은 대상에 요청이 여럿이면 하나만 승인할 수 있음을 드러낸다. 게임이 종료되어도 이 컨트롤은 남는다(AC-ROOM-009-10). 승인·거절의 `CLAIM_ALREADY_RESOLVED`는 단건 조회(§4.15)로 현재 상태와 처리한 방장(`resolvedById`를 참여자 목록의 닉네임으로)을 안내한다(§6.5, AC-ROOM-004-5).
- 정산 단위·방 이름·닉네임의 변경 UI를 만들지 않는다(AC-ROOM-003-1, 006-8, PART-003-1). 방장 이전, 강제 퇴장, 링크 재발급, 이어받기 밖의 신원 연결·해제 UI도 만들지 않는다(AC-ROOM-004-4, 007-3).
- 한도 초과(`PARTICIPANT_LIMIT_EXCEEDED`)는 초과 항목을 안내하고 입력한 닉네임을 화면에 유지한다(AC-ROOM-008-1, -2).
- 참여자 화면: 목록은 `order` 순. 방장 표시(`isHost`), 비활성 참여자 표시, 방장에게만 직접 추가·비활성화·재활성화 컨트롤. 방장 자기 자신의 행에는 비활성화 컨트롤이 없다(AC-PART-002-10). 종료 후에는 직접 추가·상태 변경 컨트롤을 숨기거나 비활성화한다(AC-PART-004-3). 비활성 참여자는 거래 입력의 당사자 선택지에서 제외한다(AC-PART-002-3의 UI 쪽).
- 비활성 참여자 자신의 화면: 조회만 가능함을 알리고 거래 입력·수정·삭제 컨트롤을 비활성화하거나 숨긴다(AC-PART-002-11의 UI 쪽, 거래 화면은 S2·S3). 재활성화되면 컨트롤이 돌아온다(AC-PART-002-12).
- 참여자 직접 추가의 `NICKNAME_TAKEN` 수신 시 §6.5의 재조회·안내를 한다.
- 오류 `code`로 분기하고 `message`는 그대로 쓴다. 클라이언트 검증은 서버를 대체하지 않는다.

## 10. 백엔드 책임

- §3.1 신원 키 해시 저장과 방 단위 인증, §2.2 키 상태 관리, §3.3 검사 순서, §3.4 오류 형식을 정확히 구현한다.
- §4 모든 엔드포인트와 §4.8의 비제공 동작.
- §7의 원자성·유일성·직렬화 보장. 방 존재 여부를 모르는 호출자에게 다른 방의 정보를 노출하지 않는다. 이어받기 요청 브라우저를 식별하는 정보(키 해시)를 응답에 담지 않는다.
- 클라이언트 값 불신: 방장 여부, 상태, 한도, 닉네임 규칙, 이어받기 대상의 자격을 모두 서버가 판정한다(NFR-002).
- 이 Spec의 계약을 다른 저장소 문서에 복제하지 않고 Spec 버전 또는 `ddallang` 커밋으로 참조한다.

## 13. 위험
- 신원 키는 브라우저 저장소에 있으므로 같은 브라우저에서 스크립트가 읽을 수 있다(XSS 방지는 프론트 Plan 책임). 유출되면 해당 참여자를 도용할 수 있다. 피해 참여자가 이어받기로 되찾을 수 있지만(이어받으면 유출된 키는 접근을 잃는다) 방장 참여자는 되찾을 수 없다.
- **이어받기 남용**: 초대 링크를 가진 누구나 방장이 아닌 참여자의 이어받기를 요청할 수 있다. 방장의 승인만이 방어선이며, 방장이 요청자를 대면으로 확인하지 않고 승인하면 다른 사람이 참여자를 가져갈 수 있다(가져간 참여자의 이전 키는 접근을 잃는다). 요청 횟수 제한은 없다(남용 방지는 PRD 범위 밖). 프론트엔드는 승인 전에 "요청한 사람이 그 참여자 본인인지 확인하세요"를 안내한다.
- 이어받기 후보 닉네임은 링크만 가진 사람에게 공개된다. 종료된 방과 가득 찬 방에서는 입장할 수 없는 사람도 닉네임을 볼 수 있다(PRD §8 수용).
- 방장 신원을 잃은 방에서 대기 요청은 처리될 수 없고 만료도 없어 영구히 남는다(P-9, OQ-034).
- 호환 자모 낱자 나열("ㅎㅏㄴ")과 완성형 음절("한")은 서로 다른 닉네임이라 읽기에 비슷한 닉네임이 공존할 수 있고, 이어받기 후보에서도 헷갈릴 수 있다. 조합용 자모는 NFC 뒤 남으면 거부하므로 눈으로 구별되지 않는 코드 포인트 쌍은 허용되지 않는다.
- 서버는 서로 다른 신원 키를 같은 브라우저로 묶지 못한다. 탭 사이 배타 수행(§3.1)을 지키지 못하는 클라이언트는 같은 사람이 둘로 보일 수 있다.
- 방 생성은 멱등하지 않다. 응답 유실 후 같은 시도를 재시도하면 별도의 방이 중복 생성될 수 있고(이름 중복 허용 정책의 귀결), 이때 같은 신원 키가 두 방의 방장 참여자에 연결된다. 서버는 이 두 방을 서로 연결하는 정보(같은 해시)를 보관하게 되지만 다른 사용자에게는 노출하지 않는다. 키가 유출되면 두 방이 모두 영향을 받는다. 응답을 잃은 방은 아무도 초대 코드를 모르는 고아 방으로 남을 수 있다(OQ-034).
- R-01(`open-questions.md`): 한도 슬롯을 회수할 수단이 없다. 비활성 참여자와 신원을 잃은 참여자가 슬롯을 계속 점유한다. 이어받기가 신원을 잃은 참여자를 되살리는 길이 되어 R-01의 영향은 줄었다.
- 닉네임 오입력: 입장한 브라우저는 자기 참여자에 묶여 다른 참여자로 옮길 수 없고, 방장의 오입력 닉네임은 고칠 수 없다(PRD §8, 사용자 수용).
- 남용 방지(요청 속도 제한 등)는 PRD 범위가 아니며 이 Spec에서 정하지 않았다.
