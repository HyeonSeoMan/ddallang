## 1. 제품 목적과 MVP 범위

### 1.1 목적
딸랑은 오프라인 게임 참여자 사이의 지급 의무를 기록하고, 실시간 순손익과 정산 결과를 계산하는 웹 서비스다. (POL §1)

### 1.2 하지 않는 일
게임 점수를 자동 산출하지 않는다. 실제 송금·결제를 처리하지 않고 송금 완료 여부도 관리하지 않는다. (POL §1)

### 1.3 MVP 포함 범위 (C§1.1)
1. 방 생성, 초대 링크 입장, 익명 RoomMember
2. 참여자 등록·관리
3. 단건 거래 생성·수정·삭제
4. 실시간 거래 목록과 누적 손익
5. 진행 중 예상 정산
6. 게임 종료, 최종 정산, 정산 결과 복사
7. 필수 서버 권한 검사, 데이터 정합성, 중복 요청 방지, 오류 처리

## 2. 용어

| 용어 | 정의 |
| --- | --- |
| 방 (Room) | 하나의 게임 정산 단위. 방 이름과 정산 단위를 가진다. |
| RoomMember (접속자) | 초대 링크로 입장한 익명 접속 주체. 거래 작성자·방장이 될 수 있다. |
| Participant (참여자) | 손익이 집계되는 게임 참여자. 접속하지 않아도 존재한다. 활성/비활성 상태를 가진다. |
| 방장 | 현재 방장 권한을 가진 RoomMember. 방 생성 브라우저의 RoomMember가 최초 방장이다. |
| 거래 | 지급자(Participant)가 수취자(Participant)에게 금액을 지급할 의무를 기록한 단건 기록. |
| 유효 거래 | 삭제되지 않은 거래. 목록·순손익·정산에 포함된다. |
| 게임 상태 | `진행 중` 또는 `종료됨`. |
| 순손익 | 참여자별로 (수취한 유효 거래 금액 합) − (지급한 유효 거래 금액 합). |
| 예상 정산 | 진행 중 전체 유효 거래로 계산한 정산 결과. |
| 최종 정산 | 게임 종료 후 표시하는 정산 결과. 계산 알고리즘은 예상 정산과 같다. |
| 멱등 키 (idempotency key) | 같은 요청의 재전송을 서버가 식별하는 값. |

## 3. 사용자 역할과 권한

| 역할 | 설명 | 주요 권한 |
| --- | --- | --- |
| 방장 | 현재 방장인 RoomMember | 참여자 추가·비활성화·재활성화, 모든 거래 수정·삭제, 게임 종료, (일반 접속자 권한 전부) |
| 일반 접속자 | 방장이 아닌 RoomMember | 거래 생성, 본인이 작성한 거래의 수정·삭제, 목록·손익·정산 조회 |
| 참여자 | 게임 참여자(Participant). 접속 여부와 무관 | 거래의 지급자·수취자가 됨. 별도 권한 없음 |

참여자 **추가**는 방장만 할 수 있다(사용자 결정 OQ-037, 2026-11-07). 통합 정책 C§2.7은 추가 주체를 명시하지 않고 기존 POL-PART-001은 방장이 추가한다고 하는데, 사용자가 방장만으로 확정했다.

방장 권한은 초대 링크 자체로 부여되지 않는다. (POL-ROOM-006)

## 4. 주요 사용자 흐름

- **S1 방 시작**: 사용자가 방 이름과 정산 단위를 정해 방을 만든다. 서버가 방 생성 브라우저의 RoomMember를 최초 방장으로 지정하고 초대 링크를 만든다. 다른 사람은 링크와 닉네임만으로 입장한다. (FR-ROOM-001~003)
- **S2 참여자 구성**: 방장이 참여자를 등록하고, 진행 중에도 추가한다. 이탈한 참여자는 비활성화한다. (FR-PART-001~003)
- **S3 거래 기록**: 접속자가 "A가 B에게 N"을 기록한다. 금액·사유·라운드를 잘못 적었으면 작성자 또는 방장이 수정한다. 당사자를 잘못 적었으면 삭제 후 새로 기록한다. (FR-TXN-001~008)
- **S4 실시간 확인**: 누적 손익 순위와 거래 목록을 보고, 참여자별 필터로 거래를 좁혀 본다. 진행 중에는 예상 정산을 본다. (FR-VIEW-001~005, FR-SET-008)
- **S5 종료와 정산**: 방장이 확인 후 게임을 종료하고, 최종 정산을 조회해 텍스트로 복사한다. 종료 후에도 유효한 초대 링크로 입장한 사람은 조회할 수 있다. (FR-SET-001~007, FR-ROOM-002)
- **S6 연결 끊김**: 오래된 데이터를 최신처럼 보이지 않게 하고, 복구 시 서버 상태를 다시 조회한다. (FR-SYS-001~002)
- **S7 브라우저 재접속**: 같은 브라우저면 이전 신원을 복원한다. 신원을 잃으면 새 접속자로 입장하며 권한은 복구되지 않는다. (FR-ROOM-005)

## 5. 기능 요구사항

표기: 각 FR은 근거 `POL`과 `통합`(C§) 앵커, 수용 기준(AC)을 가진다. 서버 측 거부는 클라이언트 검증과 무관하게 서버 API가 거부함을 뜻한다. `[결정 대기: OQ-xxx]`는 해당 부분이 확정되지 않았음을 뜻한다.

**AC 해석 규약** (모든 AC에 적용된다. 이 규약은 개별 AC보다 먼저 읽는다)

1. 별도 표기가 없으면 AC가 말하는 "요청"은 **처음 도착한 새 요청**이다. 서버가 이미 처리해 결과를 기록한 요청의 재전송은 부록 A를 따른다.
2. "등록된다·생성된다·저장된다·성공한다"처럼 정상 처리를 말하는 AC는 그 요청이 권한·유효성 검사를 통과하고 한도(수용 여력)와 게임 상태 조건을 만족한다고 전제한다. 이 전제를 충족하지 못하는 경우의 결과는 해당 거부 AC가 정한다.
3. 여러 요청의 동시 도착을 말하는 AC는 서로 다른 키 또는 서로 다른 입력의 요청을 뜻하며, 같은 신원(예: 방장 한 사람의 여러 탭)이 보낸 요청도 포함한다. 같은 키의 중복은 부록 A, 같은 브라우저(같은 신원)의 중복 입장은 AC-ROOM-005-1을 따른다.

### 5.1 방과 익명 신원

#### FR-ROOM-001 방 생성
- POL: POL-ROOM-002
- 통합: C§2.1, C§2.2, C§2.3
- 요구사항: 사용자는 방 이름과 정산 단위를 정해 방을 만든다. 방 이름은 필수이며 1~12자, 한글·영문·숫자·중간 공백만 허용한다. 앞뒤 공백, 특수문자, 이모지는 불가하다. 방 이름은 중복될 수 있다. 서버는 방 생성 브라우저에 익명 RoomMember 신원을 발급하고 그 RoomMember를 최초 방장으로 지정한다. 생성된 방은 `진행 중`이며 초대 링크를 가진다. 방 생성 시 생성자의 RoomMember 닉네임을 필수로 입력받는다(사용자 결정 OQ-027). 방 이름 길이(1~12자)는 NFC 정규화 후 문자 수로 판정하고 중간 연속 공백은 거부한다(사용자 결정 OQ-008). 정산 단위는 필수이며 목록(`원`, `점수`, `칩`)에서 고르거나 직접 입력한다. 직접 입력은 방 이름과 같은 규칙을 따른다(NFC 정규화 후 1~12자, 한글·영문·숫자·중간 공백만, 연속·앞뒤 공백·특수문자·이모지 불가). 이 결정은 사용자 위임에 따른 Claude 결정이다(OQ-036, `open-questions.md` 2.2절).
- AC:
  - AC-ROOM-001-1: 유효한 방 이름과 정산 단위로 생성하면 `진행 중` 상태의 방과 초대 링크가 만들어지고, 생성 브라우저에 RoomMember 신원이 발급된다.
  - AC-ROOM-001-2: 방 이름이 비어 있으면 생성되지 않는다.
  - AC-ROOM-001-3: 방 이름 길이 1과 12는 허용되고 0과 13은 거부된다.
  - AC-ROOM-001-4: "Friday 7"처럼 한글·영문·숫자와 중간 공백 하나로 구성된 이름은 허용되고, 앞뒤 공백, 특수문자, 이모지가 포함된 이름은 거부된다. 앞뒤 공백은 자동으로 제거되지 않고 거부된다.
  - AC-ROOM-001-5: 같은 이름의 방을 여러 개 만들 수 있다.
  - AC-ROOM-001-6: 정산 단위가 선택·입력되지 않으면 생성되지 않는다.
  - AC-ROOM-001-7: 생성 직후 방장 수는 1이고, 그 방장은 생성 브라우저의 RoomMember다.
  - AC-ROOM-001-8: 위 규칙 위반은 클라이언트 검증을 우회한 요청에서도 서버가 거부하고 방이 만들어지지 않는다.
  - AC-ROOM-001-9: 방 생성 시 생성자의 RoomMember 닉네임이 없거나 FR-ROOM-006의 규칙을 어기면 방이 만들어지지 않는다. 유효하면 그 닉네임이 최초 방장의 닉네임이 된다.
  - AC-ROOM-001-10: 중간에 공백이 둘 이상 연속된 방 이름("Friday  7")은 거부된다.
  - AC-ROOM-001-11: 방 이름의 길이는 NFC 정규화 후 문자 수로 판정한다. 조합형 한글과 분해형 한글로 쓴 같은 이름은 같은 길이로 계산된다.
  - AC-ROOM-001-12: 방 생성 화면에서 정산 단위를 목록(`원`, `점수`, `칩`)에서 선택할 수 있다.
  - AC-ROOM-001-13: 정산 단위를 직접 입력할 수 있다. "포인트"와 "Chip 10"처럼 방 이름 규칙(NFC 정규화 후 1~12자, 한글·영문·숫자·중간 공백 하나)에 맞는 값은 허용된다. 길이 0과 13, 앞뒤 공백, 중간 연속 공백, 특수문자, 이모지가 포함된 값은 클라이언트 검증을 우회한 요청에서도 서버가 거부하고 방이 만들어지지 않는다.
  - AC-ROOM-001-14: 선택하거나 입력한 정산 단위가 그 방의 단위로 저장되어 금액 표시와 정산 결과, 복사 텍스트에 같은 값으로 쓰이며 이후 변경할 수 없다(FR-ROOM-003).

#### FR-ROOM-002 초대 링크 입장
- POL: POL-ROOM-001
- 통합: C§1.1, C§2.3, C§2.7
- 요구사항: 회원가입이나 비밀번호 없이 닉네임과 초대 링크만으로 방에 입장한다. 방 코드 입력 방식과 최근 방 목록은 제공하지 않는다. 게임이 종료된 뒤에도 유효한 초대 링크로 새 RoomMember가 입장해 조회할 수 있다. RoomMember 한도는 FR-ROOM-008을 따른다.
- AC:
  - AC-ROOM-002-1: 유효한 초대 링크와 유효한 닉네임으로 입장하면 계정 생성이나 비밀번호 없이 RoomMember가 생성된다.
  - AC-ROOM-002-2: 방 코드를 입력해 입장하는 화면·API가 없다.
  - AC-ROOM-002-3: 최근 방 목록 화면이 없다.
  - AC-ROOM-002-4: 존재하지 않거나 잘못된 초대 링크로는 입장되지 않고 오류가 표시된다.
  - AC-ROOM-002-5: 게임이 `종료됨`이어도 유효한 초대 링크로 새 RoomMember가 입장하고 손익·거래 목록·최종 정산을 조회할 수 있다. 종료 후 입장자는 거래 추가·수정·삭제 등 변경 동작을 할 수 없다.

#### FR-ROOM-003 정산 단위 불변
- POL: POL-ROOM-002
- 통합: C§2.2
- 요구사항: 정산 단위는 방 생성 시 정해지며 이후 변경할 수 없다. 단위 간 환산은 없다.
- AC:
  - AC-ROOM-003-1: 방 생성 후 정산 단위를 변경하는 UI가 없다.
  - AC-ROOM-003-2: 정산 단위 변경 요청은 방장 여부와 게임 상태와 무관하게 서버가 거부한다.
  - AC-ROOM-003-3: 금액·정산 결과는 방의 정산 단위로만 표시되며 환산 값은 표시되지 않는다.

#### FR-ROOM-004 RoomMember와 Participant 독립
- POL: POL-ROOM-003
- 통합: C§2.4, C§1.2
- 요구사항: RoomMember와 Participant는 독립된 개체이며 MVP에서 둘을 연결하거나 해제하는 기능은 없다. 참여자가 아닌 접속자도 거래를 기록할 수 있고, 접속하지 않은 참여자도 존재할 수 있다.
- AC:
  - AC-ROOM-004-1: 어떤 Participant와도 연결되지 않은 RoomMember가 거래를 등록할 수 있다.
  - AC-ROOM-004-2: 접속한 RoomMember가 없는 Participant가 거래의 지급자·수취자가 될 수 있다.
  - AC-ROOM-004-3: 입장(RoomMember 생성)만으로 Participant가 자동 생성되지 않는다.
  - AC-ROOM-004-4: Participant 등록만으로 RoomMember가 자동 생성되지 않는다.
  - AC-ROOM-004-5: RoomMember와 Participant를 연결하거나 해제하는 UI·API가 없다.

#### FR-ROOM-005 브라우저 기반 신원 복원
- POL: POL-ROOM-004
- 통합: C§2.3
- 요구사항: 동일 브라우저로 같은 방에 재접속하면 기존 RoomMember 신원을 복원한다. 신원을 잃으면 새 RoomMember로 입장하며 기존 작성자 신원과 방장 권한을 복구하지 않고, 다른 RoomMember에게 방장이 자동 승계되지도 않는다.
- AC:
  - AC-ROOM-005-1: 입장한 브라우저에서 같은 초대 링크를 다시 열면 닉네임 재입력 없이 같은 RoomMember로 복원된다.
  - AC-ROOM-005-2: 복원된 RoomMember는 이전에 작성한 거래를 수정·삭제할 수 있다.
  - AC-ROOM-005-3: 브라우저 식별자가 삭제된 상태에서 입장하면 새 RoomMember가 되고, 이전 거래의 작성자로 인식되지 않는다.
  - AC-ROOM-005-4: 브라우저 식별자를 잃은 이전 방장은 새 RoomMember로 입장해도 방장 권한이 없다.
  - AC-ROOM-005-5: 다른 브라우저·기기에서 같은 링크로 입장하면 새 RoomMember가 된다.
  - AC-ROOM-005-6: 브라우저 식별자를 유지한 방장이 같은 브라우저로 재접속하면 같은 RoomMember로 복원되고 방장 권한을 그대로 가진다.
  - AC-ROOM-005-7: 방장 신원이 복구 불가능하게 사라져도 다른 RoomMember가 자동으로 방장이 되지 않는다. 이 방은 게임을 종료할 수 없는 상태로 남을 수 있으며, 이는 정책의 귀결로 수용된다.

#### FR-ROOM-006 닉네임 규칙
- POL: POL-ROOM-005
- 통합: C§2.6
- 요구사항: RoomMember 닉네임과 Participant 닉네임은 각각 1~12자이며 한글·영문·숫자·중간 공백만 허용한다. 앞뒤 공백, 특수문자, 이모지는 불허한다. 같은 방 안에서 같은 유형끼리 대소문자 구분 없이 중복될 수 없다. 자동 공백 제거는 없으며 등록 후 변경할 수 없다. 비활성 Participant의 닉네임도 재사용할 수 없다(활성·비활성 참여자 모두 고유성 대상). 길이(1~12자)는 NFC 정규화 후 문자 수로 판정하고, 중간 연속 공백은 거부한다. 대소문자 무시 중복 비교는 정규화한 문자열에 적용한다(사용자 결정 OQ-008).
- AC:
  - AC-ROOM-006-1: 길이 1과 12의 닉네임은 허용되고, 길이 0과 13은 거부된다.
  - AC-ROOM-006-2: 한글·영문·숫자로 구성된 닉네임과 단어 사이 공백 하나("Kim Min")는 허용된다.
  - AC-ROOM-006-3: 앞 또는 뒤에 공백이 있는 닉네임은 자동 제거되지 않고 거부된다.
  - AC-ROOM-006-4: 특수문자(예: `!`, `_`, `-`)와 이모지가 포함된 닉네임은 거부된다.
  - AC-ROOM-006-5: 같은 방에서 "Kim"이 사용 중이면 "kim"과 "KIM"은 같은 유형(RoomMember끼리, Participant끼리)에서 거부된다.
  - AC-ROOM-006-6: RoomMember 닉네임 "Kim"과 Participant 닉네임 "Kim"은 같은 방에서 공존할 수 있다.
  - AC-ROOM-006-7: 서로 다른 방에서는 같은 닉네임을 사용할 수 있다.
  - AC-ROOM-006-8: 등록된 RoomMember·Participant 닉네임을 변경하는 UI가 없고, 변경 요청은 서버가 거부한다.
  - AC-ROOM-006-9: 위 규칙 위반은 클라이언트 검증을 우회한 요청에서도 서버가 거부한다.
  - AC-ROOM-006-10: 비활성 참여자의 닉네임과 대소문자 구분 없이 같은 닉네임으로 새 참여자를 등록하면 거부된다.
  - AC-ROOM-006-12: 중간에 공백이 둘 이상 연속된 닉네임("Kim  Min")은 거부된다.
  - AC-ROOM-006-13: 길이는 NFC 정규화 후 문자 수로 판정하고, 조합형·분해형으로 쓴 같은 한글 닉네임은 같은 길이이며 서로 중복으로 취급된다.
  - AC-ROOM-006-11: 같은 방에서 같은 유형의 같은 닉네임(대소문자 무시)으로 새 RoomMember 또는 Participant를 만드는 서로 다른 요청이 동시에 둘 이상 도착하면(서로 다른 신원의 입장, 또는 방장의 여러 참여자 등록 요청), 정확히 하나만 성공하고 나머지는 중복으로 거부된다. 같은 브라우저(같은 신원)가 보낸 중복 입장 요청은 새 RoomMember를 만들지 않고 AC-ROOM-005-1에 따라 같은 RoomMember로 복원된다.

#### FR-ROOM-007 방장 권한 경계
- POL: POL-ROOM-006, POL-PART-001, POL-PART-002, POL-TXN-004, POL-SET-001
- 통합: C§2.3, C§2.7, C§3.2, C§5.1, C§1.2
- 요구사항: 방장 권한은 초대 링크 자체로 부여되지 않는다. 최초 방장은 서버가 방 생성 브라우저의 RoomMember로 지정한다. 방장 전용 동작은 참여자 추가·비활성화·재활성화, 타인 거래 수정·삭제, 게임 종료다. 방장 이전, 강제 퇴장, 초대 링크 재발급은 MVP 범위가 아니다.
- AC:
  - AC-ROOM-007-1: 초대 링크로 새로 입장해 생성된 RoomMember는 방장이 아니다. 방장이 복원 가능한 재접속을 한 경우는 AC-ROOM-005-6을 따른다.
  - AC-ROOM-007-2: 방장 전용 동작을 비방장 RoomMember가 요청하면 서버가 거부한다.
  - AC-ROOM-007-3: 방장 이전, 강제 퇴장, 초대 링크 재발급 기능과 API가 없다.

#### FR-ROOM-008 운영 한도
- POL: 해당 없음 (통합 정책 신규)
- 통합: C§2.5, C§7.3
- 요구사항: 방마다 RoomMember는 최대 10명, Participant는 최대 10명, 거래는 최대 1,000건이다. 통합 정책 C§2.5는 RoomMember·Participant 한도에 상태별 예외를 두지 않으므로, **비활성 참여자와 신원을 잃어 남은 RoomMember를 포함해 방에 존재하는 모든 개체를 센다.** 한도를 초과하는 요청은 원자적으로 거부하고, 입력을 보존하며, 초과한 항목을 안내한다. 거래 한도 1,000건에는 삭제된 거래를 포함해 센다. 삭제해도 슬롯은 회복되지 않는다(사용자 결정 OQ-004). 슬롯을 회수할 수단이 없다는 운영 위험은 `open-questions.md`의 R-01에 기록했다.
- AC:
  - AC-ROOM-008-1: RoomMember가 10명인 방에서 11번째 입장은 거부되고 RoomMember 한도 초과가 안내되며, 입력한 닉네임은 화면에 유지된다. 10번째 입장은 성공한다.
  - AC-ROOM-008-2: Participant가 10명인 방에서 11번째 등록은 거부되고 참여자 한도 초과가 안내되며, 입력한 닉네임은 화면에 유지된다.
  - AC-ROOM-008-3: 삭제된 거래를 포함해 거래가 1,000건인 방에서 1,001번째 거래를 만드는 새 생성 요청은 거부되고 거래 한도 초과가 안내되며, 입력값은 유지된다.
  - AC-ROOM-008-10: 1,000번째 거래 생성이 성공한 뒤 같은 키·같은 내용의 생성 요청이 재전송되면 한도 초과로 거부되지 않고 최초 성공 결과가 반환되며 거래는 1,000건을 넘지 않는다.
  - AC-ROOM-008-4: 한도 초과로 거부된 요청은 부분적으로도 저장되지 않는다.
  - AC-ROOM-008-5: 다른 검증(권한·유효성·닉네임 중복)을 모두 통과한 서로 다른 새 요청(서로 다른 멱등 키의 거래 생성, 그리고 멱등 키 규정이 없는 입장·참여자 등록) 둘 이상이 마지막 남은 슬롯에 동시에 도착하면 슬롯을 소비하는 요청은 정확히 하나이고 나머지 새 요청은 한도 초과로 거부되며 한도를 넘지 않는다. 이미 기록된 요청의 재전송, 같은 브라우저의 신원 복원, 닉네임 중복으로 거부되는 요청은 이 AC의 대상이 아니다(각각 AC-TXN-007-8, AC-ROOM-005-1, AC-ROOM-006-11). 같은 키·같은 내용의 거래 생성 요청이 동시에 둘 이상 도착하면 슬롯은 한 번만 소비되고 모두 같은 성공 결과를 받는다.
  - AC-ROOM-008-11: RoomMember가 10명인 방에서 기존 신원을 복원하는 재접속은 한도를 이유로 거부되지 않는다(AC-ROOM-005-1). 한도는 새 RoomMember의 생성에만 적용된다.
  - AC-ROOM-008-6: 한도는 상태와 무관하게 방에 존재하는 모든 RoomMember와 Participant를 센다. 비활성 참여자와, 신원을 잃어 더는 접속하지 않는 RoomMember도 한도에 포함된다.
  - AC-ROOM-008-7: Participant가 10명인 방에서 1명을 비활성화해도 11번째 참여자 등록은 거부된다.
  - AC-ROOM-008-8: RoomMember가 10명인 방에서 그중 일부가 접속 중이 아니어도 새 입장은 거부된다.
  - AC-ROOM-008-9: 거래 한도 1,000건은 삭제된 거래를 포함해 센다. 거래 1,000건 중 일부를 삭제해도 슬롯은 회복되지 않으며, 그 방에서 새 거래를 만드는 새 요청은 거부된다.

### 5.2 참여자

#### FR-PART-001 참여자 등록
- POL: POL-PART-001
- 통합: C§2.7
- 요구사항: 진행 중 참여자를 추가할 수 있다. 닉네임은 FR-ROOM-006을 따른다. 참여자 추가는 방장만 할 수 있다(사용자 결정 OQ-037). 참여자 수 한도는 FR-ROOM-008을 따른다. 참여자 추가·상태 변경 요청에는 멱등 키 규정이 없다(C§3.4는 거래 생성·수정·삭제, C§5.1은 종료에만 적용). 응답 유실 뒤 재시도의 동작은 OQ-038에서 확인한다.
- AC:
  - AC-PART-001-1: 방장이 유효한 닉네임으로 참여자를 등록하면 참여자가 `활성` 상태로 생성된다.
  - AC-PART-001-2: 게임 `진행 중`에도 참여자를 추가할 수 있다.
  - AC-PART-001-3: 방장이 아닌 RoomMember의 참여자 추가 요청은 서버가 거부한다.
  - AC-PART-001-4: 참여자에게 등록 순서가 부여되고 이후 변하지 않는다(정렬 기준: FR-VIEW-002, FR-SET-003, FR-SET-004).
  - AC-PART-001-5: 서로 다른 닉네임의 참여자 등록 요청이 동시에 도착해도 모든 참여자의 등록 순서는 서로 다르며, 순서는 서버가 처리한 순서로 결정된다.
  - AC-PART-001-6: 참여자 등록의 응답이 유실된 뒤 같은 닉네임으로 다시 등록하면 닉네임 중복으로 거부될 수 있다. 이때의 안내와 재조회 동작은 OQ-038 해결 전까지 정의하지 않는다.

#### FR-PART-002 참여자 비활성화·재활성화
- POL: POL-PART-002
- 통합: C§2.7, C§3.2
- 요구사항: 방장만 참여자를 비활성화·재활성화할 수 있다. 비활성 참여자는 새 거래의 당사자로 선택할 수 없다. 과거 거래와 손익은 보존된다. 비활성 참여자가 포함된 기존 거래는 허용된 필드(금액·사유·라운드)를 수정할 수 있다.
- AC:
  - AC-PART-002-1: 방장이 활성 참여자를 비활성화하면 상태가 `비활성`이 되고, 재활성화하면 `활성`으로 돌아간다.
  - AC-PART-002-2: 비활성화 전후로 해당 참여자의 과거 거래와 누적 손익 값이 변하지 않는다.
  - AC-PART-002-3: 신규 거래 등록 시 비활성 참여자는 지급자·수취자로 선택할 수 없고, 서버도 이를 지정한 신규 거래 요청을 거부한다.
  - AC-PART-002-4: 재활성화된 참여자는 다시 신규 거래의 당사자로 선택할 수 있다.
  - AC-PART-002-5: 비방장의 비활성화·재활성화 요청은 서버가 거부한다.
  - AC-PART-002-6: 비활성 참여자의 손익은 순손익 목록과 정산 계산에서 제외되지 않는다.
  - AC-PART-002-7: 비활성 참여자가 지급자 또는 수취자인 기존 거래의 금액·사유·라운드를 권한 있는 사용자가 수정할 수 있다.
  - AC-PART-002-8: 참여자 비활성화와 그 참여자를 당사자로 하는 신규 거래 생성이 동시에 도착하면 서버가 처리 시점의 참여자 상태로 판정하며, 비활성화 이후에 처리된 거래는 거부된다.
  - AC-PART-002-9: 비활성화와 재활성화는 참여자의 등록 순서를 바꾸지 않는다.

#### FR-PART-003 참여자 이름 변경·기록 이전 금지
- POL: POL-PART-003
- 통합: C§2.6
- 요구사항: 참여자 이름 직접 변경과 기록의 다른 참여자 이전은 제공하지 않는다. 오입력은 기존 참여자를 비활성화하고 새 참여자를 등록해 처리한다. 비활성 참여자의 닉네임은 재사용할 수 없으므로 새 참여자는 다른 닉네임을 사용해야 한다.
- AC:
  - AC-PART-003-1: 참여자 이름 변경 UI와 API가 없다.
  - AC-PART-003-2: 거래의 지급자·수취자를 다른 참여자로 일괄 이전하는 기능이 없다.
  - AC-PART-003-3: 오입력 참여자를 비활성화한 뒤 다른 닉네임의 새 참여자를 등록하는 흐름이 가능하다.

#### FR-PART-004 종료 후 참여자 변경 금지
- POL: POL-PART-004
- 통합: C§2.7
- 요구사항: 게임 종료 후에는 참여자 추가와 활성 상태 변경이 불가능하다.
- AC:
  - AC-PART-004-1: 종료된 게임에서 참여자 추가 요청은 서버가 거부한다.
  - AC-PART-004-2: 종료된 게임에서 참여자 비활성화·재활성화 요청은 서버가 거부한다.
  - AC-PART-004-3: 종료된 게임에서는 관련 UI 컨트롤이 비활성화되거나 숨겨진다.

### 5.3 단건 거래

#### FR-TXN-001 거래 데이터
- POL: POL-TXN-001
- 통합: C§3.1, C§3.2
- 요구사항: 거래는 지급자, 수취자, 금액(필수)과 사유, 라운드(선택)를 가진다. 지급자와 수취자는 서로 다른 Participant ID다. 사유는 최대 50자, 라운드는 최대 12자의 텍스트이며 둘 다 선택 입력이다(사용자 결정 OQ-009). 허용 문자와 공백 처리는 미결정이다(OQ-039). 오류가 있으면 저장을 거부하고 입력을 유지한다.
- AC:
  - AC-TXN-001-1: 유효한 지급자, 수취자, 금액을 지정하면 거래가 등록된다.
  - AC-TXN-001-2: 사유와 라운드 없이도 거래가 등록된다.
  - AC-TXN-001-3: 지급자, 수취자, 금액 중 하나라도 없으면 거래가 등록되지 않고 입력이 화면에 유지된다.
  - AC-TXN-001-4: 거래는 작성자(RoomMember)와 서버가 부여한 원본 생성 시각을 기록한다.
  - AC-TXN-001-5: 한 번의 요청·입력으로 여러 거래를 일괄 등록하는 기능이 없다.
  - AC-TXN-001-6: 사유 50자와 라운드 12자는 허용되고 사유 51자와 라운드 13자는 거부되며 입력은 화면에 유지된다. 수정에도 같은 규칙이 적용된다. 허용 문자와 앞뒤·연속 공백 처리는 OQ-039 해결 전까지 정의하지 않는다.

#### FR-TXN-002 거래 값 검증
- POL: POL-TXN-002
- 통합: C§3.1
- 요구사항: 금액은 1 이상 999,999,999 이하의 정수다. 상한은 모든 정산 단위에 동일하다. 지급자와 수취자가 같은 Participant ID인 거래는 금지한다.
- AC:
  - AC-TXN-002-1: 금액 1과 999,999,999는 허용된다.
  - AC-TXN-002-2: 금액 0, 음수, 소수(예: 1.5), 숫자가 아닌 값, 1,000,000,000은 거부된다.
  - AC-TXN-002-3: 지급자와 수취자가 동일 Participant ID이면 거부된다.
  - AC-TXN-002-4: 위 위반은 등록·수정 모두에서 서버가 거부한다.
  - AC-TXN-002-5: 정산 단위가 원이든 점수든 칩이든 같은 상한이 적용된다.

#### FR-TXN-003 거래 등록 권한
- POL: POL-TXN-003
- 통합: C§3.2
- 요구사항: 진행 중에는 방에 입장한 모든 RoomMember가 거래를 등록할 수 있다.
- AC:
  - AC-TXN-003-1: 방장이 아닌 RoomMember도 진행 중 게임에서 거래를 등록할 수 있다.
  - AC-TXN-003-2: 방에 입장하지 않은 주체의 거래 등록 요청은 서버가 거부한다.
  - AC-TXN-003-3: 등록된 거래의 작성자는 요청한 RoomMember로 서버가 기록한다. 요청 본문의 작성자 값은 신뢰하지 않는다.

#### FR-TXN-004 거래 수정·삭제 권한
- POL: POL-TXN-004
- 통합: C§3.2
- 요구사항: 거래의 수정·삭제는 해당 거래의 작성자 또는 현재 방장만 할 수 있으며, 서버가 권한을 검증한다.
- AC:
  - AC-TXN-004-1: 작성자는 자신의 거래를 수정·삭제할 수 있다.
  - AC-TXN-004-2: 현재 방장은 타인이 작성한 거래를 수정·삭제할 수 있다.
  - AC-TXN-004-3: 작성자도 방장도 아닌 RoomMember의 수정·삭제 요청은 서버가 거부한다.
  - AC-TXN-004-4: 화면의 버튼 노출 여부와 무관하게 서버가 요청 시점에 권한을 검증한다.

#### FR-TXN-005 수정·삭제 동작
- POL: POL-TXN-005
- 통합: C§3.2, C§3.3
- 요구사항: 수정은 금액·사유·라운드만 가능하며 별도 확인 없이 저장한다. 지급자, 수취자, 거래 ID, 작성자, 원본 생성 시각은 변경할 수 없다. 당사자를 잘못 적었으면 삭제 후 새 거래를 만든다. 삭제는 확인 절차를 거친다. 삭제된 거래는 일반 목록, 순손익, 정산에서 제외하고 최소한의 감사 데이터를 보존한다. 상세 감사 UI는 MVP에 없다. 최초 삭제만 성공하고, 새로운 반복 삭제 요청은 `이미 삭제된 거래입니다`로 거부한다.
- AC:
  - AC-TXN-005-1: 수정 시 확인 대화상자 없이 저장 동작으로 곧바로 반영된다.
  - AC-TXN-005-2: 삭제 시 확인 절차가 있고, 확인 전에는 거래가 삭제되지 않는다. 취소하면 거래는 그대로다.
  - AC-TXN-005-3: 삭제 확정 후 해당 거래는 일반 거래 목록, 모든 참여자의 순손익, 예상·최종 정산에서 제외된다.
  - AC-TXN-005-4: 삭제 후에도 서버에 원본 내용과 작성자 식별 정보가 최소한으로 보존된다. 이 기록의 조회 화면과 변경 이력 조회 기능은 MVP에 없다.
  - AC-TXN-005-5: 수정이 성공하면 이후 조회되는 순손익과 예상 정산은 수정된 금액을 기준으로 정확히 계산된다. 반영 지연의 수치 기준은 OQ-019 해결 전까지 정의하지 않는다.
  - AC-TXN-005-6: 지급자, 수취자, 거래 ID, 작성자, 원본 생성 시각을 바꾸는 수정 요청은 서버가 거부하고 거래는 변하지 않으며, 수정 UI에 해당 입력이 없다.
  - AC-TXN-005-7: 당사자를 잘못 적은 거래를 삭제한 뒤 올바른 당사자로 새 거래를 만들 수 있고, 새 거래는 새 거래 ID와 새 생성 시각을 가진다.
  - AC-TXN-005-8: 이미 삭제된 거래에 대한 새로운 삭제 요청(다른 멱등 키)은 `이미 삭제된 거래입니다`로 거부되고 순손익은 변하지 않는다.

#### FR-TXN-006 동시 수정과 삭제된 거래
- POL: POL-TXN-006
- 통합: C§3.5
- 요구사항: 같은 거래에 대한 동시 수정은 서버에서 마지막으로 성공한 저장을 최종값으로 한다. 삭제된 거래는 수정할 수 없다.
- AC:
  - AC-TXN-006-1: 두 사용자가 같은 거래를 거의 동시에 수정하면, 서버에서 나중에 성공한 저장 값이 최종값이 된다.
  - AC-TXN-006-2: 삭제된 거래에 대한 새 수정 요청(다른 멱등 키)은 서버가 거부하고 오류를 사용자에게 알린다. 같은 키의 재전송은 AC-TXN-007-9를 따른다.
  - AC-TXN-006-3: 동시 수정 후에도 모든 참여자의 순손익 합계는 0이다.
  - AC-TXN-006-4: 서로 다른 키의 수정과 삭제가 동시에 도착하면 서버 처리 순서에 따라 하나의 일관된 결과만 남고, 삭제 후 처리된 새 수정 요청은 AC-TXN-006-2로 거부된다.

#### FR-TXN-007 중복 요청 방지 (멱등 키)
- POL: POL-TXN-007
- 통합: C§3.4
- 요구사항: 거래 생성·수정·삭제 요청에 멱등 키를 적용한다. 동일 키·동일 내용 재시도는 최초 결과를 재사용한다. 이 재전송(replay)은 새 변경이 아니므로, 서버가 이미 처리해 결과를 기록한 요청이라면 게임 종료나 거래 삭제 이후에도 상태 검사로 다시 판정하지 않고 최초 결과를 그대로 반환하며 추가 변경을 일으키지 않는다. 이 보장은 키 유효 기간(24시간) 이내에, 최초 결과가 성공이거나 상태에 따른 영구적 거부(`이미 삭제된 거래입니다`, 게임 종료 후 거부, 한도 초과)였던 경우에 적용한다. 한도 초과는 현재 정책에 슬롯을 회수할 수단이 없어(R-01) 영구적 거부로 본다. 비활성 참여자 지정이나 검증 실패로 거부된 요청은 부작용이 없으므로 서버는 그 키와 결과를 기록하지 않으며, 같은 키·같은 내용으로 키 유효 기간 이내에 다시 보내면 새 요청으로 처리해 그 시점의 상태를 다시 검사한다(OQ-026 잔여의 위임 결정, `open-questions.md` 2.2절). 서버가 처리한 기록이 없는 키(요청이 도달하지 못한 경우)는 새 요청으로 취급해 현재 상태를 검사한다. 정리표는 부록 A에 있다. 동일 키·다른 내용은 충돌로 거부한다. 불명확한 네트워크 실패는 동일 키로 수동 재시도하고, 요청 내용이 바뀌면 새 키를 쓴다. 저장 중에는 중복 제출을 막는다. 내용이 같아도 키가 다른 별개 거래는 허용한다. 멱등 키는 방과 접속자(RoomMember) 단위로 유효하다(사용자 결정 OQ-026). **키 유효 기간은 클라이언트가 요청을 처음 시도한 시각부터 24시간**이며, 서버는 최소 그 시점까지 키와 결과를 보관한다(사용자 결정 OQ-026·OQ-040). 키 유효 기간이 지난 뒤 같은 키로 재시도하면 서버 기록의 유무와 상관없이 새 요청으로 처리하지 않고 만료로 거부한다(사용자 결정 OQ-040). 서버 처리 결과를 알 수 없는 실패는 같은 키로 수동 재시도하고, 서버가 확정 거부한 뒤 입력을 바꾸면 새 키를 쓴다. 비활성 참여자 지정·검증 실패로 거부된 요청의 키 처리는 위에 적은 대로다(AC-TXN-007-13).
- AC:
  - AC-TXN-007-1: 저장 요청이 진행 중인 동안 저장 컨트롤이 비활성화되어 두 번째 제출이 발생하지 않는다.
  - AC-TXN-007-2: 같은 키·같은 내용의 생성 요청이 키 유효 기간(24시간) 이내에 두 번 이상 도달해도 거래 생성은 최대 한 번만 일어난다. 최초 결과가 성공이면 거래는 정확히 1건 존재하고 이후 요청에는 그 성공 결과가 반환된다. 최초 결과가 영구적 거부이면 거래는 0건이고 이후 요청에는 같은 거부 결과가 반환된다(AC-TXN-007-10). 비활성 참여자 지정·검증 실패로 거부된 요청은 키가 기록되지 않으므로 AC-TXN-007-13을 따른다. 수정·삭제도 같은 키·같은 내용 재요청이 부작용을 한 번만 일으킨다. 24시간이 지난 재시도는 AC-TXN-007-12를 따른다.
  - AC-TXN-007-3: 지급자·수취자·금액·사유·라운드가 모두 같아도 키가 다른 두 생성 요청은, 두 요청 모두 유효하고 거래 한도에 두 건을 받을 여력이 있으면 별개의 거래 2건으로 저장된다. 여력이 한 건뿐이면 AC-ROOM-008-5를 따른다.
  - AC-TXN-007-4: 키 유효 기간 이내에 서버가 기록한 키로 다른 내용의 요청이 오면 충돌로 거부되고 기존 데이터는 변하지 않는다. 키 유효 기간이 지난 뒤에는 내용이 같든 다르든 만료 거부가 우선한다(AC-TXN-007-12).
  - AC-TXN-007-5: 서버가 거래를 저장했으나 응답이 도달하지 못한 경우, 사용자가 화면에 유지된 같은 입력을 키 유효 기간(최초 시도 후 24시간) 이내에 수동 재시도하면 같은 키가 사용되어 거래는 1건만 존재한다.
  - AC-TXN-007-6: 사용자가 입력 내용을 바꿔 다시 제출하면 새 키를 사용한다.
  - AC-TXN-007-7: 멱등 키는 (방, 접속자) 범위에서만 유효하다. 다른 방 또는 다른 RoomMember가 같은 키 값을 보내도 별개의 요청으로 취급되며 서로의 결과를 재사용하지 않는다.
  - AC-TXN-007-8: 거래 생성이 성공한 뒤 게임이 종료되고 키 유효 기간(24시간) 이내에 같은 키·같은 내용의 생성 요청이 재전송되면, 종료를 이유로 거부되지 않고 최초 성공 결과가 반환되며 거래는 1건만 존재한다. 같은 상황에서 다른 키의 새 생성 요청은 거부된다(AC-TXN-009-1).
  - AC-TXN-007-9: 거래 수정 또는 삭제가 성공한 뒤 그 거래가 삭제되었거나 게임이 종료된 상태에서 키 유효 기간(24시간) 이내에 같은 키·같은 내용의 요청이 재전송되면, `이미 삭제된 거래입니다`나 종료 거부가 아니라 최초 성공 결과가 반환되고 추가 변경은 일어나지 않는다. 다른 키의 새 요청은 AC-TXN-005-8, AC-TXN-006-2, AC-TXN-009-1에 따라 거부된다.
  - AC-TXN-007-10: 키 유효 기간(24시간) 이내에, 최초 결과가 상태에 따른 영구적 거부(`이미 삭제된 거래입니다`, 게임 종료 후 거부, 한도 초과)였던 요청의 같은 키·같은 내용 재전송은 같은 거부 결과를 반환하고 데이터를 바꾸지 않는다. 한도 초과는 현재 정책에 슬롯 회수 수단이 없어 영구적 거부로 본다. 비활성 참여자 지정이나 검증 실패로 거부된 요청은 키가 기록되지 않으므로 AC-TXN-007-13을 따른다. 어떤 경우에도 거래가 중복 생성되거나 한도를 넘는 일은 없어야 한다.
  - AC-TXN-007-11: 서버가 처리한 기록이 없는 키(요청이 서버에 도달하지 못했던 경우)로 요청이 키 유효 기간(최초 시도 후 24시간) 이내에 처음 도착하면 새 요청으로 취급하며, 그 시점의 게임 상태·권한·한도·거래 상태 검사를 모두 거친다. 따라서 게임 종료 뒤에 처음 도착한 요청은 같은 키여도 거부된다(AC-TXN-009-1). 키 유효 기간이 지난 뒤의 도착은 AC-TXN-007-12를 따른다.
  - AC-TXN-007-12: 키 유효 기간은 클라이언트가 요청을 처음 시도한 시각부터 24시간이다. 서버는 최소 그 시점까지 키와 결과를 보관하며 더 오래 보관해도 된다. 유효 기간 이내의 같은 키·같은 내용 재전송은 AC-TXN-007-2, -8, -9, -10을 따른다. 유효 기간이 지난 뒤 같은 키로 재시도하면, 서버에 기록이 남아 있든 없든 요청을 처리하지 않고 만료로 거부하며 거래·게임 상태는 변하지 않고, 사용자에게 요청이 만료되었음과 거래 목록에서 저장 여부를 확인하라는 안내가 표시된다(사용자 결정 OQ-040). 예: 최초 시도 후 23시간에 처음 도착해 처리된 요청도, 최초 시도 후 24시간이 지나면 같은 키의 재시도가 거부된다. 만료 거부는 같은 키로 다른 내용이 온 경우의 충돌 거부(AC-TXN-007-4)보다 우선한다. 새 키의 새 요청은 이 규칙의 대상이 아니며 AC-TXN-009-1 등 상태 검사를 받는다. 최초 시도 시각을 서버가 식별하는 방법과 안내 문구는 Spec에서 정한다.
  - AC-TXN-007-13: 비활성 참여자 지정이나 검증 실패로 거부된 요청은 부작용이 없으므로 서버는 그 키와 결과를 기록하지 않는다. 같은 키·같은 내용을 키 유효 기간 이내에 다시 보내면 새 요청으로 처리해 그 시점의 참여자 상태와 유효성을 다시 검사하므로, 참여자를 재활성화한 뒤에는 성공할 수 있고 이때 거래는 최대 1건만 생성된다. 같은 키로 내용을 바꿔 보내도 기록이 없으므로 충돌이 아니라 새 요청이다(사용자는 내용을 바꾸면 새 키를 쓴다). 키 유효 기간이 지난 뒤의 재시도는 AC-TXN-007-12에 따라 만료로 거부된다.

#### FR-TXN-008 저장 실패 처리
- POL: POL-TXN-008
- 통합: C§3.1, C§3.4, C§4.5
- 요구사항: 저장 실패 시 성공한 것처럼 표시하지 않는다. 입력값은 현재 화면에 유지되며 사용자가 수동으로 재시도한다. 서버 처리 결과를 알 수 없는 경우에도 성공으로 표시하지 않는다.
- AC:
  - AC-TXN-008-1: 서버 오류·네트워크 오류로 저장이 실패하면 실패 메시지가 표시되고 성공 표시는 나타나지 않는다.
  - AC-TXN-008-2: 실패 후 입력 필드 값이 유지된다.
  - AC-TXN-008-3: 시스템은 실패한 저장을 자동으로 재전송하지 않는다.
  - AC-TXN-008-4: 서버가 확정적으로 거부한 저장은 순손익과 거래 목록에 반영되지 않는다.
  - AC-TXN-008-5: 응답을 받지 못해 저장 여부를 알 수 없는 경우, 시스템은 성공으로 표시하지 않고 결과가 확인되지 않았음을 알린다. 재조회 후 해당 거래가 삭제되지 않고 남아 있으면 목록에 나타난다. 목록에서 확인할 수 없으면 알 수 없음 상태를 유지하며 성공이나 실패로 단정하지 않는다(AC-SYS-002-5). 자동 재제출은 하지 않는다.

#### FR-TXN-009 종료 후 일반 거래 잠금
- POL: POL-TXN-009
- 통합: C§5.6, C§5.1
- 요구사항: 수동 종료 후에는 일반 거래의 생성·수정·삭제가 불가능하며, 서버가 요청 처리 시점의 게임 상태를 검사한다. 종료 후 정정 거래는 MVP에 없다.
- AC:
  - AC-TXN-009-1: 종료된 게임에서 거래 추가·수정·삭제 새 요청(다른 멱등 키)은 서버가 거부한다. 방장도 예외가 아니다. 종료 전에 성공한 요청과 같은 키의 재전송은 AC-TXN-007-8, AC-TXN-007-9를 따른다.
  - AC-TXN-009-2: 종료 직전에 시작된 새 요청(처음 도착한 요청)이 종료 이후에 처리되면 처리 시점의 상태 기준으로 거부된다. 종료 전에 이미 성공 처리된 요청의 같은 키 재전송은 이 AC로 거부되지 않으며 AC-TXN-007-8, AC-TXN-007-9를 따른다.
  - AC-TXN-009-3: 종료된 게임에서는 거래 입력·수정·삭제 UI가 비활성화되거나 숨겨진다.
  - AC-TXN-009-4: 종료 후 정정 거래를 등록하는 별도 기능이 없다.
  - AC-TXN-009-5: 서로 다른 거래 저장 요청과 게임 종료 요청이 거의 동시에 도착하면 서버가 처리 시점의 게임 상태로 각 요청을 판정한다. 종료 전에 처리된 거래는 최종 정산에 반영되고, 종료 후에 처리된 새 거래 요청은 거부된다. 순서 결정 규칙의 세부는 OQ-030 해결 전까지 정의하지 않는다.

### 5.4 거래 목록과 실시간 손익

#### FR-VIEW-001 누적 손익과 거래 내역 구분
- POL: POL-VIEW-001
- 통합: C§4.1, C§4.3
- 요구사항: '누적 손익'과 '거래 내역'을 구분해 제공한다.
- AC:
  - AC-VIEW-001-1: 한 화면 안에서 누적 손익 영역과 거래 내역 영역이 구분되어 표시된다.
  - AC-VIEW-001-2: 누적 손익 영역에는 거래 항목이 아닌 참여자별 순손익이 표시된다.

#### FR-VIEW-002 순손익 정렬
- POL: POL-VIEW-002
- 통합: C§4.1
- 요구사항: 참여자별 순손익은 내림차순으로 표시하고, 동률이면 참여자 등록 순서를 따른다.
- AC:
  - AC-VIEW-002-1: 순손익이 +300, +100, -400인 세 참여자는 +300, +100, -400 순으로 표시된다.
  - AC-VIEW-002-2: 순손익이 같은 참여자들은 등록이 먼저인 참여자가 앞에 표시된다.
  - AC-VIEW-002-3: 거래가 없는 참여자(순손익 0)도 표시되고, 0 위치에 정렬 규칙대로 놓인다.

#### FR-VIEW-003 거래 목록 정렬
- POL: POL-VIEW-003
- 통합: C§4.2
- 요구사항: 거래 목록은 원본 서버 생성 시각 내림차순, 같으면 서버 생성 순번 내림차순이다. 수정은 목록 위치를 바꾸지 않는다. 삭제된 거래는 일반 목록에 표시하지 않는다.
- AC:
  - AC-VIEW-003-1: 나중에 등록한 거래가 먼저 등록한 거래보다 위에 표시된다.
  - AC-VIEW-003-2: 원본 생성 시각이 같은 거래는 서버 생성 순번이 큰 거래가 위에 표시된다.
  - AC-VIEW-003-3: 거래를 수정해도 목록 순서가 바뀌지 않는다.
  - AC-VIEW-003-4: 페이지를 넘기거나 새 거래가 추가되어도 항목이 중복되거나 누락되지 않는다.
  - AC-VIEW-003-5: 삭제된 거래는 목록에 나타나지 않는다.
  - AC-VIEW-003-6: 생성 순번의 고유성 보장 방식은 OQ-031 해결 전까지 정의하지 않는다.

#### FR-VIEW-004 목록 페이지 단위와 참여자 필터
- POL: POL-VIEW-004
- 통합: C§4.2, C§4.3
- 요구사항: 거래 목록은 20건 단위로 불러오고, 참여자 1명 기준 필터를 제공한다. 필터는 해당 참여자가 지급자 또는 수취자인 거래를 포함하며 목록에만 적용된다. 누적 손익은 항상 전체 유효 거래 기준이다. 필터를 바꾸면 페이지네이션을 처음부터 다시 시작한다. 페이지네이션의 구현 방식은 요구하지 않는다.
- AC:
  - AC-VIEW-004-1: 삭제되지 않은 거래가 45건이고 필터가 없으며 조회 중 다른 변경이 없으면, 첫 로드에 20건, 이후 추가 로드에 20건, 다시 5건이 불러와진다. 삭제된 거래는 페이지 계산에서 제외된다.
  - AC-VIEW-004-2: 참여자 A를 필터로 선택하면 A가 지급자인 거래와 수취자인 거래가 모두 표시되고, A가 관여하지 않은 거래는 표시되지 않는다.
  - AC-VIEW-004-3: 필터는 한 번에 참여자 1명만 선택할 수 있다.
  - AC-VIEW-004-4: 필터 적용 상태에서도 20건 단위 로드가 동작한다.
  - AC-VIEW-004-5: 필터를 해제하면 전체 거래 목록으로 돌아간다.
  - AC-VIEW-004-6: 비활성 참여자도 필터 대상으로 선택할 수 있다.
  - AC-VIEW-004-7: 필터를 적용해도 누적 손익 영역과 예상 정산의 값은 전체 유효 거래 기준 그대로다.
  - AC-VIEW-004-8: 필터를 바꾸면 이전 필터에서 불러온 페이지는 폐기되고 새 필터의 첫 20건부터 표시된다.
  - AC-VIEW-004-9: 삭제된 거래가 섞여 있어도 목록에는 삭제되지 않은 거래만 20건 단위로 나오며, 삭제된 거래 때문에 페이지가 비거나 20건보다 적게 채워지지 않는다(마지막 페이지 제외).

#### FR-VIEW-005 실시간 반영
- POL: POL-VIEW-005
- 통합: C§4.4
- 요구사항: 거래 변경(생성·수정·삭제), 참여자 추가·활성 상태 변경, 게임 종료, 정산 변경을 새로고침 없이 다른 접속자에게 반영한다. 변경 토스트는 필수가 아니다. 지연 목표는 미결정이다(OQ-019).
- AC:
  - AC-VIEW-005-1: 접속자 A가 거래를 등록하면 접속 중인 B의 순손익과 거래 목록이 새로고침 없이 갱신된다.
  - AC-VIEW-005-2: 수정과 삭제도 동일하게 다른 접속자에게 반영된다.
  - AC-VIEW-005-3: 참여자 추가와 활성 상태 변경이 다른 접속자의 참여자 표시와 거래 입력 선택지에 반영된다.
  - AC-VIEW-005-4: 게임 종료가 다른 접속자 화면에 반영되어 거래 입력·수정·삭제 UI가 잠기고 최종 정산이 표시된다.
  - AC-VIEW-005-5: 거래 변경으로 예상 정산 결과가 바뀌면 다른 접속자의 예상 정산이 갱신된다.
  - AC-VIEW-005-6: 변경 알림 토스트가 없어도 요구사항을 충족한다.
  - AC-VIEW-005-7: 실시간 갱신이 현재 필터 선택과 정렬 규칙(FR-VIEW-002, FR-VIEW-003)을 유지한다.
  - AC-VIEW-005-8: 반영 지연의 수치 기준은 OQ-019 해결 전까지 정의하지 않는다.

### 5.5 게임 종료와 정산

#### FR-SET-001 게임 종료
- POL: POL-SET-001
- 통합: C§5.1, C§5.6
- 요구사항: 방장만 게임을 수동으로 종료할 수 있다. 종료 전 확인 절차를 거친다. 서버는 동시 종료 요청을 원자적으로 처리해 `진행 중 → 종료됨` 상태 전이를 정확히 한 번만 일으킨다. 그 전이를 일으킨 요청과 같은 멱등 키의 재전송은(키 유효 기간 24시간 이내) 최초 성공 결과를 받고, 다른 키의 새로운 종료 요청은 `이미 종료된 게임입니다`로 거부한다. 종료 후 일반 거래를 잠근다. 자동 종료·재개·접근 만료·데이터 자동 삭제는 MVP에 없다.
- AC:
  - AC-SET-001-1: 방장이 종료를 요청하면 확인 절차가 표시되고, 확인 후에만 게임이 `종료됨`이 된다. 취소하면 상태가 바뀌지 않는다.
  - AC-SET-001-2: 비방장의 종료 요청은 서버가 거부한다.
  - AC-SET-001-3: 종료 후 일반 거래의 추가·수정·삭제는 FR-TXN-009에 따라 거부된다.
  - AC-SET-001-4: 시간 경과나 비활동으로 게임이 자동 종료되지 않는다.
  - AC-SET-001-5: `종료됨` 게임을 `진행 중`으로 되돌리는 기능이 없다.
  - AC-SET-001-6: 이미 종료된 게임에 대한 새로운 종료 요청(다른 멱등 키)은 `이미 종료된 게임입니다`로 거부되고 게임 상태와 정산 결과는 변하지 않는다.
  - AC-SET-001-7: 시간 경과에 따른 방 접근 만료와 데이터 자동 삭제 기능이 없다. 방 데이터 보관·삭제 운영은 OQ-034에서 정한다.
  - AC-SET-001-8: 같은 멱등 키로 종료 요청이 키 유효 기간(24시간) 이내에 재전송되면(동시 도착 포함) 최초 요청의 결과가 그대로 반환된다. 종료에 성공했던 요청의 재전송은 성공 결과를 받고 오류로 취급되지 않는다. 최초 결과가 `이미 종료된 게임입니다` 거부였던 요청의 재전송은 같은 거부 결과를 받는다. 24시간이 지난 재시도는 AC-TXN-007-12를 따른다.
  - AC-SET-001-9: 둘 이상의 종료 요청이 동시에 도착하면 `종료됨`으로의 상태 전이는 정확히 한 번만 일어난다. 전이를 일으킨 요청과 그 요청과 같은 키의 재전송만 성공 결과를 받고, 다른 키의 요청은 AC-SET-001-6에 따라 거부된다.

#### FR-SET-002 순손익 계산
- POL: POL-SET-002
- 통합: C§5.3
- 요구사항: 유효한 각 거래에 대해 지급자의 순손익을 차감하고 수취자의 순손익을 가산한다. 모든 참여자의 순손익 합계는 0이어야 한다.
- AC:
  - AC-SET-002-1: A→B 100 거래 한 건이면 A는 −100, B는 +100이다.
  - AC-SET-002-2: 여러 거래 후 참여자 순손익의 합이 항상 0이다.
  - AC-SET-002-3: 삭제된 거래는 계산에서 제외된다.
  - AC-SET-002-4: 수정된 거래는 수정 후 값으로만 계산된다.
  - AC-SET-002-5: 비활성 참여자의 순손익도 계산에 포함되고 합계 0에 기여한다.

#### FR-SET-003 정산 매칭
- POL: POL-SET-003
- 통합: C§5.3
- 요구사항: 순채무자(순손익 < 0)와 순채권자(순손익 > 0)를 탐욕 방식으로 매칭한다. 매칭할 때마다 남은 채무·채권 잔액을 갱신하고, 매번 잔액 내림차순으로 다시 정렬한다. 동률은 참여자 등록 순서를 따른다. 잔액 0인 참여자는 제외한다. 결과는 정확해야 하며(정산 항목의 합으로 모든 순손익이 0), 전역 최소 송금 횟수는 보장하지 않는다.
- AC:
  - AC-SET-003-1: 채무자 A(−300), B(−100), 채권자 C(+250), D(+150)이면 정산 항목은 A→C 250, B→D 100, A→D 50이다.
  - AC-SET-003-2: 채무자 A(−300), B(−200), 채권자 C(+250), D(+150), E(+100)이고 A가 B보다 먼저 등록되었으면, 매번 재정렬하는 방식으로 정산 항목은 A→C 250, B→D 150, A→E 50, B→E 50이다. (재정렬 없이 처음 순서를 유지하면 A→C 250, A→D 50, B→D 100, B→E 100이 되어 달라진다.)
  - AC-SET-003-3: 채무자 또는 채권자의 잔액이 같으면 등록 순서가 빠른 참여자가 먼저 매칭된다.
  - AC-SET-003-4: 정산 항목을 모두 이행하면 모든 참여자의 순손익이 정확히 0이 된다.
  - AC-SET-003-5: 순손익이 0인 참여자는 정산 항목에 나타나지 않는다.
  - AC-SET-003-6: 위 알고리즘 결과가 송금 횟수 최소가 아니어도 결함으로 보지 않는다.
  - AC-SET-003-7: 동일한 거래 집합은 항상 동일한 정산 결과를 만든다(결정적).

#### FR-SET-004 정산 항목 정렬
- POL: POL-SET-004
- 통합: C§5.4
- 요구사항: 정산 항목은 금액 내림차순으로 표시하고, 동률은 참여자 등록 순서를 따른다. 화면과 복사 텍스트의 순서는 같다. 동률은 지급자의 등록 순서가 빠른 항목을 먼저, 지급자도 같으면 수취자의 등록 순서가 빠른 항목을 먼저 표시한다(사용자 결정 OQ-035).
- AC:
  - AC-SET-004-1: 정산 항목이 250, 100, 50이면 그 순서로 표시된다.
  - AC-SET-004-2: 금액이 같은 항목은 지급자의 등록 순서가 빠른 항목이 먼저 표시되고, 지급자도 같으면 수취자의 등록 순서가 빠른 항목이 먼저 표시된다.
  - AC-SET-004-4: 지급자 A가 B보다 먼저 등록되었을 때 정산 항목 A→E 50과 B→E 50은 A→E, B→E 순으로 표시된다. 지급자 A의 항목 A→D 50과 A→E 50은 D가 E보다 먼저 등록되었으면 A→D, A→E 순으로 표시된다.
  - AC-SET-004-3: 화면의 정산 항목 순서와 복사 텍스트의 순서가 같다.

#### FR-SET-005 정산 조회와 텍스트 복사
- POL: POL-SET-005
- 통합: C§5.5, C§2.7
- 요구사항: 종료 후 최종 정산을 조회하고 일반 텍스트로 복사할 수 있다. 복사 텍스트에는 방 이름, 상태 문자열 `게임 종료`(고정), 지급자→수취자, 금액이 포함되며 거래 전체 내역은 포함하지 않는다. 정산 확정 상태와 버전은 포함하지 않는다. 복사 텍스트에는 정산 단위를 포함한다. 복사는 최종 정산에서만 할 수 있고 예상 정산은 복사할 수 없다(사용자 결정 OQ-029).
- AC:
  - AC-SET-005-1: 종료된 게임에서 방의 모든 RoomMember(종료 후 입장자 포함)가 최종 정산을 조회할 수 있다.
  - AC-SET-005-2: 복사 버튼을 누르면 일반 텍스트가 클립보드에 복사된다.
  - AC-SET-005-3: 복사된 텍스트에 방 이름, 상태 문자열 `게임 종료`, 각 항목의 지급자→수취자, 금액, 정산 단위가 포함된다.
  - AC-SET-005-4: 복사된 텍스트에 개별 거래 목록(사유·라운드·작성자 등)과 정산 확정 상태·버전이 포함되지 않는다.
  - AC-SET-005-5: 클립보드 접근이 실패하면 사용자에게 복사 실패가 알려지고 성공으로 표시되지 않는다.
  - AC-SET-005-6: 게임이 `진행 중`일 때 예상 정산에는 복사 버튼이 없거나 동작하지 않으며, 복사 요청이 최종 정산 텍스트(`게임 종료`)를 만들어 내지 않는다.

#### FR-SET-006 정산 항목 없음
- POL: POL-SET-006
- 통합: 해당 없음 (기존 정책에만 있던 규칙 7건 중 하나이며 v1.0.0에 반영 대상. `policy-verification.md` C-05)
- 요구사항: 정산할 송금 항목이 없으면 '정산할 내역이 없습니다.'를 표시하고 복사 버튼을 비활성화한다. 문구는 예상 정산과 최종 정산 모두에 표시하고, 복사 버튼 비활성화는 복사 기능이 있는 최종 정산에 적용한다(예상 정산은 복사할 수 없다. 사용자 결정 OQ-029).
- AC:
  - AC-SET-006-1: 거래가 없거나 모든 순손익이 0이면 정확히 '정산할 내역이 없습니다.' 문구가 표시된다.
  - AC-SET-006-2: 종료된 게임의 최종 정산이 이 경우이면 복사 버튼이 비활성화되어 클릭해도 복사되지 않는다. 진행 중의 예상 정산에는 복사 기능이 없다(AC-SET-005-6).
  - AC-SET-006-3: 정산 항목이 1건 이상이면 이 문구가 표시되지 않는다.

#### FR-SET-007 정산 확정·버전 없음
- POL: POL-SET-007
- 통합: C§5.5, C§1.2
- 요구사항: MVP에는 정산 확정과 버전 관리가 없다. 정산 결과는 별도 확정 단계 없이 계산 결과로 제공한다.
- AC:
  - AC-SET-007-1: 게임 종료 후 최종 정산이 별도 확정 조작 없이 조회된다.
  - AC-SET-007-2: 정산 확정·확정 취소·과거 버전 조회 UI와 API가 없다.
  - AC-SET-007-3: 최종 정산은 종료 시점의 유효 거래로 계산되며(종료 후 거래가 잠겨 있으므로) 조회 시마다 동일하다.

#### FR-SET-008 예상 정산
- POL: 해당 없음 (통합 정책 신규)
- 통합: C§5.2, C§4.4
- 요구사항: 진행 중에도 전체 유효 거래로 예상 정산을 제공하고 실시간으로 갱신한다. 종료 후에는 최종 정산을 표시한다. 두 정산은 같은 계산 알고리즘(FR-SET-002~004)을 쓴다. 예상 정산은 복사할 수 없다(사용자 결정 OQ-029).
- AC:
  - AC-SET-008-1: 진행 중 접속자는 현재 유효 거래로 계산된 정산 항목을 '예상 정산'으로 볼 수 있다.
  - AC-SET-008-2: 거래가 생성·수정·삭제되면 예상 정산이 새로고침 없이 갱신된다.
  - AC-SET-008-3: 게임이 종료되면 같은 영역이 '최종 정산'으로 표시된다.
  - AC-SET-008-4: 거래 집합이 같으면 예상 정산과 최종 정산의 정산 항목은 같다.
  - AC-SET-008-5: 예상 정산 화면은 진행 중임을 구분해서 표시하며 최종 결과로 오인되지 않는다.
  - AC-SET-008-6: 필터 상태와 무관하게 전체 유효 거래 기준으로 계산된다.
  - AC-SET-008-7: 예상 정산은 복사할 수 없다. 복사는 게임이 종료된 뒤 최종 정산에서만 가능하다(AC-SET-005-6).

### 5.6 연결과 오류 처리

#### FR-SYS-001 온라인 전용과 오래된 데이터 표시 금지
- POL: POL-SYS-001
- 통합: C§4.5
- 요구사항: 데이터는 온라인 상태에서만 조회·변경한다. 연결이 끊기면 최신으로 오인할 수 있는 오래된 캐시를 표시하지 않고 조회를 차단하며 오류를 안내한다. 현재 작성 중인 입력은 유지한다.
- AC:
  - AC-SYS-001-1: 연결이 끊기면 사용자에게 연결 끊김 상태와 오류 안내가 표시된다.
  - AC-SYS-001-2: 연결이 끊긴 동안 손익·거래 목록·정산 결과의 조회는 차단되고 오류 안내가 표시된다. 이전에 불러온 값은 "최신이 아님" 표시를 붙이더라도 표시하지 않는다.
  - AC-SYS-001-3: 오프라인에서 거래 등록·수정·삭제·종료 같은 변경은 수행되지 않는다. 오프라인 큐잉은 없다.
  - AC-SYS-001-4: 조회가 차단된 영역에 이전 조회 결과를 캐시로 대체 표시하는 기능이 없다.
  - AC-SYS-001-5: 연결이 끊긴 동안 현재 화면에서 작성 중이던 입력값은 유지된다.

#### FR-SYS-002 연결 복구
- POL: POL-SYS-002
- 통합: C§4.4, C§4.5, C§1.2
- 요구사항: 연결이 복구되면 최신 서버 상태를 다시 조회한다. 미완료 거래를 자동으로 제출하지 않는다. 현재 화면에서의 입력 유지와 달리, 새로고침·재방문 이후 입력 초안의 자동 복원은 MVP 범위가 아니다.
- AC:
  - AC-SYS-002-1: 연결 복구 후 서버의 최신 순손익·거래 목록·참여자 목록·게임 상태·정산이 다시 조회되어 표시된다.

## 7. MVP 제외 범위

다음은 폐기가 아니라 후속 개발로 연기된 항목이다. MVP의 PRD·Spec·구현 대상이 아니다. (POL §9, C§1.2)

1. 여러 거래 일괄 입력
2. 정산 확정·버전 관리, 과거 확정 버전 조회
3. 종료 후 정정 거래

7. 미저장 입력 초안 자동 복원
8. RoomMember–Participant 연결·해제 (통합 정책에서 제외로 결정)

데이터 모델이 이 확장들을 막을 위험은 `open-questions.md`의 "확장 위험 제안"에 별도로 기록한다. 이 제안은 구현 범위 확대가 아니다.

## 8. 정책 간 해석 메모

- 거래의 "원본·작성자 기록 보존"(POL-TXN-005)은 화면 제공 의무가 아니다. 상세 감사 UI는 후속이다(C§3.3).
- 방장 이전이 없고 신원을 잃어도 권한이 복구·승계되지 않으므로(C§2.3), 방장 신원을 잃은 방은 종료할 수 없는 상태가 될 수 있다. 이 결과는 정책의 귀결로 수용되었다(AC-ROOM-005-7). 운영 정책은 OQ-034에서 다룬다.
- 통합 정책에서 사라졌으나 기존 정책에 있고 충돌하지 않는 요구(방 코드 없음, 삭제·종료 전 확인, 빈 정산 문구, 중복 제출 UI 차단 등)는 기존 POL을 근거로 유지했다(`policy-verification.md` C-05).
- 멱등 키(C§3.4)와 커서 페이지네이션 권장(C§4.2)은 구현 용어다. PRD는 전자를 동작 계약으로만 요구하고, 후자는 요구하지 않는다.

## 부록 A. 같은 키 재전송(replay) 정리표

FR-TXN-007과 NFR-003, 종료 요청(FR-SET-001)에 걸린 규칙을 한 곳에 모은 표다. 규칙 자체를 새로 정하는 것이 아니라 본문 AC를 교차 확인하기 위한 표이며, 표와 본문이 다르면 본문 AC가 우선하고 표를 고친다.

"요청 종류"는 거래 생성·수정·삭제와 게임 종료다. 표의 "같은 키" 칸은 모두 키 유효 기간(24시간, 최초 시도 시각 기준) **이내**를 기준으로 하며, 유효 기간이 지난 재시도는 마지막 행을 따른다. 참여자 추가·상태 변경, 입장에는 멱등 키 규정이 없다(OQ-038).

| 최초 결과 | 이후 상태 | 같은 키 · 같은 내용 | 같은 키 · 다른 내용 | 새 키 (새 요청) |
| --- | --- | --- | --- | --- |
| 성공 | 거래 삭제됨 / 게임 종료됨 / 거래 한도 가득 참 | 최초 성공 결과 반환, 추가 변경 없음 (AC-TXN-007-8, 007-9, ROOM-008-10, SET-001-8) | 충돌 거부 (AC-TXN-007-4) | 현재 상태 검사 (AC-TXN-005-8, 006-2, 009-1, ROOM-008-3, SET-001-6) |
| 영구적 거부 (`이미 삭제된 거래입니다`, 게임 종료 후 거부, `이미 종료된 게임입니다`, **한도 초과** — 슬롯 회수 수단이 없음) | 거래 삭제됨 / 게임 종료됨 / 한도 가득 참 | 같은 거부 결과 반환, 데이터 변경 없음 (AC-TXN-007-10, SET-001-8) | 충돌 거부 (AC-TXN-007-4) | 현재 상태 검사 (같음) |
| 상태에 따라 달라지는 거부 (비활성 참여자 지정, 검증 실패) — 부작용이 없어 키·결과를 **기록하지 않음** | 재활성화·입력 수정 | 기록이 없으므로 **새 요청으로 처리**, 현재 상태 재검사 (AC-TXN-007-13) | 기록이 없으므로 새 요청 | 현재 상태 검사 |
| 서버가 처리한 기록 없음 (요청 미도달) | 무관 | 새 요청으로 취급, 현재 상태 검사 (AC-TXN-007-11, 009-1) | 새 요청으로 취급 | 현재 상태 검사 |
| 키 유효 기간(최초 시도 후 24시간)이 지남 | 무관 (서버 기록이 남아 있어도) | **만료로 거부**, 데이터 변경 없음, 목록 확인 안내 (AC-TXN-007-12) | 만료로 거부 (충돌 거부보다 우선, 같은 키를 쓰는 한) | 현재 상태 검사. 새 키의 새 요청은 이 행의 대상이 아님 |

동시 도착: 거래 저장과 종료가 동시에 도착하면, 처음 도착한 새 요청은 요청별로 처리 시점 상태로 판정한다(AC-TXN-009-5, SET-001-9). 이미 기록된 요청의 재전송은 위 표의 해당 행을 따른다. 순서 규칙의 세부는 OQ-030이다.
