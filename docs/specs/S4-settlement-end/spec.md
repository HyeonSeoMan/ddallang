## 1. 범위

### 1.1 담당 FR (AC 39개 + 다른 Spec이 넘긴 계약)
FR-SET-001(9), 003(7), 004(4), 005(6), 006(3), 007(3), 008(7). FR-SET-002(순손익)는 S3가 정의하고 S4는 그 정의를 입력으로 쓴다. 그리고 S5가 S4에 건 요구(S5 §8.2: 종료 전이당 `room.ended` 정확히 한 번, 정산 조회 API, 별도 정산 이벤트 없음), S1·S2가 S4로 넘긴 계약(종료 전이 `IN_PROGRESS → ENDED`, 종료 요청의 멱등 키, 최종 정산, S1 §5.1, S2 §1.3). AC별 담당과 검증은 §11 추적표.

## 2. 도메인 모델과 불변식

### 2.1 개체
S4가 새로 노출하는 개체는 없다. 읽거나 바꾸는 개체는 다음이다.

| 개체 | S4에서의 사용 |
| --- | --- |
| Room(S1 §2.1) | `status`를 `IN_PROGRESS → ENDED`로 한 번 바꾼다. `name`, `unit`은 복사 텍스트에 쓴다. S1의 Room 필드 목록은 바꾸지 않는다 |
| Participant(S1 §2.1) | 정산의 참여자 집합과 `order`(동률 기준). 비활성 참여자도 포함한다 |
| Transaction(S2 §2.1) | 삭제되지 않은 유효 거래의 금액(S3 §6.1) |
| 멱등 기록(S2 §2.1) | 종료 요청의 성공과 `GAME_ENDED` 거부를 같은 방식으로 기록한다(§3.2) |
| 방 변경 번호(S5 §2.1) | 종료 전이가 1 증가시킨다(§6.1, §8) |

정산 항목은 **저장하지 않는다**(D-5). 요청 때마다 유효 거래에서 계산한다(§6.2).

### 2.2 불변식
- E-I1. `ENDED → IN_PROGRESS` 전이는 없다(AC-SET-001-5). 방 상태는 `IN_PROGRESS → ENDED`로 최대 한 번 바뀐다.
- E-I2. 전이는 방마다 정확히 한 번 일어나고, 그 전이가 방의 `revision`을 정확히 1 올리며 `room.ended`를 만든다(AC-SET-001-9, S5 §8.2 1).
- E-I3. `ENDED` 이후 방의 상태를 바꾸는 요청(거래·참여자·종료)은 모두 거부되므로 **`revision`은 `room.ended`의 값에서 더 올라가지 않는다.**
- E-I4. 같은 방에서 같은 시점(같은 스냅샷)의 예상 정산과 최종 정산은 같은 입력과 같은 알고리즘의 결과다(AC-SET-008-4).
- E-I5. 최종 정산은 `ENDED` 이후 입력(유효 거래, 참여자 `order`)이 바뀌지 않으므로 조회할 때마다 같다(AC-SET-007-3).
- E-I6. 정산 항목을 모두 이행하면 모든 참여자의 순손익이 정확히 0이다(AC-SET-003-4). 정산 항목의 금액은 항상 1 이상의 정수다.

## 3. 공통 규약

### 3.1 인증과 권한
모든 API는 `Authorization: Bearer <신원 키>`가 필요하고 이 방의 RoomMember여야 한다(S1 §3.1). 비멤버는 `404 ROOM_NOT_FOUND`다(S1 §3.3 3). **종료는 방장만** 할 수 있다(`403 HOST_ONLY`, S1 §5.1, AC-SET-001-2). 정산 조회는 방장과 일반 접속자가 같고, 종료 후 입장한 RoomMember도 조회할 수 있다(AC-SET-005-1, AC-ROOM-002-5).

### 3.2 종료 요청의 멱등 처리
종료 요청은 S2 §5를 **그대로** 따른다. 이 절은 S2를 다시 정의하지 않고 종료에 대한 적용만 적는다.
- 헤더 `Idempotency-Key`, `Idempotency-First-Attempt-At`의 형식·필수·미래 시각 규칙(S2 §5.1), 24시간 유효 기간과 만료(`409 IDEMPOTENCY_KEY_EXPIRED`, 방 잠금을 얻은 시점의 DB 시각으로 판정, S2 §5.4), 기록 보관(`expiresAt` 이후 1시간 이상, S2 §5.4), 키의 효력 범위(방, 요청자 RoomMember, S2 §5.1)를 쓴다.
- **연산 종류에 `END`(종료)를 더한다.** 지문(S2 §5.2)은 연산 종류 `END`와 요청 본문의 정규형으로 만든다(대상 거래 ID는 없다). 같은 키를 거래 요청과 종료 요청에 번갈아 쓰면 연산 종류가 달라 다른 내용이다(`409 IDEMPOTENCY_CONFLICT`).
- **기록하는 결과**: 성공, 그리고 영구적 거부인 `409 GAME_ENDED`(AC-SET-001-8). 응답의 상태 코드와 본문을 그대로 저장하고 재전송에는 `Idempotent-Replayed: true`를 더한다(S2 §5.3).
- **기록하지 않는 결과**: 헤더·만료(S2 §3.4의 3·4번에 해당), 401, 404, 403 `HOST_ONLY`, 422. 부작용이 없는 거부이므로 같은 키·같은 내용의 재전송은 새 요청으로 상태를 다시 검사한다(S2 §5.2).
- 만료 오류의 `message`는 거래 목록이 아니라 **방의 현재 상태를 확인하라**는 안내를 담는다(D-11).

### 3.3 검사 순서 (종료)
S1 §3.3, S2 §3.4와 같은 원칙이다. 처음 걸린 오류 하나를 반환한다.
0. **라우트**: 없는 경로 `404 ROUTE_NOT_FOUND`, 없는 메서드 `405 NOT_SUPPORTED`(`Allow` 포함)
1. 신원 키 누락·형식 오류: `401 UNAUTHENTICATED`
2. 방 존재, 방 멤버 여부(비멤버는 방이 없는 것과 같은 응답): `404 ROOM_NOT_FOUND`
3. 멱등 헤더 검증(S2 §5.1): `422 VALIDATION_FAILED`
**4~8번은 방 단위 잠금(S2 §7 1)을 얻은 뒤 같은 트랜잭션에서 평가하며 "현재 시각"은 잠금을 얻은 시점의 DB 시각이다**(S2 §3.4와 같다).
4. 만료: `409 IDEMPOTENCY_KEY_EXPIRED`
5. 재전송 판정: 기록이 있으면 같은 내용(지문 일치)은 저장된 결과를 반환하고 끝낸다. 다른 내용은 `409 IDEMPOTENCY_CONFLICT`
6. 방장 여부: `403 HOST_ONLY`. 종료된 방이어도 비방장은 `HOST_ONLY`다(S1 §3.3의 4번이 5번보다 앞)
7. 방 상태: 이미 `ENDED`이면 `409 GAME_ENDED`(`message`는 `이미 종료된 게임입니다`). **기록한다**
8. 본문 검증: 본문은 없거나 `{}`여야 한다. 이 밖의 필드는 `422 VALIDATION_FAILED`(`NOT_ALLOWED_FIELD`), 객체가 아닌 본문은 `INVALID_TYPE`(필드 `body`). 기록하지 않는다

정산 조회(§4.2)의 검사 순서는 S3 §3.3과 같다(0 라우트, 1 인증, 2 방·멤버, 3 쿼리 검증).

### 3.4 오류 응답
S1 §3.4의 형식과 코드, S2 §3.6의 코드를 쓴다. S4가 새로 정하는 코드는 없다. `GAME_ENDED`는 S1·S2와 같은 코드이며 종료 요청에서는 `message`가 `이미 종료된 게임입니다`다.

### 3.5 읽기 일관성
정산 조회의 응답은 **하나의 일관된 DB 스냅샷**에서 만든다(S3 §3.2와 같은 원칙). 방 `status`, 참여자, 유효 거래를 한 스냅샷에서 읽어 `kind`와 `items`가 서로 다른 시점에서 섞이지 않는다. 조회는 방 잠금을 쓰지 않는다. 정산 조회와 다른 조회(방, 참여자, 순손익, 거래 목록)는 서로 다른 시점일 수 있으며 클라이언트는 S5 §6.4의 재동기화로 맞춘다.

## 4. API 계약

### 4.1 `POST /rooms/{roomId}/end` — 게임 종료 (FR-SET-001)
- 인증: 필수, 방장.
- 요청 헤더: `Idempotency-Key`, `Idempotency-First-Attempt-At`(필수, §3.2). 본문은 없다(또는 `{}`).
- 처리: §3.3 순서. 통과하면 같은 트랜잭션에서 (a) 방 `status`를 `ENDED`로 바꾸고 (b) 방 `revision`을 1 올리고 (c) 멱등 기록(성공 응답)을 쓴 뒤 커밋한다(§6.1). 커밋 뒤 `room.ended`를 전달한다(S5 §6.2).
- 응답 `200`: `{ "roomId": string, "status": "ENDED" }`. 재전송은 같은 본문과 `Idempotent-Replayed: true`다.
- 오류: 401, 404 `ROOM_NOT_FOUND`(비멤버 포함), 403 `HOST_ONLY`, 409 `IDEMPOTENCY_KEY_EXPIRED`/`IDEMPOTENCY_CONFLICT`/`GAME_ENDED`, 422.
- 거래가 0건이거나 참여자가 없어도 종료할 수 있다(U-2, §6.1).

### 4.2 `GET /rooms/{roomId}/settlement` — 정산 조회 (FR-SET-003~008)
- 인증: 필수, 이 방의 RoomMember.
- 쿼리: 없다. 어떤 쿼리 매개변수도 허용하지 않으며 `422 VALIDATION_FAILED`(`NOT_ALLOWED_FIELD`)다(S3 §3.3 표와 같은 방식). 참여자 필터는 정산에 적용되지 않는다(AC-SET-008-6).
- 응답 `200`:
```json
{ "settlement": { "kind": "EXPECTED", "items": [ { "payerId": "…", "payerNickname": "…", "payeeId": "…", "payeeNickname": "…", "amount": 250 } ] } }
```
  - `kind`: 방이 `IN_PROGRESS`이면 `EXPECTED`(예상 정산), `ENDED`이면 `FINAL`(최종 정산). 같은 스냅샷에서 정한다(§3.5).
  - `items`: §6.2로 계산하고 §6.3의 순서로 정렬한 정산 항목. 항목이 없으면 `[]`다(§6.6). 이 경우에도 `kind`는 방 상태를 따른다.
  - `amount`: 1 이상의 정수. 단일 거래 상한(999,999,999)을 넘을 수 있다(순손익의 합이므로 최대 약 10¹², §6.2).
- 오류: 401, 404 `ROOM_NOT_FOUND`(비멤버 포함), 422.
- 정산 `unit`과 방 이름은 응답에 싣지 않는다. 클라이언트가 방 조회(S1 §4.4)의 값을 쓴다. 한 번의 재동기화(S5 §6.4)로 함께 받아 같은 시점의 값을 쓰며, 방 이름·정산 단위는 생성 뒤 바뀌지 않는다(S1 I6).

### 4.3 존재하지 않는 동작 (S1 §4.8과 같은 원칙)
| 동작 | 응답 |
| --- | --- |
| `GET`/`PUT`/`PATCH`/`DELETE /rooms/{roomId}/end` | 405 `NOT_SUPPORTED`, `Allow: POST` |
| `POST`/`PUT`/`PATCH`/`DELETE /rooms/{roomId}/settlement` | 405 `NOT_SUPPORTED`, `Allow: GET` |
| 게임 재개, 종료 취소, 정산 확정·확정 취소·버전 조회, 송금 완료 표시, 종료 후 정정, 정산 저장·수정, 자동 종료 설정 | 경로를 정의하지 않으므로 404 `ROUTE_NOT_FOUND` |

## 5. 상태와 권한 표

| 동작 | `IN_PROGRESS` | `ENDED` |
| --- | --- | --- |
| 종료 요청 | 방장: 종료 전이. 비방장: `403 HOST_ONLY` | 방장의 새 키: `409 GAME_ENDED`. 같은 키 재전송: 기록된 결과. 비방장: `403 HOST_ONLY` |
| 정산 조회 | 방 멤버: `kind = EXPECTED` | 방 멤버(종료 후 입장자 포함): `kind = FINAL` |
| 정산 복사(UI) | 불가(§6.5) | 가능. 항목이 1건 이상일 때만 |

## 6. 동작 규칙

### 6.1 종료 전이: 멱등성과 원자성 (기준 위치)
종료에는 서로 다른 두 보장이 있고 이 절이 **유일한 기준**이다. 다른 절은 이 절을 참조한다.

**(1) 상태 전이의 원자성** — 방당 전이는 정확히 한 번이다.
- 종료 요청은 방 단위 잠금(S2 §7 1)을 얻은 트랜잭션에서 처리한다. 다중 서버 인스턴스에서도 성립해야 하며 프로세스 메모리 잠금만으로 구현하지 않는다.
- 잠금 안에서 §3.3의 4~8번을 평가하고, 통과하면 같은 트랜잭션에서 **상태 변경, `revision` 증가, 멱등 기록 쓰기**를 한다. 셋 중 하나라도 실패하면 모두 롤백한다. 상태만 바뀌고 `revision`이나 기록이 없는 커밋은 없다.
- 둘 이상의 종료 요청이 동시에 도착하면 잠금 순서대로 직렬 처리된다. 첫 요청이 전이를 일으키고, 나머지는 잠금 안에서 `ENDED`를 보고 §3.3의 5번(같은 키의 재전송) 또는 7번(`GAME_ENDED`)으로 판정된다. 이 판정은 전이 이후 상태를 기준으로 하므로 전이는 두 번 일어나지 않는다(AC-SET-001-9).
- 종료는 방 안의 모든 변경과 직렬화되므로(S2 §7 1) 종료 이후에 거래·참여자 변경이 반영되는 일은 없다.

**(2) 요청의 멱등성** — 같은 요청의 재전송이 결과를 한 번만 만든다.
- 같은 키·같은 내용·키 유효 기간 이내의 재전송은 **저장된 결과**를 돌려준다. 전이를 일으켰던 요청이면 성공(`200`), 거부였던 요청이면 같은 `GAME_ENDED`다(AC-SET-001-8). 상태를 다시 판정하지 않으며 `revision`·이벤트·상태를 바꾸지 않는다.
- 이미 종료된 방에 **새 키**로 온 방장의 종료 요청은 `409 GAME_ENDED`이고 상태, 정산, `revision`은 변하지 않는다(AC-SET-001-6). 이 거부도 기록한다. 이 요청의 같은 키 재전송은 같은 `GAME_ENDED`를 받는다.
- 전이를 일으킨 요청과 **그 요청과 같은 키(같은 내용)의 재전송**만 성공 결과를 받는다. 다른 키의 요청은 성공하지 않는다(AC-SET-001-9).
- 키 유효 기간(24시간)이 지난 재시도는 §3.2에 따라 `IDEMPOTENCY_KEY_EXPIRED`이며 상태·이벤트가 없다(AC-TXN-007-12).

**(3) 종료 이벤트**(S5 §8.2 1) — 논리적 생성은 정확히 한 번이다.
- `room.ended`의 논리적 생성은 전이 트랜잭션 안에서 부여된 `revision` 하나다. 이 `revision`은 방에서 유일하고 **마지막**이다(E-I3). 전이를 일으키지 않은 요청(재전송, 이미 종료된 방에 대한 새 키 요청, 만료 거부, 403, 422)은 `revision`을 소비하지 않고 이벤트를 만들지 않는다.
- 이벤트 **전달**은 커밋 뒤의 별도 단계이며 S5의 규칙을 따른다(S5 §6.2). 한 스트림에 같은 `room.ended`가 두 번 이상 도착할 수 있고(전달 경로 중복) 도착하지 않을 수도 있다(커밋과 발행 사이의 장애, 연결 끊김). 이는 논리적 단일 생성과 충돌하지 않는다. 클라이언트는 `seen` 검사로 중복을 걸러내고(S5 §6.3), 유실은 하트비트의 `revision` 불일치 또는 재연결 때의 전체 재동기화가 방 상태 `ENDED`를 가져와 메운다(S5 §6.4, §6.6).
- 따라서 클라이언트는 **`room.ended`를 받았는지가 아니라 방 조회의 `status`로** 종료 여부를 판단한다. 재연결 뒤에는 `room.ended`가 다시 오지 않지만(S5 §6.2 이벤트 재전송 없음) 재동기화가 같은 결과를 만든다.

**(4) 기타**
- 종료에는 서버 쪽 확인 절차(확인 토큰, 두 단계 요청)가 없다. 확인 절차는 클라이언트가 요청을 보내기 전에 한다(AC-SET-001-1, D-4, §9).
- 자동 종료, 재개, 접근 만료, 데이터 자동 삭제의 경로, 스케줄러, 만료 작업이 없다(AC-SET-001-4, -5, -7). 방 데이터 보관·삭제는 OQ-034다.
- 거래가 0건이거나 참여자가 없어도 방장은 종료할 수 있다. 종료는 거래·참여자 수에 조건이 없다(U-2).

### 6.2 정산 계산 (기준 위치)
정산 항목의 계산은 이 절이 **유일한 기준**이며 예상 정산과 최종 정산이 같은 계산을 쓴다(AC-SET-008-4). 입력은 같은 스냅샷의 다음 둘뿐이다.
- 각 참여자의 순손익 `balance(p)` — **S3 §6.1의 정의 그대로**다. 유효 거래만 쓰고, 비활성 참여자와 거래가 없는 참여자를 포함하며 모든 참여자의 합은 0이다.
- 각 참여자의 등록 순서 `order`(S1 §2.1, 유일하고 변하지 않는다).

**알고리즘**
1. 채무자 집합 `D = { p | balance(p) < 0 }`, 남은 채무 `d(p) = −balance(p)`. 채권자 집합 `C = { p | balance(p) > 0 }`, 남은 채권 `c(p) = balance(p)`. 순손익이 0인 참여자는 어느 쪽에도 넣지 않는다(AC-SET-003-5).
2. `D`와 `C`가 모두 비어 있지 않은 동안 반복한다.
   1. 채무자 `x` = `d`가 가장 큰 참여자, 같으면 `order`가 작은(먼저 등록된) 참여자.
   2. 채권자 `y` = `c`가 가장 큰 참여자, 같으면 `order`가 작은 참여자.
   3. `m = min(d(x), c(y))`. 항목 `(x → y, m)`을 만든다.
   4. `d(x) −= m`, `c(y) −= m`. 0이 된 쪽은 집합에서 뺀다(둘 다 0이 될 수 있다).
3. 반복이 끝난 결과가 정산 항목이다.

- 2-1, 2-2는 PRD의 "매번 남은 잔액을 갱신하고 잔액 내림차순으로 다시 정렬하며 동률은 등록 순서"(FR-SET-003)와 같다. 매 반복마다 맨 앞을 고르는 것이 곧 매번 재정렬한 결과의 첫 항목이다. 처음 순서를 유지하는 방식이 아니다(AC-SET-003-2).
- **결정성**: 입력(순손익과 `order`)이 같으면 결과가 항상 같다(AC-SET-003-7). 선택 기준은 정수 값과 유일한 `order`뿐이라 동률이 남지 않고, 거래의 생성 순서·ID·시각, 참여자 ID·닉네임, 서버 인스턴스, 해시 순회 순서에 의존하지 않는다. 구현은 정렬이 안정적이어야 한다는 가정에 기대지 않고 위 비교 기준을 명시적으로 쓴다.
- **종료**: `balance`의 합이 0이므로 `D`와 `C`의 총량이 같고, 각 반복이 둘 중 하나 이상을 0으로 만들어 유한 번에 끝나며 마지막에 둘 다 비어 있다. 항목 수는 `D`와 `C`가 모두 비어 있지 않으면 `|D| + |C| − 1` 이하이고, 어느 한쪽이 비어 있으면(모든 순손익이 0이거나 거래가 없는 경우) 0건이며(§6.6), 참여자가 10명 이하이므로 9건 이하다(S1 I4).
- **같은 쌍의 중복 없음**: 한 반복이 `x`나 `y` 중 하나를 집합에서 빼므로 같은 (지급자, 수취자) 쌍은 두 번 나오지 않는다. 그래서 §6.3의 정렬 키가 항목을 전순서로 정한다.
- **정확성과 최적성**: 항목을 모두 이행하면 모든 순손익이 0이다(AC-SET-003-4, E-I6). 송금 횟수가 전역 최소임은 보장하지 않으며 결함이 아니다(AC-SET-003-6).
- **정수와 크기**: 정수 연산만 쓴다. 순손익은 절댓값이 약 10¹²를 넘지 않는 64비트 정수이므로(NFR-009) 항목의 `amount`도 이를 넘지 않는다. 서버는 64비트 정수로 계산하고 부동소수점을 쓰지 않는다. 항목 금액은 단일 거래 상한(S2 T-I2)의 적용 대상이 아니다.
- **예시(AC 값)**: 채무자 A(−300), B(−100), 채권자 C(+250), D(+150)이면 A→C 250, B→D 100, A→D 50이다(AC-SET-003-1). 채무자 A(−300), B(−200), 채권자 C(+250), D(+150), E(+100)이고 A가 먼저 등록되었으면 A→C 250, B→D 150, A→E 50, B→E 50이다(AC-SET-003-2). 이 값들은 단위 테스트의 기준 벡터다.

### 6.3 정산 항목 정렬 (FR-SET-004)
- 금액 내림차순. 같으면 지급자의 `order` 오름차순. 지급자도 같으면 수취자의 `order` 오름차순(AC-SET-004-2, 사용자 결정 OQ-035).
- 이 정렬은 **서버가 하고** 응답 `items`의 순서가 곧 화면과 복사 텍스트의 순서다. 클라이언트는 다시 정렬하지 않는다(AC-SET-004-3). §6.2의 같은 쌍 중복 없음 때문에 정렬 키는 항목마다 다르다.
- 예: 항목 A→E 50, B→E 50은 A가 먼저 등록되었으면 A→E, B→E 순이다. 지급자 A의 A→D 50과 A→E 50은 D가 먼저 등록되었으면 A→D, A→E 순이다(AC-SET-004-4).
- 생성 순서(§6.2)와 표시 순서(§6.3)는 서로 독립이다. 표시 순서가 기준이다.

### 6.4 예상 정산과 최종 정산 (기준 위치)
두 정산의 차이는 이 표가 **유일한 기준**이다. 계산(§6.2)과 정렬(§6.3)은 같다.

| 항목 | 예상 정산 (`EXPECTED`) | 최종 정산 (`FINAL`) |
| --- | --- | --- |
| 조회 가능한 때 | 방이 `IN_PROGRESS` | 방이 `ENDED` |
| 입력 | 전체 유효 거래(필터와 무관, AC-SET-008-6) | 종료 시점의 전체 유효 거래. 종료 뒤 거래가 잠겨 있어 조회 시마다 같다(E-I5) |
| 갱신 | 거래·참여자 변경 이벤트 뒤 재조회로 바뀜(AC-SET-008-2, S5 §8.2 3) | 바뀌지 않음 |
| 화면 이름 | `예상 정산`. 진행 중이며 최종 결과가 아님을 구분해 표시(AC-SET-008-5) | `최종 정산`. 종료 때 같은 영역이 바뀐다(AC-SET-008-3) |
| 복사 | **불가.** 복사 버튼이 없거나 동작하지 않고 `게임 종료` 텍스트를 만들지 않는다(AC-SET-005-6, 008-7) | 가능(§6.5). 항목이 있을 때만 |
| 항목 없음 문구 | 표시(§6.6) | 표시하고 복사 버튼 비활성화 |
| 같은 거래 집합 | 항목이 최종 정산과 같다(AC-SET-008-4) | 항목이 예상 정산과 같다 |
| 서버의 구분 | 응답 `kind` | 응답 `kind` |

조회 API는 하나이며(§4.2) 구분은 `kind`뿐이다. 같은 스냅샷의 `kind`와 `items`를 함께 쓴다.

**표시와 전환 기준(방 조회와 정산 조회의 시점 차이)**: 방 조회(S1 §4.4)와 정산 조회는 서로 다른 스냅샷일 수 있다(§3.5). 클라이언트는 재동기화(S5 §6.4)에서 받은 두 응답이 **일치할 때만** 반영한다. 일치는 방 `status = IN_PROGRESS`와 `kind = EXPECTED`, 또는 `ENDED`와 `FINAL`이다. 어긋나면(예: 방은 `ENDED`인데 정산이 `EXPECTED`, 또는 방은 `IN_PROGRESS`인데 정산이 `FINAL`) 그 결과를 화면에 반영하지 않고 재동기화를 다시 한다. 종료는 되돌릴 수 없으므로(E-I1) 다시 조회하면 일치로 수렴한다. 이 확인은 S5의 "모두 성공한 뒤에만 반영" 규칙에 더하는 일치 검사이며, 어긋남 자체는 연결 실패(S5 §6.5)가 아니다. 영역의 이름(`예상 정산`/`최종 정산`)과 복사 가능 여부는 일치한 응답의 `kind`를 따른다.

### 6.5 정산 텍스트 복사 (기준 위치, FR-SET-005, U-1)
복사 텍스트는 **클라이언트가 현재 화면에 표시된 최종 정산의 응답**과 방 정보(S1 §4.4)로 만든다. 서버는 복사 텍스트를 만들지 않는다. 형식은 다음이다(사용자 확정 U-1, `open-questions.md` 2.8절).

```
{방 이름}
게임 종료

{지급자 닉네임} → {수취자 닉네임} {금액} {정산 단위}
{지급자 닉네임} → {수취자 닉네임} {금액} {정산 단위}
```
- 첫 줄은 방 이름, 둘째 줄은 고정 문자열 `게임 종료`, 셋째 줄은 빈 줄이다. 이어서 정산 항목을 응답 `items`의 순서 그대로 한 줄씩 쓴다. 줄바꿈은 `\n`이고 마지막 줄 뒤에 줄바꿈을 붙이지 않는다.
- 각 줄: 지급자 닉네임, 공백 한 칸, `→`(U+2192), 공백 한 칸, 수취자 닉네임, 공백 한 칸, 금액, 공백 한 칸, 방의 정산 단위(`unit`)다.
- 금액은 10진 정수이며 **세 자리마다 ASCII 쉼표**를 넣는다(예: `1,250,000`). 브라우저 로캘에 따라 달라지지 않는다. 화면의 숫자 서식은 이와 무관하며 OQ-033이다.
- 방 이름과 닉네임은 허용 문자가 한글·영문·숫자·공백으로 제한되어 있어(S1 §3.2) 줄바꿈이나 `→`가 들어갈 수 없으므로 텍스트를 해석할 때 모호하지 않다.
- **포함하지 않는 것**: 개별 거래(사유·라운드·작성자·시각), 정산 확정 상태·버전, 예상 정산, `kind` 표기(AC-SET-005-4).
- 예: 방 이름 `주말 고스톱`, 단위 `원`, 항목 A→C 250, B→D 100이면
```
주말 고스톱
게임 종료

A → C 250 원
B → D 100 원
```
- **복사 가능 조건**: 방이 `ENDED`이고, 최종 정산을 서버에서 받아 현재 표시하고 있으며(S5 §6.5로 데이터가 숨겨진 상태가 아님), 항목이 1건 이상일 때다. 하나라도 어긋나면 버튼이 없거나 비활성화되어 동작하지 않는다(AC-SET-005-6, AC-SET-006-2).
- **실패**: 클립보드 쓰기가 실패하거나 사용할 수 없으면 복사 실패를 사용자에게 알리고 성공으로 표시하지 않는다(AC-SET-005-5). 성공은 쓰기가 완료된 뒤에만 표시한다.

### 6.6 정산 항목 없음 (FR-SET-006)
- `items`가 비어 있으면(거래가 없거나 모든 순손익이 0이면) 화면은 정확히 `정산할 내역이 없습니다.`를 표시한다(AC-SET-006-1). 예상 정산과 최종 정산 모두에 표시한다.
- `items`가 1건 이상이면 이 문구를 표시하지 않는다(AC-SET-006-3).
- 최종 정산이 비어 있으면 복사 버튼은 비활성화되어 클릭해도 복사되지 않는다. 예상 정산에는 복사 기능이 없다(AC-SET-006-2, §6.4).
- 서버는 이 경우에도 `200`과 `items: []`를 돌려주며 오류가 아니다.

## 7. 동시성과 정합성
서버는 다음을 보장해야 한다. 구현 방법은 Plan이 정한다. "직렬 순서"는 방 단위 잠금(S2 §7 1)에서 차례를 얻은 순서다.

| 상황 | 결과 | 근거 |
| --- | --- | --- |
| 종료와 거래 생성이 동시에(다른 키) | 거래가 먼저면 최종 정산에 포함된다. 종료가 먼저면 거래 요청은 `409 GAME_ENDED`(기록됨)이고 최종 정산에 없으며 거래 이벤트도 없다 | S2 §7 2, AC-TXN-009-5, OQ-030 |
| 종료와 거래 수정·삭제가 동시에 | 같다. 수정·삭제가 먼저면 최종 정산에 반영, 종료가 먼저면 `GAME_ENDED`(권한 없으면 `NOT_AUTHOR_OR_HOST`, S2 §3.4) | S2 §7 2 |
| 종료와 참여자 등록·상태 변경이 동시에 | 종료가 먼저면 참여자 변경은 `GAME_ENDED`다. 참여자 변경이 먼저면 그 상태가 최종 정산에 쓰인다 | S1 §7 5, AC-PART-004-1, -2 |
| 종료와 종료가 동시에(다른 키) | 한 요청만 전이를 일으키고 `room.ended`가 한 번 만들어진다. 나머지는 `409 GAME_ENDED`(기록됨)이며 상태·`revision`·정산은 변하지 않는다 | AC-SET-001-9 |
| 종료와 종료가 동시에(같은 키, 같은 내용) | 한 요청만 처리하고 나머지는 저장된 성공 결과를 `Idempotent-Replayed: true`로 받는다. `room.ended`는 한 번이다 | AC-SET-001-8, S2 §5.3 |
| 같은 키로 다른 내용(본문이 다름) | 기록이 있으면 `409 IDEMPOTENCY_CONFLICT`. 기록이 없으면 새 요청으로 검증(§3.3 8번) | S2 §5.3 |
| 종료 요청이 잠금 대기 중에 키가 만료됨 | `409 IDEMPOTENCY_KEY_EXPIRED`. 전이도 이벤트도 없다 | S2 §5.4 |
| 종료와 정산 조회가 동시에 | 조회는 잠금을 쓰지 않고 한 스냅샷을 읽으므로 전이 전이면 `EXPECTED`, 후면 `FINAL`이다. `kind`와 `items`가 섞이지 않는다 | §3.5 |
| 종료 직후 이미 성공한 거래 요청의 같은 키 재전송 | 종료를 이유로 거부되지 않고 저장된 성공 결과를 받는다 | S2 §5.3, AC-TXN-007-8, -9 |
| 종료 직후 새 거래 요청 | `409 GAME_ENDED` | AC-TXN-009-1 |

- **원자성**: 전이, `revision` 증가, 멱등 기록은 한 트랜잭션이다(§6.1). 전이 후 이벤트 전달 전에 서버가 중단되어도 상태는 `ENDED`로 남고 클라이언트는 방 조회·재동기화로 이를 안다(§6.1 (3)).
- **최종 정산의 안정성**: `ENDED` 이후 입력이 바뀌지 않으므로(E-I3, E-I5) 어떤 인스턴스에서 몇 번을 조회해도 같다.
- **합 0**: 모든 거래가 지급자 −, 수취자 +이므로 합은 0이다(S2 §7 8, S3 V-I2). 정산은 이를 입력으로 쓰며 속성 기반 테스트로 검증한다(§11).

## 8. 실시간 이벤트 발생 지점 (스키마는 S5)
- **발생**: 게임 종료 전이 성공 시 `room.ended` 한 번(S5 §4.2, §6.1). 전이를 일으킨 트랜잭션에서 `revision`이 1 오르고 커밋 뒤에 전달된다.
- **없음**: 같은 키의 재전송, 이미 종료된 방에 대한 새 키 종료 요청(`GAME_ENDED`), `IDEMPOTENCY_*` 거부, 403, 422는 이벤트를 만들지 않고 `revision`을 소비하지 않는다(S5 §8.2 1).
- **정산 이벤트는 없다.** 정산은 순손익에서 계산되는 파생 값이므로 `transaction.*`, `participant.*`, `room.ended` 뒤 정산 조회 API를 다시 조회한다(S5 §8.2 3, §6.4). 예상 정산이 바뀌는 시점은 그 이벤트들과 같다(AC-VIEW-005-5).
- **페이로드**: `room.ended`의 `data`는 `roomId`, `revision`, `serverTime`이며 정산을 싣지 않는다(S5 §8.2 5).
- S5의 재동기화는 정산 조회 API를 다섯 번째 대상으로 함께 조회한다(S5 §6.4). 각 조회는 서로 다른 스냅샷일 수 있으므로 방 상태와 정산 `kind`의 일치 검사(§6.4)를 통과한 재동기화 결과만 반영되어, 방 상태, 참여자, 순손익, 목록, 정산이 함께 `ENDED`·`FINAL` 기준으로 바뀐다.

## 9. 프론트엔드 책임
- **종료 확인**: 방장에게만 종료 컨트롤을 보이고(방장이 아니거나 `ENDED`이면 숨기거나 비활성화), 누르면 확인 절차를 표시한다. 확인한 뒤에만 `POST /rooms/{roomId}/end`를 보낸다. 취소하면 아무것도 보내지 않고 상태가 바뀌지 않는다(AC-SET-001-1). 확인 창은 종료가 되돌릴 수 없고 이후 거래·참여자 변경이 잠긴다는 점을 알려야 한다. 문구의 세부는 OQ-033이다. 노출 여부와 무관하게 서버가 권한을 검증한다.
- **요청 보호와 멱등 키**: 요청이 진행 중이면 종료 컨트롤을 비활성화한다. 키와 최초 시도 시각의 수명·시각 보정·재시도·24시간 후 자동 재전송 금지는 S2 §9의 규칙을 그대로 쓴다. 종료는 입력 내용이 없으므로 새 키는 사용자가 확인 절차를 새로 거쳐 종료를 다시 누를 때만 만든다.
- **결과 처리**: 확정 성공(`200`)이면 종료 상태를 반영한다(실제 반영은 방 조회·재동기화의 `status`가 기준, §6.1 (3)). `GAME_ENDED`(`이미 종료된 게임입니다`)를 받으면 그 메시지를 보이고 재동기화로 현재 상태를 가져온다(다른 탭·다른 요청이 먼저 종료했을 수 있다). 응답이 없어 결과를 모르면 "결과를 확인하지 못했습니다"로 알리고 종료됐다고 단정하지 않는다. 연결이 복구되면 방 상태를 조회하고, 사용자가 원하면 같은 키로 수동 재시도한다(S2 §9와 같은 원칙). `IDEMPOTENCY_KEY_EXPIRED`는 서버 `message`를 그대로 보이고 방의 현재 상태를 확인하게 한다.
- **종료 반영**: 방이 `ENDED`이면(자기 요청의 결과든 `room.ended` 이벤트든 재동기화든) 거래 입력·수정·삭제와 참여자 등록·상태 변경 컨트롤을 숨기거나 비활성화하고(AC-SET-001-3, AC-TXN-009-3, AC-PART-004-3) 정산 영역을 `최종 정산`으로 바꾼다(AC-SET-008-3).
- **정산 영역**: 서버 `items`의 순서를 그대로 보인다(AC-SET-004-3). 닉네임과 금액을 방의 `unit`으로 표시한다(AC-ROOM-003-3). `kind = EXPECTED`이면 `예상 정산`이라는 이름과 진행 중임을 구분하는 표시를 함께 보이고(AC-SET-008-5) 복사 컨트롤을 두지 않는다. `kind = FINAL`이면 `최종 정산`이라 부른다. `items`가 비면 `정산할 내역이 없습니다.`를 보이고 최종 정산의 복사 버튼은 비활성화한다(§6.6).
- **복사**: §6.5의 형식과 조건을 따른다. 복사 텍스트는 현재 표시 중인 `FINAL` 응답과 방 이름·`unit`으로만 만들고, 연결이 끊겨 데이터가 숨겨진 동안(S5 §6.5)에는 복사할 수 없다. 실패는 알리고 성공으로 표시하지 않는다(AC-SET-005-5).
- **갱신**: 변경 이벤트를 받으면 S5 §6.4에 따라 정산 조회를 포함한 전체를 재조회해 모두 성공하고 방 상태와 정산 `kind`가 일치한 뒤에만 반영한다(§6.4). 필터를 바꿔도 정산 요청은 달라지지 않는다(AC-SET-008-6).
- **금액 표시**: 정산 항목 금액은 단일 거래 상한을 넘을 수 있으므로(최대 약 10¹²) 표시·복사 서식이 이 범위를 정확히 다루어야 한다(JavaScript 정수 정밀도 안, §6.2).
- 오류 `code`로 분기하고 `message`는 그대로 쓴다. 사용자 입력 문자열(방 이름, 닉네임)은 항상 일반 텍스트로 이스케이프해 표시한다.

## 10. 백엔드 책임
- S1 §3.1 인증, 이 Spec의 §3.3 검사 순서, §4의 두 엔드포인트와 비제공 동작을 구현한다.
- 종료 처리는 S2 §7 1의 방 단위 직렬화 안에서 §6.1의 상태 변경, `revision` 증가, 멱등 기록 쓰기를 한 트랜잭션으로 한다. 다중 서버 인스턴스에서 성립해야 한다(Plan에서 DB 수준 잠금으로 정한다).
- 멱등 기록의 연산 종류에 `END`를 둔다(§3.2, D-2). 기록 보관·정리는 S2 §5.4와 같다.
- 정산은 요청 때마다 같은 스냅샷에서 계산한다(D-5). 순손익은 S3 §6.1의 서버 계산을 쓰고 두 번째 수식을 만들지 않는다. 알고리즘은 §6.2의 비교 기준을 명시적으로 구현한다.
- 이 Spec의 계약을 다른 저장소 문서에 복제하지 않고 Spec 버전 또는 `ddallang` 커밋으로 참조한다.

### 12.3 자체 점검 (상위 문서와의 충돌)
1. **PRD와 정책**: FR-SET-001~008의 AC 39개를 §11에서 모두 대응시켰다. 새 요구를 더하지 않았다. 정책의 MVP 제외(정산 확정·버전, 자동 종료·재개·만료·삭제, 종료 후 정정)는 §4.3과 §1.3에 비제공으로 명시했다.
2. **S1**: 방장 전용(`HOST_ONLY`, S1 §5.1), 방 상태별 허용(S1 §5.2), 검사 순서(S1 §3.3)를 따른다. Room 필드를 늘리지 않았다.
3. **S2**: 멱등 규칙과 방 단위 직렬화를 그대로 인용한다. 연산 종류 `END` 추가(D-2)는 S2의 확정 계약을 바꾸지 않는 저장 모델 의존성이며 해석 위험을 §13에 적었다.
4. **S3**: 순손익 정의는 §6.1 하나이며 S4는 두 번째 수식을 만들지 않는다(S3 §1.3).
5. **S5**: §8.2의 5개 요구를 §6.1 (3), §4.2, §8로 충족한다. 정산 이벤트 없음, 정산 조회 API 지정, `room.ended` 정확히 한 번, 거부·재전송·만료는 이벤트 없음.

### 12.4 후속 후보 (범위 밖, 기록만)
- 정산 결과 이미지·공유 링크, 송금 완료 표시는 MVP 제외이며 만들지 않는다. 자동 만료·삭제도 제외다(AC-SET-001-7). 수동 삭제·보관 운영 정책은 미결(OQ-034)이며 S4는 이를 정하지 않는다.

## 13. 위험
- **복사 형식(U-1)**: PRD가 형식을 정하지 않아 사용자가 정했다. 바꾸려면 §6.5와 추적표(005-3)의 변경과 재검수가 필요하다.
- **S2 연산 종류 해석(D-2)**: S2 §5.2가 지문의 연산 종류를 생성·수정·삭제로 적었다. `END`를 더하는 것을 S2 개정으로 보면 S2 재검수가 필요하다. 이 Spec은 저장 모델 의존성으로 처리한다.
- **이벤트 유실과 종료 인지 지연**: 커밋과 발행 사이의 장애로 `room.ended`가 사라질 수 있다. 종료 상태는 DB에 있고 하트비트(15초)와 재동기화가 메운다(S5 §6.4, §13). 종료 직후 최대 약 20초까지 다른 접속자가 종료를 모를 수 있으며(S5 §6.7의 수렴 기준), 이 동안의 새 변경 요청은 서버가 `GAME_ENDED`로 거부한다.
- **종료 불가 방(OQ-034)**: 방장 신원 키 분실 시 종료할 수 없다. 이는 S1이 수용한 귀결이며 S4는 새 복구 경로를 만들지 않는다.
- **큰 금액의 표시**: 정산 항목 금액은 최대 약 10¹²다. JavaScript 정수 정밀도 안이나 표시·복사 서식이 이를 검증해야 한다(§11.8의 NFR-009).
- **알고리즘의 비최적성**: 송금 횟수가 최소가 아닐 수 있다. 정책이 수용한 것이다(AC-SET-003-6).
- **다중 인스턴스 검증**: 종료의 단일 전이와 같은 키 동시 재전송은 서버 인스턴스 2개 이상으로 검증해야 한다(§11.1 001-9). Plan의 테스트 항목이 된다.
- **정산 조회와 다른 조회의 시점 차이(§3.5)**: 순간적으로 서로 다른 시점의 값이 보일 수 있다. S5의 재동기화가 모두 성공한 뒤에만 반영해 완화한다.
