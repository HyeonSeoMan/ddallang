### 2.2 아키텍처 결정

| ID | 결정 | 근거 Spec | 비고·대안 |
| --- | --- | --- | --- |
| PD-1 | NestJS(Express 어댑터) 단일 앱. 모듈: `common`, `rooms`(S1 방·입장), `participants`(S1), `transactions`(S2), `idempotency`(S2·S4 공용), `balances`(S3), `realtime`(S5), `settlement`(S4). 모듈 사이 의존은 아래 방향만 허용한다: `common` ← 나머지, `idempotency`·`realtime` ← `transactions`·`participants`·`settlement`. 순환 의존을 만들지 않는다 | S1~S5 §10 | Fastify는 쓰지 않는다(SSE 직접 쓰기에서 Express가 더 단순) |
| PD-2 | Prisma는 스키마·마이그레이션·일반 질의에 쓰고, 방 잠금·DB 시각·집계는 `$queryRaw`로 쓴다. CHECK 제약과 부분 인덱스는 SQL 마이그레이션에 직접 쓴다 | S2 §2.1, S3 §2.3.1 | Prisma가 표현하지 못하는 제약을 DB가 강제하게 한다 |
| PD-3 | **방 단위 직렬화**: 방을 바꾸는 모든 요청(참여자 등록·상태 변경, 입장(새 RoomMember), 거래 생성·수정·삭제, 종료)은 하나의 진입점 `withRoomLock`에서 `SELECT … FROM "Room" WHERE id = $1 FOR UPDATE`로 방 행 잠금을 **하나만** 잡는다. 잠금 순서가 하나라 요청 사이 데드락이 구조적으로 생기지 않는다. 잠금은 커밋까지 유지한다. `lock_timeout`·`statement_timeout`을 설정하고 요청 제한 시간은 멱등 기록 보관 여유(1시간)보다 짧게 둔다 | S2 §7 1, S1 §7, S5 §6.1, S4 §6.1 | 대안: advisory lock. 방 행이 `revision`·`seq` 카운터도 담으므로 행 잠금을 택했다. 프로세스 메모리 잠금은 쓰지 않는다 |
| PD-4 | 방 행에 `revision`(S5 E-3), `nextTxnSeq`와 `lastTxnCreatedAt`(S3 C-1)을 둔다. 잠금을 쥔 채 증가·부여한다. `createdAt`은 `greatest(clock_timestamp(), lastTxnCreatedAt)`이다. 모든 시각 판정은 **DB 시각**(`clock_timestamp()`) 하나를 기준으로 하며 서버 인스턴스 시계에 의존하지 않는다 | S3 §2.3.1, S5 §6.1, S2 §5.4 | `now()`는 트랜잭션 시작 시각이라 잠금 대기 뒤 값으로 쓰지 않는다 |
| PD-5 | **이벤트 전달**: 변경 트랜잭션 안에서 `pg_notify('room_events', payload)`를 호출한다. PostgreSQL은 통지를 **커밋될 때만** 전달하므로 "커밋 전 전달 금지"(S5 R-I2)가 저장소 수준에서 보장되고 롤백된 변경의 이벤트는 나가지 않는다. 각 서버 인스턴스는 `LISTEN` 전용 연결(풀과 분리, 직접 `pg` 클라이언트)을 하나 유지하고 받은 통지를 로컬 SSE 구독자에게 방 단위로 나눠 준다. 이벤트를 저장하거나 재전송하지 않는다(S5 §6.2). 연결이 끊기면 자동 재연결 후 다시 `LISTEN`하고, 그 사이 유실은 하트비트가 보완한다 | S5 §6.1, §6.2 | 대안(이벤트 테이블, outbox): 재전송이 없는 계약에 비해 복잡해 채택하지 않았다. Redis는 쓰지 않는다. **제약**: `LISTEN` 연결은 세션 단위라 트랜잭션 모드 연결 풀러 뒤에 둘 수 없다(PD-16) |
| PD-6 | **SSE 구현**: NestJS `@Sse`를 쓰지 않고 응답 객체에 직접 쓴다(헤더 `Cache-Control: no-store`, `X-Accel-Buffering: no`, 연결 한도 거부는 스트림 열기 전 JSON 429). 방마다 구독자 집합과 **하트비트 타이머 하나**(15초)를 두고 그 시점의 DB `revision`을 한 번 읽어 모든 스트림에 보낸다. 스트림별 전송 대기열이 100을 넘으면 닫는다(역압 처리). 끊어진 연결은 쓰기 실패·하트비트 실패로 15초 안에 정리한다. 연결 한도는 RoomMember당 5, 방당 50이며 **서버 인스턴스 전체를 합산해** 적용한다(사용자 결정 D1, `open-questions.md` 2.10절). 방법: `StreamLease` 테이블(`id`·`roomId`·`memberId`·`instanceId`·`expiresAt`)에 연결마다 임대를 기록한다. 연결 요청은 방 단위 **advisory lock**(방 행 잠금과 분리해 쓰기를 막지 않는다) 안에서 만료된 임대를 지우고 방·멤버별 개수를 센 뒤 한도 미만이면 삽입, 아니면 `429`로 거부한다. 연결 종료와 정리 때 임대를 즉시 지우고, 임대 만료 시간 T는 **15초**다(사용자 결정 D2, `open-questions.md` 2.10절. Spec §4.1의 "15초 안에 슬롯 반환"을 서버 비정상 종료에도 지킨다). 한도 불변식은 다음으로 지킨다: (1) 각 인스턴스가 T/3마다 자기 임대를 **한 번의 UPDATE로 일괄 갱신**하며(`WHERE expiresAt > clock_timestamp()`, 갱신된 행을 반환받음) 갱신되지 않은(이미 만료된) 임대의 스트림은 즉시 닫는다. (2) 자기 종료 마감은 **갱신 요청을 보낸 시각**을 기준으로 정한다: 갱신이 성공하면 스트림의 마감을 `그 요청의 송신 시각(로컬 단조 시계) + 2T/3`으로 올리고(더 이른 값으로 낮추지는 않는다), 응답이 늦게 도착해도 **응답 수신 시각은 쓰지 않는다**. DB는 요청을 처리한 시각(송신 이후) + T를 만료로 기록하므로 마감(송신+10초)은 항상 DB 만료(송신 이상+15초)보다 앞선다. 마감이 지나면 인스턴스는 그 스트림을 닫고 되살리지 않는다. **최초 임대도 같다**: 연결 시 임대 발급 요청의 송신 시각 + 2T/3이 초기 마감이며, 발급 성공 응답이 마감 뒤에 도착하면 그 연결을 열지 않고 임대를 반납한다(늦은 응답 폐기). **모든 스트림 쓰기(이벤트·하트비트) 직전에 마감을 먼저 검사**하고 지났으면 쓰지 않고 닫는다. 이로써 응답 지연이 있어도 만료된 임대를 가진 스트림이 데이터를 받는 일이 없다. **프로세스 전체가 정지**(SIGSTOP, 긴 정지 등)하면 타이머도 실행되지 못해 TCP 연결은 열린 채로 남지만 그 동안 정지한 프로세스는 아무 데이터도 보내지 못하고, 재개되면 단조 시계 기준으로 마감이 이미 지났으므로 첫 쓰기 전에 닫힌다. 따라서 보장하는 것은 "한도를 넘어 **데이터를 받는** 스트림이 없다"이며, 정지한 프로세스 쪽 TCP 소켓이 열려 있는 것까지는 서버가 통제할 수 없다(RK-14) (3) 닫힌 클라이언트는 재연결·재동기화한다(S5 §6.6). 서버 프로세스가 비정상 종료해도 임대는 T 안에 만료되어 슬롯이 돌아온다(RK-13) | S5 §4.1, §6.2 | |
| PD-7 | **멱등 기록**: 테이블 `IdempotencyRecord`(S2 §2.1)와 (방, RoomMember, 키) 유일 제약. 지문은 연산 종류(`CREATE`/`UPDATE`/`DELETE`/`END`)·대상 거래 ID·본문 정규형의 SHA-256이다. 기록은 거래·종료 변경과 **같은 트랜잭션**에서 쓴다. 정리는 인스턴스 안의 주기 작업이 `expiresAt + 1시간`이 지난 행을 배치로 지우며(`FOR UPDATE SKIP LOCKED`, 여러 인스턴스가 돌려도 안전), 정리 시각이 판정 결과를 바꾸지 않는다(헤더만으로 만료 판정) | S2 §5, S4 §3.2 D-2 | `END`는 S2 §5.2가 연산 종류를 3개로 적은 것에 대한 해석 위험 D-2(S4 §13)가 있다. 구현은 저장 모델 의존성으로 처리한다 |

## 4. 구현 순서와 근거

작성 순서(S1→S2→S3→S5→S4)를 의존 순서로 따른다. `Room`·`RoomMember`·`Participant` 테이블(BE-S1-1)이 먼저 있어야 인증(BE-F4)·변경 파이프라인(BE-F7)·멱등(BE-F6)이 그 위에 마이그레이션을 쌓을 수 있다. 문자열 검증(BE-F5)은 테이블과 무관하므로 앞에 둔다.

```
BE-F1 → BE-F2 → BE-F8 → BE-F3 → BE-F5 → BE-S1-1 → BE-F4 → BE-F7
   → S1 (BE-S1-2 … BE-S1-7)
   → BE-F6 → S2 (BE-S2-1 … BE-S2-7)
   → S3 (BE-S3-1 … BE-S3-4)
   → S5 (BE-S5-1 … BE-S5-6)
   → S4 (BE-S4-1 … BE-S4-7)
   → BE-Z1 (통합 검증·G4 증거 묶음)
```

- S3(읽기)를 S5(SSE)보다 먼저 둔다. S5의 재동기화가 S3·S4 조회를 대상으로 삼고, 이벤트 발생 지점은 이미 S1·S2에서 BE-F7로 구현되어 있어 S5는 전달·연결·측정에 집중한다.
- S4를 마지막에 둔다. 종료 전이가 BE-F6(`END`)·BE-F7(`room.ended`)·S5 계약에 모두 기대고, 정산 알고리즘은 S3 순손익을 쓴다.
- 각 묶음은 **그 묶음이 소유한 시험**(자기 Spec 계약·동시성)을 통과해야 다음 묶음이 시작된다. 다른 Spec의 기능이 있어야 하는 횡단 시험(예: 종료 후 참여자 변경 거부, 종료 변경의 지연 측정)은 `tasks.md`의 "횡단 시험 이관표"가 소유 Task를 정하며 이관된 시험이 통과하기 전에는 해당 AC를 완료로 세지 않는다.

## 5. 변경 통제와 상위 문서와의 관계

- 이 Plan은 PRD·Spec을 바꾸지 않는다. 구현 중 Spec과 어긋나는 사정(예: S2 내부 기록 목록의 `seq`·`revision`·`END` 해석)이 생기면 **구현을 멈추고** 어느 Spec 절인지 인용해 사용자에게 올린다(`.agents/governance.md` §5).
- Spec의 저장 모델 의존성(S3 C-1, S5 E-3, S4 D-2)은 이 Plan이 이행한다(§7). 이 의존성을 S1·S2 문서의 "내부 기록" 목록을 엄격히 완전 목록으로 읽는 해석이 나오면 해당 Spec 재검수가 필요하다(각 Spec §13). 이 Plan은 그 해석이 나오지 않는다는 것을 전제하지 않고 §6 RK-1에 위험으로 둔다.
- 이 Plan 자체의 변경은 재검수를 거친다. 프론트엔드 Plan은 이 문서와 별개이며 같은 Spec 버전을 참조한다.

## 8. 검증 전략 (OQ-033 G 적용)

- **AC 매핑**: 모든 AC는 하나 이상의 자동 테스트에 매핑한다. 매핑표는 `ac-matrix.md`이며 Spec §11 추적표에서 만들었다(Spec이 기준). 시험 제목에는 `[AC-…]` 태그를 붙이고 BE-F8의 검사 스크립트가 "백엔드 담당 AC마다 태그 달린 시험이 있는가"를 실패 조건으로 검사한다. UI 전용 AC는 프론트엔드 Plan이 맡는다.
- **시험 종류**:
  - 단위: 문자열·금액 검증(PD-10), 정산 알고리즘(PD-13), 멱등 지문·만료 판정, 커서 암호화.
  - DB 통합: 실제 PostgreSQL에서 각 엔드포인트의 검사 순서·권한·한도·멱등·오류 코드(계약 시험).
  - 동시성: **서로 다른 프로세스 2개 이상**의 서버 인스턴스를 같은 DB에 붙여 마지막 슬롯 경쟁, 닉네임 경쟁, 같은 키 재전송 경쟁, 종료와 저장 경쟁, 단일 전이 보장.
  - 속성 기반(`fast-check`): 순손익 합 0, 정산 항목 수 ≤ |D|+|C|−1, 정산 결정성·합 0, 문자열 검증의 NFC 동치.
  - 실시간: SSE 형식·하트비트·연결 한도·유실 시나리오, 지연 측정 하네스(S5 §6.7의 표를 그대로 사용). **S5 지연 시험의 CI 필수 게이트 여부(OQ-033 G 요구)**: 제안은 "공유 CI 러너에서는 변동이 커 매 커밋 필수 게이트로 두지 않고, 전용 환경에서 릴리스 전 필수 시험(BE-S5-4, BE-S4-7)으로 실행해 기준 초과 시 불합격으로 판정"이다. 사용자가 바꿀 수 있다.
  - 정적: 자동 종료 경로·스케줄러·재개 경로·확정 저장이 없음(AC-SET-001-4, -5, -7).
- **실행하지 못한 검증은 숨기지 않고 보고한다**(예: 환경 제약으로 지연 측정을 못 한 경우).
- **S5 지연 시험의 완료**: BE-S5-4는 S4 없이 가능한 부분(이벤트 전달)만, 5개 조회 재동기화 완료까지의 반영·수렴·종료 변경은 BE-S4-7이 측정한다. AC-VIEW-005-8은 이 두 서버 측 시험과 **프론트엔드 Plan의 화면 표시 측정(렌더링 포함)이 모두 통과해야** 완료다. 서버 측 시험만으로는 완료로 세지 않는다.
- **G4 증거**: 타입 검사·린트·빌드·전체 시험 결과, AC 매핑 검사 결과, 다중 인스턴스 시험 결과, 지연 측정 결과, 남은 위험을 `BE-Z1`이 묶는다.

## 9. G3 검수에서 확인받고 싶은 점

1. 방 행 잠금 하나(PD-3)와 `pg_notify`(PD-5)가 Spec의 직렬화·"커밋 뒤 전달"·다중 인스턴스 요구를 충족하는가.
2. 전체 합산 연결 한도(D1, BE-S5-6)가 S5 §3.3·§4.1 문구와 맞는가. 갱신 실패 시 스트림 자기 종료로 한도 불변식이 지켜지는가.
3. Task 사이 의존과 공통 기반 소유가 중복·누락 없이 정의되었는가.
4. `ac-matrix.md`가 백엔드 담당 AC를 빠뜨리지 않았는가.
5. 저장 모델 의존성 이행표(§7)가 Spec §10·§13과 어긋나지 않는가.
